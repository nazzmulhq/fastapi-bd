কনকারেন্সি এবং async / await¶

🌐 AI এবং মানুষের যৌথ অনুবাদ

এই অনুবাদটি মানুষের নির্দেশনায় AI দিয়ে করা হয়েছে। 🤝

এতে মূল অর্থ ভুল বোঝা বা অস্বাভাবিক শোনানোর মতো ভুল থাকতে পারে। 🤖

ইংরেজি সংস্করণ

পাথ অপারেশন ফাংশনের জন্য async def সিনট্যাক্সের বিস্তারিত, এবং অ্যাসিঙ্ক্রোনাস কোড, কনকারেন্সি ও প্যারালালিজম সম্পর্কে কিছু প্রেক্ষাপট।

তাড়াহুড়োয় আছেন?¶

সংক্ষেপে:

আপনি যদি এমন থার্ড পার্টি লাইব্রেরি ব্যবহার করেন যেগুলো await দিয়ে কল করতে বলে, যেমন:

results = await some_library()

তাহলে আপনার পাথ অপারেশন ফাংশনগুলো async def দিয়ে ঘোষণা করুন, যেমন:

@app.get('/')
async def read_results():
    results = await some_library()
    return results

নোট

await কেবল async def দিয়ে তৈরি ফাংশনের ভেতরেই ব্যবহার করা যায়।

আপনি যদি এমন কোনো থার্ড পার্টি লাইব্রেরি ব্যবহার করেন যা কোনো কিছুর সাথে যোগাযোগ করে (একটি ডেটাবেস, একটি API, ফাইল সিস্টেম ইত্যাদি) এবং await ব্যবহারের সাপোর্ট নেই (বর্তমানে বেশিরভাগ ডেটাবেস লাইব্রেরির ক্ষেত্রে এমনটাই), তাহলে আপনার পাথ অপারেশন ফাংশনগুলো স্বাভাবিকভাবে শুধু def দিয়ে ঘোষণা করুন, যেমন:

@app.get('/')
def results():
    results = some_library()
    return results

আপনার অ্যাপ্লিকেশনকে যদি (কোনোভাবে) অন্য কিছুর সাথে যোগাযোগ করে তার উত্তরের জন্য অপেক্ষা করতে না হয়, তাহলে ভেতরে await ব্যবহারের দরকার না থাকলেও async def ব্যবহার করুন।

আপনি যদি নিশ্চিত না হন, তাহলে সাধারণ def ব্যবহার করুন।

নোট: আপনার পাথ অপারেশন ফাংশনগুলোতে যত খুশি def ও async def মিশিয়ে ব্যবহার করতে পারেন, এবং প্রতিটিকে আপনার জন্য সেরা অপশন দিয়ে সংজ্ঞায়িত করতে পারেন। FastAPI এগুলোর সাথে সঠিক আচরণই করবে।

যাই হোক, ওপরের যেকোনো ক্ষেত্রে FastAPI তবুও অ্যাসিঙ্ক্রোনাসভাবে কাজ করবে এবং অত্যন্ত দ্রুত থাকবে।

তবে ওপরের ধাপগুলো অনুসরণ করলে এটি কিছু পারফরম্যান্স অপটিমাইজেশন করতে পারবে।

কারিগরি বিবরণ¶

Python-এর আধুনিক ভার্সনগুলো "কোরুটিন" নামের একটি জিনিস ব্যবহার করে async ও await সিনট্যাক্স দিয়ে "অ্যাসিঙ্ক্রোনাস কোড" সাপোর্ট করে।

চলুন নিচের অংশগুলোতে এই বাক্যটিকে টুকরো টুকরো করে দেখি:

  • অ্যাসিঙ্ক্রোনাস কোড
  • async ও await
  • কোরুটিন

অ্যাসিঙ্ক্রোনাস কোড¶

অ্যাসিঙ্ক্রোনাস কোড মানে শুধু এই যে, ভাষাটির 💬 কাছে কম্পিউটার / প্রোগ্রামকে 🤖 জানানোর একটি উপায় আছে যে কোডের কোনো এক জায়গায় তাকে 🤖 অন্য কোথাও অন্য কিছু শেষ হওয়ার জন্য অপেক্ষা করতে হবে। ধরা যাক সেই অন্য কিছুর নাম "slow-file" 📝।

তাই সেই সময়ে, "slow-file" 📝 শেষ হতে হতে কম্পিউটার গিয়ে অন্য কিছু কাজ করতে পারে।

তারপর কম্পিউটার / প্রোগ্রাম 🤖 প্রতিবার সুযোগ পেলেই ফিরে আসবে, কারণ সে আবার অপেক্ষা করছে, অথবা যখনই সে 🤖 তখনকার সব কাজ শেষ করে ফেলে। আর সে 🤖 দেখবে যে যেসব কাজের জন্য সে অপেক্ষা করছিল সেগুলোর কোনোটি ইতিমধ্যে শেষ হয়েছে কিনা, তারপর যা করার ছিল তা করবে।

এরপর সে 🤖 প্রথম শেষ হওয়া কাজটি নেয় (ধরা যাক, আমাদের "slow-file" 📝) এবং সেটি নিয়ে যা করার ছিল তা চালিয়ে যায়।

এই "অন্য কিছুর জন্য অপেক্ষা" সাধারণত তুলনামূলকভাবে "ধীর" (প্রসেসর ও RAM মেমরির গতির তুলনায়) I/O অপারেশনগুলোকে বোঝায়, যেমন অপেক্ষা করা:

  • ক্লায়েন্টের ডেটা নেটওয়ার্কের মাধ্যমে পাঠানো হওয়ার জন্য
  • আপনার প্রোগ্রামের পাঠানো ডেটা নেটওয়ার্কের মাধ্যমে ক্লায়েন্টের কাছে পৌঁছানোর জন্য
  • ডিস্কে থাকা একটি ফাইলের বিষয়বস্তু সিস্টেম পড়ে আপনার প্রোগ্রামকে দেওয়ার জন্য
  • আপনার প্রোগ্রাম সিস্টেমকে যে বিষয়বস্তু দিয়েছে তা ডিস্কে লেখা হওয়ার জন্য
  • একটি রিমোট API অপারেশনের জন্য
  • একটি ডেটাবেস অপারেশন শেষ হওয়ার জন্য
  • একটি ডেটাবেস কুয়েরির ফলাফল ফেরত আসার জন্য
  • ইত্যাদি।

যেহেতু এক্সিকিউশনের সময় বেশিরভাগই I/O অপারেশনের অপেক্ষায় খরচ হয়, তাই এগুলোকে বলা হয় "I/O bound" অপারেশন।

একে "অ্যাসিঙ্ক্রোনাস" বলা হয় কারণ কম্পিউটার / প্রোগ্রামকে ধীর কাজটির সাথে "সিঙ্ক্রোনাইজড" থাকতে হয় না, অর্থাৎ কাজের ফলাফল নিয়ে কাজ চালিয়ে যাওয়ার জন্য কাজটি ঠিক যে মুহূর্তে শেষ হয় সেই মুহূর্তের জন্য কিছু না করে বসে অপেক্ষা করতে হয় না।

তার বদলে, একটি "অ্যাসিঙ্ক্রোনাস" সিস্টেম হওয়ায়, কাজটি শেষ হলে কম্পিউটার / প্রোগ্রাম যা করতে গিয়েছিল তা শেষ করা পর্যন্ত কাজটি একটু (কয়েক মাইক্রোসেকেন্ড) লাইনে অপেক্ষা করতে পারে, তারপর কম্পিউটার ফিরে এসে ফলাফল নিয়ে কাজ চালিয়ে যায়।

"সিঙ্ক্রোনাস" (অর্থাৎ "অ্যাসিঙ্ক্রোনাস"-এর বিপরীত) বোঝাতে সাধারণত "সিকোয়েনশিয়াল" শব্দটিও ব্যবহার করা হয়, কারণ কম্পিউটার / প্রোগ্রাম অন্য কাজে যাওয়ার আগে সব ধাপ ক্রমানুসারে অনুসরণ করে, এমনকি সেই ধাপগুলোতে অপেক্ষা থাকলেও।

কনকারেন্সি ও বার্গার¶

ওপরে বর্ণিত অ্যাসিঙ্ক্রোনাস কোডের এই ধারণাটিকে কখনো কখনো "কনকারেন্সি"-ও বলা হয়। এটি "প্যারালালিজম" থেকে আলাদা।

কনকারেন্সি ও প্যারালালিজম দুটোই "কমবেশি একই সময়ে ভিন্ন ভিন্ন জিনিস ঘটা"-র সাথে সম্পর্কিত।

তবে কনকারেন্সি ও প্যারালালিজমের খুঁটিনাটি বেশ আলাদা।

পার্থক্যটি দেখতে বার্গার নিয়ে নিচের গল্পটি কল্পনা করুন:

কনকারেন্ট বার্গার¶

আপনি আপনার ক্রাশের সাথে ফাস্ট ফুড খেতে গেলেন, ক্যাশিয়ার আপনার সামনের লোকদের অর্ডার নিচ্ছেন আর আপনি লাইনে দাঁড়িয়ে আছেন। 😍

তারপর আপনার পালা এলো, আপনি আপনার ক্রাশ আর নিজের জন্য ২টি খুবই দারুণ বার্গারের অর্ডার দিলেন। 🍔🍔

ক্যাশিয়ার রান্নাঘরের রাঁধুনিকে কিছু একটা বললেন, যাতে তিনি জানেন যে আপনার বার্গার বানাতে হবে (যদিও তিনি এই মুহূর্তে আগের ক্রেতাদের বার্গার বানাচ্ছেন)।

আপনি টাকা দিলেন। 💸

ক্যাশিয়ার আপনাকে আপনার সিরিয়াল নম্বর দিলেন।

অপেক্ষা করার সময় আপনি আপনার ক্রাশকে নিয়ে একটি টেবিল বেছে নিয়ে বসলেন, আর অনেকক্ষণ ধরে আপনার ক্রাশের সাথে গল্প করলেন (কারণ আপনার বার্গারগুলো খুবই দারুণ, বানাতে কিছুটা সময় লাগে)।

বার্গারের অপেক্ষায় ক্রাশের সাথে টেবিলে বসে থাকার সময়টা আপনি কাটাতে পারেন আপনার ক্রাশ কতটা অসাধারণ, মিষ্টি আর বুদ্ধিমান তা মুগ্ধ হয়ে দেখে ✨😍✨।

অপেক্ষা আর ক্রাশের সাথে গল্প করার ফাঁকে ফাঁকে আপনি কাউন্টারে দেখানো নম্বরটি দেখে নেন, আপনার পালা এসেছে কিনা।

তারপর একসময় অবশেষে আপনার পালা আসে। আপনি কাউন্টারে গিয়ে বার্গারগুলো নিয়ে টেবিলে ফিরে আসেন।

আপনি আর আপনার ক্রাশ বার্গার খান আর চমৎকার সময় কাটান। ✨

নোট

চমৎকার ইলাস্ট্রেশনগুলো করেছেন Ketrina Thompson। 🎨

কল্পনা করুন, ওই গল্পে আপনিই কম্পিউটার / প্রোগ্রাম 🤖।

লাইনে থাকার সময় আপনি কেবল অলস 😴, আপনার পালার অপেক্ষা করছেন, খুব "উৎপাদনশীল" কিছু করছেন না। তবে লাইনটি দ্রুত এগোয়, কারণ ক্যাশিয়ার কেবল অর্ডার নিচ্ছেন (বানাচ্ছেন না), তাই সমস্যা নেই।

তারপর যখন আপনার পালা আসে, আপনি সত্যিকারের "উৎপাদনশীল" কাজ করেন: মেনু দেখেন, কী চান ঠিক করেন, ক্রাশের পছন্দ জেনে নেন, টাকা দেন, ঠিক নোট বা কার্ড দিচ্ছেন কিনা দেখেন, সঠিক বিল হয়েছে কিনা দেখেন, অর্ডারে সঠিক আইটেমগুলো আছে কিনা দেখেন ইত্যাদি।

কিন্তু এরপর, যদিও আপনার হাতে এখনো বার্গার নেই, ক্যাশিয়ারের সাথে আপনার কাজ "বিরতিতে" ⏸, কারণ বার্গার তৈরি হওয়ার জন্য আপনাকে অপেক্ষা 🕙 করতে হবে।

তবে যেহেতু আপনি সিরিয়াল নম্বর নিয়ে কাউন্টার থেকে সরে টেবিলে বসেছেন, তাই আপনি আপনার মনোযোগ ক্রাশের দিকে সরাতে 🔀 পারেন, আর তাতে "কাজ" ⏯ 🤓 করতে পারেন। তখন আপনি আবার খুবই "উৎপাদনশীল" কিছু করছেন, যেমন ক্রাশের সাথে ফ্লার্ট করা 😍।

তারপর ক্যাশিয়ার 💁 কাউন্টারের ডিসপ্লেতে আপনার নম্বর দেখিয়ে জানান "বার্গার তৈরি শেষ", কিন্তু ডিসপ্লের নম্বর আপনার নম্বরে বদলানোর সাথে সাথেই আপনি পাগলের মতো লাফিয়ে ওঠেন না। আপনি জানেন কেউ আপনার বার্গার চুরি করবে না, কারণ আপনার কাছে আপনার সিরিয়াল নম্বর আছে, আর তাদের কাছে তাদেরটা।

তাই আপনি অপেক্ষা করেন আপনার ক্রাশের গল্পটা শেষ হওয়া পর্যন্ত (বর্তমান কাজ ⏯ / প্রসেস হতে থাকা টাস্ক 🤓 শেষ করা), মৃদু হাসেন আর বলেন যে আপনি বার্গার আনতে যাচ্ছেন ⏸।

তারপর আপনি কাউন্টারে যান 🔀, সেই প্রাথমিক কাজে যা এখন শেষ ⏯, বার্গারগুলো নেন, ধন্যবাদ বলেন এবং টেবিলে নিয়ে আসেন। এতে কাউন্টারের সাথে যোগাযোগের ওই ধাপ / টাস্কটি শেষ হয় ⏹। আর এটি থেকে একটি নতুন টাস্ক তৈরি হয়, "বার্গার খাওয়া" 🔀 ⏯, কিন্তু আগের "বার্গার আনা" টাস্কটি শেষ ⏹।

প্যারালাল বার্গার¶

এবার কল্পনা করা যাক এগুলো "কনকারেন্ট বার্গার" নয়, বরং "প্যারালাল বার্গার"।

আপনি আপনার ক্রাশের সাথে প্যারালাল ফাস্ট ফুড খেতে গেলেন।

আপনি লাইনে দাঁড়িয়ে আছেন, আর কয়েকজন (ধরা যাক ৮ জন) ক্যাশিয়ার, যারা একই সাথে রাঁধুনিও, আপনার সামনের লোকদের অর্ডার নিচ্ছেন।

আপনার আগের সবাই কাউন্টার ছাড়ার আগে তাদের বার্গার তৈরি হওয়ার অপেক্ষা করছেন, কারণ ৮ জন ক্যাশিয়ারের প্রত্যেকে পরের অর্ডার নেওয়ার আগে গিয়ে সাথে সাথে বার্গার বানিয়ে আনেন।

তারপর অবশেষে আপনার পালা আসে, আপনি আপনার ক্রাশ আর নিজের জন্য ২টি খুবই দারুণ বার্গারের অর্ডার দেন।

আপনি টাকা দেন 💸।

ক্যাশিয়ার রান্নাঘরে চলে যান।

আপনি কাউন্টারের সামনে দাঁড়িয়ে অপেক্ষা করেন 🕙, যাতে আপনার আগে অন্য কেউ আপনার বার্গার নিয়ে না যায়, কারণ এখানে কোনো সিরিয়াল নম্বর নেই।

যেহেতু আপনি আর আপনার ক্রাশ ব্যস্ত, যাতে কেউ সামনে এসে বার্গার আসামাত্র নিয়ে না যায়, তাই আপনি আপনার ক্রাশের দিকে মনোযোগ দিতে পারছেন না। 😞

এটি হলো "সিঙ্ক্রোনাস" কাজ, আপনি ক্যাশিয়ার/রাঁধুনির 👨‍🍳 সাথে "সিঙ্ক্রোনাইজড"। আপনাকে অপেক্ষা 🕙 করতে হবে এবং ঠিক সেই মুহূর্তে সেখানে থাকতে হবে যখন ক্যাশিয়ার/রাঁধুনি 👨‍🍳 বার্গার বানানো শেষ করে আপনার হাতে দেবেন, নইলে অন্য কেউ সেগুলো নিয়ে যেতে পারে।

তারপর কাউন্টারের সামনে অনেকক্ষণ অপেক্ষার 🕙 পর অবশেষে আপনার ক্যাশিয়ার/রাঁধুনি 👨‍🍳 আপনার বার্গার নিয়ে ফিরে আসেন।

বার্গারের উপসংহার¶

"ক্রাশের সাথে ফাস্ট ফুড বার্গার"-এর এই পরিস্থিতিতে যেহেতু প্রচুর অপেক্ষা 🕙 আছে, তাই একটি কনকারেন্ট সিস্টেম ⏸🔀⏯ থাকাই অনেক বেশি যুক্তিসঙ্গত।

বেশিরভাগ ওয়েব অ্যাপ্লিকেশনের ক্ষেত্রেও এমনটাই।

অনেক, অনেক ইউজার, কিন্তু আপনার সার্ভার তাদের খুব-একটা-ভালো-নয় এমন কানেকশনে রিকোয়েস্ট পাঠানোর জন্য অপেক্ষা 🕙 করছে।

তারপর আবার রেসপন্স ফেরত আসার জন্য অপেক্ষা 🕙 করছে।

এই "অপেক্ষা" 🕙 মাপা হয় মাইক্রোসেকেন্ডে, তবুও সব মিলিয়ে শেষ পর্যন্ত এটি অনেক অপেক্ষা।

এ কারণেই ওয়েব API-এর জন্য অ্যাসিঙ্ক্রোনাস ⏸🔀⏯ কোড ব্যবহার করা খুবই যুক্তিসঙ্গত।

এই ধরনের অ্যাসিঙ্ক্রোনিসিটিই NodeJS-কে জনপ্রিয় করেছে (যদিও NodeJS প্যারালাল নয়), আর প্রোগ্রামিং ভাষা হিসেবে Go-এর শক্তিও এটাই।

আর FastAPI-তে আপনি একই মানের পারফরম্যান্স পান।

আর যেহেতু একই সাথে প্যারালালিজম ও অ্যাসিঙ্ক্রোনিসিটি দুটোই পাওয়া যায়, তাই আপনি পরীক্ষিত বেশিরভাগ NodeJS ফ্রেমওয়ার্কের চেয়ে বেশি পারফরম্যান্স পান, যা C-এর কাছাকাছি একটি কম্পাইলড ভাষা Go-এর সমকক্ষ (সবই Starlette-এর কৃতিত্ব)।

কনকারেন্সি কি প্যারালালিজমের চেয়ে ভালো?¶

না! গল্পের শিক্ষা সেটা নয়।

কনকারেন্সি প্যারালালিজম থেকে আলাদা। আর প্রচুর অপেক্ষা থাকে এমন নির্দিষ্ট পরিস্থিতিতে এটি ভালো। এ কারণে ওয়েব অ্যাপ্লিকেশন ডেভেলপমেন্টে এটি সাধারণত প্যারালালিজমের চেয়ে অনেক ভালো। কিন্তু সবকিছুর জন্য নয়।

তাই ভারসাম্য আনতে নিচের ছোট গল্পটি কল্পনা করুন:

আপনাকে একটি বড়, নোংরা বাড়ি পরিষ্কার করতে হবে।

হ্যাঁ, এটাই পুরো গল্প।

কোথাও কোনো অপেক্ষা 🕙 নেই, শুধু বাড়ির বিভিন্ন জায়গায় প্রচুর কাজ করার আছে।

আপনি বার্গারের উদাহরণের মতো পালা করে কাজ করতে পারেন, প্রথমে বসার ঘর, তারপর রান্নাঘর, কিন্তু যেহেতু আপনি কোনো কিছুর জন্য অপেক্ষা 🕙 করছেন না, শুধু পরিষ্কার করেই যাচ্ছেন, তাই পালা করায় কিছুই বদলাবে না।

পালা (কনকারেন্সি) থাকুক বা না থাকুক, শেষ করতে একই সময় লাগবে এবং আপনি একই পরিমাণ কাজ করবেন।

কিন্তু এক্ষেত্রে, আপনি যদি সেই ৮ জন সাবেক-ক্যাশিয়ার/রাঁধুনি/এখন-পরিচ্ছন্নতাকর্মীকে নিয়ে আসতে পারেন, আর তাদের প্রত্যেকে (আপনিসহ) বাড়ির একটি করে অংশ পরিষ্কারের দায়িত্ব নেন, তাহলে অতিরিক্ত সাহায্য নিয়ে আপনি সব কাজ প্যারালালভাবে করতে পারবেন এবং অনেক তাড়াতাড়ি শেষ করবেন।

এই পরিস্থিতিতে প্রত্যেক পরিচ্ছন্নতাকর্মী (আপনিসহ) হবেন একেকটি প্রসেসর, যিনি কাজের নিজের অংশটুকু করছেন।

আর যেহেতু এক্সিকিউশনের বেশিরভাগ সময় আসল কাজে যায় (অপেক্ষায় নয়), এবং কম্পিউটারে কাজটি করে CPU, তাই এই সমস্যাগুলোকে বলা হয় "CPU bound"।

CPU bound অপারেশনের সাধারণ উদাহরণ হলো এমন কাজ যাতে জটিল গাণিতিক প্রসেসিং লাগে।

যেমন:

  • অডিও বা ইমেজ প্রসেসিং।
  • কম্পিউটার ভিশন: একটি ছবি লক্ষ লক্ষ পিক্সেল দিয়ে তৈরি, প্রতিটি পিক্সেলের ৩টি ভ্যালু / রঙ থাকে, আর এটি প্রসেস করতে সাধারণত ওই সব পিক্সেলের ওপর একই সময়ে কিছু হিসাব করতে হয়।
  • মেশিন লার্নিং: এতে সাধারণত প্রচুর "ম্যাট্রিক্স" ও "ভেক্টর" গুণ লাগে। সংখ্যায় ভরা একটি বিশাল স্প্রেডশিট কল্পনা করুন এবং সেগুলো সব একই সময়ে একসাথে গুণ করার কথা ভাবুন।
  • ডিপ লার্নিং: এটি মেশিন লার্নিংয়ের একটি উপক্ষেত্র, তাই একই কথা প্রযোজ্য। পার্থক্য শুধু এই যে গুণ করার জন্য একটিমাত্র সংখ্যার স্প্রেডশিট নয়, বরং সেগুলোর বিশাল এক সেট থাকে, এবং অনেক ক্ষেত্রে ওই মডেলগুলো তৈরি এবং / অথবা ব্যবহার করতে একটি বিশেষ প্রসেসর ব্যবহার করা হয়।

কনকারেন্সি + প্যারালালিজম: ওয়েব + মেশিন লার্নিং¶

FastAPI দিয়ে আপনি ওয়েব ডেভেলপমেন্টে খুবই প্রচলিত কনকারেন্সির সুবিধা নিতে পারেন (NodeJS-এর প্রধান আকর্ষণও এটাই)।

তবে মেশিন লার্নিং সিস্টেমের মতো CPU bound কাজের জন্য প্যারালালিজম ও মাল্টিপ্রসেসিংয়ের (একাধিক প্রসেস প্যারালালভাবে চলা) সুবিধাও আপনি কাজে লাগাতে পারেন।

এর সাথে এই সাধারণ সত্যটি যে Python হলো ডেটা সায়েন্স, মেশিন লার্নিং এবং বিশেষ করে ডিপ লার্নিংয়ের প্রধান ভাষা, FastAPI-কে ডেটা সায়েন্স / মেশিন লার্নিং ওয়েব API ও অ্যাপ্লিকেশনের (আরও অনেক কিছুর পাশাপাশি) জন্য খুবই উপযুক্ত করে তোলে।

প্রোডাকশনে এই প্যারালালিজম কীভাবে অর্জন করবেন তা দেখতে ডিপ্লয়মেন্ট সম্পর্কিত অংশটি দেখুন।

async ও await¶

Python-এর আধুনিক ভার্সনগুলোতে অ্যাসিঙ্ক্রোনাস কোড সংজ্ঞায়িত করার একটি খুবই সহজবোধ্য উপায় আছে। এতে এটি দেখতে ঠিক সাধারণ "সিকোয়েনশিয়াল" কোডের মতো হয়, আর সঠিক মুহূর্তে আপনার হয়ে "অপেক্ষা" করে।

যখন এমন কোনো অপারেশন থাকে যা ফলাফল দেওয়ার আগে অপেক্ষা করতে হবে এবং Python-এর এই নতুন ফিচারগুলো সাপোর্ট করে, তখন আপনি এভাবে কোড লিখতে পারেন:

burgers = await get_burgers(2)

এখানে মূল বিষয় হলো await। এটি Python-কে জানায় যে burgers-এ ফলাফল রাখার আগে get_burgers(2)-এর কাজ শেষ হওয়া 🕙 পর্যন্ত তাকে অপেক্ষা ⏸ করতে হবে। এর ফলে Python জানবে যে এর মধ্যে সে গিয়ে অন্য কিছু 🔀 ⏯ করতে পারে (যেমন আরেকটি রিকোয়েস্ট গ্রহণ করা)।

await কাজ করার জন্য এটিকে অবশ্যই এমন একটি ফাংশনের ভেতরে থাকতে হবে যা এই অ্যাসিঙ্ক্রোনিসিটি সাপোর্ট করে। এর জন্য শুধু ফাংশনটি async def দিয়ে ঘোষণা করুন:

async def get_burgers(number: int):
    # বার্গার তৈরির জন্য কিছু অ্যাসিঙ্ক্রোনাস কাজ করুন
    return burgers

...def-এর বদলে:

# এটি অ্যাসিঙ্ক্রোনাস নয়
def get_sequential_burgers(number: int):
    # বার্গার তৈরির জন্য কিছু সিকোয়েনশিয়াল কাজ করুন
    return burgers

async def থাকলে Python জানে যে ওই ফাংশনের ভেতরে তাকে await এক্সপ্রেশনগুলোর দিকে খেয়াল রাখতে হবে, এবং সে ওই ফাংশনের এক্সিকিউশন "বিরতি" ⏸ দিয়ে অন্য কিছু 🔀 করে আবার ফিরে আসতে পারে।

আপনি যখন একটি async def ফাংশন কল করতে চান, তখন সেটিকে "await" করতে হয়। তাই এটি কাজ করবে না:

# এটি কাজ করবে না, কারণ get_burgers সংজ্ঞায়িত করা হয়েছে এভাবে: async def
burgers = get_burgers(2)

তাই আপনি যদি এমন একটি লাইব্রেরি ব্যবহার করেন যা বলে যে একে await দিয়ে কল করা যায়, তাহলে যে পাথ অপারেশন ফাংশনগুলো এটি ব্যবহার করে সেগুলো async def দিয়ে তৈরি করতে হবে, যেমন:

@app.get('/burgers')
async def read_burgers():
    burgers = await get_burgers(2)
    return burgers

আরও কারিগরি বিবরণ¶

আপনি হয়তো লক্ষ করেছেন যে await কেবল async def দিয়ে সংজ্ঞায়িত ফাংশনের ভেতরেই ব্যবহার করা যায়।

আবার একই সাথে, async def দিয়ে সংজ্ঞায়িত ফাংশনগুলোকে "await" করতে হয়। তাই async def ফাংশনগুলো কেবল async def দিয়ে সংজ্ঞায়িত ফাংশনের ভেতরেই কল করা যায়।

তাহলে ডিম আগে না মুরগি আগে, প্রথম async ফাংশনটি কীভাবে কল করবেন?

আপনি যদি FastAPI নিয়ে কাজ করেন, তাহলে এ নিয়ে চিন্তা করতে হবে না, কারণ ওই "প্রথম" ফাংশনটি হবে আপনার পাথ অপারেশন ফাংশন, আর FastAPI জানে কীভাবে সঠিক কাজটি করতে হয়।

তবে আপনি যদি FastAPI ছাড়া async / await ব্যবহার করতে চান, সেটাও করতে পারেন।

নিজের async কোড লিখুন¶

Starlette (এবং FastAPI) AnyIO-এর ওপর ভিত্তি করে তৈরি, যা একে Python-এর স্ট্যান্ডার্ড লাইব্রেরি asyncio এবং Trio দুটোর সাথেই সামঞ্জস্যপূর্ণ করে।

বিশেষ করে, আপনার নিজের কোডে আরও অ্যাডভান্সড প্যাটার্ন লাগে এমন অ্যাডভান্সড কনকারেন্সির ক্ষেত্রে আপনি সরাসরি AnyIO ব্যবহার করতে পারেন।

এমনকি আপনি FastAPI ব্যবহার না করলেও, অত্যন্ত সামঞ্জস্যপূর্ণ হতে এবং এর সুবিধাগুলো (যেমন structured concurrency) পেতে AnyIO দিয়ে আপনার নিজের async অ্যাপ্লিকেশন লিখতে পারেন।

টাইপ অ্যানোটেশন একটু উন্নত করতে এবং আরও ভালো অটোকমপ্লিশন, ইনলাইন এরর ইত্যাদি পেতে আমি AnyIO-এর ওপর একটি পাতলা স্তর হিসেবে আরেকটি লাইব্রেরি তৈরি করেছি। এতে আপনাকে বুঝতে এবং নিজের async কোড লিখতে সাহায্য করার জন্য একটি বন্ধুত্বপূর্ণ পরিচিতি ও টিউটোরিয়ালও আছে: Asyncer। আপনাকে যদি async কোডকে সাধারণ (ব্লকিং/সিঙ্ক্রোনাস) কোডের সাথে মেলাতে হয়, তাহলে এটি বিশেষভাবে কাজে আসবে।

অ্যাসিঙ্ক্রোনাস কোডের অন্যান্য রূপ¶

async ও await ব্যবহারের এই ধরনটি ভাষাটিতে তুলনামূলকভাবে নতুন।

তবে এটি অ্যাসিঙ্ক্রোনাস কোড নিয়ে কাজ করাকে অনেক সহজ করে দেয়।

এই একই সিনট্যাক্স (বা প্রায় একই রকম) সম্প্রতি JavaScript-এর আধুনিক ভার্সনগুলোতেও (ব্রাউজার ও NodeJS-এ) যুক্ত হয়েছে।

কিন্তু তার আগে অ্যাসিঙ্ক্রোনাস কোড সামলানো বেশ জটিল ও কঠিন ছিল।

Python-এর আগের ভার্সনগুলোতে আপনি থ্রেড বা Gevent ব্যবহার করতে পারতেন। কিন্তু সেই কোড বোঝা, ডিবাগ করা ও তা নিয়ে ভাবা অনেক বেশি জটিল।

NodeJS / ব্রাউজার JavaScript-এর আগের ভার্সনগুলোতে আপনি "কলব্যাক" ব্যবহার করতেন। যা নিয়ে যায় "callback hell"-এ।

কোরুটিন¶

কোরুটিন হলো একটি async def ফাংশন যা রিটার্ন করে তার জন্য খুবই গালভরা একটি শব্দ। Python জানে যে এটি একটি ফাংশনের মতো কিছু, যা শুরু করা যায় এবং একসময় শেষ হবে, তবে এর ভেতরে যখনই কোনো await থাকে তখন এটি ভেতর থেকে বিরতিও ⏸ নিতে পারে।

তবে async ও await দিয়ে অ্যাসিঙ্ক্রোনাস কোড ব্যবহারের এই পুরো কার্যকারিতাকে অনেক সময় সংক্ষেপে "কোরুটিন" ব্যবহার বলা হয়। এটি Go-এর প্রধান মূল ফিচার "Goroutines"-এর সাথে তুলনীয়।

উপসংহার¶

ওপরের সেই একই বাক্যটি দেখা যাক:

Python-এর আধুনিক ভার্সনগুলো "কোরুটিন" নামের একটি জিনিস ব্যবহার করে async ও await সিনট্যাক্স দিয়ে "অ্যাসিঙ্ক্রোনাস কোড" সাপোর্ট করে।

এখন এটি আরও বোধগম্য হওয়া উচিত। ✨

এই সবকিছুই (Starlette-এর মাধ্যমে) FastAPI-কে চালায় এবং একে এমন চমকপ্রদ পারফরম্যান্স দেয়।

খুবই কারিগরি বিবরণ¶

সতর্কতা

আপনি সম্ভবত এটি এড়িয়ে যেতে পারেন।

এগুলো FastAPI ভেতরে ভেতরে কীভাবে কাজ করে তার খুবই কারিগরি বিবরণ।

আপনার যদি বেশ ভালো কারিগরি জ্ঞান থাকে (কোরুটিন, থ্রেড, ব্লকিং ইত্যাদি) এবং FastAPI কীভাবে async def বনাম সাধারণ def সামলায় তা জানতে কৌতূহলী হন, তাহলে এগিয়ে যান।

পাথ অপারেশন ফাংশন¶

আপনি যখন async def-এর বদলে সাধারণ def দিয়ে একটি পাথ অপারেশন ফাংশন ঘোষণা করেন, তখন সেটি সরাসরি কল না হয়ে (কারণ তাতে সার্ভার ব্লক হয়ে যেত) একটি বাহ্যিক থ্রেডপুলে চালানো হয় এবং তারপর সেটিকে await করা হয়।

আপনি যদি এমন অন্য কোনো async ফ্রেমওয়ার্ক থেকে আসেন যা ওপরে বর্ণিত পদ্ধতিতে কাজ করে না, এবং সামান্য পারফরম্যান্স লাভের (প্রায় ১০০ ন্যানোসেকেন্ড) জন্য শুধু হিসাব-নির্ভর সাধারণ পাথ অপারেশন ফাংশনগুলো সাধারণ def দিয়ে সংজ্ঞায়িত করতে অভ্যস্ত হন, তাহলে লক্ষ করুন যে FastAPI-তে এর প্রভাব হবে একেবারে উল্টো। এসব ক্ষেত্রে async def ব্যবহার করাই ভালো, যদি না আপনার পাথ অপারেশন ফাংশনগুলো এমন কোড ব্যবহার করে যা ব্লকিং I/O করে।

তবুও, দুই পরিস্থিতিতেই সম্ভাবনা হলো FastAPI আপনার আগের ফ্রেমওয়ার্কের চেয়ে তবুও দ্রুততর হবে (বা অন্তত তুলনীয় হবে)।

ডিপেন্ডেন্সি¶

ডিপেন্ডেন্সির ক্ষেত্রেও একই কথা প্রযোজ্য। কোনো ডিপেন্ডেন্সি যদি async def-এর বদলে একটি স্ট্যান্ডার্ড def ফাংশন হয়, তাহলে সেটি বাহ্যিক থ্রেডপুলে চালানো হয়।

সাব-ডিপেন্ডেন্সি¶

আপনার একাধিক ডিপেন্ডেন্সি ও সাব-ডিপেন্ডেন্সি থাকতে পারে যেগুলো একে অপরকে প্রয়োজন করে (ফাংশন সংজ্ঞার প্যারামিটার হিসেবে), এগুলোর কয়েকটি async def দিয়ে আর কয়েকটি সাধারণ def দিয়ে তৈরি হতে পারে। এটি তবুও কাজ করবে, এবং সাধারণ def দিয়ে তৈরিগুলো "await" না হয়ে একটি বাহ্যিক থ্রেডে (থ্রেডপুল থেকে) কল হবে।

অন্যান্য ইউটিলিটি ফাংশন¶

আপনি সরাসরি কল করেন এমন অন্য যেকোনো ইউটিলিটি ফাংশন সাধারণ def বা async def দিয়ে তৈরি করা যায়, আর আপনি সেটি কীভাবে কল করবেন তাতে FastAPI কোনো প্রভাব ফেলবে না।

এটি সেই ফাংশনগুলোর বিপরীত যেগুলো FastAPI আপনার হয়ে কল করে: পাথ অপারেশন ফাংশন ও ডিপেন্ডেন্সি।

আপনার ইউটিলিটি ফাংশন যদি def দিয়ে তৈরি একটি সাধারণ ফাংশন হয়, তাহলে সেটি থ্রেডপুলে নয়, সরাসরি কল হবে (যেমন আপনি কোডে লেখেন)। আর ফাংশনটি যদি async def দিয়ে তৈরি হয়, তাহলে কোডে কল করার সময় সেটিকে await করা উচিত।

আবারও বলি, এগুলো খুবই কারিগরি বিবরণ, যা সম্ভবত তখনই কাজে লাগবে যদি আপনি এগুলোই খুঁজতে আসেন।

নইলে ওপরের অংশের নির্দেশনাগুলোই আপনার জন্য যথেষ্ট: তাড়াহুড়োয় আছেন?।
