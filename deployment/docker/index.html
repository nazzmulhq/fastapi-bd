কন্টেইনারে FastAPI - Docker¶

🌐 AI এবং মানুষের যৌথ অনুবাদ

এই অনুবাদটি মানুষের নির্দেশনায় AI দিয়ে করা হয়েছে। 🤝

এতে মূল অর্থ ভুল বোঝা বা অস্বাভাবিক শোনানোর মতো ভুল থাকতে পারে। 🤖

ইংরেজি সংস্করণ

FastAPI অ্যাপ্লিকেশন ডিপ্লয় করার সময় একটি প্রচলিত পদ্ধতি হলো একটি Linux কন্টেইনার ইমেজ তৈরি করা। এটি সাধারণত করা হয় Docker ব্যবহার করে। তারপর আপনি সম্ভাব্য কয়েকটি উপায়ের একটিতে সেই কন্টেইনার ইমেজ ডিপ্লয় করতে পারেন।

Linux কন্টেইনার ব্যবহারের বেশ কিছু সুবিধা আছে, যার মধ্যে আছে সিকিউরিটি, পুনরুৎপাদনযোগ্যতা, সরলতা এবং আরও অনেক কিছু।

পরামর্শ

তাড়াহুড়োয় আছেন এবং এসব আগে থেকেই জানেন? নিচের Dockerfile-এ চলে যান 👇।

Dockerfile প্রিভিউ 👀 
FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

COPY ./app /code/app

CMD ["fastapi", "run", "app/main.py", "--port", "80"]

# Nginx বা Traefik-এর মতো কোনো প্রক্সির পেছনে চালালে --proxy-headers যোগ করুন
# CMD ["fastapi", "run", "app/main.py", "--port", "80", "--proxy-headers"]

কন্টেইনার কী¶

কন্টেইনার (প্রধানত Linux কন্টেইনার) হলো অ্যাপ্লিকেশনকে তাদের সব ডিপেন্ডেন্সি ও প্রয়োজনীয় ফাইলসহ প্যাকেজ করার একটি খুবই হালকা উপায়, আর একই সাথে একই সিস্টেমের অন্যান্য কন্টেইনার (অন্যান্য অ্যাপ্লিকেশন বা কম্পোনেন্ট) থেকে সেগুলোকে বিচ্ছিন্ন রাখে।

Linux কন্টেইনারগুলো হোস্টের (মেশিন, ভার্চুয়াল মেশিন, ক্লাউড সার্ভার ইত্যাদি) একই Linux কার্নেল ব্যবহার করে চলে। এর মানে শুধু এই যে এগুলো খুবই হালকা (একটি পুরো অপারেটিং সিস্টেমের অনুকরণ করা পূর্ণ ভার্চুয়াল মেশিনের তুলনায়)।

এভাবে কন্টেইনারগুলো কম রিসোর্স খরচ করে, যা সরাসরি প্রসেস চালানোর সাথে তুলনীয় (একটি ভার্চুয়াল মেশিন অনেক বেশি খরচ করত)।

কন্টেইনারগুলোর নিজস্ব বিচ্ছিন্ন চলমান প্রসেস (সাধারণত মাত্র একটি প্রসেস), ফাইল সিস্টেম ও নেটওয়ার্কও থাকে, যা ডিপ্লয়মেন্ট, সিকিউরিটি, ডেভেলপমেন্ট ইত্যাদি সহজ করে।

কন্টেইনার ইমেজ কী¶

একটি কন্টেইনার চালানো হয় একটি কন্টেইনার ইমেজ থেকে।

একটি কন্টেইনার ইমেজ হলো সব ফাইল, এনভায়রনমেন্ট ভেরিয়েবল এবং একটি কন্টেইনারে থাকা উচিত এমন ডিফল্ট কমান্ড/প্রোগ্রামের একটি স্থির ভার্সন। এখানে স্থির মানে কন্টেইনার ইমেজটি চলছে না, এক্সিকিউট হচ্ছে না, এটি কেবল প্যাকেজ করা ফাইল ও মেটাডেটা।

সংরক্ষিত স্থির বিষয়বস্তু "কন্টেইনার ইমেজ"-এর বিপরীতে, একটি "কন্টেইনার" সাধারণত চলমান ইনস্ট্যান্সকে বোঝায়, যে জিনিসটি এক্সিকিউট হচ্ছে।

যখন কন্টেইনারটি চালু হয় এবং চলতে থাকে (একটি কন্টেইনার ইমেজ থেকে চালু হয়ে), তখন এটি ফাইল, এনভায়রনমেন্ট ভেরিয়েবল ইত্যাদি তৈরি বা পরিবর্তন করতে পারে। ওই পরিবর্তনগুলো কেবল ওই কন্টেইনারেই থাকবে, কিন্তু মূল কন্টেইনার ইমেজে স্থায়ী হবে না (ডিস্কে সংরক্ষিত হবে না)।

একটি কন্টেইনার ইমেজ প্রোগ্রাম ফাইল ও বিষয়বস্তুর সাথে তুলনীয়, যেমন python এবং কোনো একটি ফাইল main.py।

আর কন্টেইনারটি নিজে (কন্টেইনার ইমেজের বিপরীতে) হলো ইমেজের আসল চলমান ইনস্ট্যান্স, যা একটি প্রসেসের সাথে তুলনীয়। আসলে একটি কন্টেইনার কেবল তখনই চলে যখন এতে একটি প্রসেস চলে (এবং সাধারণত এটি মাত্র একটি প্রসেস)। এতে কোনো প্রসেস না চললে কন্টেইনারটি থেমে যায়।

কন্টেইনার ইমেজ¶

কন্টেইনার ইমেজ ও কন্টেইনার তৈরি ও পরিচালনার প্রধান টুলগুলোর একটি হলো Docker।

আর একটি পাবলিক Docker Hub আছে, যেখানে অনেক টুল, এনভায়রনমেন্ট, ডেটাবেস ও অ্যাপ্লিকেশনের জন্য আগে থেকে তৈরি অফিসিয়াল কন্টেইনার ইমেজ আছে।

যেমন, একটি অফিসিয়াল Python Image আছে।

আর ডেটাবেসের মতো বিভিন্ন জিনিসের জন্য আরও অনেক ইমেজ আছে, যেমন:

  • PostgreSQL
  • MySQL
  • MongoDB
  • Redis ইত্যাদি।

আগে থেকে তৈরি একটি কন্টেইনার ইমেজ ব্যবহার করে বিভিন্ন টুল একত্রিত করে ব্যবহার করা খুবই সহজ। যেমন, একটি নতুন ডেটাবেস চেষ্টা করে দেখতে। বেশিরভাগ ক্ষেত্রে আপনি অফিসিয়াল ইমেজ ব্যবহার করে শুধু এনভায়রনমেন্ট ভেরিয়েবল দিয়ে সেগুলো কনফিগার করতে পারেন।

এভাবে অনেক ক্ষেত্রে আপনি কন্টেইনার ও Docker সম্পর্কে শিখে সেই জ্ঞান অনেক ভিন্ন ভিন্ন টুল ও কম্পোনেন্টের সাথে পুনরায় ব্যবহার করতে পারেন।

তাই আপনি ভিন্ন ভিন্ন জিনিসসহ একাধিক কন্টেইনার চালাবেন, যেমন একটি ডেটাবেস, একটি Python অ্যাপ্লিকেশন, একটি React ফ্রন্টএন্ড অ্যাপ্লিকেশনসহ একটি ওয়েব সার্ভার, এবং তাদের অভ্যন্তরীণ নেটওয়ার্কের মাধ্যমে সেগুলো একসাথে যুক্ত করবেন।

সব কন্টেইনার ম্যানেজমেন্ট সিস্টেমে (যেমন Docker বা Kubernetes) এই নেটওয়ার্কিং ফিচারগুলো অন্তর্ভুক্ত আছে।

কন্টেইনার ও প্রসেস¶

একটি কন্টেইনার ইমেজ সাধারণত এর মেটাডেটায় সেই ডিফল্ট প্রোগ্রাম বা কমান্ড অন্তর্ভুক্ত করে যা কন্টেইনার চালু হওয়ার সময় চালানো উচিত, এবং সেই প্রোগ্রামে পাঠানোর প্যারামিটারগুলোও। কমান্ড লাইনে থাকলে যেমন হতো তার খুবই অনুরূপ।

যখন একটি কন্টেইনার চালু হয়, তখন এটি ওই কমান্ড/প্রোগ্রাম চালাবে (যদিও আপনি এটি ওভাররাইড করে ভিন্ন একটি কমান্ড/প্রোগ্রাম চালাতে পারেন)।

মূল প্রসেস (কমান্ড বা প্রোগ্রাম) যতক্ষণ চলে, একটি কন্টেইনার ততক্ষণ চলে।

একটি কন্টেইনারে সাধারণত একটি একক প্রসেস থাকে, তবে মূল প্রসেস থেকে সাবপ্রসেস চালু করাও সম্ভব, আর এভাবে একই কন্টেইনারে আপনার একাধিক প্রসেস থাকবে।

কিন্তু অন্তত একটি চলমান প্রসেস ছাড়া একটি চলমান কন্টেইনার থাকা সম্ভব নয়। মূল প্রসেস থামলে কন্টেইনার থেমে যায়।

FastAPI-এর জন্য একটি Docker ইমেজ তৈরি করুন¶

ঠিক আছে, এবার কিছু তৈরি করা যাক! 🚀

আমি আপনাকে দেখাব কীভাবে অফিসিয়াল Python ইমেজের ওপর ভিত্তি করে একদম শুরু থেকে FastAPI-এর জন্য একটি Docker ইমেজ তৈরি করতে হয়।

বেশিরভাগ ক্ষেত্রে আপনি এটিই করতে চাইবেন, যেমন:

  • Kubernetes বা এরকম টুল ব্যবহারের সময়
  • একটি Raspberry Pi-তে চালানোর সময়
  • আপনার হয়ে একটি কন্টেইনার ইমেজ চালাবে এমন একটি ক্লাউড সার্ভিস ব্যবহারের সময়, ইত্যাদি।

প্যাকেজের প্রয়োজনীয়তা¶

আপনি যখন uv দিয়ে আপনার প্রজেক্ট পরিচালনা করেন, তখন এর সরাসরি ডিপেন্ডেন্সিগুলো pyproject.toml-এ ঘোষণা করা থাকে এবং নির্ধারিত হুবহু ভার্সনগুলো uv.lock-এ সংরক্ষিত থাকে।

আপনার অ্যাপ্লিকেশনের প্রয়োজনীয় প্যাকেজগুলো আপনি এভাবে যোগ করতে পারেন:

$ uv add "fastapi[standard]" pydantic
---> 100%

নোট

নিচের Dockerfile কন্টেইনারের ভেতরে pip ব্যবহার করে। আপনার uv প্রজেক্ট থেকে লক করা ডিপেন্ডেন্সিগুলো এর প্রত্যাশিত requirements.txt ফরম্যাটে এক্সপোর্ট করতে পারেন:

$ uv export --format requirements-txt --no-dev --no-emit-project --output-file requirements.txt

তৈরি হওয়া requirements.txt হলো কন্টেইনার বিল্ডের জন্য একটি এক্সপোর্ট। uv add দিয়ে ডিপেন্ডেন্সি পরিচালনা চালিয়ে যান এবং uv.lock বদলালে এটি আবার তৈরি করুন।

FastAPI কোড তৈরি করুন¶

  • একটি app ডিরেক্টরি তৈরি করে তাতে প্রবেশ করুন।
  • একটি খালি ফাইল __init__.py তৈরি করুন।
  • একটি main.py ফাইল তৈরি করুন, এতে লিখুন:
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def read_root():
    return {"Hello": "World"}


@app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}

Dockerfile¶

এবার একই প্রজেক্ট ডিরেক্টরিতে Dockerfile নামে একটি ফাইল তৈরি করুন, এতে লিখুন:

# (1)!
FROM python:3.14

# (2)!
WORKDIR /code

# (3)!
COPY ./requirements.txt /code/requirements.txt

# (4)!
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# (5)!
COPY ./app /code/app

# (6)!
CMD ["fastapi", "run", "app/main.py", "--port", "80"]

  1. অফিসিয়াল Python বেস ইমেজ থেকে শুরু করুন।

  2. বর্তমান ওয়ার্কিং ডিরেক্টরি /code-এ সেট করুন।

    এখানেই আমরা requirements.txt ফাইল ও app ডিরেক্টরি রাখব।

  3. প্রয়োজনীয়তাসহ ফাইলটি /code ডিরেক্টরিতে কপি করুন।

    প্রথমে কেবল প্রয়োজনীয়তাসহ ফাইলটি কপি করুন, বাকি কোড নয়।

    যেহেতু এই ফাইলটি খুব একটা বদলায় না, তাই Docker এটি শনাক্ত করে এই ধাপের জন্য ক্যাশে ব্যবহার করবে, ফলে পরের ধাপের জন্যও ক্যাশে চালু হবে।

  4. প্রয়োজনীয়তা ফাইলের প্যাকেজ ডিপেন্ডেন্সিগুলো ইনস্টল করুন।

    --no-cache-dir অপশন pip-কে ডাউনলোড করা প্যাকেজগুলো লোকালি সংরক্ষণ না করতে বলে, কারণ তা কেবল তখনই দরকার যদি একই প্যাকেজ ইনস্টল করতে pip আবার চালানো হতো, কিন্তু কন্টেইনার নিয়ে কাজ করার সময় তা হয় না।

    নোট

    --no-cache-dir কেবল pip-এর সাথে সম্পর্কিত, Docker বা কন্টেইনারের সাথে এর কোনো সম্পর্ক নেই।

    --upgrade অপশন pip-কে প্যাকেজগুলো আগে থেকে ইনস্টল থাকলে আপগ্রেড করতে বলে।

    যেহেতু ফাইল কপি করার আগের ধাপটি Docker ক্যাশে শনাক্ত করতে পারে, তাই উপলব্ধ থাকলে এই ধাপটিও Docker ক্যাশে ব্যবহার করবে।

    এই ধাপে ক্যাশে ব্যবহার করলে ডেভেলপমেন্টের সময় বারবার ইমেজ তৈরির সময় প্রতিবার সব ডিপেন্ডেন্সি ডাউনলোড ও ইনস্টল না করে আপনার অনেক সময় বাঁচবে।

  5. ./app ডিরেক্টরিটি /code ডিরেক্টরির ভেতরে কপি করুন।

    যেহেতু এতে সব কোড আছে, যা সবচেয়ে ঘন ঘন বদলায়, তাই এই ধাপ বা পরের কোনো ধাপের জন্য Docker ক্যাশে সহজে ব্যবহার হবে না।

    তাই কন্টেইনার ইমেজ তৈরির সময় অপটিমাইজ করতে এটিকে Dockerfile-এর শেষের কাছাকাছি রাখা গুরুত্বপূর্ণ।

  6. fastapi run ব্যবহার করতে কমান্ড সেট করুন, যা ভেতরে ভেতরে Uvicorn ব্যবহার করে।

    CMD স্ট্রিংয়ের একটি লিস্ট নেয়, এই প্রতিটি স্ট্রিং হলো কমান্ড লাইনে স্পেস দিয়ে আলাদা করে আপনি যা লিখতেন।

    এই কমান্ডটি বর্তমান ওয়ার্কিং ডিরেক্টরি থেকে চলবে, ওপরে WORKDIR /code দিয়ে সেট করা সেই একই /code ডিরেক্টরি।

পরামর্শ

কোডের প্রতিটি সংখ্যার বুদবুদে ক্লিক করে প্রতিটি লাইন কী করে তা দেখে নিন। 👆

সতর্কতা

নিচে যেমন ব্যাখ্যা করা হয়েছে, সবসময় CMD নির্দেশনার exec form ব্যবহার করবেন।

CMD ব্যবহার করুন - Exec Form¶

CMD Docker নির্দেশনাটি দুটি রূপে লেখা যায়:

✅ Exec form:

# ✅ Do this
CMD ["fastapi", "run", "app/main.py", "--port", "80"]

⛔️ Shell form:

# ⛔️ Don't do this
CMD fastapi run app/main.py --port 80

FastAPI যাতে সুন্দরভাবে বন্ধ হতে পারে এবং lifespan ইভেন্ট চালু হয় তা নিশ্চিত করতে সবসময় exec form ব্যবহার করবেন।

এ সম্পর্কে আরও পড়তে পারেন shell ও exec form নিয়ে Docker ডকুমেন্টেশনে।

docker compose ব্যবহারের সময় এটি বেশ লক্ষণীয় হতে পারে। আরও কারিগরি বিবরণের জন্য Docker Compose FAQ-এর এই অংশটি দেখুন: Why do my services take 10 seconds to recreate or stop?।

ডিরেক্টরি কাঠামো¶

এখন আপনার এরকম একটি ডিরেক্টরি কাঠামো থাকা উচিত:

.
├── app
│   ├── __init__.py
│   └── main.py
├── Dockerfile
└── requirements.txt

একটি TLS Termination Proxy-র পেছনে¶

আপনি যদি Nginx বা Traefik-এর মতো একটি TLS Termination Proxy (লোড ব্যালান্সার)-এর পেছনে আপনার কন্টেইনার চালান, তাহলে --proxy-headers অপশন যোগ করুন, এটি Uvicorn-কে (FastAPI CLI-এর মাধ্যমে) ওই প্রক্সির পাঠানো হেডারগুলো বিশ্বাস করতে বলবে, যা জানায় যে অ্যাপ্লিকেশনটি HTTPS-এর পেছনে চলছে, ইত্যাদি।

CMD ["fastapi", "run", "app/main.py", "--proxy-headers", "--port", "80"]

Docker ক্যাশে¶

এই Dockerfile-এ একটি গুরুত্বপূর্ণ কৌশল আছে, আমরা প্রথমে শুধু ডিপেন্ডেন্সিসহ ফাইলটি কপি করি, বাকি কোড নয়। কেন তা বলছি।

COPY ./requirements.txt /code/requirements.txt

Docker ও অন্যান্য টুল এই কন্টেইনার ইমেজগুলো ধাপে ধাপে তৈরি করে, একটি স্তরের ওপর আরেকটি স্তর যোগ করে, Dockerfile-এর ওপর থেকে শুরু করে এবং Dockerfile-এর প্রতিটি নির্দেশনায় তৈরি হওয়া যেকোনো ফাইল যোগ করে।

ইমেজ তৈরির সময় Docker ও এরকম টুলগুলো একটি অভ্যন্তরীণ ক্যাশেও ব্যবহার করে, গতবার কন্টেইনার ইমেজ তৈরির পরে কোনো ফাইল না বদলালে এটি আবার ফাইল কপি করে শুরু থেকে নতুন স্তর তৈরি না করে গতবার তৈরি করা একই স্তর পুনরায় ব্যবহার করবে।

শুধু ফাইলের কপি এড়ানো খুব একটা উন্নতি নাও আনতে পারে, কিন্তু যেহেতু এটি ওই ধাপের জন্য ক্যাশে ব্যবহার করেছে, তাই এটি পরের ধাপের জন্যও ক্যাশে ব্যবহার করতে পারে। যেমন, এটি ডিপেন্ডেন্সি ইনস্টল করার নির্দেশনার জন্য ক্যাশে ব্যবহার করতে পারে:

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

প্যাকেজের প্রয়োজনীয়তাসহ ফাইলটি খুব একটা বদলাবে না। তাই কেবল ওই ফাইলটি কপি করে Docker ওই ধাপের জন্য ক্যাশে ব্যবহার করতে পারবে।

আর তারপর Docker ওই ডিপেন্ডেন্সিগুলো ডাউনলোড ও ইনস্টল করার পরের ধাপের জন্য ক্যাশে ব্যবহার করতে পারবে। আর এখানেই আমরা অনেক সময় বাঁচাই। ✨ ...আর অপেক্ষার একঘেয়েমি এড়াই। 😪😆

প্যাকেজ ডিপেন্ডেন্সি ডাউনলোড ও ইনস্টল করতে কয়েক মিনিট লাগতে পারে, কিন্তু ক্যাশে ব্যবহার করলে বড়জোর কয়েক সেকেন্ড লাগবে।

আর যেহেতু আপনার কোডের পরিবর্তনগুলো কাজ করছে কিনা যাচাই করতে ডেভেলপমেন্টের সময় আপনি বারবার কন্টেইনার ইমেজ তৈরি করবেন, তাই এতে জমে জমে অনেক সময় বাঁচবে।

তারপর Dockerfile-এর শেষের কাছাকাছি আমরা সব কোড কপি করি। যেহেতু এটিই সবচেয়ে ঘন ঘন বদলায়, তাই আমরা এটি শেষের কাছাকাছি রাখি, কারণ প্রায় সবসময় এই ধাপের পরের কোনো কিছু ক্যাশে ব্যবহার করতে পারবে না।

COPY ./app /code/app

Docker ইমেজ তৈরি করুন¶

এখন যেহেতু সব ফাইল জায়গামতো আছে, চলুন কন্টেইনার ইমেজ তৈরি করি।

  • প্রজেক্ট ডিরেক্টরিতে যান (যেখানে আপনার Dockerfile আছে, যাতে আপনার app ডিরেক্টরি আছে)।
  • আপনার FastAPI ইমেজ তৈরি করুন:
$ docker build -t myimage .

---> 100%

পরামর্শ

শেষের .-টি লক্ষ করুন, এটি ./-এর সমতুল্য, এটি Docker-কে কন্টেইনার ইমেজ তৈরিতে ব্যবহারের ডিরেক্টরি জানায়।

এক্ষেত্রে এটি একই বর্তমান ডিরেক্টরি (.)।

Docker কন্টেইনার চালু করুন¶

  • আপনার ইমেজের ওপর ভিত্তি করে একটি কন্টেইনার চালান:
$ docker run -d --name mycontainer -p 80:80 myimage

যাচাই করুন¶

আপনার Docker কন্টেইনারের URL-এ আপনি এটি যাচাই করতে পারবেন, যেমন: http://192.168.99.100/items/5?q=somequery বা http://127.0.0.1/items/5?q=somequery (বা আপনার Docker হোস্ট ব্যবহার করে সমতুল্য)।

আপনি এরকম কিছু দেখবেন:

{"item_id": 5, "q": "somequery"}

একক-ফাইল FastAPI দিয়ে একটি Docker ইমেজ তৈরি করুন¶

আপনার FastAPI যদি একটিমাত্র ফাইল হয়, যেমন ./app ডিরেক্টরি ছাড়া main.py, তাহলে আপনার ফাইল কাঠামো দেখতে এরকম হতে পারে:

.
├── Dockerfile
├── main.py
└── requirements.txt

তাহলে আপনাকে শুধু Dockerfile-এর ভেতরে ফাইলটি কপি করার সংশ্লিষ্ট পাথগুলো বদলাতে হবে:

FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# (1)!
COPY ./main.py /code/

# (2)!
CMD ["fastapi", "run", "main.py", "--port", "80"]

  1. main.py ফাইলটি সরাসরি /code ডিরেক্টরিতে কপি করুন (কোনো ./app ডিরেক্টরি ছাড়া)।

  2. একক ফাইল main.py-তে থাকা আপনার অ্যাপ্লিকেশন সার্ভ করতে fastapi run ব্যবহার করুন।

আপনি যখন fastapi run-এ ফাইলটি দেন, তখন এটি স্বয়ংক্রিয়ভাবে শনাক্ত করবে যে এটি একটি একক ফাইল, কোনো প্যাকেজের অংশ নয়, এবং জানবে কীভাবে এটি ইম্পোর্ট করে আপনার FastAPI অ্যাপ সার্ভ করতে হয়। 😎

ডিপ্লয়মেন্টের ধারণাসমূহ¶

চলুন কন্টেইনারের প্রেক্ষাপটে সেই একই কিছু ডিপ্লয়মেন্টের ধারণা নিয়ে আবার কথা বলি।

কন্টেইনার প্রধানত একটি অ্যাপ্লিকেশন তৈরি ও ডিপ্লয় করার প্রক্রিয়া সহজ করার একটি টুল, তবে এই ডিপ্লয়মেন্টের ধারণাগুলো সামলানোর জন্য এটি কোনো নির্দিষ্ট পদ্ধতি চাপিয়ে দেয় না, এবং বেশ কয়েকটি সম্ভাব্য কৌশল আছে।

সুখবর হলো, প্রতিটি ভিন্ন কৌশলেই সব ডিপ্লয়মেন্ট ধারণা কাভার করার একটি উপায় আছে। 🎉

চলুন কন্টেইনারের প্রেক্ষাপটে এই ডিপ্লয়মেন্টের ধারণাগুলো পর্যালোচনা করি:

  • HTTPS
  • startup-এ চালু হওয়া
  • রিস্টার্ট
  • রেপ্লিকেশন (চলমান প্রসেসের সংখ্যা)
  • মেমরি
  • শুরুর আগের ধাপগুলো

HTTPS¶

আমরা যদি কেবল একটি FastAPI অ্যাপ্লিকেশনের কন্টেইনার ইমেজে (এবং পরে চলমান কন্টেইনারে) মনোযোগ দিই, তাহলে HTTPS সাধারণত অন্য কোনো টুল দিয়ে বাহ্যিকভাবে সামলানো হবে।

এটি আরেকটি কন্টেইনার হতে পারে, যেমন Traefik-সহ, যা HTTPS এবং সার্টিফিকেটের স্বয়ংক্রিয় সংগ্রহ সামলায়।

পরামর্শ

Traefik-এর Docker, Kubernetes ও অন্যান্যের সাথে ইন্টিগ্রেশন আছে, তাই এটি দিয়ে আপনার কন্টেইনারের জন্য HTTPS সেট আপ ও কনফিগার করা খুবই সহজ।

বিকল্পভাবে, HTTPS একটি ক্লাউড প্রোভাইডার তাদের সার্ভিসগুলোর একটি হিসেবে সামলাতে পারে (তখনও একটি কন্টেইনারে অ্যাপ্লিকেশন চালানো অবস্থায়)।

startup-এ চালু হওয়া ও রিস্টার্ট¶

সাধারণত আরেকটি টুল আপনার কন্টেইনার চালু ও চালানোর দায়িত্বে থাকে।

এটি সরাসরি Docker, Docker Compose, Kubernetes, একটি ক্লাউড সার্ভিস ইত্যাদি হতে পারে।

বেশিরভাগ (বা সব) ক্ষেত্রে startup-এ কন্টেইনার চালু করা এবং ব্যর্থতায় রিস্টার্ট চালু করার একটি সহজ অপশন থাকে। যেমন, Docker-এ এটি হলো কমান্ড লাইন অপশন --restart।

কন্টেইনার ব্যবহার না করে অ্যাপ্লিকেশনগুলো startup-এ এবং রিস্টার্টসহ চালানো ঝামেলাপূর্ণ ও কঠিন হতে পারে। কিন্তু কন্টেইনার নিয়ে কাজ করার সময় বেশিরভাগ ক্ষেত্রে সেই কার্যকারিতা ডিফল্টভাবেই অন্তর্ভুক্ত থাকে। ✨

রেপ্লিকেশন - প্রসেসের সংখ্যা¶

আপনার যদি Kubernetes, Docker Swarm Mode, Nomad, বা একাধিক মেশিনে ডিস্ট্রিবিউটেড কন্টেইনার পরিচালনার অন্য কোনো অনুরূপ জটিল সিস্টেমসহ মেশিনের একটি ক্লাস্টার থাকে, তাহলে আপনি সম্ভবত প্রতিটি কন্টেইনারে একটি প্রসেস ম্যানেজার (যেমন ওয়ার্কারসহ Uvicorn) ব্যবহার না করে ক্লাস্টার স্তরে রেপ্লিকেশন সামলাতে চাইবেন।

Kubernetes-এর মতো ওই ডিস্ট্রিবিউটেড কন্টেইনার ম্যানেজমেন্ট সিস্টেমগুলোর একটিতে সাধারণত আগত রিকোয়েস্টের জন্য লোড ব্যালান্সিং সাপোর্ট বজায় রেখেই কন্টেইনারের রেপ্লিকেশন সামলানোর কোনো অন্তর্ভুক্ত উপায় থাকে। সবই ক্লাস্টার স্তরে।

সেসব ক্ষেত্রে আপনি সম্ভবত ওপরে যেমন ব্যাখ্যা করা হয়েছে সেভাবে একদম শুরু থেকে একটি Docker ইমেজ তৈরি করতে চাইবেন, আপনার ডিপেন্ডেন্সি ইনস্টল করে, এবং একাধিক Uvicorn ওয়ার্কার ব্যবহারের বদলে একটি একক Uvicorn প্রসেস চালিয়ে।

লোড ব্যালান্সার¶

কন্টেইনার ব্যবহারের সময় সাধারণত আপনার কোনো কম্পোনেন্ট থাকবে যা মূল পোর্টে শুনছে। এটি সম্ভবত আরেকটি কন্টেইনার হতে পারে যা HTTPS সামলানোর জন্য একটি TLS Termination Proxy-ও, বা এরকম কোনো টুল।

যেহেতু এই কম্পোনেন্ট রিকোয়েস্টের ভার (load) নিয়ে সেগুলো ওয়ার্কারদের মধ্যে (আশা করি) ভারসাম্যপূর্ণভাবে (balanced) বণ্টন করবে, তাই একে সাধারণত একটি লোড ব্যালান্সার-ও বলা হয়।

পরামর্শ

HTTPS-এর জন্য ব্যবহৃত একই TLS Termination Proxy কম্পোনেন্টটি সম্ভবত একটি লোড ব্যালান্সার-ও হবে।

আর কন্টেইনার নিয়ে কাজ করার সময় যে সিস্টেম দিয়ে আপনি সেগুলো চালু ও পরিচালনা করেন, তাতে ইতিমধ্যে সেই লোড ব্যালান্সার (যা একটি TLS Termination Proxy-ও হতে পারে) থেকে আপনার অ্যাপসহ কন্টেইনার(গুলো)-এ নেটওয়ার্ক যোগাযোগ (যেমন HTTP রিকোয়েস্ট) পাঠানোর অভ্যন্তরীণ টুল থাকবে।

একটি লোড ব্যালান্সার - একাধিক ওয়ার্কার কন্টেইনার¶

Kubernetes বা অনুরূপ ডিস্ট্রিবিউটেড কন্টেইনার ম্যানেজমেন্ট সিস্টেম নিয়ে কাজ করার সময় তাদের অভ্যন্তরীণ নেটওয়ার্কিং ব্যবস্থা ব্যবহার করলে মূল পোর্টে শোনা একক লোড ব্যালান্সারটি আপনার অ্যাপ চালানো সম্ভবত একাধিক কন্টেইনারে যোগাযোগ (রিকোয়েস্ট) পাঠাতে পারবে।

আপনার অ্যাপ চালানো এই প্রতিটি কন্টেইনারে সাধারণত মাত্র একটি প্রসেস থাকবে (যেমন আপনার FastAPI অ্যাপ্লিকেশন চালানো একটি Uvicorn প্রসেস)। সেগুলো সবই হবে অভিন্ন কন্টেইনার, একই জিনিস চালাচ্ছে, কিন্তু প্রতিটির নিজস্ব প্রসেস, মেমরি ইত্যাদি। এভাবে আপনি CPU-র ভিন্ন ভিন্ন কোরে, বা এমনকি ভিন্ন ভিন্ন মেশিনে প্যারালালাইজেশনের সুবিধা নেবেন।

আর লোড ব্যালান্সারসহ ডিস্ট্রিবিউটেড কন্টেইনার সিস্টেমটি আপনার অ্যাপসহ প্রতিটি কন্টেইনারে পালাক্রমে রিকোয়েস্টগুলো বণ্টন করবে। তাই প্রতিটি রিকোয়েস্ট আপনার অ্যাপ চালানো একাধিক রেপ্লিকেট করা কন্টেইনারের একটি সামলাতে পারে।

আর সাধারণত এই লোড ব্যালান্সার আপনার ক্লাস্টারের অন্যান্য অ্যাপে যাওয়া রিকোয়েস্টও সামলাতে পারবে (যেমন একটি ভিন্ন ডোমেইনে, বা একটি ভিন্ন URL পাথ prefix-এর অধীনে), এবং আপনার ক্লাস্টারে চলমান ওই অন্য অ্যাপ্লিকেশনের সঠিক কন্টেইনারগুলোতে সেই যোগাযোগ পাঠাবে।

প্রতি কন্টেইনারে একটি প্রসেস¶

এ ধরনের পরিস্থিতিতে আপনি সম্ভবত প্রতি কন্টেইনারে একটি একক (Uvicorn) প্রসেস রাখতে চাইবেন, কারণ আপনি ইতিমধ্যে ক্লাস্টার স্তরে রেপ্লিকেশন সামলাচ্ছেন।

তাই এক্ষেত্রে আপনি কন্টেইনারে একাধিক ওয়ার্কার, যেমন --workers কমান্ড লাইন অপশন দিয়ে, রাখতে চাইবেন না। আপনি প্রতি কন্টেইনারে কেবল একটি একক Uvicorn প্রসেস রাখতে চাইবেন (তবে সম্ভবত একাধিক কন্টেইনার)।

কন্টেইনারের ভেতরে আরেকটি প্রসেস ম্যানেজার রাখলে (একাধিক ওয়ার্কারের ক্ষেত্রে যেমন হতো) তা কেবল অপ্রয়োজনীয় জটিলতা যোগ করবে, যা আপনি খুব সম্ভবত ইতিমধ্যে আপনার ক্লাস্টার সিস্টেম দিয়ে সামলাচ্ছেন।

একাধিক প্রসেসসহ কন্টেইনার ও বিশেষ ক্ষেত্র¶

অবশ্যই, এমন বিশেষ ক্ষেত্র আছে যেখানে আপনি ভেতরে কয়েকটি Uvicorn ওয়ার্কার প্রসেসসহ একটি কন্টেইনার রাখতে চাইতে পারেন।

সেসব ক্ষেত্রে আপনি যতগুলো ওয়ার্কার চালাতে চান তা সেট করতে --workers কমান্ড লাইন অপশন ব্যবহার করতে পারেন:

FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

COPY ./app /code/app

# (1)!
CMD ["fastapi", "run", "app/main.py", "--port", "80", "--workers", "4"]
  1. এখানে আমরা ওয়ার্কারের সংখ্যা ৪-এ সেট করতে --workers কমান্ড লাইন অপশন ব্যবহার করি।

কখন এটি যুক্তিসঙ্গত হতে পারে তার কিছু উদাহরণ এখানে দেওয়া হলো:

একটি সহজ অ্যাপ¶

আপনার অ্যাপ্লিকেশন যদি যথেষ্ট সহজ হয় যে এটি একটি ক্লাস্টারে নয়, একটি একক সার্ভারে চালাতে পারেন, তাহলে আপনি কন্টেইনারে একটি প্রসেস ম্যানেজার চাইতে পারেন।

Docker Compose¶

আপনি হয়তো Docker Compose দিয়ে একটি একক সার্ভারে (ক্লাস্টার নয়) ডিপ্লয় করছেন, তাই শেয়ার করা নেটওয়ার্ক ও লোড ব্যালান্সিং বজায় রেখে কন্টেইনারের রেপ্লিকেশন পরিচালনার কোনো সহজ উপায় আপনার থাকবে না (Docker Compose দিয়ে)।

তখন আপনি ভেতরে কয়েকটি ওয়ার্কার প্রসেস চালু করা একটি প্রসেস ম্যানেজারসহ একটি একক কন্টেইনার রাখতে চাইতে পারেন।

মূল কথা হলো, এগুলোর কোনোটিই এমন পাথরে খোদাই করা নিয়ম নয় যা আপনাকে অন্ধভাবে মানতে হবে। এই ধারণাগুলো ব্যবহার করে আপনি নিজের ব্যবহারের ক্ষেত্র মূল্যায়ন করে আপনার সিস্টেমের জন্য সেরা পদ্ধতি কোনটি তা ঠিক করতে পারেন, এই ধারণাগুলো কীভাবে পরিচালনা করবেন তা যাচাই করে:

  • সিকিউরিটি - HTTPS
  • startup-এ চালু হওয়া
  • রিস্টার্ট
  • রেপ্লিকেশন (চলমান প্রসেসের সংখ্যা)
  • মেমরি
  • শুরুর আগের ধাপগুলো

মেমরি¶

আপনি যদি প্রতি কন্টেইনারে একটি একক প্রসেস চালান, তাহলে ওই প্রতিটি কন্টেইনার (রেপ্লিকেট করা হলে একাধিক) মোটামুটি সুনির্দিষ্ট, স্থিতিশীল ও সীমিত পরিমাণ মেমরি খরচ করবে।

আর তারপর আপনি আপনার কন্টেইনার ম্যানেজমেন্ট সিস্টেমের কনফিগারেশনে (যেমন Kubernetes-এ) সেই একই মেমরি সীমা ও প্রয়োজনীয়তা সেট করতে পারেন। এভাবে এটি কন্টেইনারগুলোর প্রয়োজনীয় মেমরির পরিমাণ এবং ক্লাস্টারের মেশিনগুলোতে উপলব্ধ পরিমাণ বিবেচনায় নিয়ে উপলব্ধ মেশিনে কন্টেইনারগুলো রেপ্লিকেট করতে পারবে।

আপনার অ্যাপ্লিকেশন যদি সহজ হয়, তাহলে এটি সম্ভবত কোনো সমস্যা হবে না, এবং আপনার হয়তো কঠোর মেমরি সীমা উল্লেখ করার দরকার নেই। কিন্তু আপনি যদি অনেক মেমরি ব্যবহার করেন (যেমন মেশিন লার্নিং মডেলসহ), তাহলে আপনি কতটা মেমরি খরচ করছেন তা যাচাই করে প্রতিটি মেশিনে চলা কন্টেইনারের সংখ্যা সামঞ্জস্য করা উচিত (এবং হয়তো আপনার ক্লাস্টারে আরও মেশিন যোগ করা উচিত)।

আপনি যদি প্রতি কন্টেইনারে একাধিক প্রসেস চালান, তাহলে আপনাকে নিশ্চিত করতে হবে যে চালু হওয়া প্রসেসের সংখ্যা উপলব্ধের চেয়ে বেশি মেমরি খরচ করছে না।

শুরুর আগের ধাপ ও কন্টেইনার¶

আপনি যদি কন্টেইনার (যেমন Docker, Kubernetes) ব্যবহার করেন, তাহলে আপনি দুটি প্রধান পদ্ধতি ব্যবহার করতে পারেন।

একাধিক কন্টেইনার¶

আপনার যদি একাধিক কন্টেইনার থাকে, সম্ভবত প্রতিটি একটি একক প্রসেস চালাচ্ছে (যেমন একটি Kubernetes ক্লাস্টারে), তাহলে আপনি সম্ভবত একটি আলাদা কন্টেইনার রাখতে চাইবেন যা রেপ্লিকেট করা ওয়ার্কার কন্টেইনারগুলো চালানোর আগে একটি একক কন্টেইনারে, একটি একক প্রসেস চালিয়ে আগের ধাপগুলোর কাজ করে।

নোট

আপনি যদি Kubernetes ব্যবহার করেন, তাহলে এটি সম্ভবত একটি Init Container হবে।

আপনার ব্যবহারের ক্ষেত্রে যদি ওই আগের ধাপগুলো প্যারালালভাবে একাধিকবার চালাতে কোনো সমস্যা না থাকে (যেমন যদি আপনি ডেটাবেস মাইগ্রেশন না চালান, শুধু যাচাই করেন ডেটাবেস প্রস্তুত কিনা), তাহলে আপনি সেগুলো মূল প্রসেস চালু করার ঠিক আগে প্রতিটি কন্টেইনারেও রাখতে পারেন।

একক কন্টেইনার¶

আপনার যদি একটি সহজ সেটআপ থাকে, একটি একক কন্টেইনারসহ যা তারপর একাধিক ওয়ার্কার প্রসেস (বা মাত্র একটি প্রসেসও) চালু করে, তাহলে আপনি অ্যাপসহ প্রসেসটি চালু করার ঠিক আগে একই কন্টেইনারে ওই আগের ধাপগুলো চালাতে পারেন।

বেস Docker ইমেজ¶

একসময় একটি অফিসিয়াল FastAPI Docker ইমেজ ছিল: tiangolo/uvicorn-gunicorn-fastapi। কিন্তু এটি এখন ডেপ্রিকেটেড। ⛔️

আপনার সম্ভবত এই বেস Docker ইমেজ (বা অন্য কোনো অনুরূপ ইমেজ) ব্যবহার করা উচিত নয়।

আপনি যদি Kubernetes (বা অন্যান্য) ব্যবহার করেন এবং ইতিমধ্যে একাধিক কন্টেইনারসহ ক্লাস্টার স্তরে রেপ্লিকেশন সেট করছেন। সেসব ক্ষেত্রে ওপরে যেমন বর্ণনা করা হয়েছে সেভাবে একদম শুরু থেকে একটি ইমেজ তৈরি করাই আপনার জন্য ভালো: FastAPI-এর জন্য একটি Docker ইমেজ তৈরি করুন।

আর আপনার যদি একাধিক ওয়ার্কার দরকার হয়, তাহলে আপনি শুধু --workers কমান্ড লাইন অপশন ব্যবহার করতে পারেন।

কারিগরি বিবরণ

Docker ইমেজটি তৈরি হয়েছিল যখন Uvicorn মৃত ওয়ার্কারদের পরিচালনা ও রিস্টার্ট সাপোর্ট করত না, তাই Uvicorn-এর সাথে Gunicorn ব্যবহার করতে হতো, যা বেশ জটিলতা যোগ করত, শুধু Gunicorn দিয়ে Uvicorn ওয়ার্কার প্রসেসগুলো পরিচালনা ও রিস্টার্ট করানোর জন্য।

কিন্তু এখন যেহেতু Uvicorn (এবং fastapi কমান্ড) --workers ব্যবহার সাপোর্ট করে, তাই নিজের ইমেজ তৈরির বদলে একটি বেস Docker ইমেজ ব্যবহারের কোনো কারণ নেই (কোডের পরিমাণ প্রায় একই 😅)।

কন্টেইনার ইমেজ ডিপ্লয় করুন¶

একটি কন্টেইনার (Docker) ইমেজ হয়ে গেলে এটি ডিপ্লয় করার বেশ কয়েকটি উপায় আছে।

যেমন:

  • একটি একক সার্ভারে Docker Compose দিয়ে
  • একটি Kubernetes ক্লাস্টার দিয়ে
  • একটি Docker Swarm Mode ক্লাস্টার দিয়ে
  • Nomad-এর মতো অন্য কোনো টুল দিয়ে
  • এমন একটি ক্লাউড সার্ভিস দিয়ে যা আপনার কন্টেইনার ইমেজ নিয়ে ডিপ্লয় করে

uv-সহ Docker ইমেজ¶

আপনি যদি আপনার প্রজেক্ট ইনস্টল ও পরিচালনা করতে uv ব্যবহার করেন, তাহলে তাদের uv Docker গাইড অনুসরণ করতে পারেন।

সংক্ষেপে¶

কন্টেইনার সিস্টেম ব্যবহার করে (যেমন Docker ও Kubernetes-সহ) সব ডিপ্লয়মেন্টের ধারণা সামলানো বেশ সহজ হয়ে যায়:

  • HTTPS
  • startup-এ চালু হওয়া
  • রিস্টার্ট
  • রেপ্লিকেশন (চলমান প্রসেসের সংখ্যা)
  • মেমরি
  • শুরুর আগের ধাপগুলো

বেশিরভাগ ক্ষেত্রে আপনি সম্ভবত কোনো বেস ইমেজ ব্যবহার করতে চাইবেন না, বরং অফিসিয়াল Python Docker ইমেজের ওপর ভিত্তি করে একদম শুরু থেকে একটি কন্টেইনার ইমেজ তৈরি করবেন।

Dockerfile-এ নির্দেশনাগুলোর ক্রম এবং Docker ক্যাশের দিকে খেয়াল রেখে আপনি বিল্ডের সময় কমাতে পারেন, যাতে আপনার উৎপাদনশীলতা সর্বোচ্চ হয় (এবং একঘেয়েমি এড়ানো যায়)। 😎
