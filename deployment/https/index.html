HTTPS প্রসঙ্গে¶

🌐 AI এবং মানুষের যৌথ অনুবাদ

এই অনুবাদটি মানুষের নির্দেশনায় AI দিয়ে করা হয়েছে। 🤝

এতে মূল অর্থ ভুল বোঝা বা অস্বাভাবিক শোনানোর মতো ভুল থাকতে পারে। 🤖

ইংরেজি সংস্করণ

এটা ধরে নেওয়া সহজ যে HTTPS এমন কিছু যা শুধু "চালু" থাকে বা থাকে না।

কিন্তু এটি এর চেয়ে অনেক বেশি জটিল।

পরামর্শ

আপনি যদি তাড়াহুড়োয় থাকেন বা এ নিয়ে মাথাব্যথা না থাকে, তাহলে বিভিন্ন কৌশল দিয়ে সবকিছু সেট আপ করার ধাপে ধাপে নির্দেশনার জন্য পরের অংশগুলো চালিয়ে যান।

একজন ভোক্তার দৃষ্টিকোণ থেকে HTTPS-এর মূল বিষয়গুলো শিখতে https://howhttps.works/ দেখুন।

এবার একজন ডেভেলপারের দৃষ্টিকোণ থেকে, HTTPS নিয়ে ভাবার সময় মনে রাখার মতো কয়েকটি বিষয় এখানে দেওয়া হলো:

  • HTTPS-এর জন্য সার্ভারের একটি থার্ড পার্টির তৈরি করা "সার্টিফিকেট" থাকা দরকার।
    • ওই সার্টিফিকেটগুলো আসলে থার্ড পার্টির কাছ থেকে সংগ্রহ করা হয়, "তৈরি" করা হয় না।
  • সার্টিফিকেটের একটি মেয়াদ থাকে।
    • এগুলোর মেয়াদ শেষ হয়।
    • আর তারপর এগুলো নবায়ন করতে হয়, থার্ড পার্টির কাছ থেকে আবার সংগ্রহ করতে হয়।
  • কানেকশনের এনক্রিপশন ঘটে TCP স্তরে।
    • এটি HTTP-এর এক স্তর নিচে।
    • তাই সার্টিফিকেট ও এনক্রিপশন সামলানো হয় HTTP-এর আগে।
  • TCP "ডোমেইন" সম্পর্কে জানে না। কেবল IP ঠিকানা সম্পর্কে জানে।
    • অনুরোধ করা নির্দিষ্ট ডোমেইন সম্পর্কিত তথ্য থাকে HTTP ডেটায়।
  • HTTPS সার্টিফিকেট একটি নির্দিষ্ট ডোমেইনকে "প্রত্যয়ন" করে, কিন্তু প্রোটোকল ও এনক্রিপশন ঘটে TCP স্তরে, কোন ডোমেইন নিয়ে কাজ হচ্ছে তা জানার আগেই।
  • ডিফল্টভাবে, এর মানে হতো আপনার প্রতি IP ঠিকানায় কেবল একটি HTTPS সার্টিফিকেট থাকতে পারে।
    • আপনার সার্ভার যত বড়ই হোক বা এতে থাকা প্রতিটি অ্যাপ্লিকেশন যত ছোটই হোক।
    • তবে এর একটি সমাধান আছে।
  • TLS প্রোটোকলের (যেটি HTTP-এর আগে TCP স্তরে এনক্রিপশন সামলায়) একটি এক্সটেনশন আছে, যার নাম SNI।
    • এই SNI এক্সটেনশন একটিমাত্র সার্ভারকে (একটি একক IP ঠিকানাসহ) একাধিক HTTPS সার্টিফিকেট রাখতে এবং একাধিক HTTPS ডোমেইন/অ্যাপ্লিকেশন সার্ভ করতে দেয়।
    • এটি কাজ করার জন্য, সার্ভারে চলমান, পাবলিক IP ঠিকানায় শোনা একটিমাত্র কম্পোনেন্টের (প্রোগ্রাম) কাছে সার্ভারের সব HTTPS সার্টিফিকেট থাকতে হবে।
  • একটি নিরাপদ কানেকশন পাওয়ার পরে যোগাযোগের প্রোটোকল তখনও HTTP।
    • বিষয়বস্তু এনক্রিপ্টেড, যদিও সেগুলো HTTP প্রোটোকল দিয়ে পাঠানো হচ্ছে।

সার্ভারে (মেশিন, হোস্ট ইত্যাদি) একটি প্রোগ্রাম/HTTP সার্ভার চালিয়ে সব HTTPS অংশ পরিচালনা করানো একটি প্রচলিত চর্চা: এনক্রিপ্টেড HTTPS রিকোয়েস্ট গ্রহণ করা, একই সার্ভারে চলমান আসল HTTP অ্যাপ্লিকেশনে (এক্ষেত্রে FastAPI অ্যাপ্লিকেশন) ডিক্রিপ্ট করা HTTP রিকোয়েস্ট পাঠানো, অ্যাপ্লিকেশন থেকে HTTP রেসপন্স নেওয়া, উপযুক্ত HTTPS সার্টিফিকেট ব্যবহার করে এটি এনক্রিপ্ট করা এবং HTTPS ব্যবহার করে ক্লায়েন্টকে ফেরত পাঠানো। এই সার্ভারকে প্রায়ই বলা হয় একটি TLS Termination Proxy।

TLS Termination Proxy হিসেবে আপনি যে অপশনগুলো ব্যবহার করতে পারেন তার কয়েকটি হলো:

  • Traefik (যা সার্টিফিকেট নবায়নও সামলাতে পারে)
  • Caddy (যা সার্টিফিকেট নবায়নও সামলাতে পারে)
  • Nginx
  • HAProxy

Let's Encrypt¶

Let's Encrypt-এর আগে এই HTTPS সার্টিফিকেটগুলো বিশ্বস্ত থার্ড পার্টিরা বিক্রি করত।

এই সার্টিফিকেটগুলোর একটি সংগ্রহের প্রক্রিয়া ঝামেলাপূর্ণ ছিল, বেশ কিছু কাগজপত্র লাগত এবং সার্টিফিকেটগুলো বেশ ব্যয়বহুল ছিল।

কিন্তু তারপর Let's Encrypt তৈরি হলো।

এটি Linux Foundation-এর একটি প্রজেক্ট। এটি স্বয়ংক্রিয় উপায়ে বিনামূল্যে HTTPS সার্টিফিকেট দেয়। এই সার্টিফিকেটগুলো সব স্ট্যান্ডার্ড ক্রিপ্টোগ্রাফিক নিরাপত্তা ব্যবহার করে, এবং স্বল্পমেয়াদি (প্রায় ৩ মাস), তাই কম মেয়াদের কারণে নিরাপত্তা আসলে আরও ভালো।

ডোমেইনগুলো নিরাপদভাবে যাচাই করা হয় এবং সার্টিফিকেটগুলো স্বয়ংক্রিয়ভাবে তৈরি হয়। এতে এই সার্টিফিকেটগুলোর নবায়নও স্বয়ংক্রিয় করা যায়।

ধারণাটি হলো এই সার্টিফিকেটগুলোর সংগ্রহ ও নবায়ন স্বয়ংক্রিয় করা, যাতে আপনি চিরকাল, বিনামূল্যে, নিরাপদ HTTPS পেতে পারেন।

ডেভেলপারদের জন্য HTTPS¶

ডেভেলপারদের জন্য গুরুত্বপূর্ণ ধারণাগুলোতে প্রধানত মনোযোগ দিয়ে, ধাপে ধাপে একটি HTTPS API দেখতে কেমন হতে পারে তার একটি উদাহরণ এখানে দেওয়া হলো।

ডোমেইন নাম¶

সম্ভবত সবকিছু শুরু হবে আপনার কোনো ডোমেইন নাম সংগ্রহ করা দিয়ে। তারপর আপনি এটি একটি DNS সার্ভারে (সম্ভবত আপনার সেই একই ক্লাউড প্রোভাইডারে) কনফিগার করবেন।

আপনি সম্ভবত একটি ক্লাউড সার্ভার (একটি ভার্চুয়াল মেশিন) বা এরকম কিছু নেবেন, এবং এর একটি নির্দিষ্ট পাবলিক IP ঠিকানা থাকবে।

DNS সার্ভারে আপনি একটি রেকর্ড (একটি "A record") কনফিগার করবেন, যাতে আপনার ডোমেইন আপনার সার্ভারের পাবলিক IP ঠিকানার দিকে নির্দেশ করে।

আপনি সম্ভবত এটি কেবল একবারই করবেন, প্রথমবার, সবকিছু সেট আপ করার সময়।

পরামর্শ

এই ডোমেইন নামের অংশটি HTTPS-এর অনেক আগের বিষয়, কিন্তু যেহেতু সবকিছু ডোমেইন ও IP ঠিকানার ওপর নির্ভর করে, তাই এখানে এটি উল্লেখ করা যুক্তিসঙ্গত।

DNS¶

এবার আসল HTTPS অংশগুলোতে মনোযোগ দেওয়া যাক।

প্রথমে ব্রাউজার DNS সার্ভারের কাছে জানতে চাইবে ডোমেইনের IP কী, এক্ষেত্রে someapp.example.com।

DNS সার্ভারগুলো ব্রাউজারকে একটি নির্দিষ্ট IP ঠিকানা ব্যবহার করতে বলবে। সেটি হবে আপনার সার্ভারের ব্যবহৃত পাবলিক IP ঠিকানা, যা আপনি DNS সার্ভারে কনফিগার করেছিলেন।

TLS Handshake শুরু¶

তারপর ব্রাউজার ওই IP ঠিকানার সাথে পোর্ট 443-এ (HTTPS পোর্ট) যোগাযোগ করবে।

যোগাযোগের প্রথম অংশটি হলো শুধু ক্লায়েন্ট ও সার্ভারের মধ্যে কানেকশন স্থাপন করা এবং তারা কোন ক্রিপ্টোগ্রাফিক কী ব্যবহার করবে তা ঠিক করা, ইত্যাদি।

TLS কানেকশন স্থাপনের জন্য ক্লায়েন্ট ও সার্ভারের মধ্যে এই আদান-প্রদানকে বলা হয় TLS handshake।

SNI এক্সটেনশনসহ TLS¶

সার্ভারে একটি নির্দিষ্ট IP ঠিকানার একটি নির্দিষ্ট পোর্টে কেবল একটি প্রসেস শুনতে পারে। একই IP ঠিকানার অন্য পোর্টে অন্য প্রসেস শুনতে পারে, কিন্তু IP ঠিকানা ও পোর্টের প্রতিটি সমন্বয়ের জন্য কেবল একটি।

TLS (HTTPS) ডিফল্টভাবে নির্দিষ্ট পোর্ট 443 ব্যবহার করে। তাই সেটিই আমাদের দরকারি পোর্ট।

যেহেতু এই পোর্টে কেবল একটি প্রসেস শুনতে পারে, তাই যে প্রসেসটি এটি করবে সেটি হবে TLS Termination Proxy।

TLS Termination Proxy-র কাছে এক বা একাধিক TLS সার্টিফিকেট (HTTPS সার্টিফিকেট) অ্যাক্সেস থাকবে।

ওপরে আলোচিত SNI এক্সটেনশন ব্যবহার করে TLS Termination Proxy যাচাই করবে যে এই কানেকশনের জন্য উপলব্ধ TLS (HTTPS) সার্টিফিকেটগুলোর কোনটি ব্যবহার করা উচিত, ক্লায়েন্টের প্রত্যাশিত ডোমেইনের সাথে যেটি মেলে সেটি ব্যবহার করে।

এক্ষেত্রে এটি someapp.example.com-এর সার্টিফিকেট ব্যবহার করবে।

ক্লায়েন্ট ইতিমধ্যে সেই এনটিটিকে বিশ্বাস করে যে ওই TLS সার্টিফিকেট তৈরি করেছে (এক্ষেত্রে Let's Encrypt, তবে সে সম্পর্কে পরে দেখব), তাই এটি যাচাই করতে পারে যে সার্টিফিকেটটি বৈধ।

তারপর সার্টিফিকেট ব্যবহার করে ক্লায়েন্ট ও TLS Termination Proxy ঠিক করে কীভাবে বাকি TCP যোগাযোগ এনক্রিপ্ট করবে। এতে TLS Handshake অংশটি সম্পন্ন হয়।

এরপর ক্লায়েন্ট ও সার্ভারের মধ্যে একটি এনক্রিপ্টেড TCP কানেকশন থাকে, TLS এটিই দেয়। আর তারপর তারা সেই কানেকশন ব্যবহার করে আসল HTTP যোগাযোগ শুরু করতে পারে।

আর HTTPS হলো এটাই, এটি শুধু একটি খাঁটি (এনক্রিপ্ট না করা) TCP কানেকশনের বদলে একটি নিরাপদ TLS কানেকশনের ভেতরে সাধারণ HTTP।

পরামর্শ

লক্ষ করুন, যোগাযোগের এনক্রিপশন ঘটে TCP স্তরে, HTTP স্তরে নয়।

HTTPS রিকোয়েস্ট¶

এখন যেহেতু ক্লায়েন্ট ও সার্ভারের (নির্দিষ্টভাবে ব্রাউজার ও TLS Termination Proxy) মধ্যে একটি এনক্রিপ্টেড TCP কানেকশন আছে, তাই তারা HTTP যোগাযোগ শুরু করতে পারে।

তাই ক্লায়েন্ট একটি HTTPS রিকোয়েস্ট পাঠায়। এটি শুধু একটি এনক্রিপ্টেড TLS কানেকশনের মাধ্যমে একটি HTTP রিকোয়েস্ট।

রিকোয়েস্ট ডিক্রিপ্ট করা¶

TLS Termination Proxy রিকোয়েস্টটি ডিক্রিপ্ট করতে সম্মত এনক্রিপশন ব্যবহার করবে, এবং অ্যাপ্লিকেশন চালানো প্রসেসে (যেমন FastAPI অ্যাপ্লিকেশন চালানো Uvicorn-সহ একটি প্রসেস) সাধারণ (ডিক্রিপ্ট করা) HTTP রিকোয়েস্ট পাঠাবে।

HTTP রেসপন্স¶

অ্যাপ্লিকেশন রিকোয়েস্টটি প্রসেস করে TLS Termination Proxy-তে একটি সাধারণ (এনক্রিপ্ট না করা) HTTP রেসপন্স পাঠাবে।

HTTPS রেসপন্স¶

তারপর TLS Termination Proxy আগে সম্মত ক্রিপ্টোগ্রাফি (যা someapp.example.com-এর সার্টিফিকেট দিয়ে শুরু হয়েছিল) ব্যবহার করে রেসপন্সটি এনক্রিপ্ট করে ব্রাউজারে ফেরত পাঠাবে।

এরপর ব্রাউজার যাচাই করবে যে রেসপন্সটি বৈধ এবং সঠিক ক্রিপ্টোগ্রাফিক কী দিয়ে এনক্রিপ্ট করা, ইত্যাদি। তারপর এটি রেসপন্সটি ডিক্রিপ্ট করে প্রসেস করবে।

ক্লায়েন্ট (ব্রাউজার) জানবে যে রেসপন্সটি সঠিক সার্ভার থেকে এসেছে, কারণ এটি আগে HTTPS সার্টিফিকেট ব্যবহার করে সম্মত হওয়া ক্রিপ্টোগ্রাফি ব্যবহার করছে।

একাধিক অ্যাপ্লিকেশন¶

একই সার্ভারে (বা সার্ভারগুলোতে) একাধিক অ্যাপ্লিকেশন থাকতে পারে, যেমন অন্যান্য API প্রোগ্রাম বা একটি ডেটাবেস।

নির্দিষ্ট IP ও পোর্ট কেবল একটি প্রসেসই সামলাতে পারে (আমাদের উদাহরণে TLS Termination Proxy), তবে অন্যান্য অ্যাপ্লিকেশন/প্রসেসও সার্ভারে চলতে পারে, যতক্ষণ সেগুলো পাবলিক IP ও পোর্টের একই সমন্বয় ব্যবহারের চেষ্টা না করে।

এভাবে TLS Termination Proxy একাধিক অ্যাপ্লিকেশনের জন্য একাধিক ডোমেইনের HTTPS ও সার্টিফিকেট সামলাতে পারে, এবং তারপর প্রতিটি ক্ষেত্রে সঠিক অ্যাপ্লিকেশনে রিকোয়েস্টগুলো পাঠাতে পারে।

সার্টিফিকেট নবায়ন¶

ভবিষ্যতে কোনো এক সময়ে প্রতিটি সার্টিফিকেটের মেয়াদ শেষ হবে (সংগ্রহের প্রায় ৩ মাস পরে)।

আর তখন আরেকটি প্রোগ্রাম থাকবে (কিছু ক্ষেত্রে এটি আরেকটি প্রোগ্রাম, কিছু ক্ষেত্রে এটি সেই একই TLS Termination Proxy হতে পারে) যা Let's Encrypt-এর সাথে কথা বলে সার্টিফিকেট(গুলো) নবায়ন করবে।

TLS সার্টিফিকেট একটি ডোমেইন নামের সাথে যুক্ত, কোনো IP ঠিকানার সাথে নয়।

তাই সার্টিফিকেট নবায়ন করতে নবায়ন প্রোগ্রামকে কর্তৃপক্ষের (Let's Encrypt) কাছে প্রমাণ করতে হবে যে এটি আসলেই ওই ডোমেইনের "মালিক" এবং নিয়ন্ত্রণ করে।

এটি করতে, এবং বিভিন্ন অ্যাপ্লিকেশনের প্রয়োজন মেটাতে, এটি করার কয়েকটি উপায় আছে। কিছু জনপ্রিয় উপায় হলো:

  • কিছু DNS রেকর্ড পরিবর্তন করা।
    • এর জন্য নবায়ন প্রোগ্রামকে DNS প্রোভাইডারের API সাপোর্ট করতে হবে, তাই আপনি কোন DNS প্রোভাইডার ব্যবহার করছেন তার ওপর নির্ভর করে এটি একটি অপশন হতেও পারে, নাও পারে।
  • ডোমেইনের সাথে যুক্ত পাবলিক IP ঠিকানায় একটি সার্ভার হিসেবে চলা (অন্তত সার্টিফিকেট সংগ্রহ প্রক্রিয়ার সময়)।
    • ওপরে যেমন বলেছি, একটি নির্দিষ্ট IP ও পোর্টে কেবল একটি প্রসেস শুনতে পারে।
    • এটি একটি কারণ যার জন্য একই TLS Termination Proxy সার্টিফিকেট নবায়ন প্রক্রিয়ার দায়িত্বও নিলে তা খুবই কাজের হয়।
    • অন্যথায় আপনাকে হয়তো সাময়িকভাবে TLS Termination Proxy থামাতে হবে, সার্টিফিকেট সংগ্রহ করতে নবায়ন প্রোগ্রাম চালু করতে হবে, তারপর TLS Termination Proxy-র সাথে সেগুলো কনফিগার করতে হবে, এবং তারপর TLS Termination Proxy আবার চালু করতে হবে। এটি আদর্শ নয়, কারণ TLS Termination Proxy বন্ধ থাকার সময় আপনার অ্যাপ(গুলো) উপলব্ধ থাকবে না।

অ্যাপ সার্ভ করা অব্যাহত রেখে এই পুরো নবায়ন প্রক্রিয়াটিই প্রধান কারণগুলোর একটি যার জন্য আপনি সরাসরি অ্যাপ্লিকেশন সার্ভারে (যেমন Uvicorn) TLS সার্টিফিকেট ব্যবহার না করে একটি TLS Termination Proxy দিয়ে HTTPS সামলানোর জন্য একটি আলাদা সিস্টেম রাখতে চাইবেন।

প্রক্সি Forwarded হেডার¶

HTTPS সামলাতে একটি প্রক্সি ব্যবহার করলে আপনার অ্যাপ্লিকেশন সার্ভার (যেমন FastAPI CLI-এর মাধ্যমে Uvicorn) HTTPS প্রক্রিয়া সম্পর্কে কিছুই জানে না, এটি TLS Termination Proxy-র সাথে সাধারণ HTTP দিয়ে যোগাযোগ করে।

এই প্রক্সি সাধারণত অ্যাপ্লিকেশন সার্ভারে রিকোয়েস্ট পাঠানোর আগে তাৎক্ষণিকভাবে কিছু HTTP হেডার সেট করে, যাতে অ্যাপ্লিকেশন সার্ভার জানতে পারে যে রিকোয়েস্টটি প্রক্সি ফরোয়ার্ড করছে।

কারিগরি বিবরণ

প্রক্সি হেডারগুলো হলো:

  • X-Forwarded-For
  • X-Forwarded-Proto
  • X-Forwarded-Host

তবুও, যেহেতু অ্যাপ্লিকেশন সার্ভার জানে না যে এটি একটি বিশ্বস্ত প্রক্সির পেছনে আছে, তাই ডিফল্টভাবে এটি ওই হেডারগুলো বিশ্বাস করবে না।

তবে আপনি অ্যাপ্লিকেশন সার্ভারকে প্রক্সির পাঠানো forwarded হেডারগুলো বিশ্বাস করার জন্য কনফিগার করতে পারেন। আপনি যদি FastAPI CLI ব্যবহার করেন, তাহলে কোন IP থেকে আসা forwarded হেডার বিশ্বাস করা উচিত তা জানাতে CLI অপশন --forwarded-allow-ips ব্যবহার করতে পারেন।

যেমন, অ্যাপ্লিকেশন সার্ভার যদি কেবল বিশ্বস্ত প্রক্সি থেকেই যোগাযোগ পায়, তাহলে আপনি এটিকে --forwarded-allow-ips="*" সেট করে সব আগত IP বিশ্বাস করাতে পারেন, কারণ এটি কেবল প্রক্সির ব্যবহৃত IP যাই হোক তা থেকেই রিকোয়েস্ট পাবে।

এভাবে অ্যাপ্লিকেশন জানতে পারবে এর নিজস্ব পাবলিক URL কী, এটি HTTPS ব্যবহার করছে কিনা, ডোমেইন কী, ইত্যাদি।

এটি কাজে আসবে, যেমন, রিডাইরেক্ট সঠিকভাবে সামলাতে।

পরামর্শ

এ সম্পর্কে আরও জানতে পারেন প্রক্সির পেছনে - প্রক্সি Forwarded হেডার চালু করুন-এর ডকুমেন্টেশনে

সংক্ষেপে¶

HTTPS থাকা খুবই গুরুত্বপূর্ণ, এবং বেশিরভাগ ক্ষেত্রে বেশ জরুরি। একজন ডেভেলপার হিসেবে HTTPS ঘিরে আপনাকে যে পরিশ্রম করতে হয় তার বেশিরভাগই শুধু এই ধারণাগুলো বোঝা এবং এগুলো কীভাবে কাজ করে তা নিয়ে।

তবে একবার ডেভেলপারদের জন্য HTTPS-এর মূল তথ্যগুলো জানলে আপনি সহজেই বিভিন্ন টুল একত্রিত ও কনফিগার করে সবকিছু সহজভাবে পরিচালনা করতে পারবেন।

পরের কয়েকটি অধ্যায়ে আমি আপনাকে FastAPI অ্যাপ্লিকেশনের জন্য HTTPS কীভাবে সেট আপ করতে হয় তার বেশ কয়েকটি বাস্তব উদাহরণ দেখাব। 🔒
