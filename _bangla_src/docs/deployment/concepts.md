# ডিপ্লয়মেন্টের ধারণা { #deployments-concepts }

/// note | এই পেজে যা শিখবেন

* যেকোনো ওয়েব API ডিপ্লয়ের সময় যে ৬টি মূল বিষয় ভাবতে হয়।
* "প্রোগ্রাম" আর "প্রসেস"-এর পার্থক্য।
* কেন অ্যাপ নিজে থেকে চালু ও রিস্টার্ট হওয়া দরকার।
* ওয়ার্কার (একাধিক প্রসেস) আর মেমোরির হিসাব।
* মাইগ্রেশনের মতো "চালুর আগের ধাপ" আর রিসোর্সের সঠিক ব্যবহার।

///

একটি **FastAPI** অ্যাপ্লিকেশন, বা আসলে যেকোনো ধরনের ওয়েব API ডিপ্লয় করার সময়, কয়েকটি ধারণা আছে যা নিয়ে আপনি সম্ভবত ভাববেন, আর এগুলো ব্যবহার করে আপনি **আপনার অ্যাপ্লিকেশন ডিপ্লয়** করার **সবচেয়ে উপযুক্ত** উপায় খুঁজে পাবেন।

কিছু গুরুত্বপূর্ণ ধারণা হলো:

* নিরাপত্তা - HTTPS
* কম্পিউটার চালু হলে নিজে থেকে চালু হওয়া
* রিস্টার্ট
* রেপ্লিকেশন (কতগুলো প্রসেস চলছে)
* মেমোরি
* চালু করার আগের ধাপগুলো

আমরা দেখব এগুলো কীভাবে **ডিপ্লয়মেন্টকে** প্রভাবিত করবে।

শেষ পর্যন্ত, চূড়ান্ত লক্ষ্য হলো **আপনার API-র ক্লায়েন্টদের সেবা দেওয়া**, এমনভাবে যা **নিরাপদ**, যাতে **বিঘ্ন এড়ানো** যায়, আর **কম্পিউটিং রিসোর্স** (যেমন দূরের সার্ভার/ভার্চুয়াল মেশিন) যতটা সম্ভব দক্ষভাবে ব্যবহার করা যায়। 🚀

এখানে এই **ধারণাগুলো** সম্পর্কে আমি আপনাকে একটু বেশি বলব, আর আশা করি এতে আপনি সেই **অন্তর্দৃষ্টি** পাবেন যা দিয়ে খুবই ভিন্ন ভিন্ন পরিবেশে, এমনকি **ভবিষ্যতের** এমন পরিবেশেও যা এখনো তৈরিই হয়নি, আপনার API কীভাবে ডিপ্লয় করবেন তা ঠিক করতে পারবেন।

এই ধারণাগুলো বিবেচনা করে আপনি **নিজের API** ডিপ্লয় করার সেরা উপায় **মূল্যায়ন আর পরিকল্পনা** করতে পারবেন।

পরের অধ্যায়গুলোতে আমি FastAPI অ্যাপ্লিকেশন ডিপ্লয় করার আরও **বাস্তব রেসিপি** দেব।

কিন্তু আপাতত, এই গুরুত্বপূর্ণ **ধারণাগত বিষয়গুলো** দেখে নিই। এই ধারণাগুলো অন্য যেকোনো ধরনের ওয়েব API-র ক্ষেত্রেও প্রযোজ্য। 💡

/// tip | উদাহরণ দিয়ে বুঝি

একটি দোকান চালানোর কথা ভাবুন। দরজায় তালা আর নিরাপত্তা (HTTPS), সকালে নিজে থেকে দোকান খোলা (startup), কর্মচারী অসুস্থ হলে বদলি পাঠানো (restart), ভিড় বাড়লে বেশি ক্যাশিয়ার বসানো (replication), প্রতিটি ক্যাশিয়ারের জন্য আলাদা টেবিলের জায়গা (memory), আর দোকান খোলার আগে তাক সাজানো (previous steps)। এই পেজের ৬টি ধারণা ঠিক এগুলোই।

///

## নিরাপত্তা - HTTPS { #security-https }

[HTTPS নিয়ে আগের অধ্যায়ে](https.md) আমরা শিখেছি HTTPS কীভাবে আপনার API-র জন্য এনক্রিপশন দেয়।

আমরা এটাও দেখেছি যে HTTPS সাধারণত আপনার অ্যাপ্লিকেশন সার্ভারের **বাইরের** একটি কম্পোনেন্ট দেয়, একটি **TLS Termination Proxy**।

আর **HTTPS সার্টিফিকেট নবায়নের** দায়িত্বে কিছু একটা থাকতে হবে, সেটি একই কম্পোনেন্ট হতে পারে, অথবা ভিন্ন কিছু হতে পারে।

### HTTPS-এর জন্য টুলের উদাহরণ { #example-tools-for-https }

TLS Termination Proxy হিসেবে ব্যবহার করতে পারেন এমন কিছু টুল:

* Traefik
    * স্বয়ংক্রিয়ভাবে সার্টিফিকেট নবায়ন সামলায় ✨
* Caddy
    * স্বয়ংক্রিয়ভাবে সার্টিফিকেট নবায়ন সামলায় ✨
* Nginx
    * সার্টিফিকেট নবায়নের জন্য Certbot-এর মতো একটি বাইরের কম্পোনেন্টসহ
* HAProxy
    * সার্টিফিকেট নবায়নের জন্য Certbot-এর মতো একটি বাইরের কম্পোনেন্টসহ
* Nginx-এর মতো একটি Ingress Controller-সহ Kubernetes
    * সার্টিফিকেট নবায়নের জন্য cert-manager-এর মতো একটি বাইরের কম্পোনেন্টসহ
* একটি ক্লাউড প্রোভাইডার তাদের সেবার অংশ হিসেবে ভেতরে ভেতরে সামলায় (নিচে পড়ুন 👇)

আরেকটি অপশন হলো এমন একটি **ক্লাউড সার্ভিস** ব্যবহার করা যা HTTPS সেটআপসহ আরও বেশি কাজ করে দেয়। এর কিছু সীমাবদ্ধতা থাকতে পারে বা বেশি খরচ হতে পারে, ইত্যাদি। কিন্তু সেই ক্ষেত্রে আপনাকে নিজে TLS Termination Proxy সেটআপ করতে হবে না।

পরের অধ্যায়গুলোতে কিছু বাস্তব উদাহরণ দেখাব।

এরপরের ধারণাগুলো সবই আপনার আসল API চালানো প্রোগ্রাম (যেমন Uvicorn) নিয়ে।

## প্রোগ্রাম এবং প্রসেস { #program-and-process }

আমরা চলমান "**প্রসেস**" নিয়ে অনেক কথা বলব, তাই এর মানে কী, আর "**প্রোগ্রাম**" শব্দের সাথে এর পার্থক্য কী, তা পরিষ্কার থাকা দরকার।

### প্রোগ্রাম কী { #what-is-a-program }

**প্রোগ্রাম** শব্দটি সাধারণত অনেক কিছু বোঝাতে ব্যবহার হয়:

* আপনার লেখা **কোড**, **Python ফাইলগুলো**।
* অপারেটিং সিস্টেম যে **ফাইল** **চালাতে** পারে, যেমন: `python`, `python.exe` বা `uvicorn`।
* একটি নির্দিষ্ট প্রোগ্রাম যখন অপারেটিং সিস্টেমে **চলছে**, CPU ব্যবহার করছে আর মেমোরিতে জিনিস রাখছে। একে **প্রসেস**-ও বলা হয়।

### প্রসেস কী { #what-is-a-process }

**প্রসেস** শব্দটি সাধারণত আরও নির্দিষ্টভাবে ব্যবহার হয়, শুধু অপারেটিং সিস্টেমে যা চলছে তা বোঝাতে (ওপরের শেষ পয়েন্টের মতো):

* একটি নির্দিষ্ট প্রোগ্রাম যখন অপারেটিং সিস্টেমে **চলছে**।
    * এটি ফাইল বা কোড বোঝায় না, এটি **নির্দিষ্টভাবে** সেই জিনিসটি বোঝায় যা অপারেটিং সিস্টেম **চালাচ্ছে** আর পরিচালনা করছে।
* যেকোনো প্রোগ্রাম, যেকোনো কোড **শুধু তখনই কাজ করতে পারে** যখন এটি **চালানো** হচ্ছে। অর্থাৎ যখন একটি **প্রসেস চলছে**।
* প্রসেসটি আপনি বা অপারেটিং সিস্টেম **বন্ধ** (বা "kill") করতে পারে। তখন এটি চলা বন্ধ করে, আর **আর কোনো কাজ করতে পারে না**।
* আপনার কম্পিউটারে চলা প্রতিটি অ্যাপ্লিকেশনের পেছনে কোনো প্রসেস আছে, প্রতিটি চলমান প্রোগ্রাম, প্রতিটি উইন্ডো, ইত্যাদি। আর কম্পিউটার চালু থাকলে সাধারণত অনেকগুলো প্রসেস **একই সময়ে** চলে।
* **একই প্রোগ্রামের** **একাধিক প্রসেস** একই সময়ে চলতে পারে।

/// tip | উদাহরণ দিয়ে বুঝি

রেসিপির বই হলো **প্রোগ্রাম**: কাগজে লেখা নির্দেশনা, নিজে কিছু রাঁধে না। কেউ যখন সেই রেসিপি দেখে চুলায় রান্না শুরু করে, সেই রান্নার কাজটি হলো **প্রসেস**। একই রেসিপি দিয়ে একসাথে তিনটি চুলায় রান্না করলে, প্রোগ্রাম একটি, প্রসেস তিনটি।

///

আপনার অপারেটিং সিস্টেমের "task manager" বা "system monitor" (বা এমন টুল) দেখলে এমন অনেক প্রসেস চলতে দেখবেন।

আর যেমন, আপনি সম্ভবত দেখবেন একই ব্রাউজার প্রোগ্রামের (Firefox, Chrome, Edge ইত্যাদি) একাধিক প্রসেস চলছে। এরা সাধারণত প্রতিটি ট্যাবের জন্য একটি প্রসেস চালায়, সাথে আরও কিছু বাড়তি প্রসেস।

## চালু হলেই চলা (startup) { #running-on-startup }

বেশিরভাগ ক্ষেত্রে, যখন একটি ওয়েব API তৈরি করেন, আপনি চান এটি **সবসময় চলুক**, বিরতিহীনভাবে, যাতে আপনার ক্লায়েন্টরা সবসময় এটি ব্যবহার করতে পারে। অবশ্যই, যদি না আপনার কোনো নির্দিষ্ট কারণ থাকে কেন এটি শুধু নির্দিষ্ট পরিস্থিতিতে চলুক, কিন্তু বেশিরভাগ সময় আপনি চান এটি নিরন্তর চলুক আর **উপলব্ধ** থাকুক।

### একটি দূরের সার্ভারে { #in-a-remote-server }

যখন একটি দূরের সার্ভার (একটি ক্লাউড সার্ভার, একটি ভার্চুয়াল মেশিন ইত্যাদি) সেটআপ করেন, সবচেয়ে সহজ যা করতে পারেন তা হলো `fastapi run` (যা Uvicorn ব্যবহার করে) বা এমন কিছু নিজে হাতে চালানো, ঠিক যেভাবে লোকালি ডেভেলপ করার সময় করেন।

আর এটি কাজ করবে আর **ডেভেলপমেন্টের সময়** উপকারী হবে।

কিন্তু যদি সার্ভারের সাথে আপনার সংযোগ বিচ্ছিন্ন হয়, **চলমান প্রসেসটি** সম্ভবত মারা যাবে।

আর যদি সার্ভার রিস্টার্ট হয় (যেমন আপডেটের পরে, বা ক্লাউড প্রোভাইডারের মাইগ্রেশনের পরে), আপনি সম্ভবত **টেরই পাবেন না**। আর সেই কারণে, আপনি জানবেনও না যে প্রসেসটি নিজে হাতে আবার চালু করতে হবে। তাই আপনার API শুধু মৃত অবস্থায় পড়ে থাকবে। 😱

### চালু হলে স্বয়ংক্রিয়ভাবে চালানো { #run-automatically-on-startup }

সাধারণত, আপনি সম্ভবত চাইবেন সার্ভার প্রোগ্রামটি (যেমন Uvicorn) সার্ভার চালু হওয়ার সময় স্বয়ংক্রিয়ভাবে, কোনো **মানুষের হস্তক্ষেপ** ছাড়াই চালু হোক, যাতে সবসময় আপনার API-সহ একটি প্রসেস চলে (যেমন আপনার FastAPI অ্যাপ চালানো Uvicorn)।

### আলাদা প্রোগ্রাম { #separate-program }

এটি অর্জন করতে, সাধারণত আপনার একটি **আলাদা প্রোগ্রাম** থাকবে যা নিশ্চিত করবে যে চালু হওয়ার সময় আপনার অ্যাপ্লিকেশন চলে। আর অনেক ক্ষেত্রে এটি অন্যান্য কম্পোনেন্ট বা অ্যাপ্লিকেশনও চলছে তা নিশ্চিত করবে, যেমন একটি ডেটাবেস।

### চালু হলে চালানোর টুলের উদাহরণ { #example-tools-to-run-at-startup }

এই কাজটি করতে পারে এমন টুলের কিছু উদাহরণ:

* Docker
* Kubernetes
* Docker Compose
* Swarm Mode-এ Docker
* Systemd
* Supervisor
* একটি ক্লাউড প্রোভাইডার তাদের সেবার অংশ হিসেবে ভেতরে ভেতরে সামলায়
* অন্যান্য...

পরের অধ্যায়গুলোতে আরও বাস্তব উদাহরণ দেব।

## রিস্টার্ট { #restarts }

চালু হওয়ার সময় আপনার অ্যাপ্লিকেশন চলছে তা নিশ্চিত করার মতোই, আপনি সম্ভবত এটাও নিশ্চিত করতে চাইবেন যে কোনো ব্যর্থতার পরে এটি **আবার চালু** হয়।

### আমরা ভুল করি { #we-make-mistakes }

আমরা মানুষ হিসেবে সবসময় **ভুল** করি। সফটওয়্যারে প্রায় *সবসময়* বিভিন্ন জায়গায় **বাগ** লুকিয়ে থাকে। 🐛

আর ডেভেলপার হিসেবে আমরা সেই বাগগুলো খুঁজে পেয়ে আর নতুন ফিচার যোগ করে (সম্ভবত নতুন বাগও যোগ করে 😅) কোড উন্নত করতে থাকি।

### ছোট এরর স্বয়ংক্রিয়ভাবে সামলানো { #small-errors-automatically-handled }

FastAPI দিয়ে ওয়েব API তৈরি করার সময়, যদি আমাদের কোডে একটি এরর থাকে, FastAPI সাধারণত সেটিকে শুধু সেই রিকোয়েস্টের মধ্যেই আটকে রাখবে যেটি এররটি ঘটিয়েছে। 🛡

ক্লায়েন্ট সেই রিকোয়েস্টের জন্য একটি **500 Internal Server Error** পাবে, কিন্তু অ্যাপ্লিকেশন পুরোপুরি ক্র্যাশ না করে পরের রিকোয়েস্টগুলোর জন্য কাজ চালিয়ে যাবে।

### বড় এরর - ক্র্যাশ { #bigger-errors-crashes }

তবুও, এমন ক্ষেত্র থাকতে পারে যেখানে আমরা এমন কোড লিখি যা **পুরো অ্যাপ্লিকেশনকে ক্র্যাশ** করায়, Uvicorn আর Python-কে ক্র্যাশ করায়। 💥

তবুও, আপনি সম্ভবত চাইবেন না যে এক জায়গায় একটি এরর থাকার কারণে অ্যাপ্লিকেশনটি মৃত অবস্থায় থাকুক, আপনি সম্ভবত চাইবেন এটি অন্তত যে *পাথ অপারেশনগুলো* ভাঙেনি সেগুলোর জন্য **চলতে থাকুক**।

### ক্র্যাশের পরে রিস্টার্ট { #restart-after-crash }

কিন্তু সত্যিই খারাপ এররের সেই ক্ষেত্রগুলোতে যা চলমান **প্রসেসকে** ক্র্যাশ করায়, আপনি একটি বাইরের কম্পোনেন্ট চাইবেন যা প্রসেসটি **আবার চালু** করার দায়িত্বে থাকবে, অন্তত কয়েকবার...

/// tip | পরামর্শ

...যদিও যদি পুরো অ্যাপ্লিকেশন শুরুতেই **সাথে সাথে ক্র্যাশ** করে, তাহলে এটি চিরকাল রিস্টার্ট করতে থাকার কোনো মানে হয় না। কিন্তু সেই ক্ষেত্রে, আপনি সম্ভবত ডেভেলপমেন্টের সময়, বা অন্তত ডিপ্লয়মেন্টের ঠিক পরেই এটি লক্ষ্য করবেন।

তাই প্রধান ক্ষেত্রগুলোতে মনোযোগ দিই, যেখানে **ভবিষ্যতে** কিছু নির্দিষ্ট ক্ষেত্রে এটি পুরোপুরি ক্র্যাশ করতে পারে, আর তখনো এটি রিস্টার্ট করা যুক্তিসঙ্গত।

///

আপনি সম্ভবত আপনার অ্যাপ্লিকেশন রিস্টার্ট করার দায়িত্বে থাকা জিনিসটিকে একটি **বাইরের কম্পোনেন্ট** হিসেবে রাখতে চাইবেন, কারণ ততক্ষণে Uvicorn আর Python-সহ একই অ্যাপ্লিকেশনটি ইতিমধ্যে ক্র্যাশ করেছে, তাই একই অ্যাপের একই কোডে এমন কিছু নেই যা এ নিয়ে কিছু করতে পারে।

### স্বয়ংক্রিয়ভাবে রিস্টার্ট করার টুলের উদাহরণ { #example-tools-to-restart-automatically }

বেশিরভাগ ক্ষেত্রে, **চালু হলে প্রোগ্রাম চালাতে** যে টুল ব্যবহার হয়, সেটিই স্বয়ংক্রিয় **রিস্টার্ট** সামলাতেও ব্যবহার হয়।

যেমন, এটি সামলাতে পারে:

* Docker
* Kubernetes
* Docker Compose
* Swarm Mode-এ Docker
* Systemd
* Supervisor
* একটি ক্লাউড প্রোভাইডার তাদের সেবার অংশ হিসেবে ভেতরে ভেতরে সামলায়
* অন্যান্য...

## রেপ্লিকেশন - প্রসেস এবং মেমোরি { #replication-processes-and-memory }

একটি FastAPI অ্যাপ্লিকেশনকে, Uvicorn চালানো `fastapi` কমান্ডের মতো একটি সার্ভার প্রোগ্রাম দিয়ে, **একটি প্রসেসে** একবার চালালেই তা একসাথে একাধিক ক্লায়েন্টকে সেবা দিতে পারে।

কিন্তু অনেক ক্ষেত্রে আপনি একই সময়ে কয়েকটি ওয়ার্কার প্রসেস চালাতে চাইবেন।

### একাধিক প্রসেস - ওয়ার্কার { #multiple-processes-workers }

যদি আপনার এত ক্লায়েন্ট থাকে যা একটি প্রসেস সামলাতে পারে না (যেমন যদি ভার্চুয়াল মেশিনটি খুব বড় না হয়), আর সার্ভারের CPU-তে **একাধিক কোর** থাকে, তাহলে একই অ্যাপ্লিকেশনসহ একই সময়ে **একাধিক প্রসেস** চালাতে পারেন, আর সব রিকোয়েস্ট তাদের মধ্যে ভাগ করে দিতে পারেন।

একই API প্রোগ্রামের **একাধিক প্রসেস** চালালে, এদের সাধারণত **ওয়ার্কার (worker)** বলা হয়।

### ওয়ার্কার প্রসেস এবং পোর্ট { #worker-processes-and-ports }

[HTTPS সম্পর্কে](https.md) ডকসে মনে আছে, একটি সার্ভারে পোর্ট আর IP ঠিকানার একটি সমন্বয়ে শুধু একটি প্রসেস শুনতে পারে?

এটি এখনো সত্য।

তাই, একই সময়ে **একাধিক প্রসেস** রাখতে হলে, **একটি পোর্টে শুনতে থাকা একটি মাত্র প্রসেস** থাকতে হবে, যা তারপর কোনোভাবে প্রতিটি ওয়ার্কার প্রসেসে যোগাযোগ পাঠাবে।

### প্রতি প্রসেসের মেমোরি { #memory-per-process }

এখন, যখন প্রোগ্রাম মেমোরিতে কিছু লোড করে, যেমন একটি ভেরিয়েবলে একটি মেশিন লার্নিং মডেল, বা একটি ভেরিয়েবলে একটি বড় ফাইলের বিষয়বস্তু, সেই সব কিছু সার্ভারের **মেমোরির (RAM) কিছুটা খরচ করে**।

আর একাধিক প্রসেস সাধারণত **কোনো মেমোরি ভাগাভাগি করে না**। এর মানে প্রতিটি চলমান প্রসেসের নিজের জিনিস, ভেরিয়েবল আর মেমোরি আছে। আর যদি আপনার কোডে অনেক মেমোরি খরচ হয়, **প্রতিটি প্রসেস** সমপরিমাণ মেমোরি খরচ করবে।

### সার্ভারের মেমোরি { #server-memory }

যেমন, যদি আপনার কোড **1 GB আকারের** একটি মেশিন লার্নিং মডেল লোড করে, তাহলে আপনার API-সহ একটি প্রসেস চালালে এটি অন্তত 1 GB RAM খরচ করবে। আর যদি **৪টি প্রসেস** (৪টি ওয়ার্কার) চালু করেন, প্রতিটি 1 GB RAM খরচ করবে। তাই মোট, আপনার API **4 GB RAM** খরচ করবে।

আর যদি আপনার দূরের সার্ভার বা ভার্চুয়াল মেশিনে মাত্র 3 GB RAM থাকে, তাহলে 4 GB-র বেশি RAM লোড করার চেষ্টা সমস্যা তৈরি করবে। 🚨

### একাধিক প্রসেস - একটি উদাহরণ { #multiple-processes-an-example }

এই উদাহরণে, একটি **ম্যানেজার প্রসেস** আছে যা দুটি **ওয়ার্কার প্রসেস** চালু আর নিয়ন্ত্রণ করে।

এই ম্যানেজার প্রসেসটিই সম্ভবত IP-র **পোর্টে** শুনবে। আর এটি সব যোগাযোগ ওয়ার্কার প্রসেসগুলোতে পাঠাবে।

ওই ওয়ার্কার প্রসেসগুলোই আপনার অ্যাপ্লিকেশন চালাবে, একটি **রিকোয়েস্ট** গ্রহণ করে একটি **রেসপন্স** ফেরত দেওয়ার মূল হিসাবনিকাশ করবে, আর আপনি ভেরিয়েবলে যা রাখেন তা RAM-এ লোড করবে।

<img src="/img/deployment/concepts/process-ram.drawio.svg">

আর অবশ্যই, একই মেশিনে আপনার অ্যাপ্লিকেশন ছাড়াও সম্ভবত **অন্যান্য প্রসেস** চলবে।

একটি মজার বিষয় হলো, প্রতিটি প্রসেসের **CPU ব্যবহারের** শতাংশ সময়ের সাথে অনেক **ওঠানামা** করতে পারে, কিন্তু **মেমোরি (RAM)** সাধারণত কমবেশি **স্থির** থাকে।

যদি আপনার এমন একটি API থাকে যা প্রতিবার তুলনামূলক একই পরিমাণ হিসাবনিকাশ করে আর আপনার অনেক ক্লায়েন্ট থাকে, তাহলে **CPU ব্যবহারও** সম্ভবত *স্থির থাকবে* (দ্রুত ক্রমাগত ওঠানামা করার বদলে)।

### রেপ্লিকেশনের টুল আর কৌশলের উদাহরণ { #examples-of-replication-tools-and-strategies }

এটি অর্জনের কয়েকটি পদ্ধতি থাকতে পারে, আর পরের অধ্যায়গুলোতে নির্দিষ্ট কৌশল সম্পর্কে আরও বলব, যেমন Docker আর কন্টেইনার নিয়ে কথা বলার সময়।

মূল যে সীমাবদ্ধতা বিবেচনা করতে হবে তা হলো, **পাবলিক IP**-র **পোর্ট** সামলানো একটি **মাত্র** কম্পোনেন্ট থাকতে হবে। আর তারপর এর কাছে রেপ্লিকেট করা **প্রসেস/ওয়ার্কারগুলোতে** যোগাযোগ **পাঠানোর** একটি উপায় থাকতে হবে।

এখানে কিছু সম্ভাব্য সমন্বয় আর কৌশল:

* `--workers`-সহ **Uvicorn**
    * একটি Uvicorn **প্রসেস ম্যানেজার** **IP** আর **পোর্টে** শুনবে, আর এটি **একাধিক Uvicorn ওয়ার্কার প্রসেস** চালু করবে।
* **Kubernetes** আর অন্যান্য বিতরণকৃত **কন্টেইনার সিস্টেম**
    * **Kubernetes** স্তরের কিছু একটা **IP** আর **পোর্টে** শুনবে। রেপ্লিকেশন হবে **একাধিক কন্টেইনার** রেখে, প্রতিটিতে **একটি Uvicorn প্রসেস** চলবে।
* **ক্লাউড সার্ভিস** যা আপনার হয়ে এটি সামলায়
    * ক্লাউড সার্ভিস সম্ভবত **আপনার হয়ে রেপ্লিকেশন সামলাবে**। এটি সম্ভবত আপনাকে **চালানোর মতো একটি প্রসেস**, বা ব্যবহারের জন্য একটি **কন্টেইনার ইমেজ** নির্ধারণ করতে দেবে, যেকোনো ক্ষেত্রে এটি সম্ভবত **একটি মাত্র Uvicorn প্রসেস** হবে, আর ক্লাউড সার্ভিস এটি রেপ্লিকেট করার দায়িত্বে থাকবে।

/// tip | পরামর্শ

**কন্টেইনার**, Docker বা Kubernetes নিয়ে এই বিষয়গুলোর কিছু যদি এখনো খুব একটা বোধগম্য না হয়, চিন্তা করবেন না।

ভবিষ্যতের একটি অধ্যায়ে কন্টেইনার ইমেজ, Docker, Kubernetes ইত্যাদি নিয়ে আরও বলব: [কন্টেইনারে FastAPI - Docker](docker.md)।

## চালু করার আগের ধাপগুলো { #previous-steps-before-starting }

অনেক ক্ষেত্রে আপনি আপনার অ্যাপ্লিকেশন **চালু করার আগে** কিছু ধাপ সম্পন্ন করতে চান।

যেমন, আপনি হয়তো **ডেটাবেস মাইগ্রেশন** চালাতে চাইবেন (ডেটাবেসের টেবিলের কাঠামো নতুন কোডের সাথে মিলিয়ে হালনাগাদ করা)।

কিন্তু বেশিরভাগ ক্ষেত্রে, আপনি এই ধাপগুলো শুধু **একবারই** করতে চাইবেন।

তাই, অ্যাপ্লিকেশন চালু করার আগে, ওই **আগের ধাপগুলো** সম্পন্ন করার জন্য আপনি **একটি মাত্র প্রসেস** রাখতে চাইবেন।

আর আপনাকে নিশ্চিত করতে হবে যে ওই আগের ধাপগুলো একটি মাত্র প্রসেসই চালাচ্ছে, *এমনকি* যদি পরে অ্যাপ্লিকেশনের জন্য **একাধিক প্রসেস** (একাধিক ওয়ার্কার) চালু করেন। যদি ওই ধাপগুলো **একাধিক প্রসেস** চালাত, তাহলে তারা **সমান্তরালে** চালিয়ে কাজটি **দ্বিগুণ** করত, আর যদি ধাপগুলো ডেটাবেস মাইগ্রেশনের মতো সংবেদনশীল কিছু হতো, তাহলে একে অপরের সাথে সংঘাত তৈরি করতে পারত।

অবশ্যই, কিছু ক্ষেত্র আছে যেখানে আগের ধাপগুলো একাধিকবার চালাতে কোনো সমস্যা নেই, সেই ক্ষেত্রে এটি সামলানো অনেক সহজ।

/// tip | পরামর্শ

এটাও মনে রাখবেন, আপনার সেটআপের ওপর নির্ভর করে, কিছু ক্ষেত্রে অ্যাপ্লিকেশন চালু করার আগে আপনার **হয়তো কোনো আগের ধাপই দরকার নেই**।

সেই ক্ষেত্রে, এর কিছু নিয়েই আপনাকে চিন্তা করতে হবে না। 🤷

### আগের ধাপের কৌশলের উদাহরণ { #examples-of-previous-steps-strategies }

এটি **অনেকটাই নির্ভর করবে** আপনি কীভাবে **আপনার সিস্টেম ডিপ্লয় করছেন** তার ওপর, আর সম্ভবত এটি আপনি কীভাবে প্রোগ্রাম চালু করেন, রিস্টার্ট সামলান ইত্যাদির সাথে যুক্ত থাকবে।

এখানে কিছু সম্ভাব্য ধারণা:

* Kubernetes-এ একটি "Init Container", যা আপনার অ্যাপ কন্টেইনারের আগে চলে
* একটি bash স্ক্রিপ্ট যা আগের ধাপগুলো চালায় আর তারপর আপনার অ্যাপ্লিকেশন চালু করে
    * তবুও *সেই* bash স্ক্রিপ্টটি চালু/রিস্টার্ট করা, এরর শনাক্ত করা ইত্যাদির একটি উপায় আপনার লাগবে।

/// tip | পরামর্শ

ভবিষ্যতের একটি অধ্যায়ে কন্টেইনার দিয়ে এটি করার আরও বাস্তব উদাহরণ দেব: [কন্টেইনারে FastAPI - Docker](docker.md)।

## রিসোর্সের ব্যবহার { #resource-utilization }

আপনার সার্ভার(গুলো) একটি **রিসোর্স**, আপনি আপনার প্রোগ্রাম দিয়ে CPU-র হিসাবের সময় আর উপলব্ধ RAM মেমোরি খরচ বা **ব্যবহার** করতে পারেন।

আপনি সিস্টেম রিসোর্সের কতটা খরচ/ব্যবহার করতে চান? "বেশি না" ভাবা সহজ হতে পারে, কিন্তু বাস্তবে, আপনি সম্ভবত **ক্র্যাশ না করে যতটা সম্ভব বেশি** খরচ করতে চাইবেন।

যদি আপনি ৩টি সার্ভারের জন্য টাকা দেন কিন্তু তাদের RAM আর CPU-র মাত্র সামান্য অংশ ব্যবহার করেন, তাহলে আপনি সম্ভবত **টাকা নষ্ট করছেন** 💸, আর সম্ভবত **সার্ভারের বিদ্যুৎ নষ্ট করছেন** 🌎, ইত্যাদি।

সেই ক্ষেত্রে, মাত্র ২টি সার্ভার রেখে তাদের রিসোর্সের (CPU, মেমোরি, ডিস্ক, নেটওয়ার্ক ব্যান্ডউইথ ইত্যাদি) বেশি শতাংশ ব্যবহার করা ভালো হতে পারে।

অন্যদিকে, যদি আপনার ২টি সার্ভার থাকে আর আপনি তাদের **CPU আর RAM-এর ১০০%** ব্যবহার করছেন, তাহলে কোনো এক সময়ে একটি প্রসেস আরও মেমোরি চাইবে, আর সার্ভারকে ডিস্ককে "মেমোরি" হিসেবে ব্যবহার করতে হবে (যা হাজার গুণ ধীর হতে পারে), বা এমনকি **ক্র্যাশ** করবে। অথবা একটি প্রসেসকে কিছু হিসাব করতে হলে CPU আবার খালি হওয়া পর্যন্ত অপেক্ষা করতে হবে।

সেই ক্ষেত্রে, **একটি বাড়তি সার্ভার** নিয়ে তাতে কিছু প্রসেস চালানো ভালো হবে, যাতে সবার **যথেষ্ট RAM আর CPU সময়** থাকে।

এমন সম্ভাবনাও আছে যে কোনো কারণে আপনার API-র ব্যবহারে হঠাৎ **উল্লম্ফন** (spike) হলো। হয়তো এটি ভাইরাল হয়ে গেছে, বা হয়তো অন্য কোনো সার্ভিস বা বট এটি ব্যবহার করতে শুরু করেছে। আর সেই ক্ষেত্রে নিরাপদ থাকতে আপনি বাড়তি রিসোর্স রাখতে চাইতে পারেন।

আপনি লক্ষ্য হিসেবে একটি **ইচ্ছামতো সংখ্যা** ঠিক করতে পারেন, যেমন রিসোর্স ব্যবহারের **৫০% থেকে ৯০%-এর মধ্যে** কিছু। মূল কথা হলো, এগুলোই সম্ভবত প্রধান বিষয় যা আপনি মাপতে আর আপনার ডিপ্লয়মেন্ট ঠিকঠাক করতে ব্যবহার করতে চাইবেন।

আপনার সার্ভারে ব্যবহৃত CPU আর RAM, বা প্রতিটি প্রসেসের ব্যবহৃত পরিমাণ দেখতে `htop`-এর মতো সহজ টুল ব্যবহার করতে পারেন। অথবা আরও জটিল মনিটরিং টুল ব্যবহার করতে পারেন, যা হয়তো একাধিক সার্ভারে ছড়ানো থাকে, ইত্যাদি। (যেমন [OpenTelemetry](../advanced/opentelemetry.md) দিয়ে মেট্রিক সংগ্রহ।)

## সংক্ষেপে { #recap }

এখানে আপনি এমন কিছু প্রধান ধারণা পড়েছেন যা আপনার অ্যাপ্লিকেশন কীভাবে ডিপ্লয় করবেন তা ঠিক করার সময় সম্ভবত মাথায় রাখতে হবে:

* নিরাপত্তা - HTTPS
* কম্পিউটার চালু হলে নিজে থেকে চালু হওয়া
* রিস্টার্ট
* রেপ্লিকেশন (কতগুলো প্রসেস চলছে)
* মেমোরি
* চালু করার আগের ধাপগুলো

এই ধারণাগুলো আর এগুলো কীভাবে প্রয়োগ করতে হয় তা বুঝলে, আপনার ডিপ্লয়মেন্ট কনফিগার আর ঠিকঠাক করার সময় যেকোনো সিদ্ধান্ত নেওয়ার প্রয়োজনীয় অন্তর্দৃষ্টি পাবেন। 🤓

পরের অংশগুলোতে আপনি অনুসরণ করতে পারেন এমন সম্ভাব্য কৌশলের আরও বাস্তব উদাহরণ দেব। 🚀
