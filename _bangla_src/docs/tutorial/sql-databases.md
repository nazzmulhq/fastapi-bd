# SQL (রিলেশনাল) ডেটাবেস { #sql-relational-databases }

/// note | এই পেজে যা শিখবেন

* ডেটাবেস, টেবিল, সারি, কলাম, প্রাইমারি কী এর মতো মূল ধারণাগুলো সহজ ভাষায়।
* SQLModel দিয়ে টেবিল মডেল বানানো, ডেটাবেস সংযোগ (engine) আর সেশন।
* ডেটা তৈরি, পড়া, আপডেট আর মোছা (CRUD), পুরো একটি API।
* একাধিক মডেল দিয়ে নিরাপত্তা বাড়ানো: কোন ডেটা ক্লায়েন্ট পাঠাবে, কোনটা ফেরত যাবে।

///

**FastAPI**-তে SQL (রিলেশনাল) ডেটাবেস ব্যবহার করা বাধ্যতামূলক নয়। আপনি চাইলে **যেকোনো ডেটাবেস** ব্যবহার করতে পারেন।

এখানে আমরা [SQLModel](https://sqlmodel.tiangolo.com/) ব্যবহার করে একটি উদাহরণ দেখব।

**SQLModel** তৈরি [SQLAlchemy](https://www.sqlalchemy.org/) আর Pydantic-এর ওপর। এটি **FastAPI**-এর একই লেখক বানিয়েছেন, যাতে **SQL ডেটাবেস** ব্যবহার করা FastAPI অ্যাপ্লিকেশনের জন্য এটি একদম মানানসই হয়।

/// tip | ডেটাবেসের মূল শব্দগুলো সহজ ভাষায়

* **ডেটাবেস**: সাজিয়ে-গুছিয়ে তথ্য রাখার জায়গা, যা প্রোগ্রাম বন্ধ হলেও হারায় না।
* **টেবিল**: Excel শিটের মতো। যেমন `hero` টেবিলে সব নায়কের তথ্য।
* **কলাম**: টেবিলের একেকটি ঘরের নাম, যেমন `name`, `age`।
* **সারি (row)**: একেকজন নায়কের পুরো তথ্য, শিটের একেকটি লাইন।
* **প্রাইমারি কী (primary key)**: প্রতিটি সারির অনন্য পরিচয় নম্বর (`id`), দুটি সারির কখনো একই হয় না।
* **SQL**: ডেটাবেসের সাথে কথা বলার ভাষা।
* **ORM**: SQL না লিখে Python ক্লাস দিয়ে ডেটাবেসে কাজ করার টুল। SQLModel একটি ORM।

///

/// tip | পরামর্শ

আপনি যেকোনো অন্য SQL বা NoSQL ডেটাবেস লাইব্রেরি ব্যবহার করতে পারেন (কিছু ক্ষেত্রে এদের বলে <abbr title="Object Relational Mapper: এমন একটি লাইব্রেরির জমকালো নাম, যেখানে কিছু ক্লাস SQL টেবিল আর ইনস্ট্যান্সগুলো ওই টেবিলের সারি উপস্থাপন করে">"ORM"</abbr>), FastAPI আপনাকে কোনো কিছু ব্যবহারে বাধ্য করে না। 😎

///

যেহেতু SQLModel তৈরি SQLAlchemy-এর ওপর, তাই SQLAlchemy যেসব ডেটাবেস **সাপোর্ট করে** (ফলে SQLModel-ও সাপোর্ট করে) তার যেকোনোটি সহজেই ব্যবহার করতে পারবেন, যেমন:

* PostgreSQL
* MySQL
* SQLite
* Oracle
* Microsoft SQL Server ইত্যাদি।

এই উদাহরণে আমরা **SQLite** ব্যবহার করব, কারণ এটি একটিমাত্র ফাইল ব্যবহার করে আর Python-এ এর সাপোর্ট আগে থেকেই আছে। তাই এই উদাহরণ কপি করে হুবহু চালাতে পারবেন, কোনো ডেটাবেস সার্ভার ইনস্টল করতে হবে না।

পরে, আপনার প্রোডাকশন অ্যাপ্লিকেশনের জন্য হয়তো **PostgreSQL**-এর মতো একটি ডেটাবেস সার্ভার ব্যবহার করতে চাইবেন।

/// tip | পরামর্শ

**FastAPI** আর **PostgreSQL**-সহ একটি অফিসিয়াল প্রজেক্ট জেনারেটর আছে, যাতে একটি ফ্রন্টএন্ড আর আরও টুল অন্তর্ভুক্ত: [https://github.com/fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template)

///

এটি খুবই সহজ আর ছোট একটি টিউটোরিয়াল। সাধারণভাবে ডেটাবেস, SQL, বা আরও উন্নত ফিচার সম্পর্কে জানতে চাইলে [SQLModel ডকুমেন্টেশনে](https://sqlmodel.tiangolo.com/) যান।

## একটিমাত্র মডেল দিয়ে অ্যাপ তৈরি { #create-the-app-with-a-single-model }

প্রথমে একটিমাত্র **SQLModel** মডেল দিয়ে অ্যাপের সবচেয়ে সহজ প্রথম সংস্করণটি তৈরি করব।

পরে নিচে **একাধিক মডেল** দিয়ে নিরাপত্তা আর বহুমুখিতা বাড়িয়ে এটিকে উন্নত করব। 🤓

### মডেল তৈরি করুন { #create-models }

`SQLModel` ইমপোর্ট করে একটি ডেটাবেস মডেল তৈরি করুন:

{* ../../docs_src/sql_databases/tutorial001_an_py310.py ln[1:11] hl[7:11] *}

`Hero` ক্লাসটি একটি Pydantic মডেলের খুবই কাছাকাছি (আসলে ভেতরে ভেতরে এটি *একটি Pydantic মডেলই*)।

কিছু পার্থক্য আছে:

* `table=True` SQLModel-কে বলে যে এটি একটি *টেবিল মডেল*, এটি SQL ডেটাবেসের একটি **টেবিল** উপস্থাপন করবে, এটি শুধু একটি *ডেটা মডেল* নয় (যেমনটা অন্য যেকোনো সাধারণ Pydantic ক্লাস হতো)।

* `Field(primary_key=True)` SQLModel-কে বলে যে SQL ডেটাবেসে `id` হলো **প্রাইমারি কী** (SQL প্রাইমারি কী সম্পর্কে SQLModel ডকুমেন্টেশনে আরও জানতে পারবেন)।

    **নোট:** প্রাইমারি কী ফিল্ডে আমরা `int | None` ব্যবহার করি, যাতে Python কোডে *`id` ছাড়াই একটি অবজেক্ট তৈরি* করা যায় (`id=None`), এই ধরে নিয়ে যে ডেটাবেস *সংরক্ষণের সময় এটি তৈরি করবে*। SQLModel বোঝে যে ডেটাবেস `id` দেবে, আর ডেটাবেস স্কিমায় *কলামটিকে একটি non-null `INTEGER` হিসেবে সংজ্ঞায়িত* করে। বিস্তারিত দেখুন [প্রাইমারি কী নিয়ে SQLModel ডকুমেন্টেশনে](https://sqlmodel.tiangolo.com/tutorial/create-db-and-table/#primary-key-id)।

* `Field(index=True)` SQLModel-কে বলে যে এই কলামের জন্য একটি **SQL index** তৈরি করতে হবে, যা এই কলাম দিয়ে ফিল্টার করে ডেটা পড়ার সময় ডেটাবেসে দ্রুত খুঁজে পেতে সাহায্য করবে। (ইনডেক্স হলো বইয়ের শেষের সূচিপত্রের মতো: পুরো বই না উল্টে সরাসরি পাতা খুঁজে পাওয়া যায়।)

    SQLModel জানবে যে `str` হিসেবে ঘোষিত কিছু হবে `TEXT` (বা ডেটাবেস অনুযায়ী `VARCHAR`) টাইপের একটি SQL কলাম।

### একটি Engine তৈরি করুন { #create-an-engine }

একটি SQLModel `engine` (ভেতরে আসলে এটি একটি SQLAlchemy `engine`) ডেটাবেসের সাথে **সংযোগগুলো ধরে রাখে**।

একই ডেটাবেসে সংযোগের জন্য আপনার সব কোডের জন্য **একটিমাত্র `engine` অবজেক্ট** থাকবে।

{* ../../docs_src/sql_databases/tutorial001_an_py310.py ln[14:18] hl[14:15,17:18] *}

`check_same_thread=False` ব্যবহার করলে FastAPI বিভিন্ন থ্রেডে একই SQLite ডেটাবেস ব্যবহার করতে পারে। এটি দরকার, কারণ **একটিমাত্র রিকোয়েস্ট** **একাধিক থ্রেড** ব্যবহার করতে পারে (যেমন ডিপেন্ডেন্সিতে)।

চিন্তা করবেন না, কোড যেভাবে সাজানো, তাতে পরে আমরা নিশ্চিত করব যে **প্রতি রিকোয়েস্টে একটিমাত্র SQLModel *সেশন*** ব্যবহার করছি, `check_same_thread` আসলে এটাই অর্জন করতে চায়।

/// info | কোডটি সহজ ভাষায়

* লাইন ১৪-১৫: ডেটাবেস ফাইলের নাম `database.db`, আর এর ঠিকানা `sqlite:///database.db`।
* লাইন ১৭-১৮: `create_engine` দিয়ে ডেটাবেসের সাথে সংযোগ ব্যবস্থা তৈরি। PostgreSQL ব্যবহার করলে শুধু ঠিকানাটি বদলাবে, যেমন `postgresql://user:pass@host/dbname`।

### একটি Session ডিপেন্ডেন্সি তৈরি করুন { #create-a-session-dependency }

একটি **`Session`** **মেমরিতে অবজেক্টগুলো** রাখে আর ডেটায় দরকারি যেকোনো পরিবর্তনের হিসাব রাখে, তারপর ডেটাবেসের সাথে যোগাযোগ করতে **`engine` ব্যবহার করে**।

/// tip | উদাহরণ দিয়ে বুঝি

`engine` হলো ব্যাংকের সাথে সংযোগের লাইন, আর `Session` হলো একবার ব্যাংকে গিয়ে কাজ সারা। আপনি কয়েকটি কাজ (জমা, উত্তোলন) খাতায় লেখেন (`session.add`), তারপর শেষে একবারে সব চূড়ান্ত করেন (`session.commit`)। প্রতিটি রিকোয়েস্ট একটি আলাদা ব্যাংক-ভ্রমণ।

///

আমরা `yield`-সহ একটি FastAPI **ডিপেন্ডেন্সি** তৈরি করব, যা প্রতিটি রিকোয়েস্টের জন্য একটি নতুন `Session` দেবে। এটাই নিশ্চিত করে যে আমরা প্রতি রিকোয়েস্টে একটিমাত্র সেশন ব্যবহার করছি। 🤓

তারপর এই ডিপেন্ডেন্সি ব্যবহার করা বাকি কোড সহজ করতে একটি `Annotated` ডিপেন্ডেন্সি `SessionDep` তৈরি করি।

{* ../../docs_src/sql_databases/tutorial001_an_py310.py ln[25:30]  hl[25:27,30] *}

`with Session(engine) as session:` আর `yield session` মানে রিকোয়েস্টের শুরুতে সেশন খোলা, পাথ অপারেশনকে দেওয়া, আর কাজ শেষে `with` ব্লক থেকে বেরিয়ে স্বয়ংক্রিয়ভাবে বন্ধ হওয়া। এটাই [`yield`-সহ ডিপেন্ডেন্সির](dependencies/dependencies-with-yield.md) বাস্তব ব্যবহার।

এখানে আমরা `SessionDep` ডিপেন্ডেন্সি (একটি `Session`) ব্যবহার করে নতুন `Hero`-টি `Session` ইনস্ট্যান্সে যোগ করি, পরিবর্তনগুলো ডেটাবেসে commit করি, `hero`-এর ডেটা refresh করি, তারপর এটি ফেরত দিই।

/// info | কোডটি সহজ ভাষায়

* `session.add(hero)`: "এই নায়ককে যোগ করতে চাই" বলে খাতায় লেখা।
* `session.commit()`: খাতার কাজগুলো ডেটাবেসে চূড়ান্তভাবে সংরক্ষণ। এখনই ডেটাবেস `id` দেয়।
* `session.refresh(hero)`: ডেটাবেস থেকে নতুন তথ্য (যেমন তৈরি হওয়া `id`) নিয়ে `hero` অবজেক্ট হালনাগাদ করা।
* `return hero`: `id`-সহ নায়ক ফেরত।

## একাধিক মডেল দিয়ে অ্যাপ হালনাগাদ { #update-the-app-with-multiple-models }

এবার **নিরাপত্তা** আর **বহুমুখিতা** বাড়াতে এই অ্যাপটি একটু **নতুন করে সাজাই** (refactor)।

আগের অ্যাপটি দেখলে, UI-তে দেখবেন যে এখন পর্যন্ত এটি তৈরি করা `Hero`-এর `id` ক্লায়েন্টকে ঠিক করতে দিচ্ছে। 😱

এটা হতে দেওয়া উচিত নয়, তারা ডেটাবেসে আগে থেকে দেওয়া কোনো `id` মুছে দিতে পারে। `id` ঠিক করা উচিত **ব্যাকএন্ড** বা **ডেটাবেসের**, **ক্লায়েন্টের নয়**।

এছাড়াও আমরা নায়কের জন্য একটি `secret_name` (গোপন নাম) তৈরি করি, কিন্তু এখন পর্যন্ত এটি সব জায়গায় ফেরত দিচ্ছি, তাহলে তো আর খুব একটা **গোপন** থাকল না... 😅

কয়েকটি **বাড়তি মডেল** যোগ করে এগুলো ঠিক করব। এখানেই SQLModel ঝলমলিয়ে উঠবে। ✨

### একাধিক মডেল তৈরি করুন { #create-multiple-models }

**SQLModel**-এ `table=True` থাকা যেকোনো মডেল ক্লাস হলো একটি **টেবিল মডেল**।

আর `table=True` না থাকা যেকোনো মডেল ক্লাস হলো একটি **ডেটা মডেল**, এগুলো আসলে শুধু Pydantic মডেল (কয়েকটি ছোট বাড়তি ফিচারসহ)। 🤓

SQLModel-এ সব ক্ষেত্রে সব ফিল্ড **বারবার লেখা এড়াতে** **ইনহেরিট্যান্স** ব্যবহার করতে পারি।

/// tip | পরিকল্পনাটি এক নজরে

| মডেল | ধরন | কাজ | ফিল্ড |
|---|---|---|---|
| `HeroBase` | ডেটা | সবার সাধারণ ভিত্তি | `name`, `age` |
| `Hero` | টেবিল | ডেটাবেসে যা থাকে | + `id`, `secret_name` |
| `HeroPublic` | ডেটা | ক্লায়েন্টকে যা ফেরত যায় | + `id` (গোপন নাম নেই) |
| `HeroCreate` | ডেটা | তৈরির সময় ক্লায়েন্ট যা পাঠায় | + `secret_name` (`id` নেই) |
| `HeroUpdate` | ডেটা | আপডেটের সময় যা পাঠায় | সব ঐচ্ছিক |

এতে `HeroBase`-এর মতো একই ফিল্ড আছে, তাই এতে `secret_name` থাকবে না।

এছাড়া **স্বয়ংক্রিয়ভাবে তৈরি ক্লায়েন্টগুলোর** ইন্টারফেসও সহজ হবে, ফলে আপনার API-এর সাথে যোগাযোগকারী ডেভেলপাররা আপনার API নিয়ে কাজ করতে অনেক বেশি স্বস্তি পাবেন। 😎

#### `HeroUpdate` - নায়ক আপডেটের *ডেটা মডেল* { #heroupdate-the-data-model-to-update-a-hero }

`HeroUpdate` *ডেটা মডেলটি* কিছুটা বিশেষ, এতে একজন নতুন নায়ক তৈরিতে যা লাগত তার **সব একই ফিল্ড** আছে, কিন্তু সব ফিল্ড **ঐচ্ছিক** (সবার একটি ডিফল্ট মান আছে)। এভাবে একজন নায়ক আপডেট করার সময় শুধু যে ফিল্ডগুলো আপডেট করতে চান সেগুলোই পাঠাতে পারেন।

### `HeroCreate` দিয়ে তৈরি আর একটি `HeroPublic` ফেরত { #create-with-herocreate-and-return-a-heropublic }

এখন যেহেতু **একাধিক মডেল** আছে, তাই অ্যাপের যেসব অংশ এগুলো ব্যবহার করে সেগুলো হালনাগাদ করতে পারি।

রিকোয়েস্টে একটি `HeroCreate` *ডেটা মডেল* পাই, আর তা থেকে একটি `Hero` *টেবিল মডেল* তৈরি করি।

এই নতুন *টেবিল মডেল* `Hero`-তে ক্লায়েন্টের পাঠানো ফিল্ডগুলো থাকবে, আর ডেটাবেসের তৈরি একটি `id`-ও থাকবে।

তারপর ফাংশন থেকে সেই একই *টেবিল মডেল* `Hero` যেমন আছে তেমনই ফেরত দিই। কিন্তু যেহেতু `response_model` হিসেবে `HeroPublic` *ডেটা মডেল* ঘোষণা করেছি, তাই **FastAPI** ডেটা যাচাই আর সিরিয়ালাইজ করতে `HeroPublic` ব্যবহার করবে।

{* ../../docs_src/sql_databases/tutorial002_an_py310.py ln[56:62] hl[56:58] *}

`Hero.model_validate(hero)` মানে `HeroCreate` থেকে পাওয়া ডেটা দিয়ে একটি `Hero` টেবিল অবজেক্ট বানানো। ক্লায়েন্ট `id` পাঠাতেই পারে না, কারণ `HeroCreate`-এ `id` নেই।

/// tip | পরামর্শ

এখন আমরা **রিটার্ন টাইপ অ্যানোটেশন** `-> HeroPublic`-এর বদলে `response_model=HeroPublic` ব্যবহার করছি, কারণ আমরা যে মান ফেরত দিচ্ছি তা আসলে একটি `HeroPublic` *নয়*।

`-> HeroPublic` ঘোষণা করলে আপনার এডিটর আর লিন্টার আপত্তি করত (যথার্থভাবেই) যে আপনি একটি `HeroPublic`-এর বদলে একটি `Hero` ফেরত দিচ্ছেন।

`response_model`-এ ঘোষণা করে আমরা **FastAPI**-কে তার কাজ করতে বলছি, টাইপ অ্যানোটেশন আর আপনার এডিটর ও অন্য টুলের সাহায্যে কোনো বাধা না দিয়ে।

### `HeroUpdate` দিয়ে একজন Hero আপডেট করুন { #update-a-hero-with-heroupdate }

**একজন নায়ক আপডেট** করতে পারি। এর জন্য একটি HTTP `PATCH` অপারেশন ব্যবহার করি।

আর কোডে ক্লায়েন্টের পাঠানো সব ডেটাসহ একটি `dict` পাই, **শুধু ক্লায়েন্টের পাঠানো ডেটা**, শুধু ডিফল্ট মান হওয়ার কারণে যেসব মান থাকত সেগুলো বাদ দিয়ে। এটি করতে `exclude_unset=True` ব্যবহার করি। এটাই মূল কৌশল। 🪄

তারপর `hero_data`-এর ডেটা দিয়ে `hero_db` আপডেট করতে `hero_db.sqlmodel_update(hero_data)` ব্যবহার করি।

## সংক্ষেপে { #recap }

একটি SQL ডেটাবেসের সাথে কাজ করতে আর *ডেটা মডেল* ও *টেবিল মডেল* দিয়ে কোড সহজ করতে [**SQLModel**](https://sqlmodel.tiangolo.com/) ব্যবহার করতে পারেন।

**SQLModel** ডকুমেন্টেশনে আরও অনেক কিছু শিখতে পারবেন, সেখানে [**FastAPI**-এর সাথে SQLModel ব্যবহার নিয়ে](https://sqlmodel.tiangolo.com/tutorial/fastapi/) আরও লম্বা একটি মিনি টিউটোরিয়াল আছে। 🚀

/// check | সংক্ষেপে মনে রাখুন

* টেবিল মডেল: `class Hero(SQLModel, table=True)`, প্রাইমারি কী `Field(default=None, primary_key=True)`।
* সারা অ্যাপে একটি `engine`, প্রতি রিকোয়েস্টে একটি `Session` (`yield`-সহ ডিপেন্ডেন্সি)।
* তৈরি: `session.add` → `session.commit` → `session.refresh`। পড়া: `session.exec(select(...))` বা `session.get(...)`। মোছা: `session.delete` → `commit`।
* নিরাপত্তার জন্য আলাদা মডেল: তৈরির জন্য `HeroCreate`, ফেরতের জন্য `HeroPublic`, আপডেটের জন্য `HeroUpdate`।
* ক্লায়েন্টকে কখনো `id` ঠিক করতে দেবেন না, আর গোপন তথ্য রেসপন্স মডেলে রাখবেন না।
