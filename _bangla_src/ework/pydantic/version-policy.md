# সংস্করণ নীতি { #version-policy }

/// note | এই পেজে যা জানবেন

* Pydantic V1, V2 আর ভবিষ্যতের V3-এর ক্ষেত্রে কী প্রতিশ্রুতি দেওয়া হয়।
* কোন ধরনের পরিবর্তন "breaking change" হিসেবে গণ্য হয় না।
* পরীক্ষামূলক (experimental) ফিচার কীভাবে চিনবেন আর এদের জীবনচক্র।
* কোন Python সংস্করণের সমর্থন কখন বন্ধ হয়।

///

প্রথমেই, আমরা স্বীকার করি যে Pydantic V1 থেকে V2-তে যাওয়া কিছু ব্যবহারকারীর জন্য কষ্টকর ছিল এবং থাকবে।
এই কষ্টের জন্য আমরা দুঃখিত 🙏, এটি ছিল V1-এর ডিজাইনের ভুল সংশোধনের জন্য একটি দুর্ভাগ্যজনক কিন্তু প্রয়োজনীয় পদক্ষেপ।

**এই মাত্রার আর কোনো breaking change হবে না!**

## Pydantic V1 { #pydantic-v1 }

V1-এর সক্রিয় ডেভেলপমেন্ট ইতিমধ্যে থেমে গেছে, তবে Pydantic V3 প্রকাশিত না হওয়া পর্যন্ত গুরুতর বাগ আর নিরাপত্তা দুর্বলতাগুলো
V1-এ ঠিক করা হবে।

## Pydantic V2 { #pydantic-v2 }

V2-এর minor রিলিজে (যেমন 2.10 → 2.11) আমরা ইচ্ছাকৃতভাবে কোনো breaking change করব না।

deprecated হিসেবে চিহ্নিত সুবিধাগুলো পরবর্তী major রিলিজ V3-এর আগে সরানো হবে না।

অবশ্যই, আপাতদৃষ্টিতে নিরাপদ কিছু পরিবর্তন আর বাগ ফিক্স অনিবার্যভাবে কিছু ব্যবহারকারীর কোড ভেঙে দেবে &mdash; এ নিয়ে [xkcd](https://xkcd.com/1172/)-এর বাধ্যতামূলক লিংক।

(ওই কার্টুনটির মর্ম: কেউ না কেউ একটি বাগের ওপরও নির্ভর করে থাকে, তাই বাগ ঠিক করলেও কারো কোড ভাঙতে পারে।)

নিচের পরিবর্তনগুলো breaking change হিসেবে **গণ্য হবে না**, আর minor রিলিজে হতে পারে:

* এমন বাগ ফিক্স যাতে বিদ্যমান কোড ভাঙতে পারে, যদি সেই কোড ডকুমেন্টেশনে নেই এমন ফিচার বা গঠনের ওপর নির্ভর করে থাকে।
* JSON Schema-র [reference](https://json-schema.org/understanding-json-schema/structuring#dollarref)-এর ফরম্যাট বদলানো।
* [`ValidationError`][pydantic_core.ValidationError] এক্সেপশনের `msg`, `ctx` আর `loc` ফিল্ড বদলানো। `type` বদলাবে না &mdash; যদি প্রোগ্রাম দিয়ে এরর বার্তা পার্স করেন, তাহলে `type` ব্যবহার করা উচিত।
* [`ValidationError`][pydantic_core.ValidationError] এক্সেপশনে নতুন key যোগ করা &mdash; যেমন, নতুন JSON পার্সারে যাওয়ার পর JSON যাচাইয়ের সময় এররে `line_number` আর `column_number` যোগ করার পরিকল্পনা আমাদের আছে।
* নতুন [`ValidationError`][pydantic_core.ValidationError] এরর যোগ করা।
* `__repr__` কীভাবে আচরণ করে তা বদলানো, এমনকি পাবলিক ক্লাসেরও।
* [core schema](./internals/architecture.md#communicating-between-pydantic-and-pydantic-core-the-core-schema)-র বিষয়বস্তু (সাধারণত
<!-- https://github.com/DavidAnson/markdownlint/issues/1472 -->
<!-- markdownlint-disable-next-line strong-style -->
  Pydantic মডেলের [`__pydantic_core_schema__`][pydantic.BaseModel.__pydantic_core_schema__] অ্যাট্রিবিউটে আর [type adapter](./concepts/type_adapter.md)-এর `core_schema`-তে পাওয়া যায়)
  রিলিজের মধ্যে বদলাতে পারে (এটি একটি নিচু-স্তরের ফরম্যাট, যা দিয়ে Pydantic পরিকল্পনা করে কীভাবে যাচাই আর সিরিয়ালাইজেশন চালাবে)।

সব ক্ষেত্রে আমরা অস্থিরতা যতটা সম্ভব কম রাখার চেষ্টা করব, আর তা করব শুধু তখনই যখন ব্যবহারকারীদের জন্য Pydantic-এর মান বাড়ার যুক্তি থাকবে।

/// warning | সাধারণ ভুল

প্রোগ্রামে এরর চেনার জন্য বার্তার লেখা (`msg`) মিলিয়ে দেখবেন না, যেমন `if 'valid integer' in err['msg']`। বার্তার লেখা minor রিলিজে বদলাতে পারে। এর বদলে `err['type'] == 'int_parsing'` এর মতো `type` মিলিয়ে দেখুন, এটি স্থির থাকে।

///

## Pydantic V3 এবং তার পরে { #pydantic-v3-and-beyond }

V3 রিলিজে সংশ্লিষ্ট যেকোনো breaking change যত্নের সাথে আনা হবে। এর মধ্যে থাকবে এমন বাগ ফিক্স যা আচরণে পরিবর্তন না এনে V2-তে সমাধান করা যায় না
(যেমন [MRO না মেনে চলা configuration ঠিক করা](https://github.com/pydantic/pydantic/issues/9992)), অথবা এমন পরিবর্তন যা বিদ্যমান সুবিধা সরিয়ে দেয় না বা
সঠিক বিকল্প দেয় না।

V3-তে `pydantic-core`-কে Pydantic-এর একটি অভ্যন্তরীণ সাব-মডিউল হিসেবে মিশিয়ে দেওয়ার আশা করা হচ্ছে, অর্থাৎ এটি আর আলাদা লাইব্রেরি হিসেবে প্রকাশিত হবে না।

## ট্যাগ দেওয়ার নিয়ম { #tagging-conventions }

PyPI-তে প্রকাশিত সব সংস্করণ (alpha আর beta রিলিজসহ) চিহ্নিত করতে Pydantic Git ট্যাগ ব্যবহার করে, শুরুতে `v` অক্ষরসহ। v2.13 থেকে, `pydantic-core`
`pydantic` রিপোজিটরির ভেতরে একটি workspace সদস্য হিসেবে মিশে গেছে, আর পরবর্তী `pydantic-core` রিলিজগুলো ট্যাগ করা হয় `core-vx.y.z` হিসেবে।

## পরীক্ষামূলক ফিচার { #experimental-features }

Pydantic-এ আমরা দ্রুত এগোতে আর নতুন কিছু করতে ভালোবাসি! সেজন্য আমরা minor রিলিজে পরীক্ষামূলক (experimental) ফিচার আনতে পারি।

/// info | ব্যবহারের ডকুমেন্টেশন

আমাদের বর্তমান পরীক্ষামূলক ফিচার সম্পর্কে আরও জানতে দেখুন [পরীক্ষামূলক ফিচারের ডকুমেন্টেশন](./concepts/experimental.md)।

///

অনুগ্রহ করে মনে রাখবেন, পরীক্ষামূলক ফিচারগুলো সক্রিয়ভাবে তৈরির কাজ চলছে এমন জিনিস। সফল হলে এগুলো একসময় Pydantic-এর অংশ হবে। সফল না হলে, খুব সামান্য আগাম সতর্কতায় এগুলো সরিয়ে ফেলা হবে। পরীক্ষামূলক পর্যায়ে থাকাকালীন একটি ফিচারের API আর আচরণ স্থিতিশীল নাও হতে পারে, আর ফিচারটিতে করা পরিবর্তন পুরনো কোডের সাথে সামঞ্জস্যপূর্ণ না হওয়ার যথেষ্ট সম্ভাবনা আছে।

/// tip | উদাহরণ দিয়ে বুঝি

পরীক্ষামূলক ফিচার অনেকটা রেস্টুরেন্টের "আজকের বিশেষ" খাবারের মতো: খেয়ে দেখতে পারেন, ভালো লাগলে তা নিয়মিত মেনুতে আসবে, ভালো না লাগলে কাল থেকে আর পাওয়া যাবে না। তাই শখের প্রজেক্টে চেষ্টা করুন, কিন্তু গুরুত্বপূর্ণ প্রোডাকশন কোডে সাবধানে ব্যবহার করুন।

///

### নামকরণের নিয়ম { #naming-conventions }

একটি ফিচার পরীক্ষামূলক তা বোঝাতে আমরা নিচের নামকরণের নিয়মগুলোর একটি ব্যবহার করি:

1. ফিচারটি [`experimental`](api/experimental.md) মডিউলে থাকে। এই ক্ষেত্রে, ফিচারটি এভাবে ব্যবহার করতে পারেন:

    ```python
    from pydantic.experimental import feature_name
    ```

2. ফিচারটি মূল মডিউলে থাকে, কিন্তু নামের শুরুতে `experimental_` থাকে। এটি ঘটে যখন আমরা মূল `pydantic` মডিউলে ইতিমধ্যে থাকা কোনো ডেটা স্ট্রাকচারে নতুন ফিল্ড, আর্গুমেন্ট বা মেথড যোগ করি।

এই নামকরণের নিয়মসহ নতুন ফিচারগুলো বদলাতে বা সরে যেতে পারে, আর সেগুলোকে Pydantic-এর স্থায়ী অংশ করার আগে আমরা মতামত আর পরামর্শ চাই। আরও তথ্যের জন্য দেখুন [মতামত অংশ](./concepts/experimental.md#feedback)।

### পরীক্ষামূলক ফিচারের জীবনচক্র { #lifecycle-of-experimental-features }

1. একটি নতুন ফিচার যোগ হয়, হয় [`experimental`](api/experimental.md) মডিউলে, নয়তো `experimental_` উপসর্গসহ।
2. patch/minor রিলিজে প্রায়ই আচরণ বদলানো হয়, সম্ভাব্য API/আচরণের পরিবর্তনসহ।
3. ফিচারটি সফল হলে, আমরা নিচের ধাপে এটিকে Pydantic-এ উন্নীত করি:

    a. যদি এটি [`experimental`](api/experimental.md) মডিউলে থাকে, তাহলে ফিচারটি Pydantic-এর মূল মডিউলে কপি করা হয়। মূল পরীক্ষামূলক ফিচারটি [`experimental`](api/experimental.md) মডিউলে থেকে যায়, কিন্তু ব্যবহার করলে একটি সতর্কবার্তা দেখায়। যদি ফিচারটি আগেই মূল Pydantic মডিউলে থাকে, তাহলে আমরা `experimental_` উপসর্গ ছাড়া ফিচারটির একটি কপি তৈরি করি, ফলে ফিচারটি অফিসিয়াল আর পরীক্ষামূলক দুই নামেই থাকে। পরীক্ষামূলক সংস্করণে একটি deprecation সতর্কবার্তা যুক্ত হয়।

    b. কোনো এক সময়ে, পরীক্ষামূলক ফিচারের কোড সরিয়ে ফেলা হয়, কিন্তু ফিচারটির একটি খালি রূপ (stub) থাকে, যা উপযুক্ত নির্দেশনাসহ একটি এরর বার্তা দেয়।

    c. শেষ ধাপে, ফিচারটির পরীক্ষামূলক সংস্করণ কোডবেস থেকে সম্পূর্ণ সরিয়ে ফেলা হয়।

যদি ফিচারটি সফল বা জনপ্রিয় না হয়, তাহলে সামান্য আগাম সতর্কতায় সরিয়ে ফেলা হয়। deprecated ফিচারের জায়গায় একটি এরর বার্তাসহ stub থেকে যাবে।

আমাদের নতুন পরীক্ষামূলক ফিচারের ধরনের জীবনচক্র আর নামকরণের নিয়মের অনুপ্রেরণার জন্য [streamlit](https://docs.streamlit.io/develop/quick-reference/prerelease)-কে ধন্যবাদ।

## Python সংস্করণের সমর্থন { #support-for-python-versions }

নিচের শর্তগুলো পূরণ হলে Pydantic একটি Python সংস্করণের সমর্থন বন্ধ করবে:

* Python সংস্করণটি তার [প্রত্যাশিত মেয়াদ শেষে](https://devguide.python.org/versions/) পৌঁছেছে।
* সর্বশেষ minor রিলিজের ৫%-এর কম ডাউনলোড সেই সংস্করণ ব্যবহার করছে।

/// check | সংক্ষেপে মনে রাখুন

* V2-এর minor রিলিজে ইচ্ছাকৃত breaking change নেই; deprecated জিনিস V3-এর আগে সরবে না।
* এরর চিনতে `type` ব্যবহার করুন, `msg` নয়।
* `pydantic.experimental` বা `experimental_` নামের জিনিস বদলাতে বা সরে যেতে পারে।
