# বাড়তি মডেল { #extra-models }

/// note | এই পেজে যা শিখবেন

* একই জিনিসের (যেমন ইউজার) জন্য কেন একাধিক মডেল দরকার: ইনপুট, আউটপুট, ডেটাবেস।
* `.model_dump()` আর `**` দিয়ে এক মডেল থেকে আরেক মডেল বানানো।
* ইনহেরিট্যান্স দিয়ে কোডের পুনরাবৃত্তি কমানো।
* রেসপন্স হিসেবে "এটা অথবা ওটা" (`Union`), মডেলের লিস্ট আর ডিকশনারি।

///

আগের উদাহরণ থেকে চলুন, একাধিক সম্পর্কিত মডেল থাকা খুবই সাধারণ ব্যাপার।

বিশেষ করে ইউজার মডেলের ক্ষেত্রে এটা হয়, কারণ:

* **ইনপুট মডেলে** একটি পাসওয়ার্ড থাকতে পারতে হবে।
* **আউটপুট মডেলে** পাসওয়ার্ড থাকা উচিত নয়।
* **ডেটাবেস মডেলে** সম্ভবত একটি হ্যাশ করা পাসওয়ার্ড থাকতে হবে।

/// danger | বিপদ

কখনো ব্যবহারকারীর সাধারণ টেক্সট পাসওয়ার্ড সংরক্ষণ করবেন না। সবসময় একটি "নিরাপদ হ্যাশ" সংরক্ষণ করুন, যা পরে যাচাই করা যায়।

"পাসওয়ার্ড হ্যাশ" কী তা না জানলে [সিকিউরিটি অধ্যায়ে](security/simple-oauth2.md#password-hashing) শিখবেন। সংক্ষেপে: হ্যাশ হলো পাসওয়ার্ডকে এমন একটি অর্থহীন স্ট্রিংয়ে বদলে ফেলা, যা থেকে আসল পাসওয়ার্ড ফেরত বের করা যায় না। লগইনের সময় নতুন করে হ্যাশ করে দুটো মিলিয়ে দেখা হয়।

### `**user_in.model_dump()` সম্পর্কে { #about-user-in-model-dump }

#### Pydantic-এর `.model_dump()` { #pydantics-model-dump }

`user_in` হলো `UserIn` ক্লাসের একটি Pydantic মডেল।

Pydantic মডেলের একটি `.model_dump()` মেথড আছে, যা মডেলের ডেটাসহ একটি `dict` রিটার্ন করে।

তাই যদি এভাবে একটি Pydantic অবজেক্ট `user_in` তৈরি করি:

```Python
user_in = UserIn(username="john", password="secret", email="john.doe@example.com")
```

তারপর ডাকি:

```Python
user_dict = user_in.model_dump()
```

তাহলে এখন `user_dict` ভেরিয়েবলে ডেটাসহ একটি `dict` আছে (এটি Pydantic মডেল অবজেক্টের বদলে একটি `dict`)।

আর যদি ডাকি:

```Python
print(user_dict)
```

#### একটি `dict` আনপ্যাক করা { #unpacking-a-dict }

`user_dict`-এর মতো একটি `dict` নিয়ে যদি `**user_dict` লিখে একটি ফাংশনে (বা ক্লাসে) পাঠাই, তাহলে Python এটিকে "আনপ্যাক" করবে (খুলে ছড়িয়ে দেবে)। এটি `user_dict`-এর কী আর মানগুলো সরাসরি নাম=মান আর্গুমেন্ট হিসেবে পাঠাবে।

তাই ওপরের `user_dict` থেকে চলুন, লিখলে:

```Python
UserInDB(**user_dict)
```

/// tip | উদাহরণ দিয়ে বুঝি

`**` হলো একটি ব্যাগ উপুড় করে ঢালার মতো। ব্যাগে (`dict`) আছে "username: john", "email: ..." এমন কয়েকটি লেবেল লাগানো জিনিস। `**` লিখলে সবগুলো বের করে ফাংশনের হাতে আলাদা আলাদা করে দেওয়া হয়, প্রতিটি তার লেবেলের নামে।

///

#### অন্য মডেলের বিষয়বস্তু থেকে একটি Pydantic মডেল { #a-pydantic-model-from-the-contents-of-another }

ওপরের উদাহরণে যেহেতু `user_in.model_dump()` থেকে `user_dict` পেয়েছি, তাই এই কোড:

```Python
user_dict = user_in.model_dump()
UserInDB(**user_dict)
```

এর সমতুল্য হবে:

```Python
UserInDB(**user_in.model_dump())
```

...কারণ `user_in.model_dump()` একটি `dict`, আর তারপর `**` আগে বসিয়ে `UserInDB`-তে পাঠিয়ে আমরা Python-কে দিয়ে এটি "আনপ্যাক" করাই।

তাই একটি Pydantic মডেলের ডেটা থেকে আরেকটি Pydantic মডেল পাই।

## পুনরাবৃত্তি কমান { #reduce-duplication }

কোডের পুনরাবৃত্তি কমানো **FastAPI**-এর মূল ধারণাগুলোর একটি।

কারণ কোডের পুনরাবৃত্তি বাগ, নিরাপত্তা সমস্যা, কোড অসঙ্গতির সমস্যা (এক জায়গায় আপডেট করলেন কিন্তু অন্য জায়গায় করলেন না) ইত্যাদির সম্ভাবনা বাড়ায়।

আর এই মডেলগুলো অনেক ডেটা ভাগাভাগি করছে, অ্যাট্রিবিউটের নাম আর টাইপগুলো বারবার লেখা হচ্ছে।

আমরা আরও ভালো করতে পারি।

একটি `UserBase` মডেল ঘোষণা করতে পারি, যা আমাদের অন্য মডেলগুলোর ভিত্তি হিসেবে কাজ করবে। তারপর ওই মডেলের সাব-ক্লাস বানাতে পারি, যেগুলো এর অ্যাট্রিবিউট (টাইপ ঘোষণা, যাচাই ইত্যাদি) ইনহেরিট করবে।

সব ডেটা রূপান্তর, যাচাই, ডকুমেন্টেশন ইত্যাদি তখনও স্বাভাবিকভাবেই কাজ করবে।

এভাবে শুধু মডেলগুলোর মধ্যকার পার্থক্যটুকু ঘোষণা করতে পারি (সাধারণ `password`-সহ, `hashed_password`-সহ, আর পাসওয়ার্ড ছাড়া):

## `Union` বা `anyOf` { #union-or-anyof }

একটি রেসপন্সকে দুই বা ততোধিক টাইপের `Union` হিসেবে ঘোষণা করতে পারেন, মানে রেসপন্সটি এগুলোর যেকোনোটি হতে পারে।

OpenAPI-তে এটি `anyOf` দিয়ে সংজ্ঞায়িত হবে।

এটি করতে স্ট্যান্ডার্ড Python টাইপ হিন্ট [`typing.Union`](https://docs.python.org/3/library/typing.html#typing.Union) ব্যবহার করুন:

/// note | নোট

একটি [`Union`](https://pydantic.dev/docs/validation/latest/concepts/unions/) সংজ্ঞায়িত করার সময় সবচেয়ে নির্দিষ্ট টাইপটি আগে, তারপর কম নির্দিষ্টটি রাখুন। নিচের উদাহরণে `Union[PlaneItem, CarItem]`-এ বেশি নির্দিষ্ট `PlaneItem` আসে `CarItem`-এর আগে।

এখানে একটি আইটেম হয় গাড়ি (`CarItem`), নয়তো বিমান (`PlaneItem`, যাতে বাড়তি `size` আছে)। `item1` চাইলে গাড়ির আকারে, `item2` চাইলে বিমানের আকারে রেসপন্স আসবে।

### Python 3.10-এ `Union` { #union-in-python-3-10 }

এই উদাহরণে আমরা `response_model` আর্গুমেন্টের মান হিসেবে `Union[PlaneItem, CarItem]` দিই।

যেহেতু এটি একটি **টাইপ অ্যানোটেশনে** না রেখে **একটি আর্গুমেন্টের মান** হিসেবে দিচ্ছি, তাই Python 3.10-এও `Union` ব্যবহার করতে হয়।

যদি এটি একটি টাইপ অ্যানোটেশনে থাকত, তাহলে খাড়া দাগ ব্যবহার করতে পারতাম, এভাবে:

```Python
some_variable: PlaneItem | CarItem
```

কিন্তু যদি এটি `response_model=PlaneItem | CarItem` হিসেবে মান বসানোর জায়গায় রাখি, তাহলে এরর পেতাম, কারণ Python এটিকে টাইপ অ্যানোটেশন হিসেবে না বুঝে `PlaneItem` আর `CarItem`-এর মধ্যে একটি **অবৈধ অপারেশন** করার চেষ্টা করত।

## সংক্ষেপে { #recap }

প্রতিটি ক্ষেত্রের জন্য একাধিক Pydantic মডেল ব্যবহার করুন আর ইচ্ছামতো ইনহেরিট করুন।

একটি জিনিসের (entity) যদি বিভিন্ন "অবস্থা" থাকতে পারে, তাহলে প্রতি জিনিসের জন্য একটিমাত্র ডেটা মডেল রাখার দরকার নেই। **ইউজার** "জিনিসটি" এর একটি উদাহরণ, যার অবস্থাগুলোর মধ্যে আছে `password`-সহ, `password_hash`-সহ, বা পাসওয়ার্ড ছাড়া।
