# Password আর Bearer-সহ সহজ OAuth2 { #simple-oauth2-with-password-and-bearer }

/// note | এই পেজে যা শিখবেন

* `/token` পাথ বানিয়ে ইউজারনেম-পাসওয়ার্ড গ্রহণ করা (`OAuth2PasswordRequestForm`)।
* পাসওয়ার্ড হ্যাশিং কী আর কেন জরুরি।
* লগইন সফল হলে টোকেন ফেরত দেওয়া।
* নিষ্ক্রিয় (disabled) ইউজার আটকানোর ডিপেন্ডেন্সি।
* `/docs` থেকে পুরো লগইন প্রক্রিয়া পরীক্ষা করা।

///

এবার আগের অধ্যায়ের ওপর ভিত্তি করে বাকি অংশগুলো যোগ করে একটি পূর্ণাঙ্গ সিকিউরিটি প্রবাহ তৈরি করা যাক।

## `username` আর `password` নিন { #get-the-username-and-password }

`username` আর `password` পেতে আমরা **FastAPI**-এর সিকিউরিটি টুলগুলো ব্যবহার করব।

OAuth2 নির্দিষ্ট করে দেয় যে "password flow" (যা আমরা ব্যবহার করছি) ব্যবহার করার সময় ক্লায়েন্ট/ইউজারকে `username` আর `password` ফিল্ডগুলো ফর্ম ডেটা হিসেবে পাঠাতে হবে।

আর স্পেসিফিকেশন বলে যে ফিল্ডগুলোর নাম ঠিক এমনই হতে হবে। তাই `user-name` বা `email` কাজ করবে না।

তবে চিন্তা করবেন না, ফ্রন্টএন্ডে আপনার চূড়ান্ত ব্যবহারকারীদের আপনি যেভাবে খুশি দেখাতে পারেন (যেমন ঘরের লেবেল "ইমেইল" লিখতে পারেন)।

আর আপনার ডেটাবেস মডেলগুলোতে অন্য যেকোনো নাম ব্যবহার করতে পারেন।

কিন্তু লগইন *পাথ অপারেশনের* জন্য স্পেসিফিকেশনের সাথে সামঞ্জস্যপূর্ণ হতে (আর যেমন একীভূত API ডকুমেন্টেশন সিস্টেম ব্যবহার করতে পারতে) এই নামগুলোই ব্যবহার করতে হবে।

স্পেসিফিকেশন এটাও বলে যে `username` আর `password` অবশ্যই ফর্ম ডেটা হিসেবে পাঠাতে হবে (তাই এখানে JSON নয়)।

### `scope` { #scope }

স্পেসিফিকেশন এটাও বলে যে ক্লায়েন্ট আরেকটি ফর্ম ফিল্ড "`scope`" পাঠাতে পারে।

ফর্ম ফিল্ডের নাম `scope` (একবচনে), কিন্তু আসলে এটি স্পেস দিয়ে আলাদা করা "scope"-গুলোর একটি লম্বা স্ট্রিং।

প্রতিটি "scope" শুধু একটি স্ট্রিং (স্পেস ছাড়া)।

এগুলো সাধারণত নির্দিষ্ট সিকিউরিটি অনুমতি ঘোষণা করতে ব্যবহার হয়, যেমন:

* `users:read` বা `users:write` প্রচলিত উদাহরণ।
* Facebook / Instagram ব্যবহার করে `instagram_basic`।
* Google ব্যবহার করে `https://www.googleapis.com/auth/drive`।

/// note | নোট

OAuth2-তে একটি "scope" শুধু একটি স্ট্রিং, যা একটি নির্দিষ্ট প্রয়োজনীয় অনুমতি ঘোষণা করে।

এতে `:` এর মতো অন্য অক্ষর আছে কিনা বা এটি একটি URL কিনা, তাতে কিছু যায় আসে না।

ওই খুঁটিনাটিগুলো ইমপ্লিমেন্টেশনের ওপর নির্ভর করে।

OAuth2-এর কাছে এগুলো শুধুই স্ট্রিং।

///

## `username` আর `password` পাওয়ার কোড { #code-to-get-the-username-and-password }

এবার এটি সামলাতে **FastAPI**-এর দেওয়া টুলগুলো ব্যবহার করা যাক।

### `OAuth2PasswordRequestForm` { #oauth2passwordrequestform }

প্রথমে `OAuth2PasswordRequestForm` ইমপোর্ট করুন, আর `/token`-এর *পাথ অপারেশনে* `Depends` দিয়ে এটিকে একটি ডিপেন্ডেন্সি হিসেবে ব্যবহার করুন:

{* ../../docs_src/security/tutorial003_an_py310.py hl[4,78] *}

`OAuth2PasswordRequestForm` হলো একটি ক্লাস ডিপেন্ডেন্সি, যা এগুলোসহ একটি ফর্ম বডি ঘোষণা করে:

* `username`।
* `password`।
* একটি ঐচ্ছিক `scope` ফিল্ড, স্পেস দিয়ে আলাদা করা স্ট্রিং দিয়ে তৈরি একটি বড় স্ট্রিং হিসেবে।
* একটি ঐচ্ছিক `grant_type`।

/// tip | পরামর্শ

OAuth2 স্পেসিফিকেশন আসলে `password` নির্দিষ্ট মানসহ একটি `grant_type` ফিল্ড *বাধ্যতামূলক* করে, কিন্তু `OAuth2PasswordRequestForm` এটি জোর করে না।

এটি জোর করতে চাইলে `OAuth2PasswordRequestForm`-এর বদলে `OAuth2PasswordRequestFormStrict` ব্যবহার করুন।

///

* একটি ঐচ্ছিক `client_id` (আমাদের উদাহরণে দরকার নেই)।
* একটি ঐচ্ছিক `client_secret` (আমাদের উদাহরণে দরকার নেই)।

/// note | নোট

`OAuth2PasswordRequestForm`, `OAuth2PasswordBearer`-এর মতো **FastAPI**-এর জন্য কোনো বিশেষ ক্লাস নয়।

`OAuth2PasswordBearer` **FastAPI**-কে জানায় যে এটি একটি সিকিউরিটি স্কিম। তাই এটি সেভাবেই OpenAPI-তে যোগ হয়।

কিন্তু `OAuth2PasswordRequestForm` শুধু একটি ক্লাস ডিপেন্ডেন্সি, যা আপনি নিজেও লিখতে পারতেন, বা সরাসরি `Form` প্যারামিটার ঘোষণা করতে পারতেন।

তবে যেহেতু এটি একটি প্রচলিত ব্যবহারের ক্ষেত্র, তাই কাজ সহজ করতে **FastAPI** সরাসরি এটি দেয়।

///

### ফর্ম ডেটা ব্যবহার করুন { #use-the-form-data }

/// tip | পরামর্শ

ডিপেন্ডেন্সি ক্লাস `OAuth2PasswordRequestForm`-এর ইনস্ট্যান্সে স্পেস দিয়ে আলাদা লম্বা স্ট্রিংসহ `scope` অ্যাট্রিবিউট থাকবে না। বরং পাঠানো প্রতিটি scope-এর জন্য আসল স্ট্রিংয়ের লিস্টসহ একটি `scopes` অ্যাট্রিবিউট থাকবে।

এই উদাহরণে আমরা `scopes` ব্যবহার করছি না, তবে দরকার হলে সুবিধাটি আছে।

///

এমন কোনো ইউজার না থাকলে আমরা "Incorrect username or password" (ভুল ইউজারনেম বা পাসওয়ার্ড) বলে একটি এরর ফেরত দিই।

এররের জন্য `HTTPException` এক্সেপশন ব্যবহার করি:

### পাসওয়ার্ড যাচাই করুন { #check-the-password }

এই পর্যায়ে আমাদের ডেটাবেস থেকে ইউজারের ডেটা আছে, কিন্তু পাসওয়ার্ড যাচাই করিনি।

প্রথমে ওই ডেটা Pydantic `UserInDB` মডেলে রাখা যাক।

কখনো সাধারণ টেক্সট আকারে পাসওয়ার্ড সংরক্ষণ করা উচিত নয়, তাই আমরা (নকল) পাসওয়ার্ড হ্যাশিং ব্যবস্থা ব্যবহার করব।

পাসওয়ার্ড না মিললে আমরা একই এরর ফেরত দিই।

#### পাসওয়ার্ড হ্যাশিং { #password-hashing }

"হ্যাশিং" মানে: কোনো বিষয়বস্তুকে (এই ক্ষেত্রে একটি পাসওয়ার্ড) বাইটের একটি ক্রমে (শুধু একটি স্ট্রিং) রূপান্তর করা, যা দেখতে অর্থহীন হিজিবিজির মতো।

হুবহু একই বিষয়বস্তু (হুবহু একই পাসওয়ার্ড) দিলে প্রতিবার হুবহু একই হিজিবিজি পাবেন।

কিন্তু হিজিবিজি থেকে উল্টো পথে পাসওয়ার্ডে ফিরে যাওয়া যায় না।

/// tip | উদাহরণ দিয়ে বুঝি

হ্যাশিং অনেকটা আঙুলের ছাপের মতো। একজন মানুষ থেকে সবসময় একই আঙুলের ছাপ পাওয়া যায়, কিন্তু শুধু ছাপ দেখে মানুষটিকে "বানানো" যায় না। লগইনের সময় আপনি যে পাসওয়ার্ড দেন, সেটির ছাপ (হ্যাশ) বানিয়ে ডেটাবেসের ছাপের সাথে মেলানো হয়। মিললে পাসওয়ার্ড সঠিক।

///

##### কেন পাসওয়ার্ড হ্যাশিং ব্যবহার করবেন { #why-use-password-hashing }

আপনার ডেটাবেস চুরি হলে চোরের কাছে আপনার ইউজারদের সাধারণ টেক্সট পাসওয়ার্ড থাকবে না, শুধু হ্যাশ থাকবে।

তাই চোর ওই একই পাসওয়ার্ড অন্য কোনো সিস্টেমে ব্যবহারের চেষ্টা করতে পারবে না (অনেক ইউজার সব জায়গায় একই পাসওয়ার্ড ব্যবহার করে, তাই এটি বিপজ্জনক হতো)।

## টোকেন ফেরত দিন { #return-the-token }

`token` এন্ডপয়েন্টের রেসপন্স অবশ্যই একটি JSON অবজেক্ট হতে হবে।

এতে একটি `token_type` থাকা উচিত। আমাদের ক্ষেত্রে, যেহেতু "Bearer" টোকেন ব্যবহার করছি, টোকেনের টাইপ হবে "`bearer`"।

আর এতে একটি `access_token` থাকা উচিত, আমাদের অ্যাক্সেস টোকেনসহ একটি স্ট্রিং।

এই সহজ উদাহরণে আমরা পুরোপুরি অনিরাপদ হব, আর টোকেন হিসেবে সেই একই `username` ফেরত দেব।

/// tip | পরামর্শ

পরের অধ্যায়ে সত্যিকারের নিরাপদ একটি ইমপ্লিমেন্টেশন দেখবেন, পাসওয়ার্ড হ্যাশিং আর <abbr title="JSON Web Tokens">JWT</abbr> টোকেনসহ।

তবে আপাতত আমাদের দরকারি নির্দিষ্ট খুঁটিনাটিগুলোতে মনোযোগ দেওয়া যাক।

/// tip | পরামর্শ

স্পেসিফিকেশন অনুযায়ী একটি `access_token` আর একটি `token_type`-সহ একটি JSON ফেরত দেওয়া উচিত, ঠিক এই উদাহরণের মতো।

এটি আপনাকে নিজের কোডে নিজেকেই করতে হবে, আর নিশ্চিত করতে হবে যে ওই JSON কী-গুলোই ব্যবহার করছেন।

স্পেসিফিকেশনের সাথে সামঞ্জস্যপূর্ণ হতে প্রায় এটুকুই একমাত্র জিনিস, যা আপনাকে নিজে সঠিকভাবে করতে মনে রাখতে হবে।

বাকিটা **FastAPI** আপনার হয়ে সামলায়।

## ডিপেন্ডেন্সিগুলো হালনাগাদ করুন { #update-the-dependencies }

আমরা `current_user` পেতে চাই *শুধু* তখনই যখন ইউজারটি সক্রিয়।

তাই একটি বাড়তি ডিপেন্ডেন্সি `get_current_active_user` তৈরি করি, যা আবার `get_current_user`-কে ডিপেন্ডেন্সি হিসেবে ব্যবহার করে।

ইউজার না থাকলে বা নিষ্ক্রিয় হলে এই দুটি ডিপেন্ডেন্সিই শুধু একটি HTTP এরর ফেরত দেবে।

/// note | নোট

এখানে আমরা যে বাড়তি হেডার `WWW-Authenticate` মান `Bearer`-সহ ফেরত দিচ্ছি, সেটিও স্পেসিফিকেশনের অংশ।

যেকোনো HTTP (এরর) স্ট্যাটাস কোড ৪০১ "UNAUTHORIZED"-এর সাথে একটি `WWW-Authenticate` হেডারও ফেরত দেওয়ার কথা।

bearer টোকেনের ক্ষেত্রে (আমাদের ক্ষেত্রে), ওই হেডারের মান হওয়া উচিত `Bearer`।

আসলে আপনি ওই বাড়তি হেডারটি বাদ দিলেও কাজ চলবে।

তবে স্পেসিফিকেশনের সাথে সামঞ্জস্যপূর্ণ হতে এটি এখানে দেওয়া হয়েছে।

এছাড়া এমন টুল থাকতে পারে যেগুলো এটি আশা করে আর ব্যবহার করে (এখন বা ভবিষ্যতে), যা এখন বা ভবিষ্যতে আপনার বা আপনার ব্যবহারকারীদের কাজে লাগতে পারে।

## সংক্ষেপে { #recap }

আপনার API-এর জন্য `username` আর `password`-ভিত্তিক একটি পূর্ণাঙ্গ সিকিউরিটি ব্যবস্থা ইমপ্লিমেন্ট করার টুল এখন আপনার কাছে আছে।

এই টুলগুলো ব্যবহার করে সিকিউরিটি ব্যবস্থাটিকে যেকোনো ডেটাবেস আর যেকোনো ইউজার বা ডেটা মডেলের সাথে সামঞ্জস্যপূর্ণ করতে পারেন।

একমাত্র যে খুঁটিনাটি বাকি তা হলো, এটি আসলে এখনো "নিরাপদ" নয়।

পরের অধ্যায়ে দেখবেন কীভাবে একটি নিরাপদ পাসওয়ার্ড হ্যাশিং লাইব্রেরি আর <abbr title="JSON Web Tokens">JWT</abbr> টোকেন ব্যবহার করবেন।

/// check | সংক্ষেপে মনে রাখুন

* লগইন পাথ: `@app.post("/token")` আর `form_data: Annotated[OAuth2PasswordRequestForm, Depends()]`।
* ইউজার না পেলে বা পাসওয়ার্ড না মিললে একই এরর বার্তা দিন।
* পাসওয়ার্ড কখনো সরাসরি নয়, হ্যাশ করে রাখুন ও মেলান।
* সফল হলে ফেরত দিন `{"access_token": ..., "token_type": "bearer"}`।
* `get_current_active_user` দিয়ে নিষ্ক্রিয় ইউজার আটকান।
* এই উদাহরণের টোকেন নিরাপদ নয়, আসল সমাধান পরের অধ্যায়ে (JWT)।
