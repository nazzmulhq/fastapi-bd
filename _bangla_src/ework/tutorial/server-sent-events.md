# Server-Sent Events (SSE) { #server-sent-events-sse }

/// note | এই পেজে যা শিখবেন

* SSE কী, আর JSON Lines থেকে এর পার্থক্য।
* `EventSourceResponse` আর `yield` দিয়ে SSE স্ট্রিম করা।
* `ServerSentEvent` দিয়ে `event`, `id`, `retry` ইত্যাদি সেট করা।
* সংযোগ বিচ্ছিন্ন হলে যেখানে থেমেছিল সেখান থেকে আবার শুরু করা (`Last-Event-ID`)।

///

**Server-Sent Events** (SSE) ব্যবহার করে ক্লায়েন্টের কাছে ডেটা স্ট্রিম করতে পারেন।

এটি [JSON Lines স্ট্রিম করা](stream-json-lines.md)-এর মতোই, কিন্তু `text/event-stream` ফরম্যাট ব্যবহার করে, যা ব্রাউজার [`EventSource` API](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) দিয়ে নিজে থেকেই সাপোর্ট করে। অর্থাৎ ব্রাউজারের JavaScript খুব সহজে এটি পড়তে পারে, কোনো বাড়তি লাইব্রেরি ছাড়াই।

/// note | নোট

FastAPI 0.135.0-এ যোগ হয়েছে।

///

## Server-Sent Events কী? { #what-are-server-sent-events }

SSE হলো HTTP-এর মাধ্যমে সার্ভার থেকে ক্লায়েন্টে ডেটা স্ট্রিম করার একটি স্ট্যান্ডার্ড।

প্রতিটি ইভেন্ট হলো `data`, `event`, `id` আর `retry`-এর মতো "ফিল্ড"-সহ একটি ছোট টেক্সট ব্লক, যেগুলো ফাঁকা লাইন দিয়ে আলাদা।

এটি দেখতে এমন:

⟦CODE1⟧

SSE সাধারণত ব্যবহার হয় AI চ্যাট স্ট্রিমিং, লাইভ নোটিফিকেশন, লগ ও পর্যবেক্ষণ, আর অন্যান্য এমন ক্ষেত্রে যেখানে সার্ভার ক্লায়েন্টের কাছে আপডেট পাঠিয়ে দেয়। যেমন খেলার লাইভ স্কোর বা ডেলিভারির অবস্থার আপডেট।

/// tip | SSE নাকি WebSocket?

* **SSE**: শুধু সার্ভার থেকে ক্লায়েন্টে, একমুখী। সহজ, সাধারণ HTTP-এর ওপর চলে, সংযোগ ভাঙলে ব্রাউজার নিজে আবার যুক্ত হয়।
* **WebSocket**: দুই দিকেই বার্তা যায়। চ্যাট অ্যাপের মতো ক্ষেত্রে, যেখানে ক্লায়েন্টও বারবার বার্তা পাঠায়।

শুধু আপডেট পাঠাতে হলে SSE-ই সাধারণত সহজ পছন্দ।

///

/// tip | পরামর্শ

আপনি যদি বাইনারি ডেটা স্ট্রিম করতে চান, যেমন ভিডিও বা অডিও, তাহলে অ্যাডভান্সড গাইড দেখুন: [ডেটা স্ট্রিম করা](../advanced/stream-data.md)।

/// info | কোডটি সহজ ভাষায়

* লাইন ২৪: `comment="..."`: একটি মন্তব্য পাঠানো, যা ক্লায়েন্ট দেখায় না।
* লাইন ২৬: প্রতিটি আইটেমের জন্য একটি ইভেন্ট:
    * `data=item`: আসল ডেটা (JSON হয়ে যাবে)।
    * `event="item_update"`: ইভেন্টের নাম, ব্রাউজারে এই নাম দিয়ে আলাদাভাবে শোনা যায়।
    * `id=str(i + 1)`: ইভেন্টের নম্বর, সংযোগ ভাঙলে আবার শুরু করতে কাজে লাগে।
    * `retry=5000`: সংযোগ ভাঙলে ৫০০০ মিলিসেকেন্ড (৫ সেকেন্ড) পরে আবার চেষ্টা করতে বলা।

///

`data` ফিল্ড সবসময় JSON হিসেবে এনকোড হয়। JSON হিসেবে সিরিয়ালাইজ করা যায় এমন যেকোনো মান দিতে পারেন, Pydantic মডেলসহ।

## কাঁচা ডেটা { #raw-data }

আপনার যদি JSON এনকোডিং **ছাড়া** ডেটা পাঠাতে হয়, তাহলে `data`-এর বদলে `raw_data` ব্যবহার করুন।

## `Last-Event-ID` দিয়ে আবার শুরু { #resuming-with-last-event-id }

সংযোগ বিচ্ছিন্ন হওয়ার পরে একটি ব্রাউজার আবার যুক্ত হলে, এটি সবশেষে পাওয়া `id`-টি `Last-Event-ID` হেডারে পাঠায়।

/// info | কোডটি সহজ ভাষায়

* লাইন ২৫: `last_event_id` হেডার থেকে পড়া (`Last-Event-ID`)। প্রথমবার এটি থাকে না, তাই `None`।
* লাইন ২৭: আগে কোনো id পেয়ে থাকলে তার পরেরটি থেকে, নইলে শুরু থেকে।

## কারিগরি বিবরণ { #technical-details }

FastAPI নিজে থেকেই SSE-এর কিছু ভালো অভ্যাস প্রয়োগ করে।

* কোনো বার্তা না থাকলে প্রতি ১৫ সেকেন্ডে একটি **"keep alive" `ping` মন্তব্য** পাঠায়, যাতে কিছু প্রক্সি সংযোগ বন্ধ করে না দেয়, যেমনটা [HTML স্পেসিফিকেশন: Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html#authoring-notes)-এ সুপারিশ করা হয়েছে।
* স্ট্রিম **ক্যাশ হওয়া আটকাতে** `Cache-Control: no-cache` হেডার সেট করে।
* Nginx-এর মতো কিছু প্রক্সিতে **বাফারিং আটকাতে** একটি বিশেষ হেডার `X-Accel-Buffering: no` সেট করে। (বাফারিং মানে প্রক্সি ডেটা জমিয়ে একসাথে পাঠানো, যা স্ট্রিমিংয়ের উদ্দেশ্যই নষ্ট করে।)

এ নিয়ে আপনাকে কিছুই করতে হবে না, এটি নিজে থেকেই কাজ করে। 🤓

/// check | সংক্ষেপে মনে রাখুন

* SSE = সার্ভার থেকে ব্রাউজারে একমুখী লাইভ আপডেট, `text/event-stream` ফরম্যাটে।
* `@app.get(..., response_class=EventSourceResponse)` আর ফাংশনে `yield`।
* বাড়তি ফিল্ডের জন্য `ServerSentEvent(data=..., event=..., id=..., retry=...)`, JSON ছাড়া পাঠাতে `raw_data`।
* `Last-Event-ID` হেডার পড়ে থামা জায়গা থেকে আবার শুরু করা যায়।
