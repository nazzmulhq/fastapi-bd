# HTTPS সম্পর্কে { #about-https }

/// note | এই পেজে যা শিখবেন

* HTTPS আসলে কীভাবে কাজ করে, ডেভেলপারের দৃষ্টিকোণ থেকে।
* সার্টিফিকেট, TLS, SNI, TLS Termination Proxy এর মতো শব্দগুলোর সহজ অর্থ।
* Let's Encrypt কীভাবে বিনামূল্যে সার্টিফিকেট দেয়।
* প্রক্সির পেছনে থাকলে কেন forwarded হেডার দরকার।

///

ধরে নেওয়া সহজ যে HTTPS এমন একটি জিনিস যা শুধু "চালু" বা "বন্ধ" করা যায়।

কিন্তু আসলে এটি এর চেয়ে অনেক বেশি জটিল।

/// tip | পরামর্শ

আপনার তাড়া থাকলে বা এ নিয়ে মাথা ঘামাতে না চাইলে, বিভিন্ন কৌশলে সবকিছু সেটআপ করার ধাপে ধাপে নির্দেশনার জন্য পরের অংশগুলোতে চলে যান।

///

/// tip | উদাহরণ দিয়ে বুঝি

HTTP হলো খোলা পোস্টকার্ড: পথে যে-ই হাতে পায়, লেখা পড়ে ফেলতে পারে। HTTPS হলো তালাবন্ধ বাক্সে চিঠি পাঠানো, যার চাবি শুধু আপনার আর প্রাপকের কাছে। আর **সার্টিফিকেট** হলো প্রাপকের সরকারি পরিচয়পত্র, যা দেখে আপনি নিশ্চিত হন যে বাক্সটি সত্যিই সঠিক মানুষের কাছে যাচ্ছে, কোনো প্রতারকের কাছে নয়।

///

একজন ব্যবহারকারীর দৃষ্টিকোণ থেকে **HTTPS-এর মৌলিক বিষয় জানতে** দেখুন [https://howhttps.works/](https://howhttps.works/)।

এখন, একজন **ডেভেলপারের দৃষ্টিকোণ** থেকে, HTTPS নিয়ে ভাবার সময় মাথায় রাখার মতো কয়েকটি বিষয়:

* HTTPS-এর জন্য **সার্ভারের** একটি **তৃতীয় পক্ষের** তৈরি **"সার্টিফিকেট" থাকতে হয়**।
    * ওই সার্টিফিকেটগুলো আসলে তৃতীয় পক্ষের কাছ থেকে **সংগ্রহ** করা হয়, নিজে "তৈরি" করা হয় না।
* সার্টিফিকেটের একটি **মেয়াদ** থাকে।
    * এগুলো **মেয়াদোত্তীর্ণ** হয়।
    * তখন এগুলো **নবায়ন** করতে হয়, তৃতীয় পক্ষের কাছ থেকে **আবার সংগ্রহ** করতে হয়।
* সংযোগের এনক্রিপশন (গোপন সংকেতে রূপান্তর) হয় **TCP স্তরে**।
    * এটি **HTTP-এর এক স্তর নিচে**।
    * তাই **সার্টিফিকেট আর এনক্রিপশনের** কাজ হয় **HTTP-এর আগে**।
* **TCP "ডোমেইন" চেনে না**। শুধু IP ঠিকানা চেনে।
    * কোন **নির্দিষ্ট ডোমেইন** চাওয়া হয়েছে, সেই তথ্য থাকে **HTTP ডেটায়**।
* **HTTPS সার্টিফিকেট** একটি **নির্দিষ্ট ডোমেইনকে** "প্রত্যয়ন" করে, কিন্তু প্রোটোকল আর এনক্রিপশন হয় TCP স্তরে, কোন ডোমেইন নিয়ে কাজ হচ্ছে তা **জানার আগেই**।
* **ডিফল্টভাবে**, এর মানে হতো আপনি **প্রতি IP ঠিকানায় শুধু একটি HTTPS সার্টিফিকেট** রাখতে পারবেন।
    * আপনার সার্ভার যত বড়ই হোক বা এতে থাকা প্রতিটি অ্যাপ্লিকেশন যত ছোটই হোক।
    * তবে এর একটি **সমাধান** আছে।
* **TLS** প্রোটোকলের (যেটি HTTP-এর আগে, TCP স্তরে এনক্রিপশন সামলায়) একটি **এক্সটেনশন** আছে, যার নাম **[<abbr title="Server Name Indication">SNI</abbr>](https://en.wikipedia.org/wiki/Server_Name_Indication)**।
    * এই SNI এক্সটেনশন একটি মাত্র সার্ভারকে (একটি **মাত্র IP ঠিকানাসহ**) **একাধিক HTTPS সার্টিফিকেট** রাখতে আর **একাধিক HTTPS ডোমেইন/অ্যাপ্লিকেশন** চালাতে দেয়।
    * এটি কাজ করাতে, সার্ভারে চলমান, **পাবলিক IP ঠিকানায়** শুনতে থাকা **একটি মাত্র** কম্পোনেন্টের (প্রোগ্রামের) কাছে সার্ভারের **সব HTTPS সার্টিফিকেট** থাকতে হবে।
* নিরাপদ সংযোগ পাওয়ার **পরে**, যোগাযোগের প্রোটোকল **তখনো HTTP**।
    * বিষয়বস্তু **এনক্রিপ্ট করা** থাকে, যদিও সেগুলো **HTTP প্রোটোকলেই** পাঠানো হচ্ছে।

সার্ভারে (মেশিন, হোস্ট ইত্যাদি) **একটি প্রোগ্রাম/HTTP সার্ভার** চালিয়ে রাখা প্রচলিত, যা **HTTPS-এর সব অংশ সামলায়**: **এনক্রিপ্ট করা HTTPS রিকোয়েস্ট** গ্রহণ করে, একই সার্ভারে চলা আসল HTTP অ্যাপ্লিকেশনে (এখানে **FastAPI** অ্যাপ্লিকেশন) **ডিক্রিপ্ট করা HTTP রিকোয়েস্ট** পাঠায়, অ্যাপ্লিকেশন থেকে **HTTP রেসপন্স** নেয়, সঠিক **HTTPS সার্টিফিকেট** দিয়ে **এনক্রিপ্ট করে**, আর **HTTPS** দিয়ে ক্লায়েন্টকে ফেরত পাঠায়। এই সার্ভারকে প্রায়ই বলা হয় **[TLS Termination Proxy](https://en.wikipedia.org/wiki/TLS_termination_proxy)**।

/// tip | উদাহরণ দিয়ে বুঝি

TLS Termination Proxy হলো একটি অফিসের রিসেপশনিস্ট, যিনি সব ভাষা জানেন। বাইরে থেকে সব চিঠি আসে তালাবন্ধ বাক্সে (HTTPS)। রিসেপশনিস্ট চাবি দিয়ে খুলে সাধারণ চিঠিটি (HTTP) ভেতরের সঠিক কর্মকর্তার (FastAPI অ্যাপ) কাছে দেন। উত্তর এলে আবার তালাবন্ধ করে বাইরে পাঠান। ভেতরের কর্মকর্তাকে তালা-চাবি নিয়ে ভাবতে হয় না।

///

TLS Termination Proxy হিসেবে ব্যবহার করতে পারেন এমন কয়েকটি অপশন:

* Traefik (যা সার্টিফিকেট নবায়নও সামলাতে পারে)
* Caddy (যা সার্টিফিকেট নবায়নও সামলাতে পারে)
* Nginx
* HAProxy

## Let's Encrypt { #lets-encrypt }

Let's Encrypt-এর আগে, এই **HTTPS সার্টিফিকেটগুলো** বিশ্বস্ত তৃতীয় পক্ষ বিক্রি করত।

এই সার্টিফিকেটগুলোর একটি সংগ্রহ করার প্রক্রিয়া আগে ঝামেলাপূর্ণ ছিল, বেশ কিছু কাগজপত্র লাগত, আর সার্টিফিকেটগুলো বেশ দামি ছিল।

কিন্তু তারপর তৈরি হলো **[Let's Encrypt](https://letsencrypt.org/)**।

এটি Linux Foundation-এর একটি প্রজেক্ট। এটি স্বয়ংক্রিয়ভাবে, **বিনামূল্যে HTTPS সার্টিফিকেট** দেয়। এই সার্টিফিকেটগুলো সব স্ট্যান্ডার্ড ক্রিপ্টোগ্রাফিক নিরাপত্তা ব্যবহার করে, আর স্বল্পমেয়াদি (প্রায় ৩ মাস), তাই কম মেয়াদের কারণে **নিরাপত্তা আসলে আরও ভালো**।

ডোমেইনগুলো নিরাপদভাবে যাচাই করা হয় আর সার্টিফিকেট স্বয়ংক্রিয়ভাবে তৈরি হয়। এতে এই সার্টিফিকেটগুলোর নবায়নও স্বয়ংক্রিয় করা যায়।

ধারণাটি হলো এই সার্টিফিকেটগুলোর সংগ্রহ আর নবায়ন স্বয়ংক্রিয় করা, যাতে আপনি **চিরকাল, বিনামূল্যে, নিরাপদ HTTPS** পেতে পারেন।

## ডেভেলপারদের জন্য HTTPS { #https-for-developers }

এখানে একটি HTTPS API দেখতে কেমন হতে পারে তার একটি ধাপে ধাপে উদাহরণ, মূলত ডেভেলপারদের জন্য গুরুত্বপূর্ণ ধারণাগুলোর দিকে মনোযোগ দিয়ে।

### ডোমেইন নাম { #domain-name }

সম্ভবত সবকিছু শুরু হবে আপনার একটি **ডোমেইন নাম** **সংগ্রহ** করার মাধ্যমে। তারপর এটি একটি DNS সার্ভারে (সম্ভবত আপনার একই ক্লাউড প্রোভাইডারে) কনফিগার করবেন।

আপনি সম্ভবত একটি ক্লাউড সার্ভার (একটি ভার্চুয়াল মেশিন) বা এমন কিছু নেবেন, আর এর একটি <dfn title="সময়ের সাথে বদলায় না। ডায়নামিক নয়।">স্থির</dfn> **পাবলিক IP ঠিকানা** থাকবে।

DNS সার্ভারে আপনি একটি রেকর্ড (একটি "`A record`") কনফিগার করবেন, যা **আপনার ডোমেইনকে** **আপনার সার্ভারের** পাবলিক **IP ঠিকানার** দিকে নির্দেশ করবে।

সম্ভবত এটি শুধু একবারই করবেন, প্রথমবার সবকিছু সেটআপ করার সময়।

/// tip | পরামর্শ

এই ডোমেইন নামের অংশটি HTTPS-এর অনেক আগের ব্যাপার, কিন্তু যেহেতু সবকিছু ডোমেইন আর IP ঠিকানার ওপর নির্ভর করে, তাই এখানে উল্লেখ করা দরকার।

///

### DNS { #dns }

এখন HTTPS-এর আসল অংশগুলোতে মনোযোগ দিই।

প্রথমে, ব্রাউজার **DNS সার্ভারের** কাছে জানতে চাইবে **ডোমেইনের IP** কী, এই ক্ষেত্রে `someapp.example.com`।

DNS সার্ভার ব্রাউজারকে একটি নির্দিষ্ট **IP ঠিকানা** ব্যবহার করতে বলবে। সেটি হবে আপনার সার্ভারের ব্যবহৃত পাবলিক IP ঠিকানা, যা আপনি DNS সার্ভারে কনফিগার করেছিলেন।

(DNS হলো ইন্টারনেটের ফোনবুক: নাম দিলে নম্বর, অর্থাৎ IP ঠিকানা, বলে দেয়।)

### TLS Handshake শুরু { #tls-handshake-start }

তারপর ব্রাউজার সেই IP ঠিকানার সাথে **পোর্ট 443**-এ (HTTPS পোর্ট) যোগাযোগ করবে।

যোগাযোগের প্রথম অংশটি শুধু ক্লায়েন্ট আর সার্ভারের মধ্যে সংযোগ স্থাপন করা আর তারা কোন ক্রিপ্টোগ্রাফিক কী ব্যবহার করবে ইত্যাদি ঠিক করার জন্য।

<img src="/img/deployment/https/https02.drawio.svg">

TLS সংযোগ স্থাপনের জন্য ক্লায়েন্ট আর সার্ভারের এই আদান-প্রদানকে বলে **TLS handshake** (করমর্দন)।

### SNI এক্সটেনশনসহ TLS { #tls-with-sni-extension }

সার্ভারে একটি নির্দিষ্ট **IP ঠিকানার** একটি নির্দিষ্ট **পোর্টে** **শুধু একটি প্রসেস** শুনতে পারে। একই IP ঠিকানার অন্য পোর্টে অন্য প্রসেস শুনতে পারে, কিন্তু IP ঠিকানা আর পোর্টের প্রতিটি সমন্বয়ের জন্য শুধু একটি।

TLS (HTTPS) ডিফল্টভাবে নির্দিষ্ট পোর্ট `443` ব্যবহার করে। তাই আমাদের সেই পোর্টটিই লাগবে।

যেহেতু এই পোর্টে শুধু একটি প্রসেস শুনতে পারে, তাই যে প্রসেসটি এটি করবে সেটি হবে **TLS Termination Proxy**।

TLS Termination Proxy-এর কাছে এক বা একাধিক **TLS সার্টিফিকেট** (HTTPS সার্টিফিকেট) থাকবে।

ওপরে আলোচিত **SNI এক্সটেনশন** ব্যবহার করে, TLS Termination Proxy দেখবে উপলব্ধ TLS (HTTPS) সার্টিফিকেটগুলোর মধ্যে কোনটি এই সংযোগের জন্য ব্যবহার করতে হবে, ক্লায়েন্ট যে ডোমেইন আশা করছে তার সাথে মেলে এমনটি ব্যবহার করে।

এই ক্ষেত্রে, এটি `someapp.example.com`-এর সার্টিফিকেট ব্যবহার করবে।

<img src="/img/deployment/https/https03.drawio.svg">

ক্লায়েন্ট ইতিমধ্যে সেই প্রতিষ্ঠানকে **বিশ্বাস** করে যে ওই TLS সার্টিফিকেট তৈরি করেছে (এই ক্ষেত্রে Let's Encrypt, তবে এ নিয়ে পরে দেখব), তাই এটি **যাচাই** করতে পারে যে সার্টিফিকেটটি বৈধ।

তারপর, সার্টিফিকেট ব্যবহার করে, ক্লায়েন্ট আর TLS Termination Proxy **ঠিক করে কীভাবে এনক্রিপ্ট করবে** বাকি **TCP যোগাযোগ**। এতে **TLS Handshake** অংশটি সম্পূর্ণ হয়।

এরপর, ক্লায়েন্ট আর সার্ভারের একটি **এনক্রিপ্ট করা TCP সংযোগ** থাকে, এটাই TLS দেয়। তারপর তারা সেই সংযোগ ব্যবহার করে আসল **HTTP যোগাযোগ** শুরু করতে পারে।

আর এটাই **HTTPS**, এটি শুধু একটি সাধারণ **HTTP**, তবে খাঁটি (এনক্রিপ্ট না করা) TCP সংযোগের বদলে একটি **নিরাপদ TLS সংযোগের** ভেতরে।

/// tip | পরামর্শ

লক্ষ্য করুন, যোগাযোগের এনক্রিপশন হয় **TCP স্তরে**, HTTP স্তরে নয়।

///

### HTTPS রিকোয়েস্ট { #https-request }

এখন যেহেতু ক্লায়েন্ট আর সার্ভারের (নির্দিষ্টভাবে ব্রাউজার আর TLS Termination Proxy) একটি **এনক্রিপ্ট করা TCP সংযোগ** আছে, তারা **HTTP যোগাযোগ** শুরু করতে পারে।

তাই, ক্লায়েন্ট একটি **HTTPS রিকোয়েস্ট** পাঠায়। এটি শুধু একটি এনক্রিপ্ট করা TLS সংযোগের মধ্য দিয়ে একটি HTTP রিকোয়েস্ট।

<img src="/img/deployment/https/https04.drawio.svg">

### রিকোয়েস্ট ডিক্রিপ্ট করা { #decrypt-the-request }

TLS Termination Proxy সম্মত হওয়া এনক্রিপশন ব্যবহার করে **রিকোয়েস্টটি ডিক্রিপ্ট করবে**, আর **সাধারণ (ডিক্রিপ্ট করা) HTTP রিকোয়েস্টটি** অ্যাপ্লিকেশন চালানো প্রসেসে পাঠাবে (যেমন FastAPI অ্যাপ্লিকেশন চালানো Uvicorn-এর একটি প্রসেস)।

<img src="/img/deployment/https/https05.drawio.svg">

### HTTP রেসপন্স { #http-response }

অ্যাপ্লিকেশন রিকোয়েস্টটি প্রসেস করে TLS Termination Proxy-কে একটি **সাধারণ (এনক্রিপ্ট না করা) HTTP রেসপন্স** পাঠাবে।

<img src="/img/deployment/https/https06.drawio.svg">

### HTTPS রেসপন্স { #https-response }

তারপর TLS Termination Proxy আগে সম্মত হওয়া ক্রিপ্টোগ্রাফি (যা `someapp.example.com`-এর সার্টিফিকেট দিয়ে শুরু হয়েছিল) ব্যবহার করে **রেসপন্সটি এনক্রিপ্ট করবে**, আর ব্রাউজারে ফেরত পাঠাবে।

এরপর, ব্রাউজার যাচাই করবে যে রেসপন্সটি বৈধ আর সঠিক ক্রিপ্টোগ্রাফিক কী দিয়ে এনক্রিপ্ট করা, ইত্যাদি। তারপর এটি **রেসপন্সটি ডিক্রিপ্ট করে** প্রসেস করবে।

<img src="/img/deployment/https/https07.drawio.svg">

ক্লায়েন্ট (ব্রাউজার) জানবে যে রেসপন্সটি সঠিক সার্ভার থেকেই আসছে, কারণ এটি আগে **HTTPS সার্টিফিকেট** ব্যবহার করে সম্মত হওয়া ক্রিপ্টোগ্রাফি ব্যবহার করছে।

/// info | পুরো যাত্রা এক নজরে

1. ব্রাউজার DNS-কে জিজ্ঞেস করে: `someapp.example.com`-এর IP কী?
2. ব্রাউজার সেই IP-র পোর্ট 443-এ TLS handshake শুরু করে।
3. TLS Termination Proxy SNI দেখে সঠিক সার্টিফিকেট দেখায়, দুজনে গোপন চাবি ঠিক করে।
4. ব্রাউজার এনক্রিপ্ট করা HTTP রিকোয়েস্ট পাঠায়।
5. প্রক্সি ডিক্রিপ্ট করে FastAPI অ্যাপকে সাধারণ HTTP রিকোয়েস্ট দেয়।
6. FastAPI সাধারণ HTTP রেসপন্স ফেরত দেয়।
7. প্রক্সি এনক্রিপ্ট করে ব্রাউজারকে পাঠায়, ব্রাউজার ডিক্রিপ্ট করে দেখায়।

### একাধিক অ্যাপ্লিকেশন { #multiple-applications }

একই সার্ভারে (বা সার্ভারগুলোতে) **একাধিক অ্যাপ্লিকেশন** থাকতে পারে, যেমন অন্য API প্রোগ্রাম বা একটি ডেটাবেস।

নির্দিষ্ট IP আর পোর্টটি শুধু একটি প্রসেস সামলাতে পারে (আমাদের উদাহরণে TLS Termination Proxy), কিন্তু অন্য অ্যাপ্লিকেশন/প্রসেসগুলোও সার্ভারে চলতে পারে, যতক্ষণ না তারা একই **পাবলিক IP আর পোর্টের সমন্বয়** ব্যবহার করার চেষ্টা করে।

<img src="/img/deployment/https/https08.drawio.svg">

এভাবে, TLS Termination Proxy **একাধিক ডোমেইনের** জন্য, একাধিক অ্যাপ্লিকেশনের জন্য HTTPS আর সার্টিফিকেট সামলাতে পারে, আর তারপর প্রতিটি ক্ষেত্রে রিকোয়েস্টগুলো সঠিক অ্যাপ্লিকেশনে পাঠাতে পারে।

### সার্টিফিকেট নবায়ন { #certificate-renewal }

ভবিষ্যতে কোনো এক সময়ে, প্রতিটি সার্টিফিকেটের **মেয়াদ শেষ** হবে (সংগ্রহের প্রায় ৩ মাস পরে)।

আর তখন আরেকটি প্রোগ্রাম থাকবে (কিছু ক্ষেত্রে এটি আলাদা প্রোগ্রাম, কিছু ক্ষেত্রে একই TLS Termination Proxy হতে পারে) যা Let's Encrypt-এর সাথে কথা বলে সার্টিফিকেট(গুলো) নবায়ন করবে।

<img src="/img/deployment/https/https.drawio.svg">

**TLS সার্টিফিকেট** **একটি ডোমেইন নামের সাথে যুক্ত**, IP ঠিকানার সাথে নয়।

তাই, সার্টিফিকেট নবায়ন করতে, নবায়ন প্রোগ্রামকে কর্তৃপক্ষের (Let's Encrypt) কাছে **প্রমাণ** করতে হয় যে এটি সত্যিই **ওই ডোমেইনের "মালিক" আর নিয়ন্ত্রক**।

এটি করতে, আর বিভিন্ন অ্যাপ্লিকেশনের প্রয়োজন মেটাতে, এটি করার কয়েকটি উপায় আছে। কিছু জনপ্রিয় উপায়:

* **কিছু DNS রেকর্ড পরিবর্তন করা**।
    * এর জন্য নবায়ন প্রোগ্রামকে DNS প্রোভাইডারের API সাপোর্ট করতে হয়, তাই আপনি কোন DNS প্রোভাইডার ব্যবহার করছেন তার ওপর নির্ভর করে এটি একটি অপশন হতেও পারে, না-ও হতে পারে।
* ডোমেইনের সাথে যুক্ত পাবলিক IP ঠিকানায় **একটি সার্ভার হিসেবে চলা** (অন্তত সার্টিফিকেট সংগ্রহের প্রক্রিয়ার সময়)।
    * ওপরে যেমন বলেছি, একটি নির্দিষ্ট IP আর পোর্টে শুধু একটি প্রসেস শুনতে পারে।
    * এটি একটি কারণ, কেন একই TLS Termination Proxy-ই সার্টিফিকেট নবায়নের প্রক্রিয়াও সামলালে খুব সুবিধা হয়।
    * নইলে, আপনাকে হয়তো TLS Termination Proxy কিছুক্ষণের জন্য বন্ধ করতে হবে, সার্টিফিকেট সংগ্রহের জন্য নবায়ন প্রোগ্রাম চালু করতে হবে, তারপর সেগুলো TLS Termination Proxy-তে কনফিগার করতে হবে, তারপর TLS Termination Proxy আবার চালু করতে হবে। এটি আদর্শ নয়, কারণ TLS Termination Proxy বন্ধ থাকার সময় আপনার অ্যাপ(গুলো) পাওয়া যাবে না।

অ্যাপ চালু রেখেই এই পুরো নবায়ন প্রক্রিয়া, এটি একটি প্রধান কারণ কেন আপনি অ্যাপ্লিকেশন সার্ভারে (যেমন Uvicorn) সরাসরি TLS সার্টিফিকেট ব্যবহার না করে, TLS Termination Proxy দিয়ে **HTTPS সামলানোর একটি আলাদা ব্যবস্থা** রাখতে চাইবেন।

## প্রক্সির Forwarded হেডার { #proxy-forwarded-headers }

HTTPS সামলাতে একটি প্রক্সি ব্যবহার করলে, আপনার **অ্যাপ্লিকেশন সার্ভার** (যেমন FastAPI CLI-এর মাধ্যমে Uvicorn) HTTPS প্রক্রিয়া সম্পর্কে কিছুই জানে না, এটি **TLS Termination Proxy**-র সাথে সাধারণ HTTP-তে যোগাযোগ করে।

এই **প্রক্সি** সাধারণত **অ্যাপ্লিকেশন সার্ভারে** রিকোয়েস্ট পাঠানোর আগে তাৎক্ষণিকভাবে কিছু HTTP হেডার সেট করে, যাতে অ্যাপ্লিকেশন সার্ভার জানতে পারে যে রিকোয়েস্টটি প্রক্সির মাধ্যমে **ফরোয়ার্ড** (এগিয়ে দেওয়া) হচ্ছে।

/// note | কারিগরি বিবরণ

প্রক্সি হেডারগুলো হলো:

* [X-Forwarded-For](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For)
* [X-Forwarded-Proto](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-Proto)
* [X-Forwarded-Host](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-Host)

(সহজ ভাষায়: আসল ক্লায়েন্টের IP কী, আসল প্রোটোকল `https` ছিল কিনা, আর আসল ডোমেইন কী।)

///

তবুও, যেহেতু **অ্যাপ্লিকেশন সার্ভার** জানে না যে এটি একটি বিশ্বস্ত **প্রক্সির** পেছনে আছে, তাই ডিফল্টভাবে এটি ওই হেডারগুলো বিশ্বাস করবে না।

কিন্তু আপনি **অ্যাপ্লিকেশন সার্ভারকে** **প্রক্সির** পাঠানো *forwarded* হেডারগুলো বিশ্বাস করতে কনফিগার করতে পারেন। FastAPI CLI ব্যবহার করলে, `--forwarded-allow-ips` *CLI অপশন* দিয়ে বলে দিতে পারেন কোন IP থেকে আসা *forwarded* হেডার বিশ্বাস করতে হবে।

যেমন, যদি **অ্যাপ্লিকেশন সার্ভার** শুধু বিশ্বস্ত **প্রক্সি** থেকেই যোগাযোগ পায়, তাহলে এটিকে `--forwarded-allow-ips="*"` সেট করতে পারেন যাতে এটি সব আগত IP বিশ্বাস করে, কারণ এটি শুধু **প্রক্সির** ব্যবহৃত IP থেকেই রিকোয়েস্ট পাবে।

এভাবে অ্যাপ্লিকেশন জানতে পারবে এর নিজের পাবলিক URL কী, এটি HTTPS ব্যবহার করছে কিনা, ডোমেইন কী, ইত্যাদি।

এটি কাজে লাগবে, যেমন রিডাইরেক্ট সঠিকভাবে সামলাতে।

/// warning | সাধারণ ভুল

`--forwarded-allow-ips="*"` শুধু তখনই দিন যখন আপনার অ্যাপে সরাসরি বাইরে থেকে কেউ পৌঁছাতে পারে না, শুধু প্রক্সি দিয়েই পৌঁছায়। নইলে যে কেউ নকল `X-Forwarded-For` হেডার পাঠিয়ে নিজের IP লুকাতে পারবে।

## সংক্ষেপে { #recap }

**HTTPS** থাকা খুবই গুরুত্বপূর্ণ, আর বেশিরভাগ ক্ষেত্রে বেশ **জরুরি**। একজন ডেভেলপার হিসেবে HTTPS নিয়ে আপনার বেশিরভাগ পরিশ্রম শুধু **এই ধারণাগুলো বোঝা** আর এগুলো কীভাবে কাজ করে তা বোঝার মধ্যেই।

কিন্তু **ডেভেলপারদের জন্য HTTPS**-এর মৌলিক তথ্য জানা হয়ে গেলে, আপনি সহজেই বিভিন্ন টুল মিলিয়ে কনফিগার করে সবকিছু সহজভাবে পরিচালনা করতে পারবেন।

পরের কিছু অধ্যায়ে আমি আপনাকে **FastAPI** অ্যাপ্লিকেশনের জন্য **HTTPS** সেটআপ করার কয়েকটি বাস্তব উদাহরণ দেখাব। 🔒

/// check | সংক্ষেপে মনে রাখুন

* HTTPS = TLS-এর তালাবন্ধ সংযোগের ভেতরে সাধারণ HTTP।
* সার্টিফিকেট ডোমেইনের পরিচয়পত্র, Let's Encrypt বিনামূল্যে দেয়, প্রায় ৩ মাস পরপর নবায়ন লাগে।
* সাধারণত একটি TLS Termination Proxy (Traefik, Caddy, Nginx) HTTPS সামলায়, FastAPI ভেতরে সাধারণ HTTP পায়।
* প্রক্সির পেছনে থাকলে `--forwarded-allow-ips` দিয়ে forwarded হেডার বিশ্বাস করতে বলুন।
