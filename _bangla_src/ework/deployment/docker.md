# কন্টেইনারে FastAPI - Docker { #fastapi-in-containers-docker }

/// note | এই পেজে যা শিখবেন

* কন্টেইনার আর কন্টেইনার ইমেজ কী, সহজ ভাষায়।
* শূন্য থেকে FastAPI-এর জন্য একটি `Dockerfile` লেখা, প্রতিটি লাইনের ব্যাখ্যাসহ।
* Docker cache কাজে লাগিয়ে build দ্রুত করা।
* কন্টেইনার দিয়ে HTTPS, রিস্টার্ট, রেপ্লিকেশন, মেমোরি আর মাইগ্রেশন কীভাবে সামলানো হয়।

///

FastAPI অ্যাপ্লিকেশন ডিপ্লয় করার সময় একটি প্রচলিত পদ্ধতি হলো একটি **Linux কন্টেইনার ইমেজ** তৈরি করা। সাধারণত এটি করা হয় [**Docker**](https://www.docker.com/) ব্যবহার করে। তারপর সেই কন্টেইনার ইমেজ কয়েকটি সম্ভাব্য উপায়ের যেকোনো একটিতে ডিপ্লয় করতে পারেন।

Linux কন্টেইনার ব্যবহারের কয়েকটি সুবিধা আছে, যেমন **নিরাপত্তা**, **পুনরাবৃত্তিযোগ্যতা** (সবখানে একইভাবে চলা), **সরলতা**, এবং আরও কিছু।

/// tip | পরামর্শ

তাড়া আছে আর এসব আগে থেকেই জানেন? সরাসরি [নিচের `Dockerfile`-এ 👇](#build-a-docker-image-for-fastapi) চলে যান।

///

<summary>Dockerfile-এর এক ঝলক 👀</summary>

```Dockerfile
FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

COPY ./app /code/app

CMD ["fastapi", "run", "app/main.py", "--port", "80"]

# Nginx বা Traefik এর মতো প্রক্সির পেছনে চালালে --proxy-headers যোগ করুন
# CMD ["fastapi", "run", "app/main.py", "--port", "80", "--proxy-headers"]
```

## কন্টেইনার কী { #what-is-a-container }

কন্টেইনার (মূলত Linux কন্টেইনার) হলো অ্যাপ্লিকেশনকে তার সব ডিপেন্ডেন্সি আর দরকারি ফাইলসহ প্যাকেজ করার একটি খুবই **হালকা** উপায়, যেখানে একই সিস্টেমের অন্য কন্টেইনার (অন্য অ্যাপ্লিকেশন বা কম্পোনেন্ট) থেকে এদের আলাদা রাখা হয়।

Linux কন্টেইনারগুলো হোস্টের (মেশিন, ভার্চুয়াল মেশিন, ক্লাউড সার্ভার ইত্যাদি) একই Linux কার্নেল ব্যবহার করে চলে। এর মানে শুধু এই যে এগুলো খুবই হালকা (পুরো একটি অপারেটিং সিস্টেম অনুকরণ করা পূর্ণ ভার্চুয়াল মেশিনের তুলনায়)।

এভাবে কন্টেইনার **খুব কম রিসোর্স** খরচ করে, প্রসেস সরাসরি চালানোর মতোই প্রায় (একটি ভার্চুয়াল মেশিন অনেক বেশি খরচ করত)।

কন্টেইনারের নিজস্ব **আলাদা** চলমান প্রসেস (সাধারণত একটি মাত্র প্রসেস), ফাইল সিস্টেম আর নেটওয়ার্কও থাকে, যা ডিপ্লয়মেন্ট, নিরাপত্তা, ডেভেলপমেন্ট ইত্যাদি সহজ করে।

/// tip | উদাহরণ দিয়ে বুঝি

জাহাজের শিপিং কন্টেইনারের কথা ভাবুন। ভেতরে কাপড়, ইলেকট্রনিক্স বা ফল যা-ই থাকুক, বাইরে থেকে সব কন্টেইনার একই মাপের, তাই যেকোনো জাহাজ, ট্রাক বা ক্রেন এগুলো সামলাতে পারে। Docker কন্টেইনারও তেমন: ভেতরে আপনার অ্যাপ, Python-এর নির্দিষ্ট সংস্করণ, সব লাইব্রেরি। ফলে "আমার কম্পিউটারে তো চলছিল!" সমস্যা আর থাকে না, কারণ যেকোনো সার্ভারে ঠিক একই বাক্স চলে।

///

## কন্টেইনার ইমেজ কী { #what-is-a-container-image }

একটি **কন্টেইনার** চালানো হয় একটি **কন্টেইনার ইমেজ** থেকে।

একটি কন্টেইনার ইমেজ হলো সব ফাইল, এনভায়রনমেন্ট ভেরিয়েবল আর ডিফল্ট কমান্ড/প্রোগ্রামের একটি **স্থির (static)** সংস্করণ, যা একটি কন্টেইনারে থাকা উচিত। এখানে **স্থির** মানে কন্টেইনার **ইমেজটি** চলছে না, এটি চালানো হচ্ছে না, এটি শুধু প্যাকেজ করা ফাইল আর মেটাডেটা।

সংরক্ষিত স্থির বিষয়বস্তু "**কন্টেইনার ইমেজ**"-এর বিপরীতে, "**কন্টেইনার**" সাধারণত চলমান ইনস্ট্যান্সকে বোঝায়, যে জিনিসটি **চালানো** হচ্ছে।

যখন **কন্টেইনার** চালু হয়ে চলতে থাকে (একটি **কন্টেইনার ইমেজ** থেকে চালু হয়ে), এটি ফাইল, এনভায়রনমেন্ট ভেরিয়েবল ইত্যাদি তৈরি বা পরিবর্তন করতে পারে। সেই পরিবর্তনগুলো শুধু সেই কন্টেইনারেই থাকবে, কিন্তু মূল কন্টেইনার ইমেজে স্থায়ী হবে না (ডিস্কে সংরক্ষিত হবে না)।

একটি কন্টেইনার ইমেজকে তুলনা করা যায় **প্রোগ্রাম** ফাইল আর বিষয়বস্তুর সাথে, যেমন `python` আর কোনো ফাইল `main.py`।

আর **কন্টেইনার** নিজে (**কন্টেইনার ইমেজের** বিপরীতে) হলো ইমেজের আসল চলমান ইনস্ট্যান্স, যা তুলনীয় একটি **প্রসেসের** সাথে। আসলে, একটি কন্টেইনার শুধু তখনই চলে যখন এতে একটি **প্রসেস চলছে** (আর সাধারণত এটি একটি মাত্র প্রসেস)। এতে কোনো প্রসেস না চললে কন্টেইনার থেমে যায়।

/// tip | উদাহরণ দিয়ে বুঝি

কন্টেইনার ইমেজ হলো কেকের ছাঁচ (বা রেসিপি), আর কন্টেইনার হলো সেই ছাঁচে বানানো আসল কেক। এক ছাঁচ থেকে অনেক কেক বানানো যায়, আর কোনো কেকে আইসিং লাগালে ছাঁচ বদলায় না।

///

## কন্টেইনার ইমেজ { #container-images }

**কন্টেইনার ইমেজ** আর **কন্টেইনার** তৈরি ও পরিচালনার প্রধান টুলগুলোর একটি হলো Docker।

আর একটি পাবলিক [Docker Hub](https://hub.docker.com/) আছে, যেখানে অনেক টুল, পরিবেশ, ডেটাবেস আর অ্যাপ্লিকেশনের জন্য আগে থেকে তৈরি **অফিসিয়াল কন্টেইনার ইমেজ** আছে।

যেমন, একটি অফিসিয়াল [Python ইমেজ](https://hub.docker.com/_/python) আছে।

আর ডেটাবেসের মতো বিভিন্ন জিনিসের জন্য আরও অনেক ইমেজ আছে, যেমন:

* [PostgreSQL](https://hub.docker.com/_/postgres)
* [MySQL](https://hub.docker.com/_/mysql)
* [MongoDB](https://hub.docker.com/_/mongo)
* [Redis](https://hub.docker.com/_/redis), ইত্যাদি।

আগে থেকে তৈরি কন্টেইনার ইমেজ ব্যবহার করে বিভিন্ন টুল **একত্রিত** করে ব্যবহার করা খুবই সহজ। যেমন, একটি নতুন ডেটাবেস চেষ্টা করে দেখতে। বেশিরভাগ ক্ষেত্রে আপনি **অফিসিয়াল ইমেজগুলো** ব্যবহার করতে পারেন, আর শুধু এনভায়রনমেন্ট ভেরিয়েবল দিয়ে কনফিগার করতে পারেন।

এভাবে, অনেক ক্ষেত্রে আপনি কন্টেইনার আর Docker সম্পর্কে শিখে সেই জ্ঞান অনেক ভিন্ন ভিন্ন টুল আর কম্পোনেন্টের সাথে আবার ব্যবহার করতে পারেন।

তাই আপনি বিভিন্ন জিনিস নিয়ে **একাধিক কন্টেইনার** চালাবেন, যেমন একটি ডেটাবেস, একটি Python অ্যাপ্লিকেশন, একটি React ফ্রন্টএন্ড অ্যাপ্লিকেশনসহ একটি ওয়েব সার্ভার, আর তাদের অভ্যন্তরীণ নেটওয়ার্কের মাধ্যমে এগুলো একসাথে যুক্ত করবেন।

সব কন্টেইনার ব্যবস্থাপনা সিস্টেমে (যেমন Docker বা Kubernetes) এই নেটওয়ার্কিং ফিচারগুলো যুক্ত আছে।

## কন্টেইনার এবং প্রসেস { #containers-and-processes }

একটি **কন্টেইনার ইমেজ** সাধারণত এর মেটাডেটায় রাখে যে **কন্টেইনার** চালু হলে কোন ডিফল্ট প্রোগ্রাম বা কমান্ড চালাতে হবে আর সেই প্রোগ্রামে কোন প্যারামিটার দিতে হবে। কমান্ড লাইনে যেমন হতো তার খুবই কাছাকাছি।

যখন একটি **কন্টেইনার** চালু হয়, এটি সেই কমান্ড/প্রোগ্রাম চালাবে (যদিও আপনি এটি ওভাররাইড করে ভিন্ন কমান্ড/প্রোগ্রাম চালাতে পারেন)।

যতক্ষণ **মূল প্রসেস** (কমান্ড বা প্রোগ্রাম) চলছে, ততক্ষণ একটি কন্টেইনার চলে।

একটি কন্টেইনারে সাধারণত **একটি মাত্র প্রসেস** থাকে, তবে মূল প্রসেস থেকে সাবপ্রসেস চালু করাও সম্ভব, আর এভাবে একই কন্টেইনারে **একাধিক প্রসেস** থাকবে।

কিন্তু **অন্তত একটি চলমান প্রসেস** ছাড়া একটি চলমান কন্টেইনার থাকা সম্ভব নয়। মূল প্রসেস থামলে কন্টেইনার থেমে যায়।

## FastAPI-এর জন্য একটি Docker ইমেজ তৈরি করুন { #build-a-docker-image-for-fastapi }

ঠিক আছে, এবার কিছু তৈরি করি! 🚀

আমি দেখাব কীভাবে **অফিসিয়াল Python** ইমেজের ওপর ভিত্তি করে **শূন্য থেকে** FastAPI-এর জন্য একটি **Docker ইমেজ** তৈরি করতে হয়।

**বেশিরভাগ ক্ষেত্রে** আপনি এটাই করতে চাইবেন, যেমন:

* **Kubernetes** বা এমন টুল ব্যবহার করার সময়
* একটি **Raspberry Pi**-তে চালানোর সময়
* এমন একটি ক্লাউড সার্ভিস ব্যবহার করার সময় যা আপনার হয়ে একটি কন্টেইনার ইমেজ চালাবে, ইত্যাদি।

### প্যাকেজের প্রয়োজনীয়তা { #package-requirements }

যখন `uv` দিয়ে আপনার প্রজেক্ট পরিচালনা করেন, এর সরাসরি ডিপেন্ডেন্সিগুলো `pyproject.toml`-এ ঘোষণা করা থাকে আর ঠিক কোন সংস্করণ নির্বাচিত হয়েছে তা `uv.lock`-এ সংরক্ষিত থাকে।

আপনার অ্যাপ্লিকেশনের দরকারি প্যাকেজগুলো এভাবে যোগ করতে পারেন:

<div class="termy">

```console
$ uv add "fastapi[standard]" pydantic
---> 100%
```

</div>

/// note | নোট

নিচের Dockerfile কন্টেইনারের ভেতরে `pip` ব্যবহার করে। আপনার uv প্রজেক্ট থেকে লক করা ডিপেন্ডেন্সিগুলো এর প্রত্যাশিত `requirements.txt` ফরম্যাটে এক্সপোর্ট করতে পারেন:

<div class="termy">

```console
$ uv export --format requirements-txt --no-dev --no-emit-project --output-file requirements.txt
```

</div>

তৈরি হওয়া `requirements.txt` হলো কন্টেইনার build-এর জন্য একটি এক্সপোর্ট। ডিপেন্ডেন্সি পরিচালনা `uv add` দিয়েই চালিয়ে যান, আর `uv.lock` বদলালে এটি আবার তৈরি করুন।

### Dockerfile { #dockerfile }

এখন একই প্রজেক্ট ডিরেক্টরিতে একটি `Dockerfile` ফাইল তৈরি করুন, এতে লিখুন:

```{ .dockerfile .annotate }
# (1)!
FROM python:3.14

# (2)!
WORKDIR /code

# (3)!
COPY ./requirements.txt /code/requirements.txt

# (4)!
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# (5)!
COPY ./app /code/app

# (6)!
CMD ["fastapi", "run", "app/main.py", "--port", "80"]
```

1. অফিসিয়াল Python বেস ইমেজ থেকে শুরু করুন।

2. বর্তমান কাজের ডিরেক্টরি `/code` সেট করুন।

    এখানেই আমরা `requirements.txt` ফাইল আর `app` ডিরেক্টরি রাখব।

3. প্রয়োজনীয়তার ফাইলটি `/code` ডিরেক্টরিতে কপি করুন।

    প্রথমে **শুধু** প্রয়োজনীয়তার ফাইলটি কপি করুন, বাকি কোড নয়।

    যেহেতু এই ফাইলটি **খুব একটা বদলায় না**, Docker এটি শনাক্ত করে এই ধাপের জন্য **cache** ব্যবহার করবে, ফলে পরের ধাপের জন্যও cache চালু থাকবে।

4. প্রয়োজনীয়তার ফাইলে থাকা প্যাকেজ ডিপেন্ডেন্সিগুলো ইনস্টল করুন।

    `--no-cache-dir` অপশন `pip`-কে বলে ডাউনলোড করা প্যাকেজগুলো লোকালি সংরক্ষণ না করতে, কারণ সেটা শুধু তখনই দরকার যদি একই প্যাকেজ ইনস্টল করতে `pip` আবার চালানো হতো, কিন্তু কন্টেইনার নিয়ে কাজ করার সময় তা হয় না।

    /// note | নোট

    `--no-cache-dir` শুধু `pip`-এর সাথে সম্পর্কিত, Docker বা কন্টেইনারের সাথে এর কোনো সম্পর্ক নেই।

    ///

    `--upgrade` অপশন `pip`-কে বলে প্যাকেজগুলো ইতিমধ্যে ইনস্টল করা থাকলে সেগুলো আপগ্রেড করতে।

    যেহেতু ফাইল কপি করার আগের ধাপটি **Docker cache** শনাক্ত করতে পারে, তাই এই ধাপও উপলব্ধ থাকলে **Docker cache ব্যবহার করবে**।

    এই ধাপে cache ব্যবহার করলে ডেভেলপমেন্টের সময় বারবার ইমেজ তৈরি করার সময় আপনার অনেক **সময় বাঁচবে**, **প্রতিবার** সব ডিপেন্ডেন্সি **ডাউনলোড আর ইনস্টল** করার বদলে।

5. `./app` ডিরেক্টরিটি `/code` ডিরেক্টরির ভেতরে কপি করুন।

    যেহেতু এতে সব কোড আছে, যা **সবচেয়ে বেশি বদলায়**, তাই এই ধাপ বা **পরের কোনো ধাপের** জন্য Docker **cache** সহজে ব্যবহার হবে না।

    তাই কন্টেইনার ইমেজ build-এর সময় কমাতে এটি `Dockerfile`-এর **শেষের দিকে** রাখা গুরুত্বপূর্ণ।

6. `fastapi run` ব্যবহার করার জন্য **কমান্ড** সেট করুন, যা ভেতরে Uvicorn ব্যবহার করে।

    `CMD` স্ট্রিংয়ের একটি তালিকা নেয়, এই স্ট্রিংগুলোর প্রতিটি হলো কমান্ড লাইনে আপনি স্পেস দিয়ে আলাদা করে যা লিখতেন।

    এই কমান্ড চালানো হবে **বর্তমান কাজের ডিরেক্টরি** থেকে, অর্থাৎ ওপরে `WORKDIR /code` দিয়ে সেট করা সেই `/code` ডিরেক্টরি থেকে।

/// tip | পরামর্শ

কোডের প্রতিটি সংখ্যার বুদবুদে ক্লিক করে দেখুন প্রতিটি লাইন কী করে। 👆

#### `CMD` ব্যবহার করুন - Exec Form { #use-cmd-exec-form }

[`CMD`](https://docs.docker.com/reference/dockerfile/#cmd) Docker নির্দেশনা দুটি রূপে লেখা যায়:

✅ **Exec** form:

```Dockerfile
# ✅ এভাবে করুন
CMD ["fastapi", "run", "app/main.py", "--port", "80"]
```

⛔️ **Shell** form:

```Dockerfile
# ⛔️ এভাবে করবেন না
CMD fastapi run app/main.py --port 80
```

সবসময় **exec** form ব্যবহার করুন, যাতে FastAPI সুন্দরভাবে বন্ধ হতে পারে আর [lifespan ইভেন্ট](../advanced/events.md) চালু হয়।

(কারণ shell form-এ কমান্ডটি একটি শেলের ভেতরে চলে, ফলে Docker-এর পাঠানো "বন্ধ হও" সংকেত আপনার অ্যাপ পর্যন্ত পৌঁছায় না।)

এ নিয়ে আরও পড়তে পারেন [shell আর exec form নিয়ে Docker ডকসে](https://docs.docker.com/reference/dockerfile/#shell-and-exec-form)।

`docker compose` ব্যবহারের সময় এটি বেশ লক্ষণীয় হতে পারে। আরও কারিগরি বিবরণের জন্য এই Docker Compose FAQ অংশটি দেখুন: [Why do my services take 10 seconds to recreate or stop?](https://docs.docker.com/compose/faq/#why-do-my-services-take-10-seconds-to-recreate-or-stop)।

#### Docker Cache { #docker-cache }

এই `Dockerfile`-এ একটি গুরুত্বপূর্ণ কৌশল আছে: আমরা প্রথমে **শুধু ডিপেন্ডেন্সির ফাইলটি** কপি করি, বাকি কোড নয়। কেন, বলছি।

```Dockerfile
COPY ./requirements.txt /code/requirements.txt
```

Docker আর অন্যান্য টুল এই কন্টেইনার ইমেজগুলো **ধাপে ধাপে** **তৈরি** করে, **একটির ওপর আরেকটি স্তর (layer)** যোগ করে, `Dockerfile`-এর ওপর থেকে শুরু করে, আর `Dockerfile`-এর প্রতিটি নির্দেশনায় তৈরি হওয়া ফাইলগুলো যোগ করে।

ইমেজ তৈরির সময় Docker আর এমন টুলগুলো একটি **অভ্যন্তরীণ cache**-ও ব্যবহার করে। যদি শেষবার কন্টেইনার ইমেজ তৈরির পর থেকে একটি ফাইল না বদলায়, তাহলে এটি আবার ফাইল কপি করে শূন্য থেকে নতুন স্তর তৈরি করার বদলে, শেষবার তৈরি করা **একই স্তরটি আবার ব্যবহার করবে**।

শুধু ফাইল কপি এড়ানো হয়তো খুব বেশি উন্নতি আনে না, কিন্তু যেহেতু এটি সেই ধাপের জন্য cache ব্যবহার করেছে, তাই এটি **পরের ধাপের জন্যও cache ব্যবহার করতে পারে**। যেমন, ডিপেন্ডেন্সি ইনস্টল করার এই নির্দেশনার জন্য cache ব্যবহার করতে পারে:

```Dockerfile
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt
```

প্যাকেজের প্রয়োজনীয়তার ফাইলটি **খুব একটা বদলায় না**। তাই শুধু সেই ফাইলটি কপি করলে Docker সেই ধাপের জন্য **cache ব্যবহার করতে** পারবে।

আর তারপর, Docker সেই ডিপেন্ডেন্সিগুলো ডাউনলোড আর ইনস্টল করার **পরের ধাপের জন্যও cache ব্যবহার করতে** পারবে। আর এখানেই আমরা **অনেক সময় বাঁচাই**। ✨ ...আর অপেক্ষার একঘেয়েমি এড়াই। 😪😆

প্যাকেজ ডিপেন্ডেন্সি ডাউনলোড আর ইনস্টল করতে **কয়েক মিনিট লাগতে পারে**, কিন্তু **cache** ব্যবহার করলে বড়জোর **কয়েক সেকেন্ড লাগবে**।

আর যেহেতু ডেভেলপমেন্টের সময় আপনার কোডের পরিবর্তন কাজ করছে কিনা দেখতে বারবার কন্টেইনার ইমেজ তৈরি করবেন, তাই এতে জমে অনেক সময় বাঁচবে।

তারপর, `Dockerfile`-এর শেষের দিকে, আমরা সব কোড কপি করি। যেহেতু এটাই **সবচেয়ে বেশি বদলায়**, আমরা এটি শেষের দিকে রাখি, কারণ প্রায় সবসময় এই ধাপের পরের কিছুই cache ব্যবহার করতে পারবে না।

```Dockerfile
COPY ./app /code/app
```

/// tip | উদাহরণ দিয়ে বুঝি

ধরুন প্রতিদিন আপনি একটি কেক বানান। বেস (ময়দা, ডিম) প্রতিদিন একই, শুধু ওপরের সাজ বদলায়। বুদ্ধিমানের কাজ হলো বেস একবার বানিয়ে ফ্রিজে রাখা (cache), আর প্রতিদিন শুধু সাজটা নতুন করা। Dockerfile-এ ডিপেন্ডেন্সি (কম বদলায়) আগে আর কোড (বেশি বদলায়) পরে রাখার কারণ এটাই। উল্টো করলে, প্রতিবার কোডে একটি অক্ষর বদলালেও সব প্যাকেজ আবার ডাউনলোড হবে।

* `myimage`: কোন ইমেজ থেকে কন্টেইনার বানাতে হবে।

## যাচাই করুন { #check-it }

আপনার Docker কন্টেইনারের URL-এ এটি যাচাই করতে পারবেন, যেমন: [http://192.168.99.100/items/5?q=somequery](http://192.168.99.100/items/5?q=somequery) বা [http://127.0.0.1/items/5?q=somequery](http://127.0.0.1/items/5?q=somequery) (বা আপনার Docker হোস্ট ব্যবহার করে সমতুল্য কিছু)।

আপনি এমন কিছু দেখবেন:

```JSON
{"item_id": 5, "q": "somequery"}
```

## এক-ফাইলের FastAPI দিয়ে একটি Docker ইমেজ তৈরি করুন { #build-a-docker-image-with-a-single-file-fastapi }

যদি আপনার FastAPI একটি মাত্র ফাইল হয়, যেমন `./app` ডিরেক্টরি ছাড়া `main.py`, তাহলে আপনার ফাইল কাঠামো দেখতে এমন হতে পারে:

⟦CODE4⟧

তাহলে `Dockerfile`-এর ভেতরে ফাইল কপি করার সংশ্লিষ্ট পাথগুলো শুধু বদলাতে হবে:

```{ .dockerfile .annotate hl_lines="10  13" }
FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# (1)!
COPY ./main.py /code/

# (2)!
CMD ["fastapi", "run", "main.py", "--port", "80"]
```

1. `main.py` ফাইলটি সরাসরি `/code` ডিরেক্টরিতে কপি করুন (কোনো `./app` ডিরেক্টরি ছাড়া)।

2. এক ফাইল `main.py`-এ থাকা আপনার অ্যাপ্লিকেশন চালাতে `fastapi run` ব্যবহার করুন।

যখন `fastapi run`-এ ফাইলটি দেন, এটি স্বয়ংক্রিয়ভাবে শনাক্ত করবে যে এটি একটি মাত্র ফাইল, কোনো প্যাকেজের অংশ নয়, আর জানবে কীভাবে এটি ইমপোর্ট করে আপনার FastAPI অ্যাপ চালাতে হবে। 😎

## ডিপ্লয়মেন্টের ধারণা { #deployment-concepts }

কন্টেইনারের প্রেক্ষিতে একই [ডিপ্লয়মেন্টের ধারণাগুলো](concepts.md) নিয়ে আবার কথা বলি।

কন্টেইনার মূলত একটি অ্যাপ্লিকেশন **তৈরি আর ডিপ্লয়** করার প্রক্রিয়া সহজ করার একটি টুল, কিন্তু এই **ডিপ্লয়মেন্ট ধারণাগুলো** সামলানোর কোনো নির্দিষ্ট পদ্ধতি এটি চাপিয়ে দেয় না, আর কয়েকটি সম্ভাব্য কৌশল আছে।

**সুখবর** হলো, প্রতিটি ভিন্ন কৌশলেই সব ডিপ্লয়মেন্ট ধারণা কভার করার একটি উপায় আছে। 🎉

চলুন কন্টেইনারের প্রেক্ষিতে এই **ডিপ্লয়মেন্ট ধারণাগুলো** পর্যালোচনা করি:

* HTTPS
* কম্পিউটার চালু হলে নিজে থেকে চালু হওয়া
* রিস্টার্ট
* রেপ্লিকেশন (কতগুলো প্রসেস চলছে)
* মেমোরি
* চালু করার আগের ধাপগুলো

## HTTPS { #https }

যদি শুধু একটি FastAPI অ্যাপ্লিকেশনের **কন্টেইনার ইমেজে** (আর পরে চলমান **কন্টেইনারে**) মনোযোগ দিই, তাহলে HTTPS সাধারণত অন্য একটি টুল **বাইরে থেকে** সামলাবে।

এটি অন্য একটি কন্টেইনার হতে পারে, যেমন [Traefik](https://traefik.io/) দিয়ে, যা **HTTPS** আর **সার্টিফিকেটের** **স্বয়ংক্রিয়** সংগ্রহ সামলায়।

/// tip | পরামর্শ

Traefik-এর Docker, Kubernetes আর অন্যান্যের সাথে সংযোগ আছে, তাই এটি দিয়ে আপনার কন্টেইনারের জন্য HTTPS সেটআপ আর কনফিগার করা খুবই সহজ।

///

বিকল্পভাবে, একটি ক্লাউড প্রোভাইডার তাদের একটি সেবা হিসেবে HTTPS সামলাতে পারে (অ্যাপ্লিকেশন তখনো একটি কন্টেইনারে চলবে)।

## চালু হলেই চলা এবং রিস্টার্ট { #running-on-startup-and-restarts }

সাধারণত আপনার কন্টেইনার **চালু আর চালিয়ে রাখার** দায়িত্বে অন্য একটি টুল থাকে।

এটি সরাসরি **Docker**, **Docker Compose**, **Kubernetes**, একটি **ক্লাউড সার্ভিস** ইত্যাদি হতে পারে।

বেশিরভাগ (বা সব) ক্ষেত্রে, চালু হলে কন্টেইনার চালানো আর ব্যর্থ হলে রিস্টার্ট চালু করার একটি সহজ অপশন আছে। যেমন, Docker-এ এটি `--restart` কমান্ড লাইন অপশন।

কন্টেইনার ব্যবহার না করে অ্যাপ্লিকেশনগুলোকে চালু হলে চালানো আর রিস্টার্টসহ চালানো ঝামেলাপূর্ণ আর কঠিন হতে পারে। কিন্তু **কন্টেইনার নিয়ে কাজ করলে** বেশিরভাগ ক্ষেত্রে সেই সুবিধা ডিফল্টভাবেই থাকে। ✨

(যেমন `docker run -d --restart always ...` দিলে কম্পিউটার রিস্টার্ট হলে বা অ্যাপ ক্র্যাশ করলে Docker নিজেই কন্টেইনার আবার চালু করবে।)

## রেপ্লিকেশন - প্রসেসের সংখ্যা { #replication-number-of-processes }

যদি আপনার **Kubernetes**, Docker Swarm Mode, Nomad, বা একাধিক মেশিনে বিতরণকৃত কন্টেইনার পরিচালনার অন্য কোনো জটিল সিস্টেমসহ মেশিনের একটি <dfn title="কয়েকটি মেশিনের একটি দল, যেগুলো কোনোভাবে যুক্ত হয়ে একসাথে কাজ করার জন্য কনফিগার করা।">ক্লাস্টার</dfn> থাকে, তাহলে আপনি সম্ভবত প্রতিটি কন্টেইনারে একটি **প্রসেস ম্যানেজার** (যেমন ওয়ার্কারসহ Uvicorn) ব্যবহারের বদলে **ক্লাস্টার স্তরে** **রেপ্লিকেশন সামলাতে** চাইবেন।

Kubernetes-এর মতো ওই বিতরণকৃত কন্টেইনার ব্যবস্থাপনা সিস্টেমগুলোর একটিতে সাধারণত **কন্টেইনারের রেপ্লিকেশন** সামলানোর একটি সমন্বিত উপায় থাকে, আগত রিকোয়েস্টের জন্য **লোড ব্যালান্সিং** সাপোর্টসহ। সবই **ক্লাস্টার স্তরে**।

সেই ক্ষেত্রে, আপনি সম্ভবত [ওপরে ব্যাখ্যা করা](#dockerfile) মতো **শূন্য থেকে একটি Docker ইমেজ** তৈরি করতে চাইবেন, আপনার ডিপেন্ডেন্সি ইনস্টল করে, আর একাধিক Uvicorn ওয়ার্কারের বদলে **একটি মাত্র Uvicorn প্রসেস** চালিয়ে।

### লোড ব্যালান্সার { #load-balancer }

কন্টেইনার ব্যবহার করলে, সাধারণত আপনার কোনো কম্পোনেন্ট **মূল পোর্টে শুনবে**। এটি সম্ভবত অন্য একটি কন্টেইনার হতে পারে যা **HTTPS** সামলাতে একটি **TLS Termination Proxy**-ও, বা এমন কোনো টুল।

যেহেতু এই কম্পোনেন্ট রিকোয়েস্টের **ভার (load)** নিয়ে সেটি ওয়ার্কারদের মধ্যে (আশা করা যায়) **ভারসাম্যপূর্ণভাবে** ভাগ করবে, তাই একে সাধারণত **লোড ব্যালান্সার**-ও বলা হয়।

/// tip | পরামর্শ

HTTPS-এর জন্য ব্যবহৃত একই **TLS Termination Proxy** কম্পোনেন্টটি সম্ভবত একটি **লোড ব্যালান্সারও** হবে।

///

আর কন্টেইনার নিয়ে কাজ করার সময়, যে সিস্টেম দিয়ে আপনি এগুলো চালু আর পরিচালনা করেন, তাতেই ইতিমধ্যে অভ্যন্তরীণ টুল থাকবে যা সেই **লোড ব্যালান্সার** (যা একটি **TLS Termination Proxy**-ও হতে পারে) থেকে আপনার অ্যাপসহ কন্টেইনার(গুলো)তে **নেটওয়ার্ক যোগাযোগ** (যেমন HTTP রিকোয়েস্ট) পাঠাবে।

### একটি লোড ব্যালান্সার - একাধিক ওয়ার্কার কন্টেইনার { #one-load-balancer-multiple-worker-containers }

**Kubernetes** বা এমন বিতরণকৃত কন্টেইনার ব্যবস্থাপনা সিস্টেম নিয়ে কাজ করার সময়, তাদের অভ্যন্তরীণ নেটওয়ার্কিং ব্যবস্থা ব্যবহার করে মূল **পোর্টে** শুনতে থাকা একটি মাত্র **লোড ব্যালান্সার** আপনার অ্যাপ চালানো সম্ভাব্য **একাধিক কন্টেইনারে** যোগাযোগ (রিকোয়েস্ট) পাঠাতে পারবে।

আপনার অ্যাপ চালানো এই কন্টেইনারগুলোর প্রতিটিতে সাধারণত **শুধু একটি প্রসেস** থাকবে (যেমন আপনার FastAPI অ্যাপ্লিকেশন চালানো একটি Uvicorn প্রসেস)। এরা সবাই হবে **অভিন্ন কন্টেইনার**, একই জিনিস চালাবে, কিন্তু প্রত্যেকের নিজের প্রসেস, মেমোরি ইত্যাদি থাকবে। এভাবে আপনি CPU-র **ভিন্ন ভিন্ন কোরে**, বা এমনকি **ভিন্ন ভিন্ন মেশিনে** **সমান্তরাল কাজের** সুবিধা নেবেন।

আর **লোড ব্যালান্সারসহ** বিতরণকৃত কন্টেইনার সিস্টেম আপনার অ্যাপসহ প্রতিটি কন্টেইনারে **পালাক্রমে রিকোয়েস্ট ভাগ করবে**। তাই প্রতিটি রিকোয়েস্ট আপনার অ্যাপ চালানো একাধিক **রেপ্লিকেট করা কন্টেইনারের** যেকোনো একটি সামলাতে পারে।

আর সাধারণত এই **লোড ব্যালান্সার** আপনার ক্লাস্টারের *অন্য* অ্যাপে যাওয়া রিকোয়েস্টও সামলাতে পারবে (যেমন একটি ভিন্ন ডোমেইনে, বা একটি ভিন্ন URL পাথ প্রিফিক্সের নিচে), আর সেই যোগাযোগ আপনার ক্লাস্টারে চলা *সেই অন্য* অ্যাপ্লিকেশনের সঠিক কন্টেইনারে পাঠাবে।

### প্রতি কন্টেইনারে একটি প্রসেস { #one-process-per-container }

এই ধরনের পরিস্থিতিতে, আপনি সম্ভবত **প্রতি কন্টেইনারে একটি মাত্র (Uvicorn) প্রসেস** রাখতে চাইবেন, কারণ আপনি ইতিমধ্যে ক্লাস্টার স্তরে রেপ্লিকেশন সামলাচ্ছেন।

তাই এই ক্ষেত্রে আপনি কন্টেইনারে একাধিক ওয়ার্কার রাখতে চাইবেন **না**, যেমন `--workers` কমান্ড লাইন অপশন দিয়ে। আপনি প্রতি কন্টেইনারে শুধু **একটি মাত্র Uvicorn প্রসেস** রাখতে চাইবেন (কিন্তু সম্ভবত একাধিক কন্টেইনার)।

কন্টেইনারের ভেতরে আরেকটি প্রসেস ম্যানেজার রাখলে (একাধিক ওয়ার্কারের ক্ষেত্রে যেমন হতো) শুধু **অপ্রয়োজনীয় জটিলতা** যোগ হবে, যা আপনি সম্ভবত ইতিমধ্যে আপনার ক্লাস্টার সিস্টেম দিয়ে সামলাচ্ছেন।

### একাধিক প্রসেসসহ কন্টেইনার এবং বিশেষ ক্ষেত্র { #containers-with-multiple-processes-and-special-cases }

অবশ্যই, এমন **বিশেষ ক্ষেত্র** আছে যেখানে আপনি ভেতরে কয়েকটি **Uvicorn ওয়ার্কার প্রসেস**-সহ **একটি কন্টেইনার** রাখতে চাইতে পারেন।

সেই ক্ষেত্রে, যতগুলো ওয়ার্কার চালাতে চান তা সেট করতে `--workers` কমান্ড লাইন অপশন ব্যবহার করতে পারেন:

```{ .dockerfile .annotate }
FROM python:3.14

WORKDIR /code

COPY ./requirements.txt /code/requirements.txt

RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

COPY ./app /code/app

# (1)!
CMD ["fastapi", "run", "app/main.py", "--port", "80", "--workers", "4"]
```

1. এখানে আমরা ওয়ার্কারের সংখ্যা ৪ সেট করতে `--workers` কমান্ড লাইন অপশন ব্যবহার করছি।

এটি কখন যুক্তিসঙ্গত হতে পারে তার কিছু উদাহরণ:

#### একটি সহজ অ্যাপ { #a-simple-app }

যদি আপনার অ্যাপ্লিকেশন **যথেষ্ট সহজ** হয় যে এটি একটি ক্লাস্টারে নয়, **একটি মাত্র সার্ভারে** চালাতে পারেন, তাহলে কন্টেইনারে একটি প্রসেস ম্যানেজার চাইতে পারেন।

#### Docker Compose { #docker-compose }

আপনি হয়তো **Docker Compose** দিয়ে **একটি মাত্র সার্ভারে** (ক্লাস্টার নয়) ডিপ্লয় করছেন, তাই শেয়ার করা নেটওয়ার্ক আর **লোড ব্যালান্সিং** বজায় রেখে (Docker Compose দিয়ে) কন্টেইনারের রেপ্লিকেশন পরিচালনার সহজ উপায় আপনার থাকবে না।

তখন আপনি ভেতরে **কয়েকটি ওয়ার্কার প্রসেস** চালু করা একটি **প্রসেস ম্যানেজার**-সহ **একটি মাত্র কন্টেইনার** চাইতে পারেন।

---

মূল কথা হলো, এগুলোর **কোনোটিই** এমন **পাথরে খোদাই করা নিয়ম** নয় যা আপনাকে অন্ধভাবে মানতে হবে। এই ধারণাগুলো দিয়ে আপনি **নিজের ক্ষেত্রটি মূল্যায়ন** করে আপনার সিস্টেমের জন্য সেরা পদ্ধতি ঠিক করতে পারেন, এই ধারণাগুলো কীভাবে পরিচালনা করবেন তা দেখে:

* নিরাপত্তা - HTTPS
* কম্পিউটার চালু হলে নিজে থেকে চালু হওয়া
* রিস্টার্ট
* রেপ্লিকেশন (কতগুলো প্রসেস চলছে)
* মেমোরি
* চালু করার আগের ধাপগুলো

## মেমোরি { #memory }

যদি **প্রতি কন্টেইনারে একটি প্রসেস** চালান, তাহলে ওই প্রতিটি কন্টেইনারের খরচ করা মেমোরির পরিমাণ মোটামুটি সুনির্দিষ্ট, স্থির আর সীমিত থাকবে (রেপ্লিকেট করা হলে একাধিক)।

আর তারপর আপনার কন্টেইনার ব্যবস্থাপনা সিস্টেমের কনফিগারেশনে (যেমন **Kubernetes**-এ) সেই একই মেমোরি সীমা আর প্রয়োজনীয়তা সেট করতে পারেন। এভাবে এটি কন্টেইনারগুলোর দরকারি মেমোরির পরিমাণ আর ক্লাস্টারের মেশিনগুলোতে উপলব্ধ পরিমাণ বিবেচনা করে **উপলব্ধ মেশিনে** **কন্টেইনারগুলো রেপ্লিকেট** করতে পারবে।

যদি আপনার অ্যাপ্লিকেশন **সহজ** হয়, তাহলে এটি সম্ভবত **কোনো সমস্যা হবে না**, আর হয়তো কঠোর মেমোরি সীমা নির্দিষ্ট করার দরকারও হবে না। কিন্তু যদি আপনি **অনেক মেমোরি ব্যবহার করেন** (যেমন **মেশিন লার্নিং** মডেল দিয়ে), তাহলে আপনার কতটা মেমোরি খরচ হচ্ছে তা দেখে **প্রতিটি মেশিনে** চলা **কন্টেইনারের সংখ্যা** ঠিক করা উচিত (আর হয়তো আপনার ক্লাস্টারে আরও মেশিন যোগ করা উচিত)।

যদি **প্রতি কন্টেইনারে একাধিক প্রসেস** চালান, তাহলে আপনাকে নিশ্চিত করতে হবে যে চালু করা প্রসেসের সংখ্যা উপলব্ধ মেমোরির চেয়ে **বেশি মেমোরি খরচ** না করে।

## চালু করার আগের ধাপ এবং কন্টেইনার { #previous-steps-before-starting-and-containers }

যদি কন্টেইনার ব্যবহার করেন (যেমন Docker, Kubernetes), তাহলে দুটি প্রধান পদ্ধতি ব্যবহার করতে পারেন।

### একাধিক কন্টেইনার { #multiple-containers }

যদি আপনার **একাধিক কন্টেইনার** থাকে, সম্ভবত প্রতিটি **একটি মাত্র প্রসেস** চালাচ্ছে (যেমন একটি **Kubernetes** ক্লাস্টারে), তাহলে আপনি সম্ভবত রেপ্লিকেট করা ওয়ার্কার কন্টেইনারগুলো চালানোর **আগে**, একটি মাত্র প্রসেস চালানো একটি **আলাদা কন্টেইনার** রাখতে চাইবেন যা **আগের ধাপগুলোর** কাজ করবে।

/// note | নোট

যদি Kubernetes ব্যবহার করেন, তাহলে এটি সম্ভবত একটি [Init Container](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/) হবে।

///

যদি আপনার ক্ষেত্রে ওই আগের ধাপগুলো **সমান্তরালে একাধিকবার** চালাতে কোনো সমস্যা না থাকে (যেমন যদি আপনি ডেটাবেস মাইগ্রেশন না চালিয়ে শুধু দেখছেন ডেটাবেস প্রস্তুত কিনা), তাহলে মূল প্রসেস চালু করার ঠিক আগে প্রতিটি কন্টেইনারে এগুলো রাখতেও পারেন।

### একটি মাত্র কন্টেইনার { #single-container }

যদি আপনার একটি সহজ সেটআপ থাকে, যেখানে **একটি মাত্র কন্টেইনার** তারপর একাধিক **ওয়ার্কার প্রসেস** (বা শুধু একটি প্রসেস) চালু করে, তাহলে অ্যাপসহ প্রসেসটি চালু করার ঠিক আগে একই কন্টেইনারে ওই আগের ধাপগুলো চালাতে পারেন।

### বেস Docker ইমেজ { #base-docker-image }

একসময় একটি অফিসিয়াল FastAPI Docker ইমেজ ছিল: [tiangolo/uvicorn-gunicorn-fastapi](https://github.com/tiangolo/uvicorn-gunicorn-fastapi-docker)। কিন্তু এটি এখন পুরনো (deprecated)। ⛔️

আপনার সম্ভবত এই বেস Docker ইমেজ (বা এমন অন্য কোনোটি) ব্যবহার করা **উচিত নয়**।

যদি আপনি **Kubernetes** (বা অন্যগুলো) ব্যবহার করেন আর ইতিমধ্যে একাধিক **কন্টেইনার** দিয়ে ক্লাস্টার স্তরে **রেপ্লিকেশন** সেট করছেন, সেই ক্ষেত্রে ওপরে বর্ণিত মতো **শূন্য থেকে একটি ইমেজ তৈরি** করাই ভালো: [FastAPI-এর জন্য একটি Docker ইমেজ তৈরি করুন](#build-a-docker-image-for-fastapi)।

আর যদি একাধিক ওয়ার্কার দরকার হয়, তাহলে সহজভাবে `--workers` কমান্ড লাইন অপশন ব্যবহার করতে পারেন।

/// note | কারিগরি বিবরণ

Docker ইমেজটি তৈরি করা হয়েছিল যখন Uvicorn মৃত ওয়ার্কারদের পরিচালনা আর রিস্টার্ট সাপোর্ট করত না, তাই Uvicorn-এর সাথে Gunicorn ব্যবহার করতে হতো, যা শুধু Gunicorn-কে দিয়ে Uvicorn ওয়ার্কার প্রসেসগুলো পরিচালনা আর রিস্টার্ট করাতে বেশ কিছু জটিলতা যোগ করত।

কিন্তু এখন যেহেতু Uvicorn (আর `fastapi` কমান্ড) `--workers` ব্যবহার সাপোর্ট করে, তাই নিজের ইমেজ তৈরির বদলে একটি বেস Docker ইমেজ ব্যবহারের কোনো কারণ নেই (প্রায় একই পরিমাণ কোড 😅)।

## কন্টেইনার ইমেজ ডিপ্লয় করুন { #deploy-the-container-image }

একটি কন্টেইনার (Docker) ইমেজ হয়ে গেলে এটি ডিপ্লয় করার কয়েকটি উপায় আছে।

যেমন:

* একটি মাত্র সার্ভারে **Docker Compose** দিয়ে
* একটি **Kubernetes** ক্লাস্টার দিয়ে
* একটি Docker Swarm Mode ক্লাস্টার দিয়ে
* Nomad-এর মতো অন্য কোনো টুল দিয়ে
* এমন একটি ক্লাউড সার্ভিস দিয়ে যা আপনার কন্টেইনার ইমেজ নিয়ে ডিপ্লয় করে

## `uv`-সহ Docker ইমেজ { #docker-image-with-uv }

যদি আপনার প্রজেক্ট ইনস্টল আর পরিচালনার জন্য [uv](https://github.com/astral-sh/uv) ব্যবহার করেন, তাহলে তাদের [uv Docker গাইড](https://docs.astral.sh/uv/guides/integration/docker/) অনুসরণ করতে পারেন।

## সংক্ষেপে { #recap }

কন্টেইনার সিস্টেম ব্যবহার করে (যেমন **Docker** আর **Kubernetes** দিয়ে) সব **ডিপ্লয়মেন্ট ধারণা** সামলানো বেশ সহজ হয়ে যায়:

* HTTPS
* কম্পিউটার চালু হলে নিজে থেকে চালু হওয়া
* রিস্টার্ট
* রেপ্লিকেশন (কতগুলো প্রসেস চলছে)
* মেমোরি
* চালু করার আগের ধাপগুলো

বেশিরভাগ ক্ষেত্রে, আপনি সম্ভবত কোনো বেস ইমেজ ব্যবহার করতে চাইবেন না, বরং অফিসিয়াল Python Docker ইমেজের ওপর ভিত্তি করে **শূন্য থেকে একটি কন্টেইনার ইমেজ তৈরি** করবেন।

`Dockerfile`-এ নির্দেশনাগুলোর **ক্রম** আর **Docker cache**-এর দিকে খেয়াল রেখে আপনি **build-এর সময় কমাতে** পারেন, আপনার উৎপাদনশীলতা বাড়াতে (আর একঘেয়েমি এড়াতে)। 😎

/// check | সংক্ষেপে মনে রাখুন

* ইমেজ = ছাঁচ/রেসিপি, কন্টেইনার = সেই ইমেজ থেকে চলমান প্রসেস।
* `Dockerfile`-এ আগে `requirements.txt` কপি করে ইনস্টল, তারপর কোড কপি, এতে cache কাজে লাগে।
* `CMD` সবসময় exec form-এ: `CMD ["fastapi", "run", ...]`।
* `docker build -t myimage .` দিয়ে তৈরি, `docker run -d -p 80:80 myimage` দিয়ে চালান।
* Kubernetes-এ প্রতি কন্টেইনারে একটি প্রসেস, একা সার্ভারে দরকার হলে `--workers`।
