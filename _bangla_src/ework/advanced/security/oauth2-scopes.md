# OAuth2 scope { #oauth2-scopes }

/// note | এই পেজে যা শিখবেন

* scope কী: একটি টোকেনকে কোন কোন কাজের অনুমতি দেওয়া হয়েছে তার তালিকা।
* `OAuth2PasswordBearer`-এ scope ঘোষণা আর JWT টোকেনে scope রাখা।
* `Security(..., scopes=[...])` দিয়ে পাথ অপারেশন আর ডিপেন্ডেন্সিতে প্রয়োজনীয় scope ঘোষণা করা।
* `SecurityScopes` দিয়ে এক জায়গা থেকে সব scope যাচাই করা।

///

**FastAPI**-তে সরাসরি OAuth2 scope ব্যবহার করতে পারেন, এগুলো নির্বিঘ্নে কাজ করার জন্য একীভূত।

এতে OAuth2 স্ট্যান্ডার্ড অনুসরণ করে, আপনার OpenAPI অ্যাপ্লিকেশনে (আর API ডকুমেন্টেশনে) একীভূত, আরও সূক্ষ্ম একটি অনুমতি ব্যবস্থা রাখতে পারবেন।

Facebook, Google, GitHub, Microsoft, X (Twitter) ইত্যাদির মতো অনেক বড় অথেনটিকেশন প্রোভাইডার scope-সহ OAuth2 ব্যবস্থা ব্যবহার করে। তারা এটি ব্যবহারকারী আর অ্যাপ্লিকেশনগুলোকে নির্দিষ্ট অনুমতি দিতে ব্যবহার করে।

প্রতিবার যখন আপনি Facebook, Google, GitHub, Microsoft, X (Twitter) "দিয়ে লগইন করেন", তখন ওই অ্যাপ্লিকেশন scope-সহ OAuth2 ব্যবহার করছে।

/// tip | উদাহরণ দিয়ে বুঝি

কোনো অ্যাপে "Google দিয়ে লগইন" চাপলে Google জিজ্ঞেস করে: "এই অ্যাপ আপনার নাম ও ইমেইল দেখতে চায়, আর আপনার Drive-এর ফাইল পড়তে চায়। অনুমতি দেবেন?" প্রতিটি অনুমতি একেকটি scope। আপনি যতটুকু অনুমতি দেন, অ্যাপের টোকেন ঠিক ততটুকুই করতে পারে।

///

এই অংশে আপনি দেখবেন কীভাবে আপনার **FastAPI** অ্যাপ্লিকেশনে একই scope-সহ OAuth2 দিয়ে অথেনটিকেশন আর অথরাইজেশন সামলাবেন।

/// warning | সতর্কতা

এটি মোটামুটি একটি উন্নত অংশ। আপনি যদি সবে শুরু করে থাকেন, এটি বাদ দিতে পারেন।

OAuth2 scope আপনার অবশ্যই দরকার এমন নয়, আর অথেনটিকেশন ও অথরাইজেশন আপনি যেভাবে খুশি সামলাতে পারেন।

তবে scope-সহ OAuth2 আপনার API-তে (OpenAPI-সহ) আর আপনার API ডকুমেন্টেশনে সুন্দরভাবে একীভূত করা যায়।

তবুও, ওই scope বা অন্য যেকোনো সিকিউরিটি/অথরাইজেশনের শর্ত আপনার কোডে আপনি যেভাবে দরকার সেভাবেই প্রয়োগ করবেন।

অনেক ক্ষেত্রে scope-সহ OAuth2 প্রয়োজনের চেয়ে বেশি জটিল হতে পারে।

কিন্তু যদি জানেন যে আপনার এটি দরকার, বা কৌতূহলী হন, তাহলে পড়তে থাকুন।

///

## OAuth2 scope আর OpenAPI { #oauth2-scopes-and-openapi }

OAuth2 স্পেসিফিকেশন "scope"-কে স্পেস দিয়ে আলাদা করা স্ট্রিংয়ের একটি তালিকা হিসেবে সংজ্ঞায়িত করে।

এই প্রতিটি স্ট্রিংয়ের বিষয়বস্তু যেকোনো ফরম্যাটের হতে পারে, তবে এতে স্পেস থাকা উচিত নয়।

এই scope-গুলো "অনুমতি" উপস্থাপন করে।

OpenAPI-তে (যেমন API ডকুমেন্টেশনে) "সিকিউরিটি স্কিম" সংজ্ঞায়িত করতে পারেন।

যখন এই সিকিউরিটি স্কিমগুলোর একটি OAuth2 ব্যবহার করে, তখন scope-ও ঘোষণা ও ব্যবহার করতে পারেন।

প্রতিটি "scope" শুধু একটি স্ট্রিং (স্পেস ছাড়া)।

এগুলো সাধারণত নির্দিষ্ট সিকিউরিটি অনুমতি ঘোষণা করতে ব্যবহার হয়, যেমন:

* `users:read` বা `users:write` প্রচলিত উদাহরণ।
* Facebook / Instagram ব্যবহার করে `instagram_basic`।
* Google ব্যবহার করে `https://www.googleapis.com/auth/drive`।

/// note | নোট

OAuth2-তে একটি "scope" শুধু একটি স্ট্রিং, যা একটি নির্দিষ্ট প্রয়োজনীয় অনুমতি ঘোষণা করে।

এতে `:` এর মতো অন্য অক্ষর আছে কিনা বা এটি একটি URL কিনা, তাতে কিছু যায় আসে না।

ওই খুঁটিনাটিগুলো ইমপ্লিমেন্টেশনের ওপর নির্ভর করে।

OAuth2-এর কাছে এগুলো শুধুই স্ট্রিং।

## scope-সহ JWT টোকেন { #jwt-token-with-scopes }

এবার টোকেন *পাথ অপারেশনটি* বদলান, যাতে অনুরোধ করা scope-গুলো ফেরত দেয়।

আমরা এখনো একই `OAuth2PasswordRequestForm` ব্যবহার করছি। এতে একটি `scopes` প্রপার্টি আছে, রিকোয়েস্টে পাওয়া প্রতিটি scope-সহ `str`-এর একটি `list`।

আর আমরা JWT টোকেনের অংশ হিসেবে scope-গুলো ফেরত দিই।

/// danger | বিপদ

সহজ রাখতে, এখানে আমরা পাওয়া scope-গুলো সরাসরি টোকেনে যোগ করছি।

কিন্তু আপনার অ্যাপ্লিকেশনে নিরাপত্তার জন্য নিশ্চিত করা উচিত যে আপনি কেবল সেই scope-গুলোই যোগ করছেন যা ইউজারের আসলে পাওয়ার অধিকার আছে, বা যেগুলো আপনি আগে থেকে নির্ধারণ করেছেন। নইলে যে কেউ নিজেকে যেকোনো অনুমতি দিয়ে দিতে পারবে।

## *পাথ অপারেশন* আর ডিপেন্ডেন্সিতে scope ঘোষণা করুন { #declare-scopes-in-path-operations-and-dependencies }

এবার আমরা ঘোষণা করি যে `/users/me/items/`-এর *পাথ অপারেশনে* `items` scope লাগবে।

এর জন্য `fastapi` থেকে `Security` ইমপোর্ট করে ব্যবহার করি।

ডিপেন্ডেন্সি ঘোষণা করতে `Security` ব্যবহার করতে পারেন (ঠিক `Depends`-এর মতো), কিন্তু `Security` scope-এর (স্ট্রিং) একটি তালিকাসহ `scopes` প্যারামিটারও নেয়।

এই ক্ষেত্রে আমরা `Security`-তে একটি ডিপেন্ডেন্সি ফাংশন `get_current_active_user` দিই (`Depends`-এর সাথে যেমন করতাম)।

কিন্তু scope-এর একটি `list`-ও দিই, এই ক্ষেত্রে শুধু একটি scope: `items` (আরও থাকতে পারত)।

আর ডিপেন্ডেন্সি ফাংশন `get_current_active_user`-ও শুধু `Depends` দিয়েই নয়, `Security` দিয়েও সাব-ডিপেন্ডেন্সি ঘোষণা করতে পারে। নিজের সাব-ডিপেন্ডেন্সি ফাংশন (`get_current_user`) আর আরও scope-এর শর্ত ঘোষণা করে।

এই ক্ষেত্রে এর `me` scope লাগে (একাধিক scope-ও লাগতে পারত)।

/// note | নোট

বিভিন্ন জায়গায় বিভিন্ন scope যোগ করা আপনার অবশ্যই দরকার এমন নয়।

এখানে আমরা এটি করছি এটা দেখাতে যে **FastAPI** বিভিন্ন স্তরে ঘোষিত scope কীভাবে সামলায়।

/// note | কারিগরি বিবরণ

`Security` আসলে `Depends`-এর একটি সাব-ক্লাস, আর এতে শুধু একটি বাড়তি প্যারামিটার আছে যা পরে দেখব।

কিন্তু `Depends`-এর বদলে `Security` ব্যবহার করে **FastAPI** জানবে যে এটি সিকিউরিটি scope ঘোষণা করতে, ভেতরে সেগুলো ব্যবহার করতে আর OpenAPI দিয়ে API ডকুমেন্ট করতে পারে।

তবে `fastapi` থেকে `Query`, `Path`, `Depends`, `Security` ইত্যাদি ইমপোর্ট করলে সেগুলো আসলে এমন ফাংশন যা বিশেষ ক্লাস রিটার্ন করে।

## `SecurityScopes` ব্যবহার করুন { #use-securityscopes }

এবার `get_current_user` ডিপেন্ডেন্সিটি হালনাগাদ করুন।

ওপরের ডিপেন্ডেন্সিগুলো এটিকেই ব্যবহার করে।

এখানেই আমরা আগে তৈরি করা একই OAuth2 স্কিম একটি ডিপেন্ডেন্সি হিসেবে ঘোষণা করে ব্যবহার করছি: `oauth2_scheme`।

যেহেতু এই ডিপেন্ডেন্সি ফাংশনের নিজের কোনো scope-এর শর্ত নেই, তাই `oauth2_scheme`-এর সাথে `Depends` ব্যবহার করতে পারি, সিকিউরিটি scope নির্দিষ্ট করার দরকার না থাকলে `Security` ব্যবহার করতে হয় না।

আমরা `fastapi.security` থেকে ইমপোর্ট করা `SecurityScopes` টাইপের একটি বিশেষ প্যারামিটারও ঘোষণা করি।

এই `SecurityScopes` ক্লাসটি `Request`-এর মতো (`Request` ব্যবহার হতো সরাসরি রিকোয়েস্ট অবজেক্ট পেতে)।

## `scopes` ব্যবহার করুন { #use-the-scopes }

`security_scopes` প্যারামিটারটি হবে `SecurityScopes` টাইপের।

এতে একটি `scopes` প্রপার্টি থাকবে, যাতে একটি তালিকা থাকবে: এর নিজের আর যত ডিপেন্ডেন্সি এটিকে সাব-ডিপেন্ডেন্সি হিসেবে ব্যবহার করে তাদের সবার প্রয়োজনীয় সব scope। মানে সব "dependant"... এটা হয়তো বিভ্রান্তিকর শোনাচ্ছে, নিচে আবার ব্যাখ্যা করা হয়েছে।

`security_scopes` অবজেক্টটি (`SecurityScopes` ক্লাসের) একটি `scope_str` অ্যাট্রিবিউটও দেয়, যাতে ওই scope-গুলো স্পেস দিয়ে আলাদা করে একটিমাত্র স্ট্রিংয়ে থাকে (আমরা এটি ব্যবহার করব)।

আমরা একটি `HTTPException` তৈরি করি, যা পরে কয়েক জায়গায় পুনরায় ব্যবহার (`raise`) করতে পারি।

এই এক্সেপশনে আমরা প্রয়োজনীয় scope-গুলো (যদি থাকে) স্পেস দিয়ে আলাদা একটি স্ট্রিং হিসেবে (`scope_str` ব্যবহার করে) অন্তর্ভুক্ত করি। scope-সহ ওই স্ট্রিংটি `WWW-Authenticate` হেডারে রাখি (এটি স্পেসিফিকেশনের অংশ)।

## `username` আর ডেটার আকার যাচাই করুন { #verify-the-username-and-data-shape }

আমরা যাচাই করি যে একটি `username` পাচ্ছি কিনা, আর scope-গুলো বের করি।

তারপর Pydantic মডেল দিয়ে ওই ডেটা যাচাই করি (`ValidationError` এক্সেপশন ধরে), আর JWT টোকেন পড়তে বা Pydantic দিয়ে ডেটা যাচাই করতে এরর পেলে আগে তৈরি করা `HTTPException` রেইজ করি।

এর জন্য Pydantic মডেল `TokenData`-তে একটি নতুন প্রপার্টি `scopes` যোগ করি।

Pydantic দিয়ে ডেটা যাচাই করে আমরা নিশ্চিত হতে পারি যে, যেমন, আমাদের কাছে scope-সহ হুবহু `str`-এর একটি `list` আর `username`-সহ একটি `str` আছে।

এর বদলে, যেমন, একটি `dict` বা অন্য কিছু নয়, কারণ তাতে পরে কোনো এক সময় অ্যাপ্লিকেশন ভেঙে যেতে পারত, যা একটি নিরাপত্তা ঝুঁকি।

আমরা এটাও যাচাই করি যে ওই ইউজারনেমের একজন ইউজার আছে কিনা, আর না থাকলে আগে তৈরি করা সেই একই এক্সেপশন রেইজ করি।

## `scopes` যাচাই করুন { #verify-the-scopes }

এবার আমরা যাচাই করি যে এই ডিপেন্ডেন্সি আর সব dependant-এর (*পাথ অপারেশনসহ*) প্রয়োজনীয় সব scope পাওয়া টোকেনে দেওয়া scope-গুলোর মধ্যে আছে কিনা, না থাকলে একটি `HTTPException` রেইজ করি।

এর জন্য `security_scopes.scopes` ব্যবহার করি, যাতে এই সব scope `str` হিসেবে একটি `list`-এ আছে।

1. প্রয়োজনীয় scope থাকলে `WWW-Authenticate` হেডারে সেগুলো লেখা, এরর আগে থেকে তৈরি রাখা।
2. JWT ডিকোড করে `sub` (ইউজারনেম) আর `scope` (স্পেস দিয়ে আলাদা স্ট্রিং) বের করা।

4. ডেটাবেসে ইউজার খোঁজা।
5. প্রয়োজনীয় প্রতিটি scope টোকেনে আছে কিনা দেখা, না থাকলে "Not enough permissions" (যথেষ্ট অনুমতি নেই)।

## ডিপেন্ডেন্সি-গাছ আর scope { #dependency-tree-and-scopes }

এই ডিপেন্ডেন্সি-গাছ আর scope-গুলো আবার দেখে নেওয়া যাক।

যেহেতু `get_current_active_user` ডিপেন্ডেন্সির সাব-ডিপেন্ডেন্সি হিসেবে `get_current_user` আছে, তাই `get_current_active_user`-এ ঘোষিত `"me"` scope-টি `get_current_user`-এ পাঠানো `security_scopes.scopes`-এর প্রয়োজনীয় scope-এর তালিকায় অন্তর্ভুক্ত হবে।

*পাথ অপারেশন* নিজেও একটি scope ঘোষণা করে, `"items"`, তাই এটিও `get_current_user`-এ পাঠানো `security_scopes.scopes`-এর তালিকায় থাকবে।

ডিপেন্ডেন্সি আর scope-এর স্তরবিন্যাস দেখতে এমন:

* *পাথ অপারেশন* `read_own_items`-এ আছে:
    * এই ডিপেন্ডেন্সিসহ প্রয়োজনীয় scope `["items"]`:
    * `get_current_active_user`:
        *  ডিপেন্ডেন্সি ফাংশন `get_current_active_user`-এ আছে:
            * এই ডিপেন্ডেন্সিসহ প্রয়োজনীয় scope `["me"]`:
            * `get_current_user`:
                * ডিপেন্ডেন্সি ফাংশন `get_current_user`-এ আছে:
                    * নিজের কোনো প্রয়োজনীয় scope নেই।
                    * `oauth2_scheme` ব্যবহারকারী একটি ডিপেন্ডেন্সি।
                    * `SecurityScopes` টাইপের একটি `security_scopes` প্যারামিটার:
                        * এই `security_scopes` প্যারামিটারের একটি `scopes` প্রপার্টি আছে, যাতে ওপরে ঘোষিত এই সব scope-সহ একটি `list` থাকে, তাই:
                            * *পাথ অপারেশন* `read_own_items`-এর জন্য `security_scopes.scopes`-এ থাকবে `["me", "items"]`।
                            * *পাথ অপারেশন* `read_users_me`-এর জন্য `security_scopes.scopes`-এ থাকবে `["me"]`, কারণ এটি `get_current_active_user` ডিপেন্ডেন্সিতে ঘোষিত।
                            * *পাথ অপারেশন* `read_system_status`-এর জন্য `security_scopes.scopes`-এ থাকবে `[]` (কিছুই না), কারণ এটি `scopes`-সহ কোনো `Security` ঘোষণা করেনি, আর এর ডিপেন্ডেন্সি `get_current_user`-ও কোনো `scopes` ঘোষণা করে না।

/// tip | পরামর্শ

এখানে জরুরি আর "জাদুকরী" ব্যাপার হলো, প্রতিটি *পাথ অপারেশনের* জন্য `get_current_user`-এর যাচাই করার `scopes`-এর তালিকা আলাদা হবে।

সবই নির্ভর করে প্রতিটি *পাথ অপারেশন* আর ওই নির্দিষ্ট *পাথ অপারেশনের* ডিপেন্ডেন্সি-গাছের প্রতিটি ডিপেন্ডেন্সিতে ঘোষিত `scopes`-এর ওপর।

## `SecurityScopes` নিয়ে আরও বিস্তারিত { #more-details-about-securityscopes }

যেকোনো জায়গায়, আর একাধিক জায়গায় `SecurityScopes` ব্যবহার করতে পারেন, এটিকে "মূল" ডিপেন্ডেন্সিতেই থাকতে হবে এমন নয়।

এতে সবসময় বর্তমান `Security` ডিপেন্ডেন্সিগুলোতে আর **ওই নির্দিষ্ট** *পাথ অপারেশন* ও **ওই নির্দিষ্ট** ডিপেন্ডেন্সি-গাছের সব dependant-এ ঘোষিত সিকিউরিটি scope থাকবে।

যেহেতু `SecurityScopes`-এ dependant-দের ঘোষিত সব scope থাকবে, তাই একটি কেন্দ্রীয় ডিপেন্ডেন্সি ফাংশনে একটি টোকেনের প্রয়োজনীয় scope আছে কিনা যাচাই করতে এটি ব্যবহার করতে পারেন, আর তারপর বিভিন্ন *পাথ অপারেশনে* বিভিন্ন scope-এর শর্ত ঘোষণা করতে পারেন।

প্রতিটি *পাথ অপারেশনের* জন্য সেগুলো আলাদাভাবে যাচাই হবে।

## পরীক্ষা করুন { #check-it }

API ডকুমেন্টেশন খুললে আপনি অথেনটিকেট করে কোন scope-গুলো অনুমোদন করতে চান তা নির্দিষ্ট করতে পারবেন।

<img src="/img/tutorial/security/image11.png">

কোনো scope বেছে না নিলে আপনি "অথেনটিকেটেড" থাকবেন, কিন্তু `/users/me/` বা `/users/me/items/`-এ যাওয়ার চেষ্টা করলে যথেষ্ট অনুমতি নেই বলে একটি এরর পাবেন। তবে `/status/`-এ তখনও যেতে পারবেন।

আর আপনি যদি `me` scope বেছে নেন কিন্তু `items` scope না নেন, তাহলে `/users/me/`-এ যেতে পারবেন কিন্তু `/users/me/items/`-এ পারবেন না।

একজন ব্যবহারকারীর দেওয়া টোকেন দিয়ে এই *পাথ অপারেশনগুলোর* একটিতে যাওয়ার চেষ্টা করা একটি তৃতীয় পক্ষের অ্যাপ্লিকেশনের ক্ষেত্রে ঠিক এটাই ঘটত, ব্যবহারকারী অ্যাপ্লিকেশনটিকে কতগুলো অনুমতি দিয়েছেন তার ওপর নির্ভর করে।

## তৃতীয় পক্ষের ইন্টিগ্রেশন সম্পর্কে { #about-third-party-integrations }

এই উদাহরণে আমরা OAuth2 "password" flow ব্যবহার করছি।

এটি উপযুক্ত যখন আমরা আমাদের নিজের অ্যাপ্লিকেশনে, সম্ভবত আমাদের নিজের ফ্রন্টএন্ড দিয়ে লগইন করছি।

কারণ `username` আর `password` গ্রহণের জন্য আমরা এটির ওপর ভরসা করতে পারি, যেহেতু এটি আমাদের নিয়ন্ত্রণে।

কিন্তু আপনি যদি এমন একটি OAuth2 অ্যাপ্লিকেশন বানান যার সাথে অন্যরা যুক্ত হবে (অর্থাৎ, যদি আপনি Facebook, Google, GitHub ইত্যাদির সমতুল্য একটি অথেনটিকেশন প্রোভাইডার বানান), তাহলে অন্য flow-গুলোর একটি ব্যবহার করা উচিত।

সবচেয়ে প্রচলিত হলো implicit flow।

সবচেয়ে নিরাপদ হলো code flow, তবে এটি ইমপ্লিমেন্ট করা বেশি জটিল কারণ এতে বেশি ধাপ লাগে। বেশি জটিল হওয়ায় অনেক প্রোভাইডার শেষ পর্যন্ত implicit flow-এর পরামর্শ দেয়।

/// note | নোট

প্রতিটি অথেনটিকেশন প্রোভাইডারের নিজেদের ব্র্যান্ডের অংশ বানাতে নিজেদের flow-গুলোর ভিন্ন ভিন্ন নাম দেওয়া খুবই প্রচলিত।

কিন্তু শেষ পর্যন্ত তারা একই OAuth2 স্ট্যান্ডার্ড ইমপ্লিমেন্ট করছে।

## ডেকোরেটরের `dependencies`-এ `Security` { #security-in-decorator-dependencies }

ডেকোরেটরের `dependencies` প্যারামিটারে যেভাবে `Depends`-এর একটি `list` সংজ্ঞায়িত করতে পারেন (যেমন [পাথ অপারেশন ডেকোরেটরে ডিপেন্ডেন্সি](../../tutorial/dependencies/dependencies-in-path-operation-decorators.md)-তে বোঝানো হয়েছে), সেভাবেই সেখানে `scopes`-সহ `Security`-ও ব্যবহার করতে পারেন।

/// check | সংক্ষেপে মনে রাখুন

* scope = টোকেনের অনুমতির তালিকা, যেমন `items`, `me`, `users:write`।
* `OAuth2PasswordBearer(tokenUrl="token", scopes={"me": "...", "items": "..."})` দিয়ে ঘোষণা।
* টোকেন তৈরির সময় `"scope": " ".join(form_data.scopes)` (কিন্তু শুধু ইউজারের প্রাপ্য scope-গুলোই রাখুন)।
* প্রয়োজনীয় scope: `Security(dependency, scopes=["items"])`।
* কেন্দ্রীয় ডিপেন্ডেন্সিতে `security_scopes: SecurityScopes` নিয়ে সব প্রয়োজনীয় scope একসাথে যাচাই করুন।
