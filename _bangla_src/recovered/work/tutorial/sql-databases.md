# SQL (রিলেশনাল) ডেটাবেস { #sql-relational-databases }

**FastAPI** আপনাকে SQL (রিলেশনাল) ডেটাবেস ব্যবহার করতে বাধ্য করে না। আপনি আপনার পছন্দের **যেকোনো ডেটাবেস** ব্যবহার করতে পারেন।

এখানে আমরা [SQLModel](https://sqlmodel.tiangolo.com/) ব্যবহার করে একটি উদাহরণ দেখব।

**SQLModel** তৈরি হয়েছে [SQLAlchemy](https://www.sqlalchemy.org/) ও Pydantic-এর ওপর ভিত্তি করে। **SQL ডেটাবেস** ব্যবহার করতে হয় এমন FastAPI অ্যাপ্লিকেশনের জন্য একদম উপযুক্ত হিসেবে **FastAPI**-এর একই লেখক এটি তৈরি করেছেন।

/// tip | পরামর্শ

আপনি আপনার পছন্দের অন্য যেকোনো SQL বা NoSQL ডেটাবেস লাইব্রেরি ব্যবহার করতে পারেন (কিছু ক্ষেত্রে যেগুলোকে <abbr title="Object Relational Mapper - অবজেক্ট রিলেশনাল ম্যাপার: এমন একটি লাইব্রেরির গালভরা নাম যেখানে কিছু ক্লাস SQL টেবিলকে এবং ইনস্ট্যান্সগুলো ওই টেবিলের সারিকে উপস্থাপন করে">"ORM"</abbr> বলা হয়), FastAPI আপনাকে কোনো কিছু ব্যবহারে বাধ্য করে না। 😎

///

যেহেতু SQLModel SQLAlchemy-এর ওপর ভিত্তি করে তৈরি, তাই আপনি সহজেই SQLAlchemy-এর **সাপোর্ট করা যেকোনো ডেটাবেস** ব্যবহার করতে পারেন (যা সেগুলোকে SQLModel-এও সাপোর্টেড করে), যেমন:

* PostgreSQL
* MySQL
* SQLite
* Oracle
* Microsoft SQL Server ইত্যাদি।

এই উদাহরণে আমরা **SQLite** ব্যবহার করব, কারণ এটি একটিমাত্র ফাইল ব্যবহার করে এবং Python-এ এর অন্তর্নির্মিত সাপোর্ট আছে। তাই আপনি এই উদাহরণটি কপি করে যেমন আছে তেমনই চালাতে পারবেন।

পরে, আপনার প্রোডাকশন অ্যাপ্লিকেশনের জন্য, আপনি হয়তো **PostgreSQL**-এর মতো একটি ডেটাবেস সার্ভার ব্যবহার করতে চাইবেন।

/// tip | পরামর্শ

**FastAPI** ও **PostgreSQL**-সহ একটি অফিসিয়াল প্রজেক্ট জেনারেটর আছে, যাতে একটি ফ্রন্টএন্ড ও আরও টুল অন্তর্ভুক্ত: [https://github.com/fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template)

## একটিমাত্র মডেলসহ অ্যাপ তৈরি করুন { #create-the-app-with-a-single-model }

প্রথমে আমরা একটিমাত্র **SQLModel** মডেলসহ অ্যাপটির সবচেয়ে সহজ প্রথম ভার্সন তৈরি করব।

পরে নিচে **একাধিক মডেল** দিয়ে সিকিউরিটি ও বহুমুখিতা বাড়িয়ে আমরা এটিকে উন্নত করব। 🤓

`SQLModel` ইম্পোর্ট করে একটি ডেটাবেস মডেল তৈরি করুন:

{* ../../docs_src/sql_databases/tutorial001_an_py310.py ln[1:11] hl[7:11] *}

`Hero` ক্লাসটি একটি Pydantic মডেলের খুবই অনুরূপ (আসলে, ভেতরে ভেতরে এটি সত্যিই *একটি Pydantic মডেল*)।

কয়েকটি পার্থক্য আছে:

* `table=True` SQLModel-কে জানায় যে এটি একটি *টেবিল মডেল*, এটি SQL ডেটাবেসে একটি **টেবিল** উপস্থাপন করবে, এটি শুধু একটি *ডেটা মডেল* নয় (অন্য যেকোনো সাধারণ Pydantic ক্লাস যেমন হতো)।

* `Field(primary_key=True)` SQLModel-কে জানায় যে `id` হলো SQL ডেটাবেসে **প্রাইমারি কী** (SQL প্রাইমারি কী সম্পর্কে SQLModel ডকুমেন্টেশনে আরও জানতে পারবেন)।

    **নোট:** আমরা প্রাইমারি কী ফিল্ডের জন্য `int | None` ব্যবহার করি, যাতে Python কোডে আমরা *`id` ছাড়া একটি অবজেক্ট তৈরি করতে পারি* (`id=None`), এই ধরে নিয়ে যে ডেটাবেস *সংরক্ষণের সময় এটি তৈরি করবে*। SQLModel বোঝে যে ডেটাবেস `id` দেবে এবং ডেটাবেস স্কিমায় *কলামটিকে একটি non-null `INTEGER` হিসেবে সংজ্ঞায়িত করে*। বিস্তারিত জানতে [প্রাইমারি কী নিয়ে SQLModel ডকুমেন্টেশন](https://sqlmodel.tiangolo.com/tutorial/create-db-and-table/#primary-key-id) দেখুন।

* `Field(index=True)` SQLModel-কে জানায় যে এই কলামের জন্য একটি **SQL ইনডেক্স** তৈরি করতে হবে, যা এই কলাম দিয়ে ফিল্টার করা ডেটা পড়ার সময় ডেটাবেসে দ্রুত খোঁজার সুযোগ দেবে।

    SQLModel জানবে যে `str` হিসেবে ঘোষিত কিছু হবে `TEXT` (বা ডেটাবেস অনুযায়ী `VARCHAR`) টাইপের একটি SQL কলাম।

### একটি Engine তৈরি করুন { #create-an-engine }

একটি SQLModel `engine` (ভেতরে ভেতরে এটি আসলে একটি SQLAlchemy `engine`) হলো সেই জিনিস যা ডেটাবেসের সাথে **কানেকশনগুলো ধরে রাখে**।

একই ডেটাবেসে কানেক্ট করতে আপনার সব কোডের জন্য **একটিমাত্র `engine` অবজেক্ট** থাকবে।

{* ../../docs_src/sql_databases/tutorial001_an_py310.py ln[14:18] hl[14:15,17:18] *}

`check_same_thread=False` ব্যবহার করলে FastAPI ভিন্ন ভিন্ন থ্রেডে একই SQLite ডেটাবেস ব্যবহার করতে পারে। এটি প্রয়োজনীয়, কারণ **একটিমাত্র রিকোয়েস্ট** **একাধিক থ্রেড** ব্যবহার করতে পারে (যেমন ডিপেন্ডেন্সিতে)।

চিন্তা করবেন না, কোড যেভাবে সাজানো তাতে পরে আমরা নিশ্চিত করব যে **প্রতি রিকোয়েস্টে একটিমাত্র SQLModel *সেশন*** ব্যবহার করছি, আসলে `check_same_thread` এটিই অর্জনের চেষ্টা করছে।

### একটি সেশন ডিপেন্ডেন্সি তৈরি করুন { #create-a-session-dependency }

একটি **`Session`** হলো সেই জিনিস যা **মেমরিতে অবজেক্টগুলো** সংরক্ষণ করে এবং ডেটাতে প্রয়োজনীয় যেকোনো পরিবর্তনের হিসাব রাখে, তারপর ডেটাবেসের সাথে যোগাযোগ করতে **`engine` ব্যবহার করে**।

আমরা `yield`-সহ একটি FastAPI **ডিপেন্ডেন্সি** তৈরি করব যা প্রতিটি রিকোয়েস্টের জন্য একটি নতুন `Session` দেবে। এটিই নিশ্চিত করে যে আমরা প্রতি রিকোয়েস্টে একটিমাত্র সেশন ব্যবহার করছি। 🤓

### একটি Hero তৈরি করুন { #create-a-hero }

## একাধিক মডেল দিয়ে অ্যাপ আপডেট করুন { #update-the-app-with-multiple-models }

এবার **সিকিউরিটি** ও **বহুমুখিতা** বাড়াতে এই অ্যাপটিকে একটু **রিফ্যাক্টর** করা যাক।

আগের অ্যাপটি দেখলে UI-তে দেখতে পাবেন যে এখন পর্যন্ত এটি তৈরি করার জন্য `Hero`-এর `id` ক্লায়েন্টকে ঠিক করতে দেয়। 😱

আমাদের এটি হতে দেওয়া উচিত নয়, তারা DB-তে আগে থেকে অ্যাসাইন করা একটি `id` ওভাররাইট করে ফেলতে পারে। `id` ঠিক করার কাজ **ব্যাকএন্ড** বা **ডেটাবেসের**, **ক্লায়েন্টের নয়**।

এছাড়া আমরা hero-র জন্য একটি `secret_name` তৈরি করি, কিন্তু এখন পর্যন্ত এটি সব জায়গায় রিটার্ন করছি, যা খুব একটা **গোপন** নয়... 😅

কয়েকটি **অতিরিক্ত মডেল** যোগ করে আমরা এগুলো ঠিক করব। এখানেই SQLModel ঝলমল করবে। ✨

### একাধিক মডেল তৈরি করুন { #create-multiple-models }

**SQLModel**-এ যে মডেল ক্লাসে `table=True` আছে সেটি একটি **টেবিল মডেল**।

আর যে মডেল ক্লাসে `table=True` নেই সেটি একটি **ডেটা মডেল**, এগুলো আসলে শুধুই Pydantic মডেল (সাথে কয়েকটি ছোট অতিরিক্ত ফিচার)। 🤓

SQLModel-এ সব ক্ষেত্রে সব ফিল্ডের **পুনরাবৃত্তি এড়াতে** আমরা **ইনহেরিটেন্স** ব্যবহার করতে পারি।

#### `HeroBase` - বেস ক্লাস { #herobase-the-base-class }

চলুন একটি `HeroBase` মডেল দিয়ে শুরু করি, যাতে সব মডেলের **শেয়ার করা সব ফিল্ড** আছে:

* `name`
* `age`

#### `Hero` - *টেবিল মডেল* { #hero-the-table-model }

তারপর আসল *টেবিল মডেল* `Hero` তৈরি করা যাক, সেই **অতিরিক্ত ফিল্ডগুলোসহ** যেগুলো অন্য মডেলগুলোতে সবসময় থাকে না:

* `id`
* `secret_name`

যেহেতু `Hero` `HeroBase` থেকে ইনহেরিট করে, তাই এতে `HeroBase`-এ ঘোষিত **ফিল্ডগুলোও** আছে, অর্থাৎ `Hero`-এর সব ফিল্ড হলো:

* `id`
* `name`
* `age`
* `secret_name`

#### `HeroPublic` - পাবলিক *ডেটা মডেল* { #heropublic-the-public-data-model }

এরপর আমরা একটি `HeroPublic` মডেল তৈরি করি, এটিই API-এর ক্লায়েন্টদের কাছে **রিটার্ন করা** হবে।

এতে `HeroBase`-এর মতো একই ফিল্ড আছে, তাই এতে `secret_name` থাকবে না।

অবশেষে আমাদের hero-দের পরিচয় সুরক্ষিত হলো! 🥷

এটি `id: int`-ও পুনরায় ঘোষণা করে। এটি করে আমরা API ক্লায়েন্টদের সাথে একটি **চুক্তি** করছি, যাতে তারা সবসময় আশা করতে পারে যে `id` থাকবে এবং এটি একটি `int` হবে (এটি কখনো `None` হবে না)।

/// tip | পরামর্শ

রিটার্ন মডেল যদি নিশ্চিত করে যে একটি ভ্যালু সবসময় পাওয়া যাবে এবং সবসময় `int` হবে (`None` নয়), তাহলে তা API ক্লায়েন্টদের জন্য খুবই কাজের, এই নিশ্চয়তা থাকলে তারা অনেক সহজ কোড লিখতে পারে।

এছাড়া **স্বয়ংক্রিয়ভাবে তৈরি ক্লায়েন্টগুলোর** ইন্টারফেসও সহজ হবে, ফলে আপনার API-এর সাথে যোগাযোগকারী ডেভেলপাররা আপনার API নিয়ে কাজ করতে অনেক বেশি স্বাচ্ছন্দ্য পাবেন। 😎

`HeroPublic`-এর সব ফিল্ড `HeroBase`-এর মতোই, শুধু `id` ঘোষিত `int` হিসেবে (`None` নয়):

* `id`
* `name`
* `age`

#### `HeroCreate` - hero তৈরির *ডেটা মডেল* { #herocreate-the-data-model-to-create-a-hero }

এবার আমরা একটি `HeroCreate` মডেল তৈরি করি, এটিই ক্লায়েন্টদের ডেটা **ভ্যালিডেট** করবে।

এতে `HeroBase`-এর মতো একই ফিল্ড আছে, আর `secret_name`-ও আছে।

এখন ক্লায়েন্টরা যখন **একজন নতুন hero তৈরি** করবে, তারা `secret_name` পাঠাবে, এটি ডেটাবেসে সংরক্ষিত হবে, কিন্তু ওই গোপন নামগুলো API-তে ক্লায়েন্টদের কাছে রিটার্ন করা হবে না।

/// tip | পরামর্শ

**পাসওয়ার্ড** এভাবেই সামলাবেন। এগুলো গ্রহণ করুন, কিন্তু API-তে রিটার্ন করবেন না।

সংরক্ষণের আগে পাসওয়ার্ডের ভ্যালুগুলো **হ্যাশও** করবেন, **কখনো প্লেইন টেক্সটে সংরক্ষণ করবেন না**।

* `name`
* `age`
* `secret_name`

#### `HeroUpdate` - hero আপডেটের *ডেটা মডেল* { #heroupdate-the-data-model-to-update-a-hero }

অ্যাপের আগের ভার্সনে **hero আপডেট** করার কোনো উপায় ছিল না, কিন্তু এখন **একাধিক মডেল** দিয়ে আমরা এটি করতে পারি। 🎉

`HeroUpdate` *ডেটা মডেলটি* কিছুটা বিশেষ, এতে একজন নতুন hero তৈরিতে যা যা লাগত **সেই একই সব ফিল্ড** আছে, তবে সব ফিল্ড **ঐচ্ছিক** (সবগুলোর একটি ডিফল্ট ভ্যালু আছে)। এভাবে একজন hero আপডেট করার সময় আপনি কেবল যে ফিল্ডগুলো আপডেট করতে চান সেগুলোই পাঠাতে পারেন।

যেহেতু সব **ফিল্ড আসলে পরিবর্তিত হয়** (টাইপে এখন `None` আছে এবং এখন এগুলোর ডিফল্ট ভ্যালু `None`), তাই আমাদের সেগুলো **পুনরায় ঘোষণা** করতে হবে।

যেহেতু আমরা সব ফিল্ড পুনরায় ঘোষণা করছি, তাই `HeroBase` থেকে ইনহেরিট করার আসলে দরকার নেই। আমি শুধু সামঞ্জস্যের জন্য এটিকে ইনহেরিট করা অবস্থায় রেখে দিচ্ছি, তবে এটি প্রয়োজনীয় নয়। এটি বরং ব্যক্তিগত রুচির ব্যাপার। 🤷

`HeroUpdate`-এর ফিল্ডগুলো হলো:

* `name`
* `age`
* `secret_name`

### `HeroCreate` দিয়ে তৈরি করুন এবং একটি `HeroPublic` রিটার্ন করুন { #create-with-herocreate-and-return-a-heropublic }

এখন যেহেতু আমাদের **একাধিক মডেল** আছে, তাই অ্যাপের যে অংশগুলো এগুলো ব্যবহার করে সেগুলো আপডেট করতে পারি।

আমরা রিকোয়েস্টে একটি `HeroCreate` *ডেটা মডেল* পাই, এবং তা থেকে একটি `Hero` *টেবিল মডেল* তৈরি করি।

এই নতুন *টেবিল মডেল* `Hero`-তে ক্লায়েন্টের পাঠানো ফিল্ডগুলো থাকবে, আর ডেটাবেসের তৈরি করা একটি `id`-ও থাকবে।

তারপর আমরা ফাংশন থেকে একই *টেবিল মডেল* `Hero` যেমন আছে তেমনই রিটার্ন করি। কিন্তু যেহেতু আমরা `HeroPublic` *ডেটা মডেল* দিয়ে `response_model` ঘোষণা করেছি, তাই ডেটা ভ্যালিডেট ও সিরিয়ালাইজ করতে **FastAPI** `HeroPublic` ব্যবহার করবে।

{* ../../docs_src/sql_databases/tutorial002_an_py310.py ln[56:62] hl[56:58] *}

/// tip | পরামর্শ

এখন আমরা **রিটার্ন টাইপ অ্যানোটেশন** `-> HeroPublic`-এর বদলে `response_model=HeroPublic` ব্যবহার করি, কারণ আমরা যে ভ্যালু রিটার্ন করছি তা আসলে একটি `HeroPublic` *নয়*।

আমরা যদি `-> HeroPublic` ঘোষণা করতাম, তাহলে আপনার এডিটর ও লিন্টার আপত্তি জানাত (এবং তা যথার্থই) যে আপনি একটি `HeroPublic`-এর বদলে একটি `Hero` রিটার্ন করছেন।

`response_model`-এ এটি ঘোষণা করে আমরা **FastAPI**-কে তার কাজ করতে বলছি, টাইপ অ্যানোটেশন এবং আপনার এডিটর ও অন্যান্য টুলের সাহায্যে কোনো হস্তক্ষেপ না করে।

## সংক্ষেপে { #recap }

একটি SQL ডেটাবেসের সাথে কাজ করতে এবং *ডেটা মডেল* ও *টেবিল মডেল* দিয়ে কোড সহজ করতে আপনি [**SQLModel**](https://sqlmodel.tiangolo.com/) ব্যবহার করতে পারেন।

**SQLModel** ডকুমেন্টেশনে আপনি আরও অনেক কিছু শিখতে পারবেন, সেখানে [**FastAPI**-এর সাথে SQLModel ব্যবহার নিয়ে](https://sqlmodel.tiangolo.com/tutorial/fastapi/) একটি আরও দীর্ঘ মিনি টিউটোরিয়াল আছে। 🚀
