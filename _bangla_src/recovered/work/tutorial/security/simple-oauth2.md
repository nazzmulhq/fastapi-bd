# পাসওয়ার্ড ও Bearer-সহ সহজ OAuth2 { #simple-oauth2-with-password-and-bearer }

এবার আগের অধ্যায় থেকে এগিয়ে একটি সম্পূর্ণ সিকিউরিটি প্রবাহের জন্য অনুপস্থিত অংশগুলো যোগ করা যাক।

## `username` ও `password` পান { #get-the-username-and-password }

`username` ও `password` পেতে আমরা **FastAPI**-এর সিকিউরিটি ইউটিলিটি ব্যবহার করব।

OAuth2 নির্দিষ্ট করে যে "password flow" (যা আমরা ব্যবহার করছি) ব্যবহারের সময় ক্লায়েন্ট/ইউজারকে ফর্ম ডেটা হিসেবে `username` ও `password` ফিল্ড পাঠাতে হবে।

আর স্পেক বলে যে ফিল্ডগুলোর নাম অবশ্যই এরকমই হতে হবে। তাই `user-name` বা `email` কাজ করবে না।

তবে চিন্তা করবেন না, ফ্রন্টএন্ডে আপনার চূড়ান্ত ইউজারদের কাছে আপনি এটি যেভাবে খুশি দেখাতে পারেন।

আর আপনার ডেটাবেস মডেলগুলো আপনার পছন্দের অন্য যেকোনো নাম ব্যবহার করতে পারে।

কিন্তু লগইন *পাথ অপারেশনের* জন্য, স্পেকের সাথে সামঞ্জস্যপূর্ণ থাকতে (এবং যেমন, অন্তর্ভুক্ত API ডকুমেন্টেশন সিস্টেম ব্যবহার করতে পারার জন্য) আমাদের এই নামগুলোই ব্যবহার করতে হবে।

স্পেকে এটাও বলা আছে যে `username` ও `password` অবশ্যই ফর্ম ডেটা হিসেবে পাঠাতে হবে (তাই এখানে JSON নয়)।

### `scope` { #scope }

স্পেকে এটাও বলা আছে যে ক্লায়েন্ট আরেকটি ফর্ম ফিল্ড "`scope`" পাঠাতে পারে।

ফর্ম ফিল্ডের নাম `scope` (একবচনে), তবে এটি আসলে স্পেস দিয়ে আলাদা করা "scope"-গুলোর একটি লম্বা স্ট্রিং।

প্রতিটি "scope" শুধু একটি স্ট্রিং (স্পেস ছাড়া)।

এগুলো সাধারণত নির্দিষ্ট সিকিউরিটি অনুমতি ঘোষণা করতে ব্যবহার হয়, যেমন:

* `users:read` বা `users:write` প্রচলিত উদাহরণ।
* `instagram_basic` Facebook / Instagram ব্যবহার করে।
* `https://www.googleapis.com/auth/drive` Google ব্যবহার করে।

/// note | নোট

OAuth2-তে একটি "scope" হলো শুধু একটি স্ট্রিং যা প্রয়োজনীয় একটি নির্দিষ্ট অনুমতি ঘোষণা করে।

এতে `:`-এর মতো অন্য অক্ষর থাকুক বা এটি একটি URL হোক, তাতে কিছু যায় আসে না।

ওই বিবরণগুলো বাস্তবায়ন-নির্দিষ্ট।

OAuth2-এর কাছে এগুলো শুধুই স্ট্রিং।

///

## `username` ও `password` পাওয়ার কোড { #code-to-get-the-username-and-password }

এবার এটি সামলাতে **FastAPI**-এর দেওয়া ইউটিলিটিগুলো ব্যবহার করা যাক।

### `OAuth2PasswordRequestForm` { #oauth2passwordrequestform }

প্রথমে `OAuth2PasswordRequestForm` ইম্পোর্ট করুন, এবং `/token`-এর *পাথ অপারেশনে* `Depends` দিয়ে এটিকে ডিপেন্ডেন্সি হিসেবে ব্যবহার করুন:

{* ../../docs_src/security/tutorial003_an_py310.py hl[4,78] *}

`OAuth2PasswordRequestForm` হলো একটি ক্লাস ডিপেন্ডেন্সি যা এগুলোসহ একটি ফর্ম বডি ঘোষণা করে:

* `username`।
* `password`।
* স্পেস দিয়ে আলাদা করা স্ট্রিং নিয়ে গঠিত একটি বড় স্ট্রিং হিসেবে একটি ঐচ্ছিক `scope` ফিল্ড।
* একটি ঐচ্ছিক `grant_type`।

/// tip | পরামর্শ

OAuth2 স্পেক আসলে `password` নির্দিষ্ট ভ্যালুসহ একটি `grant_type` ফিল্ড *আবশ্যক করে*, কিন্তু `OAuth2PasswordRequestForm` এটি বাধ্যতামূলক করে না।

আপনার যদি এটি বাধ্যতামূলক করতে হয়, তাহলে `OAuth2PasswordRequestForm`-এর বদলে `OAuth2PasswordRequestFormStrict` ব্যবহার করুন।

///

* একটি ঐচ্ছিক `client_id` (আমাদের উদাহরণে এটি দরকার নেই)।
* একটি ঐচ্ছিক `client_secret` (আমাদের উদাহরণে এটি দরকার নেই)।

/// note | নোট

`OAuth2PasswordRequestForm` **FastAPI**-এর জন্য `OAuth2PasswordBearer`-এর মতো কোনো বিশেষ ক্লাস নয়।

`OAuth2PasswordBearer` **FastAPI**-কে জানায় যে এটি একটি সিকিউরিটি স্কিম। তাই এটি সেভাবেই OpenAPI-তে যোগ হয়।

কিন্তু `OAuth2PasswordRequestForm` শুধু একটি ক্লাস ডিপেন্ডেন্সি, যা আপনি নিজেই লিখতে পারতেন, অথবা সরাসরি `Form` প্যারামিটার ঘোষণা করতে পারতেন।

তবে যেহেতু এটি একটি প্রচলিত ব্যবহারের ক্ষেত্র, তাই কাজ সহজ করতে **FastAPI** এটি সরাসরি দেয়।

///

### ফর্ম ডেটা ব্যবহার করুন { #use-the-form-data }

/// tip | পরামর্শ

ডিপেন্ডেন্সি ক্লাস `OAuth2PasswordRequestForm`-এর ইনস্ট্যান্সে স্পেস দিয়ে আলাদা করা লম্বা স্ট্রিংসহ কোনো `scope` অ্যাট্রিবিউট থাকবে না, তার বদলে পাঠানো প্রতিটি scope-এর জন্য স্ট্রিংয়ের আসল লিস্টসহ একটি `scopes` অ্যাট্রিবিউট থাকবে।

এই উদাহরণে আমরা `scopes` ব্যবহার করছি না, তবে আপনার দরকার হলে কার্যকারিতাটি আছে।

### পাসওয়ার্ড যাচাই করুন { #check-the-password }

এই পর্যায়ে আমাদের ডেটাবেস থেকে ইউজারের ডেটা আমাদের কাছে আছে, কিন্তু পাসওয়ার্ড যাচাই করিনি।

প্রথমে সেই ডেটা Pydantic `UserInDB` মডেলে রাখা যাক।

আপনার কখনো প্লেইনটেক্সট পাসওয়ার্ড সংরক্ষণ করা উচিত নয়, তাই আমরা (নকল) পাসওয়ার্ড হ্যাশিং সিস্টেম ব্যবহার করব।

পাসওয়ার্ড না মিললে আমরা একই এরর রিটার্ন করি।

#### পাসওয়ার্ড হ্যাশিং { #password-hashing }

"হ্যাশিং" মানে: কোনো বিষয়বস্তুকে (এক্ষেত্রে একটি পাসওয়ার্ড) বাইটের একটি ক্রমে (শুধু একটি স্ট্রিং) রূপান্তর করা, যা দেখতে অর্থহীন হিজিবিজির মতো।

যখনই আপনি হুবহু একই বিষয়বস্তু (হুবহু একই পাসওয়ার্ড) দেবেন, হুবহু একই হিজিবিজি পাবেন।

কিন্তু আপনি হিজিবিজি থেকে আবার পাসওয়ার্ডে রূপান্তর করতে পারবেন না।

##### কেন পাসওয়ার্ড হ্যাশিং ব্যবহার করবেন { #why-use-password-hashing }

আপনার ডেটাবেস চুরি হলে চোরের কাছে আপনার ইউজারদের প্লেইনটেক্সট পাসওয়ার্ড থাকবে না, কেবল হ্যাশগুলো থাকবে।

তাই চোর ওই একই পাসওয়ার্ড অন্য কোনো সিস্টেমে ব্যবহারের চেষ্টা করতে পারবে না (যেহেতু অনেক ইউজার সব জায়গায় একই পাসওয়ার্ড ব্যবহার করেন, তাই এটি বিপজ্জনক হতো)।

## টোকেন রিটার্ন করুন { #return-the-token }

`token` এন্ডপয়েন্টের রেসপন্স অবশ্যই একটি JSON অবজেক্ট হতে হবে।

এতে একটি `token_type` থাকা উচিত। আমাদের ক্ষেত্রে, যেহেতু আমরা "Bearer" টোকেন ব্যবহার করছি, তাই টোকেন টাইপ হওয়া উচিত "`bearer`"।

আর এতে একটি `access_token` থাকা উচিত, যাতে আমাদের অ্যাক্সেস টোকেনসহ একটি স্ট্রিং থাকবে।

এই সহজ উদাহরণের জন্য আমরা পুরোপুরি অনিরাপদভাবে টোকেন হিসেবে একই `username` রিটার্ন করব।

/// tip | পরামর্শ

পরের অধ্যায়ে আপনি পাসওয়ার্ড হ্যাশিং ও <abbr title="JSON Web Tokens - JSON ওয়েব টোকেন">JWT</abbr> টোকেনসহ একটি সত্যিকারের নিরাপদ বাস্তবায়ন দেখবেন।

তবে আপাতত আমাদের প্রয়োজনীয় নির্দিষ্ট বিবরণগুলোতে মনোযোগ দেওয়া যাক।

///

/// tip | পরামর্শ

স্পেক অনুযায়ী, এই উদাহরণের মতোই আপনার একটি `access_token` ও একটি `token_type`-সহ একটি JSON রিটার্ন করা উচিত।

এটি এমন কিছু যা আপনাকে নিজের কোডে নিজেই করতে হবে, এবং নিশ্চিত করতে হবে যে আপনি ওই JSON কী-গুলো ব্যবহার করছেন।

স্পেসিফিকেশন মেনে চলার জন্য এটিই প্রায় একমাত্র জিনিস যা আপনাকে নিজে সঠিকভাবে করার কথা মনে রাখতে হবে।

বাকিগুলো **FastAPI** আপনার হয়ে সামলায়।

## ডিপেন্ডেন্সিগুলো আপডেট করুন { #update-the-dependencies }

এবার আমরা আমাদের ডিপেন্ডেন্সিগুলো আপডেট করব।

আমরা `current_user` পেতে চাই *কেবল* যদি এই ইউজার সক্রিয় থাকেন।

তাই আমরা একটি অতিরিক্ত ডিপেন্ডেন্সি `get_current_active_user` তৈরি করি, যা আবার `get_current_user`-কে ডিপেন্ডেন্সি হিসেবে ব্যবহার করে।

ইউজার না থাকলে বা নিষ্ক্রিয় থাকলে এই দুটি ডিপেন্ডেন্সিই শুধু একটি HTTP এরর রিটার্ন করবে।

/// note | নোট

এখানে আমরা যে `Bearer` ভ্যালুসহ অতিরিক্ত হেডার `WWW-Authenticate` রিটার্ন করছি, সেটিও স্পেকের অংশ।

## সংক্ষেপে { #recap }

এখন আপনার কাছে আপনার API-এর জন্য `username` ও `password`-ভিত্তিক একটি সম্পূর্ণ সিকিউরিটি সিস্টেম বাস্তবায়নের টুল আছে।

এই টুলগুলো ব্যবহার করে আপনি সিকিউরিটি সিস্টেমকে যেকোনো ডেটাবেস এবং যেকোনো ইউজার বা ডেটা মডেলের সাথে সামঞ্জস্যপূর্ণ করতে পারেন।

একমাত্র অনুপস্থিত বিষয় হলো এটি আসলে এখনো "নিরাপদ" নয়।

পরের অধ্যায়ে আপনি দেখবেন কীভাবে একটি নিরাপদ পাসওয়ার্ড হ্যাশিং লাইব্রেরি এবং <abbr title="JSON Web Tokens - JSON ওয়েব টোকেন">JWT</abbr> টোকেন ব্যবহার করতে হয়।
