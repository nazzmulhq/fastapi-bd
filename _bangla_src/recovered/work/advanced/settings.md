# সেটিংস ও এনভায়রনমেন্ট ভেরিয়েবল { #settings-and-environment-variables }

অনেক ক্ষেত্রে আপনার অ্যাপ্লিকেশনের কিছু বাহ্যিক সেটিংস বা কনফিগারেশন দরকার হতে পারে, যেমন সিক্রেট কী, ডেটাবেস ক্রেডেনশিয়াল, ইমেইল সার্ভিসের ক্রেডেনশিয়াল ইত্যাদি।

এই সেটিংসগুলোর বেশিরভাগই পরিবর্তনশীল (বদলাতে পারে), যেমন ডেটাবেস URL। আর অনেকগুলো সংবেদনশীল হতে পারে, যেমন সিক্রেট।

এ কারণে এগুলো সাধারণত এনভায়রনমেন্ট ভেরিয়েবলে দেওয়া হয়, যা অ্যাপ্লিকেশন পড়ে নেয়।

একটি **এনভায়রনমেন্ট ভেরিয়েবল** (**env var** নামেও পরিচিত) হলো এমন একটি ভ্যালু যা Python কোডের বাইরে, অপারেটিং সিস্টেমে থাকে, এবং আপনার অ্যাপ্লিকেশন ও অন্যান্য প্রোগ্রাম এটি পড়তে পারে।

কোনো কমান্ড চালানোর সময় আপনি তার জন্য একটি এনভায়রনমেন্ট ভেরিয়েবল তৈরি করতে পারেন। প্ল্যাটফর্ম-নির্দিষ্ট কমান্ডগুলো নিচে দেখবেন।

/// tip | পরামর্শ

এনভায়রনমেন্ট ভেরিয়েবল কীভাবে কাজ করে তার বিস্তারিত ব্যাখ্যার জন্য [এনভায়রনমেন্ট ভেরিয়েবল গাইড](https://tiangolo.com/guides/environment-variables/) পড়ুন।

///

## টাইপ ও ভ্যালিডেশন { #types-and-validation }

এই এনভায়রনমেন্ট ভেরিয়েবলগুলো কেবল টেক্সট স্ট্রিং সামলাতে পারে, কারণ এগুলো Python-এর বাইরের এবং অন্যান্য প্রোগ্রাম ও সিস্টেমের বাকি অংশের সাথে (এমনকি Linux, Windows ও macOS-এর মতো ভিন্ন ভিন্ন অপারেটিং সিস্টেমের সাথেও) সামঞ্জস্যপূর্ণ হতে হয়।

এর মানে Python-এ একটি এনভায়রনমেন্ট ভেরিয়েবল থেকে পড়া যেকোনো ভ্যালু হবে একটি `str`, এবং ভিন্ন টাইপে যেকোনো রূপান্তর বা যেকোনো ভ্যালিডেশন কোডে করতে হবে।

## একটি `.env` ফাইল পড়া { #reading-a-env-file }

আপনার যদি অনেক সেটিংস থাকে যেগুলো সম্ভবত অনেক বদলায়, হয়তো বিভিন্ন এনভায়রনমেন্টে, তাহলে সেগুলো একটি ফাইলে রেখে এমনভাবে পড়া কাজে আসতে পারে যেন সেগুলো এনভায়রনমেন্ট ভেরিয়েবল।

এই চর্চাটি এতটাই প্রচলিত যে এর একটি নাম আছে, এই এনভায়রনমেন্ট ভেরিয়েবলগুলো সাধারণত একটি `.env` ফাইলে রাখা হয়, এবং ফাইলটিকে বলা হয় একটি "dotenv"।

/// tip | পরামর্শ

ডট (`.`) দিয়ে শুরু হওয়া ফাইল Linux ও macOS-এর মতো Unix-ধর্মী সিস্টেমে একটি লুকানো ফাইল।

তবে একটি dotenv ফাইলের নাম আসলে হুবহু এটিই হতে হবে এমন নয়।

তারপর পরবর্তী রিকোয়েস্টগুলোর ডিপেন্ডেন্সিতে `get_settings()`-এর যেকোনো পরবর্তী কলে, `get_settings()`-এর ভেতরের কোড এক্সিকিউট করে একটি নতুন `Settings` অবজেক্ট তৈরি না করে, এটি প্রথম কলে রিটার্ন করা সেই একই অবজেক্ট বারবার রিটার্ন করবে।

#### `lru_cache` কারিগরি বিবরণ { #lru-cache-technical-details }

`@lru_cache` যে ফাংশনটি ডেকোরেট করে সেটিকে এমনভাবে পরিবর্তন করে যাতে প্রতিবার ফাংশনের কোড এক্সিকিউট করে আবার হিসাব না করে প্রথমবার যে ভ্যালু রিটার্ন হয়েছিল সেটিই রিটার্ন করে।

তাই এর নিচের ফাংশনটি আর্গুমেন্টের প্রতিটি সমন্বয়ের জন্য একবার এক্সিকিউট হবে। আর তারপর আর্গুমেন্টের ওই প্রতিটি সমন্বয়ের রিটার্ন করা ভ্যালুগুলো বারবার ব্যবহার হবে, যখনই ফাংশনটি হুবহু একই আর্গুমেন্টের সমন্বয় দিয়ে কল করা হবে।

তাহলে আপনার প্রোগ্রাম এভাবে এক্সিকিউট হতে পারে:

আমাদের ডিপেন্ডেন্সি `get_settings()`-এর ক্ষেত্রে ফাংশনটি কোনো আর্গুমেন্টই নেয় না, তাই এটি সবসময় একই ভ্যালু রিটার্ন করে।

এভাবে এটি প্রায় এমন আচরণ করে যেন এটি শুধু একটি গ্লোবাল ভেরিয়েবল। কিন্তু যেহেতু এটি একটি ডিপেন্ডেন্সি ফাংশন ব্যবহার করে, তাই টেস্টিংয়ের জন্য আমরা সহজেই এটি ওভাররাইড করতে পারি।

`@lru_cache` হলো `functools`-এর অংশ, যা Python-এর স্ট্যান্ডার্ড লাইব্রেরির অংশ, এ সম্পর্কে আরও পড়তে পারেন [`@lru_cache`-এর জন্য Python ডকুমেন্টেশনে](https://docs.python.org/3/library/functools.html#functools.lru_cache)।

## সংক্ষেপে { #recap }

Pydantic মডেলের সব শক্তিসহ আপনার অ্যাপ্লিকেশনের সেটিংস বা কনফিগারেশন সামলাতে আপনি Pydantic Settings ব্যবহার করতে পারেন।

* একটি ডিপেন্ডেন্সি ব্যবহার করে আপনি টেস্টিং সহজ করতে পারেন।
* এর সাথে আপনি `.env` ফাইল ব্যবহার করতে পারেন।
* `@lru_cache` ব্যবহার করলে প্রতিটি রিকোয়েস্টের জন্য বারবার dotenv ফাইল পড়া এড়ানো যায়, আবার টেস্টিংয়ের সময় এটি ওভাররাইডও করা যায়।
