# OAuth2 scopes { #oauth2-scopes }

আপনি **FastAPI**-এর সাথে সরাসরি OAuth2 scopes ব্যবহার করতে পারেন, এগুলো নির্বিঘ্নে কাজ করার জন্য যুক্ত করা হয়েছে।

এতে আপনি OAuth2 স্ট্যান্ডার্ড অনুসরণ করে আপনার OpenAPI অ্যাপ্লিকেশনে (এবং API ডকুমেন্টেশনে) যুক্ত আরও সূক্ষ্ম একটি অনুমতি ব্যবস্থা রাখতে পারবেন।

scopes-সহ OAuth2 হলো সেই ব্যবস্থা যা অনেক বড় অথেনটিকেশন প্রোভাইডার ব্যবহার করে, যেমন Facebook, Google, GitHub, Microsoft, X (Twitter) ইত্যাদি। ইউজার ও অ্যাপ্লিকেশনকে নির্দিষ্ট অনুমতি দিতে তারা এটি ব্যবহার করে।

প্রতিবার আপনি যখন Facebook, Google, GitHub, Microsoft, X (Twitter) "দিয়ে লগ ইন" করেন, তখন ওই অ্যাপ্লিকেশনটি scopes-সহ OAuth2 ব্যবহার করছে।

এই অংশে আপনি দেখবেন আপনার **FastAPI** অ্যাপ্লিকেশনে scopes-সহ সেই একই OAuth2 দিয়ে কীভাবে অথেনটিকেশন ও অথরাইজেশন পরিচালনা করতে হয়।

/// warning | সতর্কতা

এটি মোটামুটি একটি অ্যাডভান্সড অংশ। আপনি যদি সবে শুরু করে থাকেন, তাহলে এটি এড়িয়ে যেতে পারেন।

OAuth2 scopes আপনার অবশ্যই দরকার নেই, আর আপনি যেভাবে খুশি অথেনটিকেশন ও অথরাইজেশন সামলাতে পারেন।

তবে scopes-সহ OAuth2 আপনার API-তে (OpenAPI-সহ) এবং আপনার API ডকুমেন্টেশনে সুন্দরভাবে যুক্ত করা যায়।

তবুও, ওই scopes, বা অন্য যেকোনো সিকিউরিটি/অথরাইজেশন শর্ত আপনার কোডে আপনার প্রয়োজনমতো আপনাকেই প্রয়োগ করতে হবে।

অনেক ক্ষেত্রে scopes-সহ OAuth2 প্রয়োজনের তুলনায় বাড়াবাড়ি হতে পারে।

তবে আপনি যদি জানেন যে এটি আপনার দরকার, বা আপনি কৌতূহলী হন, তাহলে পড়তে থাকুন।

## OAuth2 scopes ও OpenAPI { #oauth2-scopes-and-openapi }

OAuth2 স্পেসিফিকেশন "scopes"-কে স্পেস দিয়ে আলাদা করা স্ট্রিংয়ের একটি লিস্ট হিসেবে সংজ্ঞায়িত করে।

এই প্রতিটি স্ট্রিংয়ের বিষয়বস্তু যেকোনো ফরম্যাটের হতে পারে, তবে এতে স্পেস থাকা উচিত নয়।

এই scopes "অনুমতি" উপস্থাপন করে।

OpenAPI-তে (যেমন API ডকুমেন্টেশনে) আপনি "সিকিউরিটি স্কিম" সংজ্ঞায়িত করতে পারেন।

যখন এই সিকিউরিটি স্কিমগুলোর একটি OAuth2 ব্যবহার করে, তখন আপনি scopes ঘোষণা ও ব্যবহারও করতে পারেন।

প্রতিটি "scope" শুধু একটি স্ট্রিং (স্পেস ছাড়া)।

এগুলো সাধারণত নির্দিষ্ট সিকিউরিটি অনুমতি ঘোষণা করতে ব্যবহার হয়, যেমন:

* `users:read` বা `users:write` প্রচলিত উদাহরণ।
* `instagram_basic` Facebook / Instagram ব্যবহার করে।
* `https://www.googleapis.com/auth/drive` Google ব্যবহার করে।

/// note | নোট

OAuth2-তে একটি "scope" হলো শুধু একটি স্ট্রিং যা প্রয়োজনীয় একটি নির্দিষ্ট অনুমতি ঘোষণা করে।

এতে `:`-এর মতো অন্য অক্ষর থাকুক বা এটি একটি URL হোক, তাতে কিছু যায় আসে না।

ওই বিবরণগুলো বাস্তবায়ন-নির্দিষ্ট।

OAuth2-এর কাছে এগুলো শুধুই স্ট্রিং।

## scopes-সহ JWT টোকেন { #jwt-token-with-scopes }

এবার টোকেন *পাথ অপারেশন* পরিবর্তন করুন যাতে এটি অনুরোধ করা scopes রিটার্ন করে।

আমরা এখনো একই `OAuth2PasswordRequestForm` ব্যবহার করছি। এতে `str`-এর একটি `list`-সহ একটি `scopes` প্রপার্টি আছে, যাতে রিকোয়েস্টে পাওয়া প্রতিটি scope থাকে।

আর আমরা JWT টোকেনের অংশ হিসেবে scopes রিটার্ন করি।

## *পাথ অপারেশন* ও ডিপেন্ডেন্সিতে scopes ঘোষণা করুন { #declare-scopes-in-path-operations-and-dependencies }

এবার আমরা ঘোষণা করি যে `/users/me/items/`-এর *পাথ অপারেশনের* জন্য `items` scope প্রয়োজন।

এর জন্য আমরা `fastapi` থেকে `Security` ইম্পোর্ট করে ব্যবহার করি।

ডিপেন্ডেন্সি ঘোষণা করতে আপনি `Security` ব্যবহার করতে পারেন (ঠিক `Depends`-এর মতো), তবে `Security` scopes-এর (স্ট্রিং) একটি লিস্টসহ `scopes` প্যারামিটারও গ্রহণ করে।

এক্ষেত্রে আমরা `Security`-তে একটি ডিপেন্ডেন্সি ফাংশন `get_current_active_user` দিই (যেভাবে `Depends`-এর সাথে করতাম)।

তবে আমরা scopes-এর একটি `list`-ও দিই, এক্ষেত্রে মাত্র একটি scope-সহ: `items` (এতে আরও থাকতে পারত)।

আর ডিপেন্ডেন্সি ফাংশন `get_current_active_user` সাব-ডিপেন্ডেন্সিও ঘোষণা করতে পারে, শুধু `Depends` দিয়ে নয়, `Security` দিয়েও। নিজের সাব-ডিপেন্ডেন্সি ফাংশন (`get_current_user`) এবং আরও scope শর্ত ঘোষণা করে।

এক্ষেত্রে এর `me` scope প্রয়োজন (এর একাধিক scope প্রয়োজন হতে পারত)।

/// note | নোট

বিভিন্ন জায়গায় বিভিন্ন scope যোগ করার আপনার অবশ্যই দরকার নেই।

বিভিন্ন স্তরে ঘোষিত scopes **FastAPI** কীভাবে সামলায় তা দেখাতে আমরা এখানে এটি করছি।

/// note | কারিগরি বিবরণ

`Security` আসলে `Depends`-এর একটি সাবক্লাস, এবং এতে মাত্র একটি অতিরিক্ত প্যারামিটার আছে যা আমরা পরে দেখব।

তবে `Depends`-এর বদলে `Security` ব্যবহার করলে **FastAPI** জানবে যে এটি সিকিউরিটি scopes ঘোষণা করতে, ভেতরে ভেতরে সেগুলো ব্যবহার করতে এবং OpenAPI দিয়ে API ডকুমেন্ট করতে পারে।

তবে আপনি যখন `fastapi` থেকে `Query`, `Path`, `Depends`, `Security` ও অন্যগুলো ইম্পোর্ট করেন, সেগুলো আসলে এমন ফাংশন যা বিশেষ ক্লাস রিটার্ন করে।

## `SecurityScopes` ব্যবহার করুন { #use-securityscopes }

এবার ডিপেন্ডেন্সি `get_current_user` আপডেট করুন।

ওপরের ডিপেন্ডেন্সিগুলো এটিই ব্যবহার করে।

এখানেই আমরা আগে তৈরি করা সেই একই OAuth2 স্কিম ব্যবহার করছি, এটিকে একটি ডিপেন্ডেন্সি হিসেবে ঘোষণা করে: `oauth2_scheme`।

যেহেতু এই ডিপেন্ডেন্সি ফাংশনের নিজের কোনো scope শর্ত নেই, তাই আমরা `oauth2_scheme`-এর সাথে `Depends` ব্যবহার করতে পারি, সিকিউরিটি scopes উল্লেখ করার দরকার না থাকলে আমাদের `Security` ব্যবহার করতে হয় না।

আমরা `fastapi.security` থেকে ইম্পোর্ট করা `SecurityScopes` টাইপের একটি বিশেষ প্যারামিটারও ঘোষণা করি।

এই `SecurityScopes` ক্লাসটি `Request`-এর অনুরূপ (`Request` সরাসরি রিকোয়েস্ট অবজেক্ট পেতে ব্যবহার হতো)।

## `scopes` ব্যবহার করুন { #use-the-scopes }

`security_scopes` প্যারামিটারটি হবে `SecurityScopes` টাইপের।

এতে একটি `scopes` প্রপার্টি থাকবে, যাতে একটি লিস্ট থাকবে যেখানে এটি নিজে এবং এটিকে সাব-ডিপেন্ডেন্সি হিসেবে ব্যবহার করে এমন সব ডিপেন্ডেন্সির প্রয়োজনীয় সব scope থাকবে। অর্থাৎ, সব "dependant"... এটি হয়তো বিভ্রান্তিকর শোনাচ্ছে, নিচে পরে আবার ব্যাখ্যা করা হয়েছে।

`security_scopes` অবজেক্টটি (`SecurityScopes` ক্লাসের) একটি `scope_str` অ্যাট্রিবিউটও দেয়, যাতে ওই scopes স্পেস দিয়ে আলাদা করা একটিমাত্র স্ট্রিং হিসেবে থাকে (আমরা এটি ব্যবহার করব)।

আমরা একটি `HTTPException` তৈরি করি যা পরে কয়েকটি জায়গায় পুনরায় ব্যবহার (`raise`) করতে পারি।

এই এক্সেপশনে আমরা প্রয়োজনীয় scopes (যদি থাকে) স্পেস দিয়ে আলাদা করা একটি স্ট্রিং হিসেবে অন্তর্ভুক্ত করি (`scope_str` ব্যবহার করে)। scopes ধারণকারী সেই স্ট্রিংটি আমরা `WWW-Authenticate` হেডারে রাখি (এটি স্পেকের অংশ)।

## `username` ও ডেটার আকৃতি যাচাই করুন { #verify-the-username-and-data-shape }

আমরা যাচাই করি যে আমরা একটি `username` পাচ্ছি, এবং scopes বের করি।

তারপর আমরা Pydantic মডেল দিয়ে সেই ডেটা ভ্যালিডেট করি (`ValidationError` এক্সেপশন ধরে), আর JWT টোকেন পড়তে বা Pydantic দিয়ে ডেটা ভ্যালিডেট করতে কোনো এরর পেলে আগে তৈরি করা `HTTPException` রেইজ করি।

এর জন্য আমরা Pydantic মডেল `TokenData`-কে একটি নতুন প্রপার্টি `scopes` দিয়ে আপডেট করি।

Pydantic দিয়ে ডেটা ভ্যালিডেট করে আমরা নিশ্চিত করতে পারি যে, যেমন, আমাদের কাছে scopes-সহ হুবহু `str`-এর একটি `list` এবং `username`-সহ একটি `str` আছে।

যেমন, একটি `dict` বা অন্য কিছুর বদলে, কারণ তা পরে কোনো এক সময়ে অ্যাপ্লিকেশন ভেঙে দিতে পারে, যা একটি সিকিউরিটি ঝুঁকি তৈরি করত।

আমরা এটাও যাচাই করি যে ওই ইউজারনেমসহ একজন ইউজার আছেন, আর না থাকলে আগে তৈরি করা সেই একই এক্সেপশন রেইজ করি।

## `scopes` যাচাই করুন { #verify-the-scopes }

এবার আমরা যাচাই করি যে এই ডিপেন্ডেন্সি এবং সব dependant (*পাথ অপারেশনসহ*)-এর প্রয়োজনীয় সব scope প্রাপ্ত টোকেনে দেওয়া scopes-এ অন্তর্ভুক্ত আছে, নইলে একটি `HTTPException` রেইজ করি।

এর জন্য আমরা `security_scopes.scopes` ব্যবহার করি, যাতে এই সব scope `str` হিসেবে একটি `list`-এ থাকে।

## ডিপেন্ডেন্সি ট্রি ও scopes { #dependency-tree-and-scopes }

চলুন আবার এই ডিপেন্ডেন্সি ট্রি ও scopes পর্যালোচনা করি।

যেহেতু `get_current_active_user` ডিপেন্ডেন্সির সাব-ডিপেন্ডেন্সি হলো `get_current_user`, তাই `get_current_active_user`-এ ঘোষিত `"me"` scope `get_current_user`-এ পাঠানো `security_scopes.scopes`-এর প্রয়োজনীয় scopes-এর লিস্টে অন্তর্ভুক্ত হবে।

*পাথ অপারেশনটি* নিজেও একটি scope ঘোষণা করে, `"items"`, তাই এটিও `get_current_user`-এ পাঠানো `security_scopes.scopes`-এর লিস্টে থাকবে।

ডিপেন্ডেন্সি ও scopes-এর হায়ারার্কি দেখতে এরকম:

* *পাথ অপারেশন* `read_own_items`-এ আছে:
    * এই ডিপেন্ডেন্সিসহ প্রয়োজনীয় scopes `["items"]`:
    * `get_current_active_user`:
        *  ডিপেন্ডেন্সি ফাংশন `get_current_active_user`-এ আছে:
            * এই ডিপেন্ডেন্সিসহ প্রয়োজনীয় scopes `["me"]`:
            * `get_current_user`:
                * ডিপেন্ডেন্সি ফাংশন `get_current_user`-এ আছে:
                    * এর নিজের কোনো প্রয়োজনীয় scope নেই।
                    * `oauth2_scheme` ব্যবহারকারী একটি ডিপেন্ডেন্সি।
                    * `SecurityScopes` টাইপের একটি `security_scopes` প্যারামিটার:
                        * এই `security_scopes` প্যারামিটারে একটি `scopes` প্রপার্টি আছে, যাতে ওপরে ঘোষিত এই সব scope ধারণকারী একটি `list` আছে, তাই:
                            * *পাথ অপারেশন* `read_own_items`-এর জন্য `security_scopes.scopes`-এ থাকবে `["me", "items"]`।
                            * *পাথ অপারেশন* `read_users_me`-এর জন্য `security_scopes.scopes`-এ থাকবে `["me"]`, কারণ এটি `get_current_active_user` ডিপেন্ডেন্সিতে ঘোষিত।
                            * *পাথ অপারেশন* `read_system_status`-এর জন্য `security_scopes.scopes`-এ থাকবে `[]` (কিছুই না), কারণ এটি `scopes`-সহ কোনো `Security` ঘোষণা করেনি, আর এর ডিপেন্ডেন্সি `get_current_user`-ও কোনো `scopes` ঘোষণা করে না।

/// tip | পরামর্শ

এখানে গুরুত্বপূর্ণ ও "জাদুকরী" বিষয় হলো, প্রতিটি *পাথ অপারেশনের* জন্য `get_current_user`-এর কাছে যাচাই করার জন্য `scopes`-এর একটি ভিন্ন লিস্ট থাকবে।

সবই নির্ভর করে প্রতিটি *পাথ অপারেশনে* এবং ওই নির্দিষ্ট *পাথ অপারেশনের* ডিপেন্ডেন্সি ট্রির প্রতিটি ডিপেন্ডেন্সিতে ঘোষিত `scopes`-এর ওপর।

///

## `SecurityScopes` সম্পর্কে আরও বিবরণ { #more-details-about-securityscopes }

আপনি যেকোনো জায়গায় এবং একাধিক জায়গায় `SecurityScopes` ব্যবহার করতে পারেন, এটিকে "মূল" ডিপেন্ডেন্সিতেই থাকতে হবে এমন নয়।

এতে সবসময় বর্তমান `Security` ডিপেন্ডেন্সিগুলোতে এবং **ওই নির্দিষ্ট** *পাথ অপারেশন* ও **ওই নির্দিষ্ট** ডিপেন্ডেন্সি ট্রির সব dependant-এ ঘোষিত সিকিউরিটি scopes থাকবে।

যেহেতু `SecurityScopes`-এ dependant-দের ঘোষিত সব scope থাকবে, তাই একটি কেন্দ্রীয় ডিপেন্ডেন্সি ফাংশনে একটি টোকেনের প্রয়োজনীয় scopes আছে কিনা যাচাই করতে আপনি এটি ব্যবহার করতে পারেন, এবং তারপর বিভিন্ন *পাথ অপারেশনে* বিভিন্ন scope শর্ত ঘোষণা করতে পারেন।

প্রতিটি *পাথ অপারেশনের* জন্য এগুলো স্বাধীনভাবে যাচাই করা হবে।

## যাচাই করুন { #check-it }

আপনি যদি API ডকুমেন্টেশন খোলেন, তাহলে অথেনটিকেট করে কোন scopes অথরাইজ করতে চান তা উল্লেখ করতে পারবেন।

<img src="/img/tutorial/security/image11.png">

আপনি যদি কোনো scope বেছে না নেন, তাহলে আপনি "অথেনটিকেটেড" থাকবেন, কিন্তু `/users/me/` বা `/users/me/items/` অ্যাক্সেস করার চেষ্টা করলে একটি এরর পাবেন যাতে বলা থাকবে আপনার যথেষ্ট অনুমতি নেই। তবে আপনি তখনও `/status/` অ্যাক্সেস করতে পারবেন।

আর আপনি যদি `me` scope বেছে নেন কিন্তু `items` scope না নেন, তাহলে `/users/me/` অ্যাক্সেস করতে পারবেন কিন্তু `/users/me/items/` পারবেন না।

একজন ইউজারের দেওয়া টোকেন দিয়ে এই *পাথ অপারেশনগুলোর* কোনো একটি অ্যাক্সেস করার চেষ্টা করা একটি থার্ড পার্টি অ্যাপ্লিকেশনের ক্ষেত্রে এটাই ঘটত, ইউজার অ্যাপ্লিকেশনটিকে কতগুলো অনুমতি দিয়েছেন তার ওপর নির্ভর করে।

## থার্ড পার্টি ইন্টিগ্রেশন সম্পর্কে { #about-third-party-integrations }

এই উদাহরণে আমরা OAuth2 "password" flow ব্যবহার করছি।

এটি উপযুক্ত যখন আমরা আমাদের নিজের অ্যাপ্লিকেশনে লগ ইন করছি, সম্ভবত আমাদের নিজের ফ্রন্টএন্ড দিয়ে।

কারণ আমরা এটিকে `username` ও `password` গ্রহণ করার ব্যাপারে বিশ্বাস করতে পারি, যেহেতু আমরা এটি নিয়ন্ত্রণ করি।

কিন্তু আপনি যদি এমন একটি OAuth2 অ্যাপ্লিকেশন তৈরি করেন যার সাথে অন্যরা কানেক্ট করবে (অর্থাৎ, আপনি যদি Facebook, Google, GitHub ইত্যাদির সমতুল্য একটি অথেনটিকেশন প্রোভাইডার তৈরি করেন), তাহলে আপনার অন্য flow-গুলোর একটি ব্যবহার করা উচিত।

সবচেয়ে প্রচলিত হলো implicit flow।

সবচেয়ে নিরাপদ হলো code flow, তবে এটি বাস্তবায়ন করা আরও জটিল কারণ এতে আরও বেশি ধাপ লাগে। যেহেতু এটি আরও জটিল, তাই অনেক প্রোভাইডার শেষ পর্যন্ত implicit flow-এর পরামর্শ দেয়।

/// note | নোট

প্রতিটি অথেনটিকেশন প্রোভাইডার তাদের flow-গুলোর ভিন্ন ভিন্ন নাম দেয়, যাতে এটি তাদের ব্র্যান্ডের অংশ হয়ে ওঠে, এটি খুবই সাধারণ।

তবে শেষ পর্যন্ত তারা একই OAuth2 স্ট্যান্ডার্ড বাস্তবায়ন করছে।

///

**FastAPI** `fastapi.security.oauth2`-এ এই সব OAuth2 অথেনটিকেশন flow-এর জন্য ইউটিলিটি অন্তর্ভুক্ত করে।

## ডেকোরেটরের `dependencies`-এ `Security` { #security-in-decorator-dependencies }

যেভাবে আপনি ডেকোরেটরের `dependencies` প্যারামিটারে `Depends`-এর একটি `list` সংজ্ঞায়িত করতে পারেন ([পাথ অপারেশন ডেকোরেটরে ডিপেন্ডেন্সি](../../tutorial/dependencies/dependencies-in-path-operation-decorators.md)-এ যেমন ব্যাখ্যা করা হয়েছে), সেখানে `scopes`-সহ `Security`-ও ব্যবহার করতে পারেন।
