# অ্যাডভান্সড ডিপেন্ডেন্সি { #advanced-dependencies }

## প্যারামিটারাইজড ডিপেন্ডেন্সি { #parameterized-dependencies }

আমরা যত ডিপেন্ডেন্সি দেখেছি সবই একটি নির্দিষ্ট ফাংশন বা ক্লাস।

কিন্তু এমন ক্ষেত্র থাকতে পারে যেখানে আপনি অনেকগুলো ভিন্ন ফাংশন বা ক্লাস ঘোষণা না করেই ডিপেন্ডেন্সিতে প্যারামিটার সেট করতে চান।

কল্পনা করা যাক আমরা এমন একটি ডিপেন্ডেন্সি চাই যা যাচাই করে কুয়েরি প্যারামিটার `q`-তে কোনো নির্দিষ্ট বিষয়বস্তু আছে কিনা।

কিন্তু আমরা চাই সেই নির্দিষ্ট বিষয়বস্তুটি প্যারামিটারাইজ করতে।

## `yield`, `HTTPException`, `except` ও ব্যাকগ্রাউন্ড টাস্কসহ ডিপেন্ডেন্সি { #dependencies-with-yield-httpexception-except-and-background-tasks }

/// warning | সতর্কতা

খুব সম্ভবত এই কারিগরি বিবরণগুলো আপনার দরকার নেই।

এই বিবরণগুলো মূলত কাজে আসে যদি আপনার 0.121.0-এর চেয়ে পুরোনো একটি FastAPI অ্যাপ্লিকেশন থাকে এবং আপনি `yield`-সহ ডিপেন্ডেন্সি নিয়ে সমস্যার মুখোমুখি হন।

///

বিভিন্ন ব্যবহারের ক্ষেত্র বিবেচনায় নিতে এবং কিছু সমস্যা ঠিক করতে `yield`-সহ ডিপেন্ডেন্সি সময়ের সাথে বিবর্তিত হয়েছে, এখানে কী কী পরিবর্তন হয়েছে তার একটি সারসংক্ষেপ দেওয়া হলো।

### `yield` ও `scope`-সহ ডিপেন্ডেন্সি { #dependencies-with-yield-and-scope }

ভার্সন 0.121.0-এ FastAPI `yield`-সহ ডিপেন্ডেন্সির জন্য `Depends(scope="function")`-এর সাপোর্ট যোগ করেছে।

`Depends(scope="function")` ব্যবহার করলে `yield`-এর পরের exit code *পাথ অপারেশন ফাংশন* শেষ হওয়ার ঠিক পরে, ক্লায়েন্টকে রেসপন্স ফেরত পাঠানোর আগে এক্সিকিউট হয়।

আর `Depends(scope="request")` (ডিফল্ট) ব্যবহার করলে `yield`-এর পরের exit code রেসপন্স পাঠানোর পরে এক্সিকিউট হয়।

এ সম্পর্কে আরও পড়তে পারেন [`yield`-সহ ডিপেন্ডেন্সি - আগাম প্রস্থান ও `scope`](../tutorial/dependencies/dependencies-with-yield.md#early-exit-and-scope)-এর ডকুমেন্টেশনে।

### `yield` ও `StreamingResponse`-সহ ডিপেন্ডেন্সি, কারিগরি বিবরণ { #dependencies-with-yield-and-streamingresponse-technical-details }

FastAPI 0.118.0-এর আগে, আপনি যদি `yield`-সহ একটি ডিপেন্ডেন্সি ব্যবহার করতেন, তাহলে এটি *পাথ অপারেশন ফাংশন* রিটার্ন করার পরে কিন্তু রেসপন্স পাঠানোর ঠিক আগে exit code চালাত।

উদ্দেশ্য ছিল রেসপন্স নেটওয়ার্কের মধ্য দিয়ে যাওয়ার অপেক্ষায় প্রয়োজনের চেয়ে বেশি সময় রিসোর্স ধরে না রাখা।

এই পরিবর্তনের মানে এটাও ছিল যে আপনি যদি একটি `StreamingResponse` রিটার্ন করতেন, তাহলে `yield`-সহ ডিপেন্ডেন্সির exit code ইতিমধ্যে চলে যেত।

যেমন, `yield`-সহ একটি ডিপেন্ডেন্সিতে যদি আপনার একটি ডেটাবেস সেশন থাকত, তাহলে ডেটা স্ট্রিম করার সময় `StreamingResponse` ওই সেশন ব্যবহার করতে পারত না, কারণ `yield`-এর পরের exit code-এ সেশনটি ইতিমধ্যে বন্ধ হয়ে যেত।

0.118.0-এ এই আচরণ ফিরিয়ে নেওয়া হয়েছে, যাতে `yield`-এর পরের exit code রেসপন্স পাঠানোর পরে এক্সিকিউট হয়।

/// note | নোট

নিচে যেমন দেখবেন, এটি ভার্সন 0.106.0-এর আগের আচরণের খুবই অনুরূপ, তবে বিভিন্ন বিরল ক্ষেত্রের জন্য বেশ কিছু উন্নতি ও বাগ ফিক্সসহ।

///

#### আগাম exit code-সহ ব্যবহারের ক্ষেত্র { #use-cases-with-early-exit-code }

নির্দিষ্ট শর্তসহ কিছু ব্যবহারের ক্ষেত্র আছে যেগুলো রেসপন্স পাঠানোর আগে `yield`-সহ ডিপেন্ডেন্সির exit code চালানোর পুরোনো আচরণ থেকে উপকৃত হতে পারে।

যেমন, কল্পনা করুন আপনার এমন কোড আছে যা `yield`-সহ একটি ডিপেন্ডেন্সিতে শুধু একজন ইউজার যাচাই করতে একটি ডেটাবেস সেশন ব্যবহার করে, কিন্তু *পাথ অপারেশন ফাংশনে* ডেটাবেস সেশনটি আর কখনো ব্যবহার হয় না, কেবল ডিপেন্ডেন্সিতেই, **এবং** রেসপন্স পাঠাতে অনেক সময় লাগে, যেমন একটি `StreamingResponse` যা ধীরে ধীরে ডেটা পাঠায়, কিন্তু কোনো কারণে ডেটাবেস ব্যবহার করে না।

### `yield` ও `except`-সহ ডিপেন্ডেন্সি, কারিগরি বিবরণ { #dependencies-with-yield-and-except-technical-details }

FastAPI 0.110.0-এর আগে, আপনি যদি `yield`-সহ একটি ডিপেন্ডেন্সি ব্যবহার করতেন, তারপর ওই ডিপেন্ডেন্সিতে `except` দিয়ে একটি এক্সেপশন ধরতেন, এবং এক্সেপশনটি আবার রেইজ না করতেন, তাহলে এক্সেপশনটি স্বয়ংক্রিয়ভাবে যেকোনো এক্সেপশন হ্যান্ডলার বা internal server error হ্যান্ডলারে রেইজ/ফরোয়ার্ড হতো।

হ্যান্ডলার ছাড়া ফরোয়ার্ড হওয়া এক্সেপশন (internal server error) থেকে নিয়ন্ত্রণহীন মেমরি খরচ ঠিক করতে এবং সাধারণ Python কোডের আচরণের সাথে সামঞ্জস্যপূর্ণ করতে ভার্সন 0.110.0-এ এটি পরিবর্তন করা হয়েছে।

### ব্যাকগ্রাউন্ড টাস্ক ও `yield`-সহ ডিপেন্ডেন্সি, কারিগরি বিবরণ { #background-tasks-and-dependencies-with-yield-technical-details }

FastAPI 0.106.0-এর আগে `yield`-এর পরে এক্সেপশন রেইজ করা সম্ভব ছিল না, `yield`-সহ ডিপেন্ডেন্সির exit code রেসপন্স পাঠানোর *পরে* এক্সিকিউট হতো, তাই [এক্সেপশন হ্যান্ডলারগুলো](../tutorial/handling-errors.md#install-custom-exception-handlers) ইতিমধ্যে চলে যেত।

এটি মূলত এভাবে ডিজাইন করা হয়েছিল যাতে ডিপেন্ডেন্সিগুলোর "yield করা" একই অবজেক্ট ব্যাকগ্রাউন্ড টাস্কের ভেতরে ব্যবহার করা যায়, কারণ ব্যাকগ্রাউন্ড টাস্ক শেষ হওয়ার পরে exit code এক্সিকিউট হতো।

রেসপন্স নেটওয়ার্কের মধ্য দিয়ে যাওয়ার অপেক্ষায় রিসোর্স ধরে না রাখার উদ্দেশ্যে FastAPI 0.106.0-এ এটি পরিবর্তন করা হয়েছে।

/// tip | পরামর্শ

এছাড়া, একটি ব্যাকগ্রাউন্ড টাস্ক সাধারণত লজিকের একটি স্বাধীন সেট, যা তার নিজস্ব রিসোর্সসহ (যেমন তার নিজস্ব ডেটাবেস কানেকশন) আলাদাভাবে সামলানো উচিত।

তাই এভাবে আপনার কোড সম্ভবত আরও পরিচ্ছন্ন হবে।

///

আপনি যদি আগে এই আচরণের ওপর নির্ভর করতেন, তাহলে এখন আপনার উচিত ব্যাকগ্রাউন্ড টাস্কের রিসোর্সগুলো ব্যাকগ্রাউন্ড টাস্কের ভেতরেই তৈরি করা, এবং ভেতরে কেবল এমন ডেটা ব্যবহার করা যা `yield`-সহ ডিপেন্ডেন্সির রিসোর্সের ওপর নির্ভর করে না।

যেমন, একই ডেটাবেস সেশন ব্যবহারের বদলে আপনি ব্যাকগ্রাউন্ড টাস্কের ভেতরে একটি নতুন ডেটাবেস সেশন তৈরি করবেন, এবং এই নতুন সেশন ব্যবহার করে ডেটাবেস থেকে অবজেক্টগুলো নেবেন। আর তারপর ডেটাবেসের অবজেক্টটি ব্যাকগ্রাউন্ড টাস্ক ফাংশনে প্যারামিটার হিসেবে পাঠানোর বদলে ওই অবজেক্টের ID পাঠাবেন এবং তারপর ব্যাকগ্রাউন্ড টাস্ক ফাংশনের ভেতরে আবার অবজেক্টটি নেবেন।
