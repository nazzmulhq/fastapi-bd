# OpenAPI কলব্যাক { #openapi-callbacks }

আপনি এমন একটি *পাথ অপারেশনসহ* API তৈরি করতে পারেন যা অন্য কারো তৈরি (সম্ভবত সেই একই ডেভেলপার যিনি আপনার API *ব্যবহার* করবেন) একটি *বাহ্যিক API*-তে রিকোয়েস্ট চালু করতে পারে।

আপনার API অ্যাপ যখন *বাহ্যিক API* কল করে, তখন যে প্রক্রিয়াটি ঘটে তাকে বলা হয় "কলব্যাক"। কারণ বাহ্যিক ডেভেলপারের লেখা সফটওয়্যার আপনার API-তে একটি রিকোয়েস্ট পাঠায় এবং তারপর আপনার API *উল্টো কল করে* (calls back), একটি *বাহ্যিক API*-তে (যা সম্ভবত সেই একই ডেভেলপার তৈরি করেছেন) একটি রিকোয়েস্ট পাঠিয়ে।

এক্ষেত্রে আপনি হয়তো ডকুমেন্ট করতে চাইবেন যে ওই বাহ্যিক API দেখতে কেমন *হওয়া উচিত*। এতে কোন *পাথ অপারেশন* থাকা উচিত, কোন বডি আশা করা উচিত, কোন রেসপন্স রিটার্ন করা উচিত, ইত্যাদি।

## কলব্যাকসহ একটি অ্যাপ { #an-app-with-callbacks }

চলুন একটি উদাহরণ দিয়ে এর সবকিছু দেখি।

কল্পনা করুন আপনি এমন একটি অ্যাপ ডেভেলপ করছেন যা ইনভয়েস তৈরি করতে দেয়।

এই ইনভয়েসগুলোতে থাকবে একটি `id`, `title` (ঐচ্ছিক), `customer` এবং `total`।

আপনার API-এর ইউজার (একজন বাহ্যিক ডেভেলপার) একটি POST রিকোয়েস্ট দিয়ে আপনার API-তে একটি ইনভয়েস তৈরি করবেন।

তারপর আপনার API (ধরা যাক):

* ইনভয়েসটি বাহ্যিক ডেভেলপারের কোনো গ্রাহকের কাছে পাঠাবে।
* টাকা সংগ্রহ করবে।
* API ইউজারকে (বাহ্যিক ডেভেলপার) একটি নোটিফিকেশন ফেরত পাঠাবে।
    * এটি করা হবে (*আপনার API* থেকে) ওই বাহ্যিক ডেভেলপারের দেওয়া কোনো *বাহ্যিক API*-তে একটি POST রিকোয়েস্ট পাঠিয়ে (এটিই "কলব্যাক")।

## কলব্যাক ডকুমেন্ট করা { #documenting-the-callback }

আসল কলব্যাক কোড অনেকটাই আপনার নিজের API অ্যাপের ওপর নির্ভর করবে।

আর এটি সম্ভবত এক অ্যাপ থেকে আরেক অ্যাপে অনেক আলাদা হবে।

এটি মাত্র এক বা দুই লাইনের কোড হতে পারে, যেমন:

⟦CODE1⟧

তবে কলব্যাকের সম্ভবত সবচেয়ে গুরুত্বপূর্ণ অংশ হলো নিশ্চিত করা যে আপনার API ইউজার (বাহ্যিক ডেভেলপার) *বাহ্যিক API*-টি সঠিকভাবে বাস্তবায়ন করছেন, *আপনার API* কলব্যাকের রিকোয়েস্ট বডিতে যে ডেটা পাঠাবে সেই অনুযায়ী, ইত্যাদি।

তাই এরপর আমরা যা করব তা হলো *আপনার API* থেকে কলব্যাক গ্রহণ করতে ওই *বাহ্যিক API* দেখতে কেমন হওয়া উচিত তা ডকুমেন্ট করার কোড যোগ করা।

সেই ডকুমেন্টেশন আপনার API-এর `/docs`-এর Swagger UI-তে দেখা যাবে, এবং এটি বাহ্যিক ডেভেলপারদের জানাবে কীভাবে *বাহ্যিক API* তৈরি করতে হবে।

এই উদাহরণটি কলব্যাক নিজে বাস্তবায়ন করে না (যা মাত্র এক লাইনের কোড হতে পারে), কেবল ডকুমেন্টেশনের অংশটুকু।

/// tip | পরামর্শ

আসল কলব্যাক শুধু একটি HTTP রিকোয়েস্ট।

কলব্যাক নিজে বাস্তবায়নের সময় আপনি [HTTPX](https://www.python-httpx.org) বা [Requests](https://requests.readthedocs.io/)-এর মতো কিছু ব্যবহার করতে পারেন।

## কলব্যাক ডকুমেন্টেশনের কোড লিখুন { #write-the-callback-documentation-code }

এই কোডটি আপনার অ্যাপে এক্সিকিউট হবে না, ওই *বাহ্যিক API* দেখতে কেমন হওয়া উচিত তা *ডকুমেন্ট* করতেই কেবল আমাদের এটি দরকার।

তবে **FastAPI** দিয়ে কীভাবে সহজে একটি API-এর স্বয়ংক্রিয় ডকুমেন্টেশন তৈরি করতে হয় তা আপনি ইতিমধ্যে জানেন।

তাই *বাহ্যিক API* দেখতে কেমন হওয়া উচিত তা ডকুমেন্ট করতে আমরা সেই একই জ্ঞান ব্যবহার করব... বাহ্যিক API-এর যে *পাথ অপারেশন(গুলো)* বাস্তবায়ন করা উচিত (যেগুলো আপনার API কল করবে) সেগুলো তৈরি করে।

/// tip | পরামর্শ

একটি কলব্যাক ডকুমেন্ট করার কোড লেখার সময় কল্পনা করা কাজে আসতে পারে যে আপনিই সেই *বাহ্যিক ডেভেলপার*। আর আপনি এখন *আপনার API* নয়, *বাহ্যিক API* বাস্তবায়ন করছেন।

সাময়িকভাবে এই দৃষ্টিকোণ (*বাহ্যিক ডেভেলপারের*) গ্রহণ করলে ওই *বাহ্যিক API*-এর প্যারামিটার, বডির জন্য Pydantic মডেল, রেসপন্স ইত্যাদি কোথায় রাখতে হবে তা আরও স্পষ্ট মনে হতে পারে।

### কলব্যাক *পাথ অপারেশন* তৈরি করুন { #create-the-callback-path-operation }

কলব্যাক *পাথ অপারেশন* তৈরি করতে ওপরে তৈরি করা একই `APIRouter` ব্যবহার করুন।

এটি দেখতে ঠিক একটি সাধারণ FastAPI *পাথ অপারেশনের* মতো হওয়া উচিত:

* এতে সম্ভবত যে বডি গ্রহণ করা উচিত তার একটি ঘোষণা থাকা উচিত, যেমন `body: InvoiceEvent`।
* আর এতে যে রেসপন্স রিটার্ন করা উচিত তার একটি ঘোষণাও থাকতে পারে, যেমন `response_model=InvoiceEventReceived`।

একটি সাধারণ *পাথ অপারেশন* থেকে ২টি প্রধান পার্থক্য আছে:

* এতে কোনো আসল কোড থাকার দরকার নেই, কারণ আপনার অ্যাপ কখনো এই কোড কল করবে না। এটি কেবল *বাহ্যিক API* ডকুমেন্ট করতে ব্যবহার হয়। তাই ফাংশনটিতে শুধু `pass` থাকতে পারে।
* *পাথে* একটি [OpenAPI 3 এক্সপ্রেশন](https://github.com/OAI/OpenAPI-Specification/blob/main/versions/3.1.0.md#key-expression) (নিচে আরও দেখুন) থাকতে পারে, যেখানে এটি *আপনার API*-তে পাঠানো মূল রিকোয়েস্টের প্যারামিটার ও অংশসহ ভেরিয়েবল ব্যবহার করতে পারে।
