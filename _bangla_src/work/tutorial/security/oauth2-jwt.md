# পাসওয়ার্ড (ও হ্যাশিং)-সহ OAuth2, JWT টোকেনসহ Bearer { #oauth2-with-password-and-hashing-bearer-with-jwt-tokens }

এখন যেহেতু আমাদের পুরো সিকিউরিটি প্রবাহ আছে, চলুন <abbr title="JSON Web Tokens - JSON ওয়েব টোকেন">JWT</abbr> টোকেন ও নিরাপদ পাসওয়ার্ড হ্যাশিং ব্যবহার করে অ্যাপ্লিকেশনটিকে সত্যিকার অর্থে নিরাপদ করি।

এই কোডটি আপনি আসলেই আপনার অ্যাপ্লিকেশনে ব্যবহার করতে পারেন, আপনার ডেটাবেসে পাসওয়ার্ড হ্যাশ সংরক্ষণ করতে পারেন ইত্যাদি।

আগের অধ্যায়ে যেখানে থেমেছিলাম সেখান থেকে শুরু করে আমরা এটিকে বাড়াব।

## JWT সম্পর্কে { #about-jwt }

JWT মানে "JSON Web Tokens"।

এটি একটি JSON অবজেক্টকে স্পেস ছাড়া একটি লম্বা ঘন স্ট্রিংয়ে রূপান্তর করার একটি স্ট্যান্ডার্ড। এটি দেখতে এরকম:

⟦CODE1⟧

এটি এনক্রিপ্টেড নয়, তাই যে কেউ বিষয়বস্তু থেকে তথ্য উদ্ধার করতে পারে।

কিন্তু এটি সাইন করা। তাই আপনি যখন নিজের ইস্যু করা একটি টোকেন পান, তখন যাচাই করতে পারেন যে এটি আপনিই ইস্যু করেছিলেন।

এভাবে আপনি এমন একটি টোকেন তৈরি করতে পারেন যার মেয়াদ, ধরা যাক, ১ সপ্তাহ। তারপর ইউজার যখন পরদিন টোকেনটি নিয়ে ফিরে আসেন, আপনি জানেন যে ইউজার এখনো আপনার সিস্টেমে লগ ইন করা আছেন।

এক সপ্তাহ পরে টোকেনটির মেয়াদ শেষ হয়ে যাবে এবং ইউজার অথরাইজড থাকবেন না, নতুন টোকেন পেতে আবার সাইন ইন করতে হবে। আর ইউজার (বা কোনো থার্ড পার্টি) যদি মেয়াদ বদলাতে টোকেনটি পরিবর্তনের চেষ্টা করেন, তাহলে আপনি তা ধরে ফেলতে পারবেন, কারণ সিগনেচার মিলবে না।

JWT টোকেন নিয়ে নাড়াচাড়া করে এগুলো কীভাবে কাজ করে দেখতে চাইলে [https://jwt.io](https://jwt.io/) দেখুন।

## পাসওয়ার্ড হ্যাশিং { #password-hashing }

"হ্যাশিং" মানে কোনো বিষয়বস্তুকে (এক্ষেত্রে একটি পাসওয়ার্ড) বাইটের একটি ক্রমে (শুধু একটি স্ট্রিং) রূপান্তর করা, যা দেখতে অর্থহীন হিজিবিজির মতো।

যখনই আপনি হুবহু একই বিষয়বস্তু (হুবহু একই পাসওয়ার্ড) দেবেন, হুবহু একই হিজিবিজি পাবেন।

কিন্তু আপনি হিজিবিজি থেকে আবার পাসওয়ার্ডে রূপান্তর করতে পারবেন না।

### কেন পাসওয়ার্ড হ্যাশিং ব্যবহার করবেন { #why-use-password-hashing }

আপনার ডেটাবেস চুরি হলে চোরের কাছে আপনার ইউজারদের প্লেইনটেক্সট পাসওয়ার্ড থাকবে না, কেবল হ্যাশগুলো থাকবে।

তাই চোর ওই পাসওয়ার্ড অন্য কোনো সিস্টেমে ব্যবহারের চেষ্টা করতে পারবে না (যেহেতু অনেক ইউজার সব জায়গায় একই পাসওয়ার্ড ব্যবহার করেন, তাই এটি বিপজ্জনক হতো)।

## পাসওয়ার্ড হ্যাশ ও যাচাই করুন { #hash-and-verify-the-passwords }

`pwdlib` থেকে আমাদের প্রয়োজনীয় টুলগুলো ইম্পোর্ট করুন।

প্রস্তাবিত সেটিংসসহ একটি PasswordHash ইনস্ট্যান্স তৈরি করুন - এটি পাসওয়ার্ড হ্যাশ ও যাচাই করতে ব্যবহার হবে।

/// tip | পরামর্শ

pwdlib bcrypt হ্যাশিং অ্যালগরিদমও সাপোর্ট করে, তবে পুরোনো (legacy) অ্যালগরিদম অন্তর্ভুক্ত করে না - পুরোনো হ্যাশ নিয়ে কাজ করতে passlib লাইব্রেরি ব্যবহারের পরামর্শ দেওয়া হয়।

যেমন, অন্য কোনো সিস্টেমের (যেমন Django) তৈরি পাসওয়ার্ড পড়তে ও যাচাই করতে আপনি এটি ব্যবহার করতে পারেন, কিন্তু নতুন পাসওয়ার্ডগুলো Argon2 বা Bcrypt-এর মতো ভিন্ন অ্যালগরিদম দিয়ে হ্যাশ করতে পারেন।

আর একই সময়ে সবগুলোর সাথে সামঞ্জস্যপূর্ণ থাকতে পারেন।

### JWT "subject" `sub` সম্পর্কে কারিগরি বিবরণ { #technical-details-about-the-jwt-subject-sub }

JWT স্পেসিফিকেশন বলে যে টোকেনের বিষয় (subject)-সহ একটি `sub` কী থাকে।

এটি ব্যবহার করা ঐচ্ছিক, তবে ইউজারের পরিচয় আপনি এখানেই রাখবেন, তাই আমরা এখানে এটি ব্যবহার করছি।

একজন ইউজারকে শনাক্ত করা এবং তাকে সরাসরি আপনার API-তে অপারেশন করতে দেওয়া ছাড়াও JWT অন্যান্য কাজে ব্যবহার হতে পারে।

যেমন, আপনি একটি "গাড়ি" বা একটি "ব্লগ পোস্ট" শনাক্ত করতে পারেন।

তারপর আপনি ওই এনটিটি সম্পর্কে অনুমতি যোগ করতে পারেন, যেমন "চালানো" (গাড়ির জন্য) বা "সম্পাদনা" (ব্লগের জন্য)।

আর তারপর আপনি ওই JWT টোকেন একজন ইউজার (বা বট)-কে দিতে পারেন, এবং তারা কোনো অ্যাকাউন্ট ছাড়াই, শুধু আপনার API-এর তৈরি করা JWT টোকেন দিয়েই ওই কাজগুলো (গাড়ি চালানো, বা ব্লগ পোস্ট সম্পাদনা) করতে পারবে।

এই ধারণাগুলো ব্যবহার করে JWT আরও অনেক জটিল পরিস্থিতিতে ব্যবহার করা যায়।

সেসব ক্ষেত্রে ওই এনটিটিগুলোর কয়েকটির একই ID থাকতে পারে, ধরা যাক `foo` (একজন ইউজার `foo`, একটি গাড়ি `foo`, এবং একটি ব্লগ পোস্ট `foo`)।

তাই ID সংঘর্ষ এড়াতে, ইউজারের জন্য JWT টোকেন তৈরির সময় আপনি `sub` কী-এর ভ্যালুর আগে একটি উপসর্গ যোগ করতে পারেন, যেমন `username:`। তাহলে এই উদাহরণে `sub`-এর ভ্যালু হতে পারত: `username:johndoe`।

মনে রাখার মতো গুরুত্বপূর্ণ বিষয় হলো `sub` কী-তে পুরো অ্যাপ্লিকেশন জুড়ে একটি অনন্য শনাক্তকারী থাকা উচিত, এবং এটি একটি স্ট্রিং হওয়া উচিত।

## `scopes`-সহ অ্যাডভান্সড ব্যবহার { #advanced-usage-with-scopes }

OAuth2-তে "scopes"-এর ধারণা আছে।

এগুলো দিয়ে আপনি একটি JWT টোকেনে অনুমতির একটি নির্দিষ্ট সেট যোগ করতে পারেন।

তারপর আপনি এই টোকেনটি সরাসরি একজন ইউজার বা কোনো থার্ড পার্টিকে দিতে পারেন, যাতে তারা কিছু বিধিনিষেধসহ আপনার API-এর সাথে কাজ করতে পারে।

এগুলো কীভাবে ব্যবহার করতে হয় এবং কীভাবে **FastAPI**-তে যুক্ত করা হয়, তা পরে **অ্যাডভান্সড ইউজার গাইডে** শিখতে পারবেন।

## সংক্ষেপে { #recap }

এ পর্যন্ত যা দেখলেন তা দিয়ে আপনি OAuth2 ও JWT-এর মতো স্ট্যান্ডার্ড ব্যবহার করে একটি নিরাপদ **FastAPI** অ্যাপ্লিকেশন সেট আপ করতে পারেন।

প্রায় যেকোনো ফ্রেমওয়ার্কে সিকিউরিটি সামলানো খুব দ্রুত বেশ জটিল একটি বিষয় হয়ে ওঠে।

এটি অনেক সহজ করে দেয় এমন অনেক প্যাকেজকে ডেটা মডেল, ডেটাবেস ও উপলব্ধ ফিচার নিয়ে অনেক আপস করতে হয়। আর অতিরিক্ত সরলীকরণ করা এমন কিছু প্যাকেজের ভেতরে আসলে সিকিউরিটির ত্রুটি থাকে।

---

**FastAPI** কোনো ডেটাবেস, ডেটা মডেল বা টুলের সাথে কোনো আপস করে না।

এটি আপনাকে আপনার প্রজেক্টের সাথে সবচেয়ে ভালোভাবে মানানসইগুলো বেছে নেওয়ার পূর্ণ নমনীয়তা দেয়।

আর আপনি সরাসরি `pwdlib` ও `PyJWT`-এর মতো অনেক সুরক্ষিত ও ব্যাপকভাবে ব্যবহৃত প্যাকেজ ব্যবহার করতে পারেন, কারণ বাহ্যিক প্যাকেজ যুক্ত করতে **FastAPI**-এর কোনো জটিল ব্যবস্থার প্রয়োজন হয় না।

তবে নমনীয়তা, মজবুতি বা সিকিউরিটির সাথে আপস না করেই প্রক্রিয়াটিকে যথাসম্ভব সহজ করার টুল এটি আপনাকে দেয়।

আর আপনি OAuth2-এর মতো নিরাপদ, স্ট্যান্ডার্ড প্রোটোকল তুলনামূলকভাবে সহজ উপায়ে ব্যবহার ও বাস্তবায়ন করতে পারেন।

এই একই স্ট্যান্ডার্ড অনুসরণ করে আরও সূক্ষ্ম অনুমতি ব্যবস্থার জন্য OAuth2 "scopes" কীভাবে ব্যবহার করতে হয়, সে সম্পর্কে **অ্যাডভান্সড ইউজার গাইডে** আরও জানতে পারবেন। scopes-সহ OAuth2 হলো সেই ব্যবস্থা যা Facebook, Google, GitHub, Microsoft, X (Twitter) ইত্যাদির মতো অনেক বড় অথেনটিকেশন প্রোভাইডার থার্ড পার্টি অ্যাপ্লিকেশনগুলোকে তাদের ইউজারদের পক্ষে তাদের API-এর সাথে কাজ করার অনুমতি দিতে ব্যবহার করে।
