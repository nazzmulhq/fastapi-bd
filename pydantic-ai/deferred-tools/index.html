Deferred টুল¶

🌐 সহজ বাংলায় ব্যাখ্যাসহ সংস্করণ

এটি শুধু অনুবাদ নয়: প্রতিটি পেজে সহজ ভাষায় ব্যাখ্যা, বাস্তব জীবনের উদাহরণ, কোডের লাইন-ধরে-ধরে ব্যাখ্যা, সাধারণ ভুল আর শেষে সারসংক্ষেপ যোগ করা হয়েছে। 🤝

কোড, প্যারামিটারের নাম আর কমান্ড ইংরেজিতেই রাখা হয়েছে, কারণ এগুলো ঠিক এভাবেই লিখতে হয়। অচেনা শব্দের মানে জানতে মেনুর "শিখুন" অংশে "সহজ শব্দকোষ" পেজটি দেখুন।

এটি মানুষের নির্দেশনায় AI দিয়ে তৈরি, তাই কোথাও ভুল থাকতে পারে। সন্দেহ হলে মূল ইংরেজি সংস্করণ মিলিয়ে নিন। 🤖

ইংরেজি সংস্করণ

এই পেজে যা শিখবেন

  • Deferred টুল কী: যে টুল একই রানে সাথে সাথে চালানো যায় না বা উচিত নয় (অনুমোদন লাগে, বা বাইরে চলে)।
  • দুই উপায়: HandleDeferredToolCalls দিয়ে রানের ভেতরেই মীমাংসা, বা DeferredToolRequests দিয়ে রান থামিয়ে পরে চালিয়ে যাওয়া।
  • মানুষের অনুমোদন (requires_approval, ApprovalRequired) আর বাইরে চালানো (CallDeferred)।
  • কথোপকথন থামানো, আর stream-এ deferred টুল কল দেখা।

কয়েকটি পরিস্থিতি আছে যেখানে মডেলের এমন একটি টুল ডাকতে পারা উচিত যা একই Python প্রসেসের ভেতরে একই এজেন্ট রানের সময় চালানো উচিত নয় বা সম্ভব নয়:

  • এটি আগে ব্যবহারকারীর অনুমোদন চাইতে পারে
  • এটি ফল দিতে একটি upstream সার্ভিস, frontend বা ব্যবহারকারীর ওপর নির্ভর করতে পারে
  • ফল তৈরি হতে এজেন্ট প্রসেস চালু রাখার যুক্তিসঙ্গত সময়ের চেয়ে বেশি লাগতে পারে

উদাহরণ দিয়ে বুঝি

একজন সহকারী আপনার হয়ে কাজ করছে, কিন্তু "১০ লাখ টাকা পাঠাও"-এর মতো কাজে আপনার স্বাক্ষর লাগে। সে ফর্মটি পূরণ করে আপনার টেবিলে রেখে যায় আর অপেক্ষা করে (deferred)। আপনি স্বাক্ষর দিলে (approve) বা না দিলে (deny), সে কাজটি শেষ করে বা অন্যভাবে এগোয়। একইভাবে কিছু কাজ অন্য কেউ করে দেয় (যেমন ব্রাউজারে চলা একটি টুল), আর ফল এলে সহকারী চালিয়ে যায়।

এই ব্যবহারগুলো সমর্থন করতে, Pydantic AI deferred টুলের ধারণা দেয়, যা দুই রকমের, নিচে নথিভুক্ত:

  • যে টুলের অনুমোদন লাগে
  • যে টুল বাইরে চালানো হয়

মডেল একটি deferred টুল ডাকলে, এটি মীমাংসার দুটি উপায় আছে:

  • সেখানেই মীমাংসা করুন, একটি handler-সহ একটি HandleDeferredToolCalls capability দিয়ে, যা অপেক্ষমাণ কলের কিছু বা সব মীমাংসা করে। এজেন্ট রান শেষ আর আবার শুরু না করেই একটি কলে চলতে থাকে — এটি ব্যবহার করুন যখন মীমাংসাকারী (যেমন একটি অনুমোদনের দরজা, একটি বাইরের সার্ভিস client) এজেন্টের একই প্রসেসে থাকে। দেখুন Resolving deferred calls with a handler।
  • রান শেষ করুন deferred টুল কলের তথ্যসহ একটি DeferredToolRequests আউটপুট অবজেক্ট দিয়ে; caller অনুমোদন/ফল সংগ্রহ করে তারপর মূল রানের বার্তার ইতিহাস আর একটি DeferredToolResults অবজেক্ট দিয়ে একটি নতুন এজেন্ট রান শুরু করে। সেই পরবর্তীটি নিজস্ব run_id-সহ একটি আলাদা এজেন্ট রান (থেমে থাকা রানেরটি আবার ব্যবহার করবেন না); থামা/আবার শুরুর সম্পর্ক conversation_id দিয়ে রাখুন। এটি ব্যবহার করুন যখন মীমাংসাকারী এজেন্ট প্রসেসের বাইরে থাকে — যেমন একটি UI adapter যা অপেক্ষমাণ কল একজন ব্যবহারকারীকে দেখায় আর তাদের উত্তর পেলে একটি পরবর্তী রান শুরু করে।

দুই প্রবাহ একসাথে মেলে: একটি handler কলের একটি উপসেট মীমাংসা করে বাকিগুলো একজন বাইরের caller-এর সামলানোর জন্য DeferredToolRequests আউটপুট হিসেবে ওপরে যেতে দিতে পারে।

সব-থামানো প্রবাহে Agent-এর output_type-এ DeferredToolRequests থাকতে হবে, যাতে এজেন্ট রানের আউটপুটের সম্ভাব্য টাইপ সঠিকভাবে অনুমিত হয়। আপনার এজেন্ট যদি এমন প্রসঙ্গেও ব্যবহার হতে পারে যেখানে কোনো deferred টুল নেই আর এজেন্ট ব্যবহারের প্রতিটি জায়গায় সেই টাইপ সামলাতে না চান, তাহলে বদলে এজেন্ট চালানোর সময় agent.run(), agent.run_sync(), agent.run_stream() বা agent.iter()-এ output_type আর্গুমেন্ট দিতে পারেন। মনে রাখবেন চলার সময়ের output_type তৈরির সময় নির্দিষ্টটি override করে (টাইপ অনুমানের কারণে), তাই মূল আউটপুট টাইপ স্পষ্টভাবে রাখতে হবে।

একটি handler দিয়ে deferred কল মীমাংসা¶

deferred টুল কল সামলানোর প্রস্তাবিত উপায় হলো একটি HandleDeferredToolCalls capability নথিভুক্ত করা, যার handler DeferredToolRequests পায় আর এর কিছু বা সব মীমাংসা করা একটি DeferredToolResults ফেরত দেয়। টুল চালানোর pipeline ফলগুলো সেখানেই প্রয়োগ করে আর এজেন্ট রান একটি কলে চলতে থাকে, যেন deferred টুলগুলো স্বাভাবিকভাবে ফেরত এসেছে।

একটি handler থাকলে, DeferredToolRequests-কে আর একটি আউটপুট টাইপ হিসেবে ঘোষণা করতে হয় না — যদি না আপনি অমীমাংসিত কলগুলোও caller পর্যন্ত যেতে দিতে চান (নিচে দেখুন)।

DeferredToolRequests.build_results() একটি সুবিধাজনক constructor — এটি যাচাই করে যে প্রতিটি টুল কল ID সঠিক ধরনের একটি অপেক্ষমাণ রিকোয়েস্ট নির্দেশ করে, আর অন্যথায় নির্দিষ্ট নয় এমন যেকোনো অনুমোদনের রিকোয়েস্ট নিজে থেকে অনুমোদন করতে approve_all=True নেয়।

deferred_tool_handler.py
from pydantic_ai import (
    Agent,
    ApprovalRequired,
    CallDeferred,
    DeferredToolRequests,
    DeferredToolResults,
    RunContext,
    ToolDenied,
)
from pydantic_ai.capabilities import HandleDeferredToolCalls


async def handle_deferred(
    ctx: RunContext, requests: DeferredToolRequests
) -> DeferredToolResults:
    approvals: dict[str, bool | ToolDenied] = {}
    for call in requests.approvals:
        if call.tool_name == 'delete_file':
            approvals[call.tool_call_id] = ToolDenied('Deleting files is not allowed')
        else:
            approvals[call.tool_call_id] = True

    calls = {call.tool_call_id: f'(external result for {call.tool_name})' for call in requests.calls}

    return requests.build_results(approvals=approvals, calls=calls)


agent = Agent(
    'openai:gpt-6.1-sol',
    capabilities=[HandleDeferredToolCalls(handler=handle_deferred)],
)


@agent.tool_plain(requires_approval=True)
def delete_file(path: str) -> str:
    return f'File {path!r} deleted'  # (1)!


@agent.tool
def update_file(ctx: RunContext, path: str, content: str) -> str:
    if path == '.env' and not ctx.tool_call_approved:
        raise ApprovalRequired
    return f'File {path!r} updated: {content!r}'


@agent.tool_plain
async def send_to_worker(task: str) -> str:
    raise CallDeferred  # (2)!
  1. এখানে কখনো পৌঁছায় না — handler এই কল প্রত্যাখ্যান করে, তাই মডেল বদলে প্রত্যাখ্যানের বার্তা দেখে।
  2. handler এই বাইরের কলের ফল দেয়, তাই টুলের body শুধু deferral-এর সংকেত দেয়।

handler কিছু বা সব কল মীমাংসা করতে অস্বীকার করলে (ফেরত দেওয়া DeferredToolResults থেকে সেগুলো বাদ দিয়ে বা None ফেরত দিয়ে), পরের HandleDeferredToolCalls (বা handle_deferred_tool_calls hook override করা অন্য যেকোনো capability) একটি সুযোগ পায়, আর তখনো অমীমাংসিত কলগুলো একটি DeferredToolRequests আউটপুট হিসেবে ওপরে যায়। সেই ওপরে যাওয়া অনুমোদন করতে, এজেন্টের output_type-এ DeferredToolRequests রাখুন — যাতে অর্থবহ হলে সেখানেই সামলানোকে সব-থামানো প্রবাহের সাথে মেলাতে পারেন।

আপনি যদি এমন একটি নিজের capability তৈরি করেন যা নিজেই অনুমোদন বা বাইরের কল মীমাংসা করে (যেমন deferred টুল দেখানো একটি sandbox), একটি আলাদা HandleDeferredToolCalls নথিভুক্ত না করে আপনার capability-তে সরাসরি handle_deferred_tool_calls hook override করুন। একই hook Hooks capability দিয়েও পাওয়া যায় — দেখুন Hooks।

নিচের অংশগুলো handler মীমাংসা করতে পারে এমন দুই ধরনের deferred টুল বর্ণনা করে, আর প্রতিটির জন্য বিকল্প সব-থামানো প্রবাহ। একাধিক capability কীভাবে মেলে, WrapperCapability আর capabilities=[...] তালিকাসহ, তা দেখুন Capabilities-এ।

Human-in-the-loop টুল অনুমোদন¶

একটি টুল ফাংশনের সবসময় অনুমোদন লাগলে, @agent.tool decorator, @agent.tool_plain decorator, Tool ক্লাস, FunctionToolset.tool decorator বা FunctionToolset.add_function() মেথডে requires_approval=True আর্গুমেন্ট দিতে পারেন। ফাংশনের ভেতরে, তখন ধরে নিতে পারেন টুল কলটি অনুমোদিত হয়েছে।

একটি realtime session-এ, অনুমোদন সেখানেই মীমাংসা হতে হবে, সাধারণত একটি HandleDeferredToolCalls handler দিয়ে (একটি capability hook-ও মীমাংসা করতে পারে); যে কল কিছুই মীমাংসা করে না তা প্রতিবার প্রত্যাখ্যাত হয়।

অনুমোদন টুল কলের আর্গুমেন্ট বা এজেন্টের run context-এর ওপর নির্ভর করলে, যেমন dependencies বা বার্তার ইতিহাস, টুল ফাংশন থেকে ApprovalRequired তুলুন। টুল কলটি আগেই অনুমোদিত হলে RunContext.tool_call_approved property True হবে।

টুলের args_validator থেকেও এটি তুলতে পারেন, যা টুল ফাংশনের আগে চলে আর একজন মানুষকে অনুমোদন করতে বলার আগে অবৈধ আর্গুমেন্ট প্রত্যাখ্যান করতে দেয়।

একটি toolset-এর দেওয়া টুলে (যেমন একটি MCP সার্ভার) কলের জন্য অনুমোদন বাধ্যতামূলক করতে, দেখুন ApprovalRequiredToolset ডকুমেন্টেশন।

অনুমোদন একটি অবিশ্বস্ত ক্লায়েন্টের বিরুদ্ধে অনুমতির সীমানা নয়

আপনি একটি UI adapter-এর মাধ্যমে একটি এজেন্ট দিলে, অনুমোদনের সিদ্ধান্ত ক্লায়েন্ট রিকোয়েস্টের বাকিটার সাথে পাঠায়, আর adapter-এর কাছে সার্ভারে কোনো রেকর্ড নেই যে এটি কোন টুল কল দিয়েছিল। endpoint-এ পৌঁছাতে পারে এমন একটি ক্লায়েন্ট নিজের বানানো একটি টুল কল অনুমোদন করতে পারে। Human-in-the-loop অনুমোদন মানুষের সম্মতি ছাড়া মডেলের কাজের বিরুদ্ধে রক্ষা করে; এটি adapter endpoint প্রমাণীকরণ আর টুল ফাংশনের ভেতরে সংবেদনশীল কাজের অনুমতি প্রয়োগের বিকল্প নয়, যা কলটি ইতিহাসে যেভাবেই ঢুকুক চলে। এটি শুধু adapter নয়, একটি ক্লায়েন্টের message_history নেওয়া যেকোনো endpoint-এ প্রযোজ্য — দেখুন Trust boundary for client-supplied history আর Trust model for client-submitted messages।

মডেল অনুমোদন লাগে এমন একটি টুল ডাকলে, এজেন্ট রান একটি DeferredToolRequests আউটপুট অবজেক্ট দিয়ে শেষ হবে, যার একটি approvals তালিকায় টুলের নাম, যাচাই করা আর্গুমেন্ট আর একটি অনন্য টুল কল ID-সহ ToolCallPart থাকে।

ব্যবহারকারীর অনুমোদন বা প্রত্যাখ্যান সংগ্রহ করার পরে, একটি approvals dictionary-সহ একটি DeferredToolResults অবজেক্ট তৈরি করতে পারেন, যা প্রতিটি টুল কল ID-কে একটি boolean, একটি ToolApproved অবজেক্ট (ঐচ্ছিক override_args-সহ), বা একটি ToolDenied অবজেক্ট (মডেলকে দেওয়ার একটি ঐচ্ছিক নিজের message-সহ)-এ ম্যাপ করে। DeferredToolResults-এ একটি metadata dictionary-ও দিতে পারেন, যা প্রতিটি টুল কল ID-কে metadata-র একটি dictionary-তে ম্যাপ করে যা টুলের RunContext.tool_call_metadata attribute-এ পাওয়া যাবে। এই DeferredToolResults অবজেক্ট তারপর মূল রানের বার্তার ইতিহাস বা এর কথোপকথনের পাশাপাশি deferred_tool_results হিসেবে এজেন্ট রান মেথডগুলোর একটিতে দেওয়া যায়, যা উত্তর পরে এলে রিকোয়েস্টগুলোও রাখে।

এখানে একটি উদাহরণ যা দেখায় সব ফাইল মোছার জন্য, আর নির্দিষ্ট সুরক্ষিত ফাইল হালনাগাদের জন্য কীভাবে অনুমোদন বাধ্যতামূলক করবেন:

বাইরে টুল চালানো¶

একটি টুল কলের ফল যে এজেন্ট রানে ডাকা হয়েছে তার ভেতরে তৈরি করা না গেলে, টুলটি বাইরের বলে ধরা হয়। বাইরের টুলের উদাহরণ হলো একটি ওয়েব বা অ্যাপ frontend-এর বাস্তবায়ন করা client-পক্ষের টুল, আর ধীর কাজ যা এজেন্ট প্রসেস চালু না রেখে একটি background worker বা বাইরের সার্ভিসে দেওয়া হয়।

একটি টুল কল বাইরে চালানো উচিত কিনা তা যদি টুল কলের আর্গুমেন্ট, এজেন্টের run context (যেমন dependencies বা বার্তার ইতিহাস), বা কাজটি কতক্ষণ নেবে বলে আশা করা হয় তার ওপর নির্ভর করে, তাহলে একটি টুল ফাংশন সংজ্ঞায়িত করে শর্তসাপেক্ষে CallDeferred exception তুলতে পারেন। exception তোলার আগে, টুল ফাংশন সাধারণত কোনো background কাজ নির্ধারণ করে আর RunContext.tool_call_id পাঠিয়ে দেয়, যাতে পরে ফলটি deferred টুল কলের সাথে মেলানো যায়।

অনুমোদনের মতো, টুলের args_validator-ও CallDeferred তুলতে পারে, তাই শুধু বৈধ আর্গুমেন্টসহ কলই হস্তান্তর হয়।

একটি টুল সবসময় বাইরে চালানো হলে আর এর সংজ্ঞা এর আর্গুমেন্টের একটি JSON schema-সহ আপনার কোডে দেওয়া হলে, একটি ExternalToolset ব্যবহার করতে পারেন। বাইরের টুলগুলো আগে থেকে জানা থাকলে আর আপনার হাতে আর্গুমেন্টের JSON schema না থাকলে, উপযুক্ত signature-সহ একটি টুল ফাংশনও সংজ্ঞায়িত করতে পারেন যা CallDeferred exception তোলা ছাড়া কিছুই করে না।

মডেল একটি বাইরের টুল ডাকলে, এজেন্ট রান একটি DeferredToolRequests আউটপুট অবজেক্ট দিয়ে শেষ হবে, যার একটি calls তালিকায় টুলের নাম, যাচাই করা আর্গুমেন্ট আর একটি অনন্য টুল কল ID-সহ ToolCallPart থাকে।

টুল কলের ফল তৈরি হলে, একটি calls dictionary-সহ একটি DeferredToolResults অবজেক্ট তৈরি করতে পারেন, যা প্রতিটি টুল কল ID-কে ম্যাপ করে মডেলে ফেরত দেওয়ার একটি যেকোনো মানে, একটি ToolReturn অবজেক্টে, বা টুল কল ব্যর্থ হলে একটি exception-এ: মডেলের আবার চেষ্টা করা উচিত হলে একটি ModelRetry, বা ব্যর্থতা মডেলকে একটি ব্যর্থ ফল হিসেবে জানানো উচিত হলে (টুলের retry বাজেট খরচ না করে) একটি ToolFailed, যাতে এটি কীভাবে এগোবে তা ঠিক করতে পারে। এই DeferredToolResults অবজেক্ট তারপর মূল রানের বার্তার ইতিহাস বা এর কথোপকথনের পাশাপাশি deferred_tool_results হিসেবে এজেন্ট রান মেথডগুলোর একটিতে দেওয়া যায়, যা উত্তর পরে এলে রিকোয়েস্টগুলোও রাখে।

এখানে একটি উদাহরণ যা দেখায় সম্পূর্ণ হতে কিছুক্ষণ লাগে এমন একটি কাজ background-এ সরিয়ে কাজ শেষ হলে ফলটি মডেলে কীভাবে ফেরত দেবেন:

from typing import Any

@dataclass
class TaskResult:
    task_id: str
    result: Any


async def calculate_answer_task(task_id: str, question: str) -> TaskResult:
    await asyncio.sleep(1)
    return TaskResult(task_id=task_id, result=42)


agent = Agent('openai:gpt-6.1-sol', output_type=[str, DeferredToolRequests])

tasks: list[asyncio.Task[TaskResult]] = []


@agent.tool
async def calculate_answer(ctx: RunContext, question: str) -> str:
    task_id = f'task_{len(tasks)}'  # (1)!
    task = asyncio.create_task(calculate_answer_task(task_id, question))
    tasks.append(task)

    raise CallDeferred(metadata={'task_id': task_id})  # (2)!

একটি কথোপকথন থামানো¶

DeferredToolRequests দিয়ে শেষ হওয়া একটি রান তার কথোপকথন থামিয়েছে: কলগুলোর উত্তর না আসা পর্যন্ত পরের রান এগোতে পারে না, আর উত্তর প্রায়ই পরে আসে — একজন পর্যালোচক কাল refund অনুমোদন করেন, আরেকটি মেশিনে একটি job শেষ হয়। রানের conversation রিকোয়েস্টগুলো deferred_tool_requests হিসেবে রাখে, তাই আপনার সংরক্ষিত কথোপকথনই আবার শুরু করার জন্য যা দরকার তার সব।

এটি গুরুত্বপূর্ণ কারণ বার্তা থেকে রিকোয়েস্ট পুনর্গঠন করা যায় না। ইতিহাস দেখায় কোন কলগুলোর উত্তর নেই, কিন্তু কোনগুলোর অনুমোদন আর কোনগুলোর একটি বাইরের ফল লাগে, বা defer করার সময় একটি টুল যে metadata জুড়েছিল তা নয়। কথোপকথনটি সংরক্ষণ করুন, আর সেগুলো এর সাথে চলে:

pausing_a_conversation.py
from pydantic_ai import (
    Agent,
    ApprovalRequired,
    ConversationTypeAdapter,
    DeferredToolRequests,
    RunContext,
)

agent = Agent('openai:gpt-6.1-sol', output_type=[str, DeferredToolRequests])


@agent.tool
def update_file(ctx: RunContext, path: str, content: str) -> str:
    if path == '.env' and not ctx.tool_call_approved:
        raise ApprovalRequired(metadata={'reason': 'protected'})
    return f'File {path!r} updated: {content!r}'


@agent.tool_plain(requires_approval=True)
def delete_file(path: str) -> str:
    return f'File {path!r} deleted'


result = agent.run_sync('Delete `__init__.py`, write `Hello, world!` to `README.md`, and clear `.env`')
stored = ConversationTypeAdapter.dump_json(result.conversation)  # (1)!

conversation = ConversationTypeAdapter.validate_json(stored)  # (2)!
requests = conversation.deferred_tool_requests
assert requests is not None
print(requests.metadata)
#> {'update_file_dotenv': {'reason': 'protected'}}

results = requests.build_results(approvals={'update_file_dotenv': True, 'delete_file': False})  # (3)!
result = agent.run_sync(
    'Now create a backup of README.md',
    conversation=conversation,
    deferred_tool_results=results,
)
print(result.conversation.deferred_tool_requests)  # (4)!
#> None
  1. থেমে থাকা কথোপকথন সংরক্ষণ করুন, যেমন result.conversation_id দিয়ে key করে।
  2. পরে — আরেকটি রিকোয়েস্টে, কেউ অপেক্ষমাণ কল পর্যালোচনা করার পরে — এটি আবার লোড করুন।
  3. build_results প্রতিটি উত্তর যে রিকোয়েস্টের উত্তর দেয় তার সাথে পরীক্ষা করে, তাই একটি পুরনো বা ভুল লেখা টুল কল ID রানে নয়, এখানেই ব্যর্থ হয়।
  4. রান শেষ হয়েছে, তাই এটি যে কথোপকথন ফেরত দেয় তা কিছুর জন্য অপেক্ষা করছে না।

একটি stream-এ deferred টুল কল দেখা¶

অন্য যেকোনো টুল কলের মতো, একটি deferred টুল কল event stream-এ একটি FunctionToolCallEvent পাঠায় — কিন্তু সেই event একা একজন stream গ্রাহককে বলে না যে কলটি মিথস্ক্রিয়ার অপেক্ষায় থেমে আছে, বা কোন ধরনের মিথস্ক্রিয়া প্রত্যাশিত। দুটি বাড়তি AgentStreamEvent সেই প্রসঙ্গ বহন করে:

  • DeferredToolRequestsEvent — deferred কলের প্রতিটি ব্যাচে একবার পাঠানো হয়, DeferredToolRequests বহন করে। কোনো HandleDeferredToolCalls handler চলার আগে এটি পাঠানো হয়, তাই একজন গ্রাহক যেমন handler অপেক্ষা করার সময় একটি frontend-কে জানাতে পারে যে ইনপুট দরকার। কোনো handler সব রিকোয়েস্ট মীমাংসা না করলে, রান অপেক্ষমাণ রিকোয়েস্টগুলোকে তার DeferredToolRequests আউটপুট হিসেবে নিয়ে শেষ হয়।
  • DeferredToolResultsEvent — একটি handler রিকোয়েস্ট (এর কিছু) মীমাংসা করলে পাঠানো হয়, DeferredToolResults বহন করে। মীমাংসিত কলগুলো তারপর সাধারণ pipeline দিয়ে চলে, প্রতিটি একটি FunctionToolResultEvent পাঠায়। ফল বদলে deferred_tool_results দিয়ে একটি নতুন রানে দেওয়া হলে কোনো event পাঠানো হয় না, কারণ সেক্ষেত্রে caller আগেই সেগুলো জানে।

এটি মীমাংসা আর উপস্থাপনাকে আলাদা রাখে: একটি handler বিশুদ্ধ মীমাংসার লজিক ধরতে পারে (যেমন একটি durable execution workflow-এ একটি সংকেতের অপেক্ষা), অথচ একজন stream গ্রাহক frontend-এর সাথে সব যোগাযোগের মালিক, কোন টুল মিথস্ক্রিয় তার নিজের ম্যাপিং না রেখেই।

ওপরের handler উদাহরণ চালিয়ে যাওয়া:

deferred_tool_events.py
from pydantic_ai import DeferredToolRequestsEvent, DeferredToolResultsEvent

from deferred_tool_handler import agent


async def main():
    async with agent.run_stream_events(
        'Delete `__init__.py`, write `Hello, world!` to `README.md`, and clear `.env`'
    ) as events:
        async for event in events:
            if isinstance(event, DeferredToolRequestsEvent):
                print(f'Approvals needed: {[call.tool_name for call in event.requests.approvals]}')
                #> Approvals needed: ['update_file', 'delete_file']
            elif isinstance(event, DeferredToolResultsEvent):
                print(f'Resolved: {list(event.results.approvals)}')
                #> Resolved: ['update_file_dotenv', 'delete_file']

আরও দেখুন¶

  • Function Tools - টুলের মৌলিক ধারণা আর নথিভুক্তি
  • Advanced Tool Features - নিজের schema, গতিশীল টুল আর চালানোর বিস্তারিত
  • Toolsets - টুলের সংগ্রহ সামলানো, বাইরের টুলের জন্য ExternalToolset-সহ
  • Message History - deferred টুলের জন্য বার্তার ইতিহাস নিয়ে কাজ, run_id / conversation_id-সহ
  • Realtime tools - একটি জীবন্ত কণ্ঠ-session-এ অনুমোদন-প্রয়োজন আর deferred টুল

সংক্ষেপে মনে রাখুন

  • অনুমোদন: requires_approval=True বা শর্তসাপেক্ষে raise ApprovalRequired(); বাইরে চালানো: raise CallDeferred()।
  • একই প্রসেসে মীমাংসা: HandleDeferredToolCalls(handler) — রান থামে না।
  • অন্যথায়: output_type=[..., DeferredToolRequests], রান থামে; পরে deferred_tool_results=... দিয়ে নতুন রান।
  • result.conversation সংরক্ষণ করুন — এতে অপেক্ষমাণ রিকোয়েস্টও থাকে; build_results() উত্তর যাচাই করে।
  • অনুমোদন ক্লায়েন্টের বিরুদ্ধে নিরাপত্তা নয়; সংবেদনশীল কাজে টুলের ভেতরে অনুমতি পরীক্ষা করুন।
